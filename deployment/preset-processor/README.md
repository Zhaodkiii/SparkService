# Preset resource processor

Deploy this container on a dedicated cn-beijing compute instance with OSS internal connectivity, never on the low-bandwidth API host. Build using the repository root as Docker build context. Give it >= 6 GiB temporary disk, resource limits and outbound HTTPS to the control API. Current implementation uses a dedicated polling container, not an FC invocation endpoint.

Required environment: PRESET_CONTROL_URL, DIARY_PRESETS_PROCESSOR_TOKEN (same random secret as API), ALIYUN_ACCESS_KEY_ID, ALIYUN_ACCESS_KEY_SECRET, ALIYUN_OSS_BUCKET. Optional: PRESET_WORKER_OSS_ENDPOINT (defaults Beijing internal), DIARY_PRESETS_OSS_PREFIX.

Use a dedicated worker RAM identity permitted to read staging and write immutable blobs only. Do not use browser upload credentials. API identity additionally needs AssumeRole on DIARY_PRESETS_UPLOAD_ROLE_ARN; that role must permit only scoped staging multipart uploads. Configure OSS CORS for the actual backoffice origin.

Production uses an independent deployment. Local development can opt in to a separately managed process using `DIARY_PRESETS_LOCAL_PROCESSOR_ENABLED=true`; see `scripts/后台管理/README.md`. The local command uses the configured public OSS endpoint, while this container retains the internal endpoint default. Set a container restart policy. Jobs use 30-minute leases; work exceeding that time is rejected and reclaimed. Tune package limits and execution resources accordingly. Failed jobs remain inspectable through the upload API; do not manually publish unvalidated input.

## One worker and one durable queue

Run only `python worker.py` (or the existing locally managed `run_preset_processor`). Public handbooks and private customization delivery ZIPs enter the same `diary_presets.ResourceTask` FIFO queue. The worker claims and reports exclusively through `/api/internal/diary-presets/processor/`; the old private claim endpoint returns 410. Do not deploy a second private worker or container. Domain Upload/Job rows remain business records; they are not independently polled queues. Task ID, lease, retries, heartbeat and pending counts all belong to the shared queue.

Apply migration `diary_presets/0003_resourcetask` before starting the new worker. It imports existing queued/processing public uploads and eligible private delivery jobs, retaining active leases. It excludes photos, deleted requests and cancelled/rejected requests. Stop the old worker, apply migrations, then restart the same managed `preset_processor` service. Retrying a failed upload reuses its queue row and moves it to the tail. Resource-specific callbacks update the corresponding business record transactionally; duplicate completion reports do not create extra candidates.

Both types use one protected control token and the same regional RAM identity. Private ZIPs additionally verify SHA-256 and write blobs only under `traveldiary/customizations/<owner>/<request>/blobs/`; public blobs retain their public preset namespace. Private processing produces a candidate awaiting review, never an automatic user delivery or public publication. The task manager shows one combined queued/processing count and the current resource type.

User photos do not require this worker. The client PUTs the photo directly into its random `inputs/<session>/photo.jpg` or `.png` object, then calls `complete`. That API performs database registration only and immediately returns `ready`; it does not HEAD, download, hash, rewrite, copy or generate thumbnails. Preview URLs refer to the same uploaded object and are fetched directly by the client/browser. Signed PUTs include `put_headers` (Content-Type and `x-oss-forbid-overwrite=true`), which the updated client must send. `ready` records the client acknowledgement, not server-verified bytes.

Deploy migration `diary_customizations/0004_direct_photo_upload` to finish legacy queued/processing/failed photo records without accessing OSS; it keeps existing object keys and clears processor leases. Restart the shared resource worker with the updated image so any old in-flight photo processing stops. Completed photo objects, including legacy staging keys, must not have a blanket one-day deletion lifecycle rule. The cleanup command excludes ready photo sessions from staging cleanup.

Add explicit IAM permission for this private prefix to the API signing identity and dedicated regional worker identity. Client sessions only get a single signed photo PUT or scoped archive staging STS. Keep the bucket private and block public ACLs. Configure the real backoffice origin in OSS CORS. No private inputs or PSDs may be placed in the public presets/material libraries.

Optional `CUSTOMIZATIONS_OSS_PREFIX` must match on API and worker. `CUSTOMIZATIONS_ACCEPTING=false` on Django can pause new draft creation (set the Django setting; the default is true). Run database migrations before enabling the feature. The API requires the notification transactional queue worker and Celery Beat for notifications; private delivery ZIP candidate preparation also requires this shared OSS processor. These are different processes; photo submission needs no OSS worker.

Cleanup is a separately scheduled command in the regional environment: `python manage.py cleanup_customizations` previews, `--execute` performs the reference-aware policy. Configure OSS lifecycle to abort stale multipart uploads after one day. Keep cleanup credentials out of iOS, browser and source briefs. The command handles cloud data; designers must separately remove matching local `custom-work/<request>/` folders and their backups after deletion requests.
