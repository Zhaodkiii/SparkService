## 工单 `SECURE-COMM-000001`：客户端与服务端全加密通讯设计

### 工单状态

需求讨论/设计中。

## 1. 背景

### 业务背景

SparkClient 与 SparkService 传输大量敏感数据：

1. 登录凭证、验证码、Apple 登录信息。
2. 用户账号、设备、国家、通知权限等身份信息。
3. 成员档案、病例、体检、检查报告、处方、用药计划、药箱。
4. 聊天内容、AI 同步消息、医疗报告引用、健康数据。
5. 文件元数据、OSS 临时凭证、下载地址。

当前依赖 HTTPS/TLS、JWT 鉴权和服务端权限控制。TLS 可以保护链路传输，但无法解决以下问题：

1. 反向代理、网关、应用日志中出现明文 body。
2. App Debug/生产日志中输出请求/响应原始报文。
3. 中间服务或基础设施可见业务 JSON。
4. 敏感字段在错误日志、API IO 日志、崩溃诊断中泄露。

因此需要讨论“全加密通讯”：在 HTTPS 之上增加应用层 payload 加密，降低业务明文在日志、网关、代理、传输中间层暴露的风险。

## 2. 参考代码风险分析

### 参考代码

参考文件：

```text
DreamHua-master/travels/views/Component/crypto_operations.py:1-73
```

核心逻辑：

```python
cipher = AES.new(EncryptionKey.encode(), AES.MODE_CBC, EncryptionIv.encode())
padded_data = pad(data.encode(), AES.block_size)
encrypted_data = cipher.encrypt(padded_data)
```

### 主要问题

| 问题 | 说明 | 风险 |
| --- | --- | --- |
| 固定 Key | `EncryptionKey` 全局固定 | 一旦泄露，历史和未来数据都可解密 |
| 固定 IV | CBC 模式使用固定 `EncryptionIv` | 相同明文块会产生相同密文模式，泄露结构 |
| AES-CBC 无认证 | 只加密不校验完整性 | 密文可被篡改，存在 padding oracle / malleability 风险 |
| 无 AAD | 未绑定 method/path/request_id/user/session | 密文可能被跨接口重放或替换 |
| 无 nonce / timestamp | 没有一次性随机数和时间窗口 | 无法防重放 |
| 无密钥版本 | 无法平滑轮换密钥 | 换密钥会导致兼容困难 |
| 无握手协议 | 客户端和服务端共享静态密钥 | App 反编译后风险高 |
| 无响应加密协议 | 只看到数据解密工具，没有完整请求响应信封 | 无法做全链路一致处理 |
| 明文日志 | `logger.debug('解密数据: ...')` 打印解密后明文 | 敏感数据直接进入日志 |
| 返回裸 bytes | 没有统一 envelope、算法、版本、kid、tag | 扩展性差，排障困难 |

### 结论

该实现不适合作为 SparkClient/SparkService 全加密通讯方案。它最多只能作为“旧项目中曾经做过 AES 包裹”的参考，不能复用其算法结构。

全加密通讯应至少满足：

1. 使用 AEAD 算法，例如 `AES-256-GCM` 或 `ChaCha20-Poly1305`。
2. 每次请求使用唯一 nonce。
3. 每个会话/设备使用独立派生密钥。
4. 密文绑定 method/path/request_id/timestamp 等 AAD。
5. 支持密钥版本、轮换和灰度。
6. 日志默认只记录密文摘要，不记录明文。

## 4. 设计目标

### 核心目标

在 HTTPS/TLS 之上增加应用层加密信封，使 SparkClient 与 SparkService 的业务 JSON 请求体和响应体在网络框架、代理、日志与中间层中默认不可读。

### 第一期目标

1. 客户端统一在 `SparkNetworkEngine` 层对 JSON body 加密。
2. 服务端统一在 middleware/parser 层解密后再交给 DRF `request.data`。
3. 服务端统一在 renderer/middleware 层加密响应 body。
4. 使用 `AES-256-GCM`，每次请求随机 nonce。
5. 使用 X25519 ECDH + HKDF 建立会话级应用层加密密钥。
6. 支持加密信封版本 `v1`、密钥 ID `kid`、会话 ID `enc_session_id`。
7. 支持灰度：部分接口、部分版本、部分用户开启。
8. 请求和响应日志不记录明文，只记录加密状态、大小、摘要、错误码。
9. 保留 HTTPS/TLS、JWT、权限校验，不用应用层加密替代鉴权。

### 第一期边界

1. 不加密 URL path 和 query。若 query 含敏感信息，应改为 POST body。
2. 不加密 HTTP headers 中的 `Authorization`，但日志必须继续脱敏。
3. OSS 直传文件内容不走 SparkService payload 加密；文件保护另走 OSS/文件加密策略。
4. WebSocket 可作为二期，第一期优先 HTTP API。
5. 登录/握手前的少数引导接口需要特殊处理。

## 5. 威胁模型与非目标

### 需要防的风险

1. 代理、网关、服务端 API IO 日志看到明文 body。
2. App 网络层日志看到明文 body。
3. 抓包时即使 TLS 终止在代理，也看不到业务 JSON。
4. 密文被篡改时能被发现。
5. 密文被跨接口重放时能被发现。

### 不作为第一期目标

1. 防止已越狱/已 Root 设备内存被读取。
2. 防止服务端业务层最终看到明文。服务端必须解密后执行业务。
3. 防止数据库明文存储。那属于静态数据加密/字段级加密。
4. 替代 JWT 鉴权、权限校验或 HTTPS。

## 6. 推荐方案总览

### 分层设计

```text
TLS/HTTPS
  负责链路加密、服务器身份校验、防公网监听

JWT
  负责用户身份与接口权限

App Payload Encryption
  负责业务请求/响应 body 加密、防日志/中间层明文暴露

Field/Storage Encryption（后续）
  负责数据库或文件静态加密
```

### 加密信封

请求体不再直接发送业务 JSON，而是发送加密信封：

```json
{
  "enc": true,
  "v": 1,
  "alg": "AES-256-GCM",
  "kid": "server-key-2026-06",
  "enc_session_id": "s_abc123",
  "nonce": "base64url...",
  "aad": "base64url...",
  "ciphertext": "base64url...",
  "tag": "base64url..."
}
```

响应体同样使用信封：

```json
{
  "enc": true,
  "v": 1,
  "alg": "AES-256-GCM",
  "enc_session_id": "s_abc123",
  "nonce": "base64url...",
  "ciphertext": "base64url...",
  "tag": "base64url..."
}
```

### AAD 绑定内容

AAD 不加密但参与认证，推荐包含：

```text
v
method
path
query_hash
request_id
timestamp
account_id 或 anonymous
enc_session_id
body_sha256_before_encrypt
```

这样可以防止密文被换到另一个接口或另一个请求 ID 下重放。

## 7. 密钥协商设计

### 为什么不用固定对称密钥？

固定密钥会导致：

1. App 包反编译后密钥泄露。
2. 所有用户共享同一风险。
3. 无法区分设备、账号、会话。
4. 密钥轮换困难。

### 推荐握手：X25519 ECDH + HKDF

流程：

```text
1. 客户端生成临时 X25519 key pair
2. 客户端请求 /api/v1/security/encryption/handshake/
   - client_pub_key
   - device_id
   - app_version
   - supported_algs
3. 服务端生成临时 X25519 key pair
4. 双方 ECDH 得到 shared_secret
5. 双方使用 HKDF-SHA256 派生：
   - request_key
   - response_key
6. 服务端返回：
   - enc_session_id
   - server_pub_key
   - expires_at
   - kid
   - alg
7. 后续 API 使用 request_key 加密请求，response_key 解密响应
```

### 会话有效期

建议：

```text
匿名加密会话：10 分钟
已登录加密会话：30~60 分钟
App 前台恢复：如果剩余小于 5 分钟，后台静默刷新
401/加密会话过期：重新握手后重试一次
```

### Keychain 存储

客户端只缓存：

```text
enc_session_id
request_key / response_key
expires_at
server_kid
```

存储位置：Keychain 或内存优先。高安全模式可以只放内存，App 重启重新握手。

## 8. 接口加密范围

### 必须加密

| 模块 | 接口类型 |
| --- | --- |
| accounts | 登录后 session、账号注销、设备资料中敏感字段 |
| medical | 成员、病例、体检、检查报告、处方、用药、药箱、完整资料 |
| chat_sync | 会话、消息、附件元数据、thread push/pull |
| ai_config | trial/apply、bootstrap 中用户权益相关响应 |
| file_manager | 文件注册、业务绑定、下载 URL 响应 |

### 可明文或半加密

| 接口 | 原因 |
| --- | --- |
| version/check | 低敏、启动早期 |
| encryption/handshake | 握手自身无法用应用层加密 |
| oss/sts/credentials | 建议加密响应，但 OSS 直传本身不走 SparkService body |
| 健康检查 | 运维用途 |

### 登录接口特殊处理

登录前没有 JWT，但可以先做匿名加密握手：

```text
App 启动
  -> anonymous encryption handshake
  -> 登录请求使用匿名 enc session 加密
  -> 登录成功拿到 JWT
  -> 重新绑定或升级为 authenticated enc session
```

如果第一期要降低改造量，可先让登录接口保持 HTTPS 明文 JSON，但这不满足“全加密通讯”的严格定义。推荐目标是登录也加密。

## 9. 客户端改造设计

### 新增组件

```swift
struct AppCryptoEnvelope: Codable
final class AppEncryptionSessionStore
final class AppEncryptionHandshakeClient
struct AppPayloadEncryptor
struct AppPayloadDecryptor
```

### `SparkNetworkEngine` 改造

当前 JSON body 构建位置：

```swift
case .json(let anyEncodable):
    urlRequest.setValue("application/json", forHTTPHeaderField: "Content-Type")
    urlRequest.httpBody = try JSONEncoder.default.encode(anyEncodable)
```

改造后：

```text
1. 编码业务 JSON 为 plainData
2. 判断 request 是否需要 app encryption
3. 如果需要：
   - ensure encryption session
   - encrypt plainData -> envelopeData
   - Content-Type: application/vnd.spark.encrypted+json
   - X-Spark-Encryption: v1
   - httpBody = envelopeData
4. 如果不需要：
   - 保持原逻辑
```

### 响应解密位置

在 `transport.send` 返回后、JSONDecoder 解码前：

```text
if response Content-Type == application/vnd.spark.encrypted+json:
  decrypt envelope -> plain response data
else:
  use raw data
```

### 日志改造

客户端日志：

```text
请求原始报文 body=<encrypted:v1 bytes=... ciphertext_sha256=...>
响应原始报文 body=<encrypted:v1 bytes=... ciphertext_sha256=...>
```

禁止打印解密后的业务明文。Debug 如需排查，必须有本地开发开关，且不能进入生产。

## 10. 服务端改造设计

### 新增模块

建议目录：

```text
SparkService/security/
  encryption/
    models.py
    services.py
    envelopes.py
    middleware.py
    renderers.py
    parsers.py
    views.py
    urls.py
```

### 握手接口

```text
POST /api/v1/security/encryption/handshake/
```

请求：

```json
{
  "client_pub_key": "...",
  "device_id": "...",
  "supported_algs": ["AES-256-GCM"],
  "app_version": "1.5.0"
}
```

响应：

```json
{
  "enc_session_id": "s_...",
  "server_pub_key": "...",
  "kid": "server-ephemeral-2026-06",
  "alg": "AES-256-GCM",
  "expires_at": "2026-06-03T12:00:00Z"
}
```

### 请求解密

优先在 DRF parser 或 Django middleware 解密。

目标：

```text
encrypted envelope body
  -> decrypt
  -> request._body = plain JSON bytes
  -> DRF request.data 正常可用
```

注意：如果在 middleware 读取 `request.body`，要确保不会破坏 DRF 后续解析。

### 响应加密

优先在 DRF renderer 或 middleware 加密。

目标：

```text
业务 view 返回普通 Response(data)
  -> renderer 生成 plain JSON bytes
  -> encrypt
  -> 返回 encrypted envelope
```

### 日志改造

`common/middleware/request_logging_middleware.py` 当前会记录 `request.body` 和 response body。加密上线后：

1. 如果请求是加密 envelope，日志只记录 envelope 元信息。
2. 不记录解密后的 body。
3. 响应同理。
4. Authorization、token、手机号、邮箱等继续脱敏。

## 11. 错误码设计

| code | msg | HTTP | 场景 |
| --- | --- | --- | --- |
| `encryption_required` | 当前接口要求加密通讯 | 426/400 | 客户端未加密 |
| `encryption_session_expired` | 加密会话已过期 | 401/440 | 需要重新握手 |
| `encryption_invalid_envelope` | 加密信封格式错误 | 400 | 缺字段/版本不支持 |
| `encryption_decrypt_failed` | 解密失败 | 400 | tag 校验失败/密文损坏 |
| `encryption_replay_detected` | 请求疑似重放 | 409 | nonce/request_id 重复 |
| `encryption_alg_unsupported` | 不支持的加密算法 | 400 | alg 不在白名单 |

客户端处理：

```text
session_expired -> 重新握手并重试一次
decrypt_failed -> 不自动重试，提示网络安全校验失败
encryption_required -> 强制握手后重试
```

## 12. 防重放设计

服务端记录短期 nonce：

```text
enc_session_id + nonce
```

存储：

1. Redis，TTL 与加密会话一致。
2. 本地内存只适合单进程开发，不适合生产多 worker。

同时校验：

```text
timestamp 在 ±5 分钟窗口内
request_id 未重复
AAD method/path 匹配当前请求
```

## 13. 灰度与兼容

### 客户端版本策略

新增服务端配置：

```text
APP_ENCRYPTION_REQUIRED_MIN_VERSION
APP_ENCRYPTION_OPTIONAL_MIN_VERSION
APP_ENCRYPTION_ENABLED_MODULES
```

灰度阶段：

1. `optional`：客户端支持则加密，不支持仍明文。
2. `required for selected modules`：medical/chat_sync 强制加密。
3. `required all sensitive APIs`：除握手/健康检查/版本检查外强制加密。

### 接口标记

服务端可按 path/module 判断：

```text
/api/v1/medical/**
/api/v1/ai/chat/sync/**
/api/v1/files/**
```

客户端也应有 `SparkNetworkRequest.encryptionPolicy`：

```swift
enum AppEncryptionPolicy {
    case automatic
    case required
    case disabled
}
```

## 14. 与 ETag/缓存/文件的关系

### ETag

如果响应体加密，每次 nonce 不同会导致密文不同，不适合直接对密文做 ETag。

建议：

1. 加密接口第一期禁用 ETag。
2. 或服务端基于明文业务版本生成 `X-Plain-ETag`，但不暴露敏感语义。
3. 客户端本地缓存仍存解密后的业务数据，但磁盘缓存也要考虑本地保护。

### OSS 文件

OSS 直传不经过 SparkService body 加密。第一期保持：

```text
SparkService API payload 加密
OSS 文件传输仍走 HTTPS + OSS STS
```

后续若要文件内容端到端加密，需要单独设计文件级 envelope key。

## 15. 实施阶段

### M1：基础能力

1. 服务端新增握手接口。
2. 客户端新增握手 client 和 session store。
3. 双端实现 AES-GCM envelope 编解码。
4. 加单元测试互通向量。

### M2：HTTP 请求响应加密

1. 客户端 `SparkNetworkEngine` 支持 request body 加密和 response 解密。
2. 服务端 parser/middleware 支持 request 解密。
3. 服务端 renderer/middleware 支持 response 加密。
4. 日志隐藏明文 body。

### M3：模块灰度

1. medical API 开启 optional。
2. chat_sync API 开启 optional。
3. file metadata API 开启 optional。
4. 稳定后切 required。

### M4：登录与启动链路

1. 匿名握手。
2. 登录请求加密。
3. 登录成功后升级 authenticated session。
4. token refresh 加密。

### M5：WebSocket/文件扩展

1. WebSocket 消息加密。
2. OSS 文件内容可选端侧加密。

## 17. 验收标准

### 安全验收

1. AES-GCM 每次请求 nonce 不重复。
2. 篡改 ciphertext/tag 后服务端拒绝。
3. 改 path/method 后 AAD 校验失败。
4. 重放同一 nonce 请求被拒绝。
5. 加密会话过期后必须重新握手。
6. 客户端和服务端日志不出现业务明文 body。

### 功能验收

1. medical API 加密后业务行为不变。
2. chat_sync API 加密后同步行为不变。
3. token refresh 可以在加密策略下正常工作。
4. 加密 session 过期时客户端自动握手并重试一次。
5. 不支持加密的旧版本在 optional 阶段仍可使用。
6. required 阶段旧版本收到明确升级/不支持提示。

### 性能验收

1. 单次 AES-GCM 加解密耗时可接受。
2. 加密后请求体增量可监控。
3. 大 payload 如聊天同步/complete-data 不明显卡顿。
4. 握手失败不阻塞 App 已有离线/缓存降级逻辑。

## 18. 重要注意事项

1. 全加密通讯不能替代 HTTPS，HTTPS 必须保留。
2. 全加密通讯不能替代 JWT 和权限校验。
3. 不要使用 AES-CBC + 固定 IV。
4. 不要在生产日志打印解密明文。
5. 不要把应用层密钥硬编码到 App。
6. 不要加密后仍把原始明文放在 header/query。
7. 灰度期间必须能快速关闭 required 策略，避免线上全量不可用。
