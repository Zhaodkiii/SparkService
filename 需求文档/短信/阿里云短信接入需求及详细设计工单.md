## 2. 背景与现状

SparkService 已存在部分阿里云短信代码：

1. `accounts/infrastructure/sms_provider.py` 已封装 `AliyunSMSProvider`，并调用官方 Python SDK 的 `SendSms`。
2. `SparkService/settings.py` 已定义 AccessKey、Endpoint、签名、通知模板和 OTP 模板配置。
3. `accounts/services/otp_service.py` 已调用短信 Provider 发送登录验证码。
4. `requirements.txt` 已声明 `alibabacloud-dysmsapi20170525`、Tea OpenAPI 和 Tea Util 依赖。
5. 后台通知任务已有短信渠道和发送记录相关业务基础。

因此本工单不是重新创建另一套短信模块，而是补齐、统一并上线现有能力。

### 2.1 现状差距

| 差距 | 影响 | 本工单处理方式 |
| --- | --- | --- |
| 指定模板 `SMS_508370089` 尚未形成明确环境配置 | 部署后仍可能提示模板未配置 | 增加环境变量示例和部署检查 |
| 不清楚模板是否包含变量 | `TemplateParam` 与控制台模板不匹配会发送失败 | 上线前核对模板内容；无变量时不传该字段 |
| 通用通知 Provider 固定拼装 `title/body/content` 三个变量 | 无变量模板或变量名不同会报错 | 改为由模板定义驱动参数，不再硬编码变量集合 |
| OTP 和通用通知复用范围不清晰 | 可能把通知模板误用于验证码 | 模板用途明确分离，禁止跨用途隐式复用 |
| SDK 异常文本直接作为 `reason` 返回 | 可能泄漏内部信息，且不利于统计 | 对外返回稳定错误码，详细异常仅写脱敏日志 |
| 配置缺失时 OTP 在开发降级路径中仍继续返回成功 | 非开发环境可能出现“接口成功但用户收不到短信” | 仅本地/测试允许降级，预发和生产快速失败 |
| 阿里云短信接口本身不提供业务幂等保证 | Celery/网络重试可能造成重复短信 | 服务端生成幂等键并持久化发送尝试 |

## 3. 需求范围

### 3.1 功能需求

1. 服务端通过阿里云短信服务向运行时指定的手机号发送短信。
2. 默认使用签名 `梦原鲸苏州科技服务` 和模板 `SMS_508370089`。
3. 支持无变量模板；未来模板包含变量时支持传入 JSON 对象并严格校验变量。
4. 支持单手机号发送；协议层允许向最多 1000 个手机号发送相同签名、相同模板变量的短信，但验证码类短信必须逐号码发送。
5. 多个手机号需要使用不同签名或不同模板变量时，必须使用 `SendBatchSms`，单次最多 100 个手机号。
6. 统一返回“提交成功/失败、BizId、RequestId、供应商状态码、稳定内部错误码”。
7. 发送日志可以按业务请求 ID、业务类型、手机号掩码、阿里云 BizId 和 RequestId 检索。
8. 支持超时、回执查询、有限重试、幂等控制和发送频率限制。
9. 本地自动化测试不得真实调用阿里云或产生短信费用。

### 3.2 非功能需求

1. AccessKey Secret 不进入仓库、接口响应、普通日志或数据库明文字段。
2. 日志中的手机号必须脱敏，例如 `138****8000`。
3. Provider 调用超时后不得无条件重试，必须先通过幂等状态避免重复发送。
4. 单次发送失败不得阻塞其他通知渠道的独立处理。
5. 发送结果统计区分：校验失败、配置失败、供应商拒绝、超时、未知异常。

### 3.3 本期不做

1. 不建设自定义短信内容发送能力，所有内容必须来自审核通过的阿里云模板。
2. 不允许前端直接传 `sign_name` 或 `template_code`。
3. 不在本工单中接入第二家短信供应商，但接口需保留替换能力。
4. 不把 AccessKey 暴露给 iOS、Android 或 Web 客户端。

## 5. 总体设计

```text
业务服务（OTP / 通知 / 邀请）
        │
        │ SmsMessage + idempotency_key
        ▼
统一短信应用服务 SmsService
  - 号码规范化与脱敏
  - 模板用途与参数校验
  - 频率限制
  - 幂等检查/发送记录
        │
        ▼
SmsProvider 接口
        │
        ▼
AliyunSMSProvider
  - 读取服务端配置
  - 构建 SendSmsRequest
  - 调用官方 SDK
  - 映射响应与错误
        │
        ▼
阿里云 Dysmsapi SendSms
```

### 5.1 分层职责

| 层 | 职责 | 禁止事项 |
| --- | --- | --- |
| 业务层 | 决定何时发送、收件人、模板用途、业务幂等键 | 不直接调用阿里云 SDK |
| `SmsService` | 参数校验、限流、幂等、落发送记录 | 不持有 AccessKey |
| `SmsProvider` | 屏蔽供应商协议，返回统一结果 | 不处理业务权限 |
| `AliyunSMSProvider` | 构建请求、调用 SDK、映射阿里云响应 | 不输出完整手机号和 Secret |

## 6. 详细设计

### 6.1 配置设计

在部署环境中配置：

```dotenv
ALIYUN_SMS_ENABLED=true
ALIYUN_SMS_ACCESS_KEY_ID=<由密钥管理系统注入>
ALIYUN_SMS_ACCESS_KEY_SECRET=<由密钥管理系统注入>
ALIYUN_SMS_ENDPOINT=dysmsapi.aliyuncs.com
ALIYUN_SMS_SIGN_NAME=梦原鲸苏州科技服务
ALIYUN_SMS_NOTIFICATION_TEMPLATE_CODE=SMS_508370089
ALIYUN_SMS_NOTIFICATION_TEMPLATE_VARIABLES=
ALIYUN_SMS_CONNECT_TIMEOUT_SECONDS=3
ALIYUN_SMS_READ_TIMEOUT_SECONDS=5
```

配置规则：

1. `ALIYUN_SMS_ENABLED=true` 时，启动检查必须验证 AK、Secret、签名和模板编码非空。
2. 生产环境配置缺失应阻止短信任务启动或使健康检查失败，不允许静默降级。
3. `ALIYUN_SMS_NOTIFICATION_TEMPLATE_VARIABLES` 为空代表模板无变量。
4. 若模板变量为 `name,code`，服务层必须校验参数键集合恰好匹配，不多传也不少传。
5. AccessKey 推荐使用仅具备短信发送权限的 RAM 用户，并定期轮换。

### 6.2 阿里云接口约束

| 项目 | 设计约束 |
| --- | --- |
| 服务地址 | `dysmsapi.aliyuncs.com`（中国站） |
| API 版本 | `Dysmsapi 2017-05-25` |
| API | `SendSms`、`QuerySendDetails` |
| 请求方式 | 通过官方 SDK 发起，底层优先 POST，不自行实现 V3 签名 |
| RAM Action | `dysms:SendSms`、`dysms:QuerySendDetails` |
| RAM Resource | `*`（阿里云当前授权模型为全部资源） |
| 官方流控 | 单用户 5000 QPS，即 5000 次/秒 |
| 同参数群发 | 半角逗号分隔，最多 1000 个号码，存在一定延迟 |
| 异参数群发 | 使用 `SendBatchSms`，单次最多 100 个号码 |
| 幂等 | 阿里云不提供，必须由 SparkService 实现 |
| 计费口径 | 国内短信按运营商回执状态计费；提交成功但运营商回执失败时不计费 |

国内短信超时必须设置为至少 1 秒，本项目默认连接超时 3 秒、读取超时 5 秒。`5000 QPS` 是供应商配额而不是系统运行目标；应用层限流和任务并发必须显著低于该值。

### 6.3 领域对象

建议新增内部对象，不直接在业务层传 SDK 模型：

```python
@dataclass(frozen=True)
class SmsMessage:
    phone_number: str
    template_key: str
    template_params: dict[str, str]
    business_type: str
    business_id: str
    idempotency_key: str

@dataclass(frozen=True)
class SmsSendResult:
    accepted: bool
    error_code: str
    provider_biz_id: str
    provider_request_id: str
    provider_code: str
```

其中 `template_key` 使用内部枚举，例如 `notification_fixed`、`login_otp`，再由服务端配置映射到真实模板编码。业务接口不得接收任意阿里云模板编码。

`accepted` 只表示阿里云返回 `Code=OK` 并受理提交，不表示运营商已经送达。`provider_biz_id` 对应 `BizId`，用于通过 `QuerySendDetails` 查询最终回执；`provider_request_id` 对应 `RequestId`，用于接口追踪。现有 Provider 把 RequestId 当作 `provider_message_id` 返回，改造时必须拆分。

### 6.4 SendSms 请求映射

| 阿里云字段 | 来源 | 规则 |
| --- | --- | --- |
| `SignName` | `ALIYUN_SMS_SIGN_NAME` | 固定为审核通过的签名 |
| `TemplateCode` | 内部 `template_key` 对应配置 | 本工单默认 `SMS_508370089` |
| `PhoneNumbers` | `SmsMessage.phone_number` | 同参数群发最多 1000 个、半角逗号分隔；验证码仅允许单号码 |
| `TemplateParam` | `SmsMessage.template_params` | 空字典时不设置该字段；非空时 JSON 序列化，禁止手拼字符串 |
| `OutId` | `business_type:business_id` 的安全摘要 | 可选，用于业务追踪，不包含敏感信息 |

无变量模板的推荐构造：

```python
kwargs = {
    "sign_name": settings.ALIYUN_SMS_SIGN_NAME,
    "template_code": settings.ALIYUN_SMS_NOTIFICATION_TEMPLATE_CODE,
    "phone_numbers": normalized_phone,
}
if template_params:
    kwargs["template_param"] = json.dumps(
        template_params,
        ensure_ascii=False,
        separators=(",", ":"),
    )
request = dysms_models.SendSmsRequest(**kwargs)
```

注意：`TemplateParam` 在模板无变量时应省略，而不是传空 JSON 字符串或业务自定义内容。

### 6.5 手机号处理

1. API 入参继续通过 `PhoneNumberService.normalize_e164` 规范化。
2. 中国大陆号码内部统一保存为 E.164（如 `+8613800138000`）；调用前按阿里云支持格式传入。
3. 空号码、格式错误号码在调用供应商前拒绝。
4. 首期业务层只允许单号码。通知群发由任务逐条投递，以保留每个收件人的状态、回执、费用归属和幂等性。
5. 后续启用同参数群发时不得超过 1000 个号码；不同号码需要不同变量时必须使用 `SendBatchSms`。
6. 日志、监控和错误响应中不得出现完整手机号。

### 6.6 幂等设计

阿里云 `SendSms` 不提供业务幂等保证，因此服务端负责幂等。

建议幂等键格式：

```text
sha256(business_type | business_id | template_key | normalized_phone | semantic_version)
```

发送流程：

1. 在数据库中以 `idempotency_key` 创建唯一发送记录，状态为 `PENDING`。
2. 若唯一键已存在且状态为 `ACCEPTED`，直接返回已有结果，不重复请求阿里云。
3. 调用前将状态改为 `SENDING` 并记录尝试次数。
4. 收到 `HTTP 200 + Code=OK` 后改为 `ACCEPTED`，分别保存阿里云 BizId 和 RequestId。
5. 明确被供应商拒绝时改为 `FAILED`，可按错误类型决定是否人工重试。
6. 网络超时属于结果未知，标记 `UNKNOWN`；先查询发送记录或等待回执，再决定是否重试。

### 6.7 响应与回执设计

| 阿里云字段 | 含义 | 系统处理 |
| --- | --- | --- |
| `Code` | 请求状态码，`OK` 表示提交成功 | 保存为 `provider_code`；仅 `OK` 进入 `ACCEPTED` |
| `Message` | 状态描述 | 脱敏截断后仅供内部排查，不向客户端原样返回 |
| `BizId` | 发送回执 ID | 保存为 `provider_biz_id`，用于查询最终状态 |
| `RequestId` | API 请求 ID | 保存为 `provider_request_id`，用于链路追踪 |

```text
PENDING -> SENDING -> ACCEPTED -> DELIVERED
                    |          -> DELIVERY_FAILED
                    -> FAILED
                    -> UNKNOWN
```

`ACCEPTED` 仅表示阿里云受理；`DELIVERED` 和 `DELIVERY_FAILED` 必须依据运营商回执判定。首期至少持久化 BizId 并支持人工查询；正式统计送达率和费用前，增加基于 `QuerySendDetails` 的定时回执同步任务。

### 6.8 QuerySendDetails 回执查询设计

`QuerySendDetails` 用于查询指定日期下某个手机号的发送详情，也可以传入 `BizId` 精确查询该号码的一条发送记录。接口只支持单个手机号和单个 BizId；批量统计应使用 `QuerySendStatistics` 或阿里云控制台。

#### 6.8.1 接口约束

| 项目 | 设计约束 |
| --- | --- |
| API | `QuerySendDetails` |
| RAM Action | `dysms:QuerySendDetails` |
| RAM Resource | `*` |
| 官方流控 | 单用户 5000 QPS，即 5000 次/秒 |
| 查询范围 | 仅支持最近 30 天 |
| PhoneNumber | 必填且只能传一个；国内号码传 11 位，国际/港澳台传国际区号加号码 |
| BizId | 可选且只能传一个，来源于发送接口返回值 |
| SendDate | 必填，格式 `yyyyMMdd`，使用原发送日期 |
| PageSize | 1–50，后台精确查询默认 20 |
| CurrentPage | 从 1 开始，并设置最大翻页数防止异常循环 |

查询任务的 QPS 和并发必须独立配置。虽然官方配额为 5000 QPS，系统默认查询速率应明显低于该值，并使用抖动分散轮询峰值。

#### 6.8.2 请求映射

```python
request = dysms_models.QuerySendDetailsRequest(
    phone_number=provider_phone_number,
    biz_id=send_record.provider_biz_id,
    send_date=send_record.accepted_at.strftime("%Y%m%d"),
    page_size=20,
    current_page=1,
)
```

1. 手机号必须来自原发送记录，不接受前端覆盖。
2. 国内 E.164 号码查询前转换为 11 位号码；国际/港澳台号码保留国际区号格式。
3. `SendDate` 使用原发送记录对应的业务时区日期，国内短信按 `Asia/Shanghai` 解释。
4. 有 BizId 时必须精确查询；没有 BizId 的 `UNKNOWN` 记录只能按手机号和日期分页匹配，并结合 OutId、模板及时间窗口谨慎判定。
5. 超过 30 天仍未同步回执的记录标记为 `RECEIPT_EXPIRED`，停止自动查询并告警。

#### 6.8.3 响应映射

| 返回字段 | 含义 | 系统处理 |
| --- | --- | --- |
| `Code` | 查询状态码 | 仅 `OK` 解析详情；非 `OK` 映射为查询错误 |
| `Message` | 状态描述 | 脱敏截断后仅供内部排查 |
| `RequestId` | 本次查询请求 ID | 保存为 `receipt_query_request_id`，不得覆盖发送 RequestId |
| `TotalCount` | 提交维度发送条数 | 安全解析为整数；不是计费条数 |
| `SmsSendDetailDTOs` | 发送详情集合 | 逐条匹配号码、模板、OutId 和发送时间 |
| `ErrCode` | 运营商回执码 | `DELIVERED` 映射为已送达；其他值按完整状态码表映射 |
| `TemplateCode` | 实际模板编码 | 与本地记录核对，不一致时告警 |
| `OutId` | 外部流水字段 | 与本地业务摘要核对，辅助防止误匹配 |
| `ReceiveDate` | 回执到达时间 | 保存为带时区的 `receipt_received_at` |
| `SendDate` | 供应商发送时间 | 保存为带时区的 `provider_sent_at` |
| `PhoneNum` | 回执手机号 | 仅用于校验，日志和落库必须脱敏或加密 |
| `Content` | 实际短信内容 | 默认不落库、不写日志，避免保存验证码和个人信息 |
| `SendStatus` | 发送状态数值 | 保存原始值并通过明确映射转换，不凭单个示例推断完整枚举 |

当 `ErrCode=DELIVERED` 且状态字段共同表明送达时，将记录更新为 `DELIVERED`。其他回执必须按阿里云完整状态码表分类；未知值保留原始 ErrCode 和 SendStatus，标记 `RECEIPT_UNKNOWN` 并告警。

#### 6.8.4 查询调度

1. `ACCEPTED` 记录延迟首次查询，避免立即轮询尚未生成的回执。
2. 未查到详情时按递增间隔重试，例如 1、5、15、30 分钟，再降低频率。
3. 到达 `DELIVERED` 或 `DELIVERY_FAILED` 后停止查询。
4. 记录查询次数、时间、RequestId 和错误码，但不记录短信 Content。
5. 查询失败不触发重新发送短信。
6. 批量报表使用 `QuerySendStatistics`，不循环滥用单号码详情接口。

### 6.9 发送状态与错误码

| 内部错误码 | 场景 | 是否重试 |
| --- | --- | --- |
| `sms_disabled` | 短信开关关闭 | 否 |
| `sms_config_invalid` | AK、签名或模板缺失 | 否，告警 |
| `sms_phone_invalid` | 手机号为空或格式错误 | 否 |
| `sms_template_params_invalid` | 变量缺失、多余或类型错误 | 否 |
| `sms_rate_limited` | 本地或阿里云触发频控 | 延迟重试或用户稍后操作 |
| `sms_provider_rejected` | 阿里云返回非 `OK` | 按供应商错误码分类 |
| `sms_provider_timeout_unknown` | 请求超时，结果未知 | 不自动重试，先查询/人工确认 |
| `sms_provider_unavailable` | SDK 或连接不可用且确认未提交 | 有限退避重试 |

对客户端仅返回稳定业务错误，不透出阿里云原始 Message。原始 `Code`、BizId、RequestId 和脱敏后的摘要写入内部发送记录。

### 6.10 超时和重试

1. 国内短信超时必须至少 1 秒；本项目默认连接超时 3 秒、读取超时 5 秒，数值可配置但不得低于 1 秒。
2. 参数错误、签名错误、模板错误、权限错误不重试。
3. 明确的服务端限流按 `retry_after` 或退避策略重试。
4. 超时后先根据 BizId、RequestId、发送记录或回执判断状态；仅在能确认请求未被受理时自动重试。
5. Celery 最大重试次数不超过 3 次，使用指数退避和抖动。
6. 每次任务重试复用相同 `idempotency_key`。

### 6.11 频率限制与防盗刷

除阿里云控制台频率限制外，SparkService 必须增加业务侧限制：

1. OTP 沿用同号码、同设备 30 秒冷却，并补充 IP、设备、号码的分钟/小时/日上限。
2. 登录接口在生成并落库 OTP 前完成限流，避免垃圾数据累积。
3. 连续触发上限时返回 429，不调用阿里云。
4. 后台批量通知需要审批权限、批次上限和操作审计。
5. 测试白名单仅在非生产环境生效；生产环境白名单改动需要审计。
6. 任务并发和应用层 QPS 必须可配置，默认值显著低于官方 5000 QPS 配额。

### 6.12 安全设计

1. 使用独立 RAM 用户，仅授予 `dysms:SendSms` 和 `dysms:QuerySendDetails` 等实际需要的短信权限。
2. Secret 由部署平台或密钥管理系统注入，不写入 `.env.example` 的真实值。
3. 禁止记录 `template_param` 原文；验证码、姓名等变量只记录字段名和长度。
4. 手机号落日志前脱敏；如需关联统计，使用带服务端盐的不可逆摘要。
5. 后台发送接口必须鉴权、授权并记录操作人、批次和审计日志。
6. 客户端不能控制签名、模板编码、Endpoint 或供应商参数。

### 6.13 可观测性

每次发送记录以下非敏感字段：

```text

business_type
business_id
template_key
template_code
phone_masked
idempotency_key
status
provider_code
provider_biz_id
provider_request_id
receipt_query_request_id
provider_err_code
provider_send_status
latency_ms
attempt_count
created_at / accepted_at / failed_at
provider_sent_at / receipt_received_at / last_receipt_query_at
```

建议监控指标：发送请求数、供应商接受率、运营商送达率、回执失败率、各错误码数量、P95 延迟、实际 QPS、限流数、未知状态数、费用估算、同一幂等键重复拦截数。配置异常、接受率或送达率突降、QPS 或费用异常需要告警。

## 12. 后台短信发送记录专项设计

### 12.1 当前查不到短信验证码的根因

结论：这是写入链路缺失，不是后台页面查询或前端渲染故障。

现有两条短信链路彼此割裂：

```text
后台通知短信
NotificationService._send_sms
  -> AliyunSMSProvider.send
  -> NotificationMessage.objects.create(channel="sms")
  -> AdminNotificationLogListView
  -> 通知中心 / 短信发送记录

手机号验证码
OTPService.request_phone_otp
  -> PhoneOTP.objects.create
  -> AliyunSMSProvider.send_login_code
  -> 仅写流程日志，不创建 NotificationMessage
  -> 后台列表无数据来源
```

代码证据：

1. `backoffice/views.py` 的 `AdminNotificationLogListView` 只查询 `NotificationMessage.objects.filter(channel=channel)`。
2. `accounts/services/notification_service.py` 的 `_send_sms` 在发送后创建 `NotificationMessage`，所以后台通知短信可以显示。
3. `accounts/services/otp_service.py` 的 `request_phone_otp` 只创建 `PhoneOTP`，调用 Provider 后没有创建任何短信发送记录。
4. `PhoneOTP` 只保存验证码哈希、手机号、有效期和请求维度，没有 BizId、供应商 RequestId、模板、提交状态及运营商回执字段。
5. `AliyunSMSProvider.send_login_code` 当前成功时只返回 RequestId，并将其命名为 `provider_message_id`；没有读取响应中的 BizId。
6. `NotificationMessage.user` 是必填外键，但登录验证码可能发生在用户注册或登录之前，此时无法可靠关联 User。因此直接让 OTP 创建现有 `NotificationMessage` 不是标准修复。

### 12.2 修复原则

新建渠道级统一模型 `SmsSendRecord`，作为所有短信的权威发送台账；`NotificationMessage` 继续承担后台活动通知的跨渠道业务记录。验证码、后台通知、成员邀请等所有短信在调用 Provider 前后都必须写入 `SmsSendRecord`。

不推荐以下方案：

1. 后台列表临时 UNION `PhoneOTP`：`PhoneOTP` 没有 BizId 和回执状态，只能展示“申请过验证码”，不能证明短信已提交或送达。
2. 强制 OTP 写 `NotificationMessage`：模型要求已有 User，不适合登录前、注册前号码。
3. 前端直接调用阿里云：会暴露云凭证、绕过权限审计并泄露手机号。
4. 用 RequestId 代替 BizId 查询：`QuerySendDetails` 的精确查询字段是 BizId，二者语义不同。

### 12.3 SmsSendRecord 数据模型

| 字段 | 类型/索引 | 说明 |
| --- | --- | --- |
| `id` | BigAutoField | 本地发送记录 ID |
| `source_type` | varchar, index | `login_otp`、`notification`、`member_invite` 等 |
| `source_id` | varchar, index | OTP ID、NotificationMessage ID 或业务记录 ID |
| `user_id` | nullable FK, index | 已知用户时关联；登录前允许为空 |
| `campaign_id` | nullable FK, index | 后台活动 ID |
| `phone_number_encrypted` | encrypted field | 必要时用于回执查询的可恢复号码 |
| `phone_masked` | varchar | 后台展示，如 `138****8000` |
| `phone_hash` | char(64), index | 带服务端盐的检索摘要 |
| `sign_name` | varchar | 实际使用的签名 |
| `template_code` | varchar, index | 实际使用的模板编码 |
| `template_param_keys` | JSON | 只保存变量名，不保存验证码等变量值 |
| `out_id` | varchar, index | 传给阿里云的外部流水摘要 |
| `idempotency_key` | varchar, unique | 防止重复提交 |
| `submit_status` | varchar, index | `pending/sending/accepted/failed/unknown/skipped` |
| `delivery_status` | varchar, index | `pending/delivered/failed/unknown/expired` |
| `provider_code` | varchar | SendSms 返回 Code |
| `provider_message` | varchar | 脱敏、截断后的 Message |
| `provider_biz_id` | varchar, index | SendSms 返回 BizId，回执精确查询依据 |
| `provider_request_id` | varchar, index | SendSms 请求 ID |
| `provider_err_code` | varchar, index | QuerySendDetails 返回 ErrCode |
| `provider_send_status` | integer | QuerySendDetails 返回 SendStatus 原值 |
| `receipt_query_request_id` | varchar | 最近一次回执查询 RequestId |
| `provider_sent_at` | datetime | 供应商发送时间 |
| `receipt_received_at` | datetime | 运营商回执时间 |
| `submitted_at` | datetime, index | 提交阿里云时间 |
| `last_receipt_query_at` | datetime | 最近查询时间 |
| `receipt_query_count` | integer | 回执查询次数 |
| `failure_reason` | varchar | 稳定内部失败原因 |
| `request_id` | varchar, index | SparkService 请求链路 ID |
| `created_at/updated_at` | datetime | 创建及更新时间 |

约束：`(source_type, source_id, phone_hash, template_code)` 应具备业务唯一性或生成唯一 `idempotency_key`。验证码正文、验证码明文和 QuerySendDetails 返回的 Content 不得写入本表。

### 12.4 写入时序

```text
业务发起发送
  -> 创建 SmsSendRecord(PENDING)
  -> 原子抢占为 SENDING
  -> Aliyun SendSms
     -> Code=OK：保存 BizId + RequestId，submit=ACCEPTED
     -> 明确拒绝：submit=FAILED
     -> 超时未知：submit=UNKNOWN
  -> 异步 QuerySendDetails
     -> DELIVERED：delivery=DELIVERED
     -> 明确失败：delivery=FAILED
     -> 未出结果：保持 PENDING/UNKNOWN，按策略复查
```

OTP 特殊处理：先创建 `PhoneOTP`，再以 `source_type=login_otp`、`source_id=otp_id` 创建短信台账；白名单固定验证码未调用阿里云时创建 `submit_status=skipped`、`failure_reason=whitelist_no_sms`，使后台能解释“未发送”，但不将其统计为供应商失败。

### 12.5 后台列表字段优化

当前 `ID / 用户 / 状态 / 标题 / 结果 / 发送时间 / 操作` 是通用通知列表，不适合短信运营排障。短信页面应使用专属列表，不再直接复用 `NotificationLogsView`。

推荐字段：

| 列 | 展示内容 | 说明 |
| --- | --- | --- |
| ID | SmsSendRecord ID | 支持复制 |
| 业务类型 | 登录验证码、后台通知、成员邀请 | 使用中文标签 |
| 用户 | 用户 ID/用户名或“登录前用户” | `user_id` 可空 |
| 接收号码 | `138****8000` | 默认只展示掩码 |
| 模板 | `SMS_508370089` | 可附模板用途 |
| 提交状态 | 待提交、提交中、已受理、提交失败、状态未知、未发送 | 不把已受理写成“发送成功” |
| 送达状态 | 待回执、已送达、送达失败、回执未知、回执过期 | 来源于 QuerySendDetails |
| 阿里云结果 | Code / ErrCode | 例如 `OK / DELIVERED` |
| BizId | 掩码或截断展示 | 支持复制完整值，受权限控制 |
| 提交时间 | `submitted_at` | 无值时显示创建时间 |
| 回执时间 | `receipt_received_at` | 未回执显示 `-` |
| 操作 | 查看详情、查询回执 | 按状态决定是否可用 |

列表默认排序 `created_at DESC, id DESC`。状态用两列展示，禁止继续用一个 `sent` 同时表达“阿里云受理”和“运营商送达”。

### 12.6 筛选与搜索

1. 关键词：本地 ID、用户 ID、用户名、BizId、RequestId、业务 source_id。
2. 手机号：管理员输入完整号码，服务端规范化后计算 phone_hash 查询；不做数据库明文模糊搜索。
3. 业务类型：验证码、通知、邀请等。
4. 提交状态与送达状态分别筛选。
5. 模板编码筛选。
6. 时间范围默认最近 7 天，最大单次 31 天。
7. “仅异常”快捷筛选：提交失败、状态未知、送达失败、回执过期。
8. 分页、排序全部由服务端完成。

### 12.7 详情抽屉

详情分为四组：

1. 基本信息：业务类型、source_id、用户、掩码号码、模板、签名、OutId、创建时间。
2. 提交信息：提交状态、Code、脱敏 Message、BizId、发送 RequestId、提交时间、耗时、尝试次数。
3. 回执信息：送达状态、ErrCode、SendStatus、供应商发送时间、回执时间、查询 RequestId、查询次数、最后查询时间。
4. 关联信息：NotificationMessage、Campaign 或 PhoneOTP 的安全跳转链接。

不展示验证码、`code_hash`、完整 TemplateParam、短信 Content、AccessKey、设备 ID 和 IP 地址。原始 JSON 仅限高权限排障角色且必须经过字段白名单与审计，不再直接渲染任意 `payload`。

### 12.8 后台 API 设计

#### 12.8.1 列表

```http
GET /api/admin/v1/sms/records/?page=1&page_size=20&source_type=login_otp&submit_status=accepted&delivery_status=pending&date_from=2026-07-01&date_to=2026-07-13
```

返回掩码后的列表字段，不返回可恢复手机号和敏感模板参数。

#### 12.8.2 详情

```http
GET /api/admin/v1/sms/records/{id}/
```

返回结构化提交信息和回执信息。读取详情写管理审计日志。

#### 12.8.3 主动查询回执

```http
POST /api/admin/v1/sms/records/{id}/query-delivery/
Idempotency-Key: <admin-action-id>
```

标准流程：

1. 校验管理员拥有 `notification:sms:query_delivery` 权限。
2. 从 `SmsSendRecord` 读取加密手机号、BizId 和原发送日期，禁止客户端提交或覆盖这三个参数。
3. 校验记录不超过 30 天、有且只有一个手机号和一个 BizId。
4. 对同一记录加分布式锁；若 30 秒内已查询过，返回最近结果，避免重复调用。
5. 调用 `QuerySendDetails(PhoneNumber, BizId, SendDate, PageSize=20, CurrentPage=1)`。
6. 校验响应详情的号码、TemplateCode、OutId 和时间窗口与本地记录一致。
7. 事务更新回执字段和送达状态，保存查询 RequestId；不保存 Content。
8. 返回最新的结构化详情，并写入管理员、记录 ID、查询前后状态的审计日志。

响应示例：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "id": 1024,
    "submit_status": "accepted",
    "delivery_status": "delivered",
    "provider_code": "OK",
    "provider_err_code": "DELIVERED",
    "provider_send_status": 3,
    "provider_sent_at": "2026-07-13T16:44:10+08:00",
    "receipt_received_at": "2026-07-13T16:44:13+08:00",
    "last_receipt_query_at": "2026-07-13T16:45:00+08:00"
  }
}
```

#### 12.8.4 错误响应

| 错误码 | HTTP | 场景 |
| --- | --- | --- |
| `sms_record_not_found` | 404 | 记录不存在 |
| `sms_receipt_query_not_allowed` | 409 | 未受理、无 BizId 或记录不适合查询 |
| `sms_receipt_query_expired` | 410 | 发送日期超过最近 30 天 |
| `sms_receipt_query_too_frequent` | 429 | 后台重复点击或内部限流 |
| `sms_receipt_provider_rate_limited` | 503 | 阿里云查询接口限流 |
| `sms_receipt_provider_failed` | 502 | 阿里云返回非 OK |
| `sms_receipt_not_ready` | 202 | 请求成功但暂未查询到回执 |
| `sms_receipt_mismatch` | 409 | 回执与本地号码、模板或 OutId 不一致 |

### 12.9 页面交互标准

1. “查询回执”仅在 `accepted/unknown` 且发送时间不超过 30 天时可用。
2. 点击后按钮进入加载状态，完成后局部刷新当前行和详情抽屉。
3. 30 秒内重复点击直接展示缓存结果和“刚刚已查询”。
4. 查询不到回执显示“供应商已受理，运营商回执暂未生成”，不得显示“发送失败”。
5. 查询失败保留原状态并展示可理解错误，不清空已有 BizId 或回执。
6. BizId、RequestId 提供复制按钮；手机号始终掩码。
7. OTP 行标题固定显示“登录验证码”，不得显示验证码正文。

### 12.10 迁移与兼容

1. 新增 `SmsSendRecord` 及索引后，所有新短信先写统一台账再调用 Provider。
2. `NotificationMessage` 增加可空的 `sms_send_record` 一对一关联，保留现有后台活动能力。
3. 历史 `NotificationMessage(channel=sms)` 可回填为 `source_type=notification`；现有 `provider_message_id` 只能暂标记为旧 RequestId，不能错误回填为 BizId。
4. 历史 `PhoneOTP` 因未保存供应商结果，最多回填“验证码申请记录”，不能伪造已受理或已送达状态；建议仅迁移上线后的新数据。
5. `/notifications/logs/sms/` 可在过渡期代理新列表，但前端最终切换到 `/sms/records/`。

### 12.11 专项验收标准

- [ ] 所有真实 OTP 短信均创建 SmsSendRecord，后台可按业务类型“登录验证码”查询。
- [ ] 登录前手机号不依赖 User 外键也能形成完整台账。
- [ ] 白名单未真实发送的验证码显示为“未发送/测试白名单”，不计入失败率。
- [ ] 发送成功分别保存 BizId 和 RequestId。
- [ ] 后台状态明确区分“已受理”和“已送达”。
- [ ] 管理员可以在详情中主动调用 QuerySendDetails，并看到更新后的回执。
- [ ] 主动查询使用服务端记录的单手机号、单 BizId 和发送日期，且限制最近 30 天。
- [ ] 查询回执时验证号码、模板、OutId 和时间窗口，防止串单。
- [ ] OTP 明文、短信 Content、完整手机号和 TemplateParam 不出现在页面、日志及普通数据库字段中。
- [ ] 查询操作具备独立 RBAC、审计、限流和防重复点击。
- [ ] 历史 RequestId 不会被误当成 BizId。
