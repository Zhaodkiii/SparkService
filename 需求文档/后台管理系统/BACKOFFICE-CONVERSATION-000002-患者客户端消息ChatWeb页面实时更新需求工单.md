## 2. 问题场景

1. 医生已登录 Chat Web，并打开患者与医生智能体绑定的会话页面。
2. 患者在 iOS 客户端的同一会话中发送一条消息。
3. 服务端能够保存该消息，重新进入或手动刷新 Chat Web 后也能读取到该消息。
4. 但是保持 Chat Web 页面打开时，消息区不会实时出现该患者消息。

由此形成双向链路不对称：

- `Chat Web 医生发送 → iOS 患者接收`：实时更新已经实现。
- `iOS 患者发送 → Chat Web 医生接收`：当前没有实时更新。

## 3. 当前代码事实与问题结论

| 能力 | 当前代码事实 | 结论 |
| --- | --- | --- |
| 统一消息数据 | 患者和医生消息均最终落入 `ChatMessage`，医生工作台通过现有消息接口读取 | 不需要新建第二套消息表 |
| 消息保存通知 | `chat_sync/signals.py` 监听 `ChatMessage.post_save`，事务提交后发送 `chat.sync.updated` | 服务端已有统一的消息变化触发点，可以复用触发时机 |
| 实时事件内容 | 当前 v2 事件已包含 `thread_id`、`event_id`、`message_ids`、`cursor`、`emitted_at` | 已具备定向定位会话的基础字段 |
| 当前事件接收范围 | `ChatSyncNotifier.notify_user_sync` 将事件发送给消息所属患者的 `user_{user_id}` 组 | 医生登录账号不属于患者用户组，不能收到该事件；也不应越权订阅患者组 |
| 医生消息读取接口 | `GET /api/hospital/v1/doctor/conversations/{thread_id}/messages/` 会先用当前医生身份校验会话访问权限，再返回消息 | 实时事件到达后可继续通过该接口拉取权威正文 |
| Chat Web 会话状态 | `DoctorConversationsProvider.loadSelected` 只在进入/切换会话及主动调用时获取详情和消息 | 页面保持打开期间没有新的读取触发器 |
| 医生自己发送 | `sendMessage` 会把发送结果加入本地 `messages`，随后再次执行 `loadSelected` | 只能保证医生自己发送后的页面更新，不能覆盖患者从另一端发来的消息 |
| Chat Web WebSocket | 医生工作台当前未订阅会话消息 WebSocket；现有 `RunControlContext` 只服务 AI Run 流事件 | AI Run 通道不能直接替代医生会话实时同步通道 |
| React 页面渲染 | 消息组件直接读取 Provider 的 `messages` 状态 | 只要状态被安全更新，页面能够正常重渲染，问题不在消息组件本身 |

### 3.1 已确认根因

该问题真实存在，根因由两个缺口共同构成：

1. 服务端只向患者账号范围发送消息变化提示，没有向有权查看该会话的医生工作台发送事件。
2. Chat Web 医生会话 Provider 没有建立实时订阅，也没有前台轮询，因此患者消息落库后不会触发已打开页面重新拉取。

### 3.2 安全边界

不能让医生账号直接加入患者的 `user_{user_id}` WebSocket 组。医生是否能读取某个会话，应继续以 `DoctorConversationPermission`、当前医生实体以及 `ClinicalConversationBinding` 为授权事实。实时通道只能通知当前医生有权查看的会话，事件本身不应携带完整医疗消息正文。

## 4. 已确认目标业务流程

```text
iOS 患者发送消息
    ↓
SparkService 校验并保存 ChatMessage
    ↓（数据库事务提交后）
产生患者账号同步提示（保留现有链路）
    ＋
产生医生工作台会话变化提示（医生专用 WebSocket）
    ↓
已认证的 Chat Web 医生连接收到 thread_id 变化提示
    ↓
DoctorConversationsProvider 判断是否为当前会话
    ↓
调用现有医生消息 REST 接口读取权威数据
    ↓
按 server_message_id / client_message_id 去重并更新 messages
    ↓
当前消息页面实时显示患者新消息
```

## 5. 总体设计原则

1. **消息表复用**：继续使用 `ChatMessage`，不复制医生工作台消息数据。
2. **WebSocket 只发提示**：事件负责告知“哪个会话发生变化”，消息正文由现有授权 REST 接口返回。
3. **医生权限独立**：医生工作台使用医生/医院会话授权组，不订阅患者账号组。
4. **数据库提交后通知**：只在消息事务成功提交后发送，避免页面拉取到尚未提交的数据。
5. **允许重复事件**：实时事件按“至少一次提示”处理，Web 端必须去重、合并，并允许补偿拉取。
6. **WebSocket 不是唯一事实源**：断线、浏览器挂起、页面切回前台后必须能够通过 REST 补齐。
7. **不影响既有反向链路**：医生发送消息到 iOS 的现有实时更新逻辑继续保留。

## 6. 建议的技术落点

### 6.1 服务端

本期采用“医生工作台专用 WebSocket 提示 + 现有 REST 定向拉取”。

建议新增医生工作台专用实时入口，例如：

```text
/ws/hospital/doctor/conversations/
```

职责边界：

- 使用短期、一次性 WebSocket ticket 建立连接，避免把长期 JWT 放入 URL。
- ticket 必须绑定准确的 `websocket_path`，并沿用 Web 会话失效校验。
- Consumer 建连时解析当前用户对应的有效医生身份和医院关系。
- 加入医生专属组，例如 `hospital_doctor_{doctor_id}`，不能加入患者账号组。
- `ChatMessage` 提交后，根据 `thread_id` 查找有效的 `ClinicalConversationBinding`，仅向该绑定医生的组发送提示。
- 事件不包含消息正文、患者完整资料或知识库内容。
- 会话解绑、医生停用、职工停用、会话不可访问时，不再下发可用事件；即使收到迟到事件，REST 权限仍作为最终防线。

建议事件契约草案：

```json
{
  "type": "hospital.conversation.updated",
  "payload_version": 1,
  "event_id": "uuid",
  "thread_id": "uuid",
  "message_ids": ["uuid"],
  "cursor": "server-updated-at",
  "emitted_at": "ISO-8601",
  "change_kind": "message_created"
}
```

其中 `message_ids` 仅用于诊断、去重提示或未来增量接口，不代表 Web 可以绕过 REST 权限直接读取消息。

### 6.2 Chat Web

建议在医生工作台布局生命周期内新增实时连接管理，并由 `DoctorConversationsProvider` 处理会话事件：

- 医生完成认证并进入医生工作台后建立连接。
- 连接成功后执行一次补偿刷新，避免建连前的时间窗丢消息。
- 收到当前 `selectedThreadId` 的事件时，定向重新读取当前会话消息。
- 同一会话连续收到多次事件时合并请求，避免并发覆盖和重复全量拉取。
- 拉取过程中再次收到事件时设置 `dirty`；当前请求结束后再补跑一次。
- REST 返回后按稳定消息 ID 合并；不得只按正文或时间去重。
- WebSocket 断线不清空当前消息；指数退避重连。
- 页面重新可见、网络恢复、连接重建成功时执行补偿刷新。
- 组件卸载、账号退出或医生身份失效时关闭连接并清理定时器。

### 6.3 现有接口复用

首版可以继续调用：

```text
GET /api/hospital/v1/doctor/conversations/{thread_id}/messages/
GET /api/hospital/v1/doctor/conversations/{thread_id}/
GET /api/hospital/v1/doctor/conversations/
```

第一项负责当前会话正文的权威读取；后两项用于实时事件后的列表、计数、会话版本、最后活跃时间与状态补齐。

## 7. 一问一答需求确认

### Q1：本期采用哪一种 Chat Web 实时更新主方案？

**为什么要问：** 当前患者账号 WebSocket 组不能安全地给医生复用。必须先决定医生工作台是建立独立授权实时通道，还是通过轮询解决；该选择会直接决定服务端 Consumer、ticket、事件权限、前端连接生命周期和后续扩展成本。

请选择：

- **A. 医生工作台专用 WebSocket 提示 + 现有 REST 定向拉取（推荐）**  
  服务端只推送包含 `thread_id` 的变化提示；Chat Web 收到后通过现有医生消息接口拉取正文。权限清楚，可补偿，也不会在实时事件中暴露完整消息。
- **B. Chat Web 前台轮询当前会话**  
  每 2～3 秒调用现有消息接口。实现面较小，但空请求多、实时性受轮询间隔影响，多医生和多页面时会持续增加服务端压力。
- **C. 医生工作台专用 WebSocket 直接推送完整消息正文**  
  到达后可以直接渲染，但实时通道需要复制 REST 序列化、权限、脱敏和兼容逻辑，重连补偿仍不能省略。

**确认答案：A。** 新增医生工作台专用 WebSocket；事件只承载会话变化提示，Chat Web 依据 `thread_id` 调用现有医生会话 REST 接口读取权威正文。

**落实影响：**

- 服务端增加医生身份范围的 WebSocket ticket、路由、Consumer 和组分发能力。
- `ChatMessage` 事务提交后，除既有患者账号同步事件外，向该会话有效绑定医生发送 `hospital.conversation.updated` 提示。
- Chat Web 在医生工作台范围维护连接；收到当前会话提示后，合并触发消息 REST 定向拉取。
- 不在 WebSocket 事件中传输完整消息正文，不复用患者 `user_{user_id}` 组。

### Q2：患者在未打开的其他会话发送消息时，Chat Web 列表本期如何更新？

**为什么要问：** 医生工作台不仅有当前消息页，还有待处理、重点、已终结等会话列表及数量。若只刷新当前会话，医生停留在列表页或打开另一位患者时，无法及时发现新咨询；若每条事件都全量刷新列表，则需要控制频率、排序和搜索筛选的稳定性。

请选择：

- **A. 当前会话定向刷新；其他会话只刷新列表与计数，不拉取正文（推荐）**  
  所有事件都使当前队列的卡片、排序和数量静默补齐；仅 `thread_id` 等于当前打开会话时读取消息正文。兼顾医生发现新消息与接口成本。
- **B. 只处理当前打开会话**  
  最小实现；医生停留在列表或查看其他患者时，新的患者消息要等手动刷新或下次进入才可见。
- **C. 所有会话均预拉取最新正文**  
  信息最完整，但会带来大量无意义读取，也会把非当前患者消息留在前端内存中。

**确认答案：A。** 所有会话变化事件均静默刷新当前筛选条件下的会话列表和队列计数；只有事件的 `thread_id` 等于当前 `selectedThreadId` 时，才读取并合并消息正文。

**落实影响：**

- `DoctorConversationsProvider` 将实时事件分为“当前会话消息刷新”和“非当前会话列表刷新”两条路径。
- 非当前会话不预拉取消息正文，不在前端缓存其他患者的完整聊天内容。
- 列表刷新必须保留当前 `queue`、`keyword`、分页与筛选语义，并采用合并/防抖机制避免连续事件造成请求风暴。
- 是否展示“新消息”提示由 Q3 单独确认。

### Q3：列表已实时刷新后，如何标记尚未打开的新患者消息？

**为什么要问：** Q2 已确定其他会话会刷新列表和计数，但若列表只改变排序，医生无法快速区分“刚刚有患者发送新内容”与普通会话。标记规则会影响卡片字段、未读状态是否需要服务端持久化，以及跨标签页/重新登录后是否一致。

请选择：

- **A. 仅本次打开页面内的轻量“新消息”标记（推荐）**  
  收到非当前会话事件后，卡片显示小圆点或“新消息”；医生点击并成功读取该会话后清除。演示期不新增服务端持久未读表，刷新页面后标记可重置。
- **B. 服务端持久化医生维度未读状态**  
  跨刷新、跨设备保持一致，适合正式工作台；但需要定义已读回执、多人/代班医生、会话转交和数据清理规则。
- **C. 不显示新消息标记，只更新排序与计数**  
  改动最少，但新消息仅靠列表位置变化发现，容易被忽略。

**确认答案：A。** 非当前会话收到患者消息事件后，仅在本次打开的医生工作台页面将该卡片标记为“新消息”；医生切换并成功读取该会话后清除标记。刷新页面、重新登录或切换设备后不承诺保留该状态。

**落实影响：**

- Web 前端维护以 `thread_id` 为键的轻量内存集合，不新增服务端未读表、已读回执或跨设备同步。
- 收到当前会话事件不添加卡片新消息标记；该会话的消息区域按 Q4 规则反馈。
- 从卡片进入会话且消息读取成功后，移除该会话的本地标记；若读取失败则保留标记。
- 列表刷新不会因为服务端数据覆盖而丢失本页面内尚未处理的标记。

### Q4：当前打开的会话收到患者新消息时，消息区如何滚动与提示？

**为什么要问：** 即使消息已拉取并写入状态，若医生正在阅读较早病史，强制跳到底部会打断阅读；若完全不提示，医生又可能不知道消息已经到达。该规则直接影响医生工作台的可用性。

请选择：

- **A. 位于底部时自动跟随；阅读历史时不跳动，显示“有新消息”按钮（推荐）**  
  医生在最新消息附近时自然看到新消息；向上阅读时保持位置，点击提示后滚到末尾并清除当前页面的轻量新消息标记。
- **B. 每次新消息都强制滚到底部**  
  最容易看到新消息，但会打断医生查看既往对话与重点信息。
- **C. 从不自动滚动，仅更新消息内容**  
  阅读最稳定，但医生需自行发现并滚到底部。

**确认答案：A。** 当前消息区接近底部时自动滚动展示新消息；医生向上阅读历史时不改变滚动位置，显示“有新消息”按钮。点击按钮后滚动至底部并清除该会话的页面内提示。

**落实影响：**

- 消息组件根据滚动容器与底部距离判断是否处于“跟随状态”，不以页面是否刚加载作为唯一判断。
- 定向拉取合并多条消息时按一次更新处理，避免每条消息触发一次滚动动画。
- 阅读历史期间的新消息数可在按钮上聚合显示；不需要将该数量持久化到服务端。
- 医生主动发送消息时视为回到当前会话末尾，可自动跟随发送结果和后续患者回复。

### Q5：连接重建、页面回前台或网络恢复后，补偿刷新范围是什么？

**为什么要问：** WebSocket 事件是“至少一次提示”而不是永久消息队列。浏览器切后台、网络切换或服务端重启期间可能漏掉事件；若不补偿，页面会长期停留在旧状态。补偿范围决定恢复速度与接口负载。

请选择：

- **A. 刷新当前列表与计数；若有已打开会话，再定向刷新该会话消息（推荐）**  
  与 Q2 的数据范围一致：恢复后立即补齐医生发现层和当前阅读层，不读取其他患者的完整正文。
- **B. 只刷新当前已打开会话**  
  请求少，但医生停留列表页时可能漏掉断线期间的新咨询。
- **C. 刷新所有可见会话的消息正文**  
  补齐最彻底，但可能一次读取大量患者聊天内容，不符合本期最小读取范围。

**确认答案：A。** 在医生工作台首次建立连接成功、WebSocket 重连成功、浏览器页面重新可见、网络从不可用恢复时，刷新当前筛选下的会话列表与队列计数；若已打开一个会话，则额外定向读取该会话的详情和消息正文。

**落实影响：**

- 补偿触发应合并到同一刷新调度器，避免“重连 + visibilitychange + online”在短时间内发出重复请求。
- 当前会话消息仍遵循最小读取原则，不补拉其他患者完整正文。
- 补偿拉取失败时保留已有 UI 数据并按网络错误规则重试，不清空当前对话或本地新消息标记。
- 连接成功后的补偿发生在 Consumer 已完成医生身份校验之后。

### Q6：当前会话短时间连续收到多条患者消息时，如何调度消息拉取？

**为什么要问：** 患者可能连续发送多条文本，或消息保存与 AI/医生消息同时触发多个事件。若每条事件都并行调用消息接口，先发起的旧请求可能后返回并覆盖新数据；若等待过长，又会损失实时感。

请选择：

- **A. 首条立即拉取；拉取期间后续事件标记为 dirty，结束后补跑一次（推荐）**  
  当前会话始终最多一个在途读取；在途期间的任何新事件都保证至少再读取一次，兼顾实时性与不丢消息。
- **B. 固定防抖 500～1000ms 后再拉取一次**  
  请求更少，但首条新消息会有明显延迟，连续输入时可能一直等待。
- **C. 每个事件都取消旧请求并发起新请求**  
  表面上总追逐最新事件，但取消和网络竞态复杂，慢网络下可能反复取消而一直没有结果。

**确认答案：A。** 同一 `thread_id` 的首条事件立即触发消息拉取；若拉取尚未结束又收到事件，仅标记该会话为 `dirty`。本轮读取完成后，若仍为 `dirty`，立即再执行一轮定向读取；每轮结束后再检查一次，直至没有新事件。

**落实影响：**

- 前端以 `thread_id` 维护 in-flight 与 dirty 状态；列表刷新也接入独立但可合并的调度器。
- 每轮读取以服务端返回的稳定消息 ID 合并或替换权威顺序，旧响应不得覆盖已经确认的更晚消息。
- 网络错误不清除 dirty 标记；交由重试/恢复补偿继续完成同步。
- 医生自己发送导致的 `loadSelected` 与实时事件进入同一会话刷新队列，避免两套请求互相覆盖。

### Q7：患者消息实时事件应发送给哪些医院账号？

**为什么要问：** 实时事件虽然不带正文，但 `thread_id`、发生时间和是否有患者新消息本身也属于敏感就医信息。当前医生消息 REST 接口按 `DoctorConversationPermission` 和会话绑定校验，实时组必须使用同一最小授权范围，不能因为“方便通知”扩大可见人群。

请选择：

- **A. 仅发送给该会话绑定的真实医生账号（推荐）**  
  与当前医生工作台可读取范围一致；医生停用、会话终结或绑定失效后不再接收。医院管理员仍可通过其现有后台审计/管理入口工作，但本期不订阅患者消息实时正文提示。
- **B. 发送给该医生及同院医院管理员**  
  管理员能即时发现会话变化，但需要新增管理员查看患者会话的明确业务权限与审计边界。
- **C. 发送给该医生及同科室所有医生**  
  便于科室协同，但会把患者咨询状态扩散给未被会话绑定的医生，需要完整的转诊、接管与责任确认设计。

**确认答案：A。** 仅向与该 `ClinicalConversationBinding` 有效绑定的真实医生账号发送 `hospital.conversation.updated`。医院管理员、同科室其他医生及未绑定职工不接收此类实时事件。

**落实影响：**

- 医生 WebSocket Consumer 的组成员资格由当前有效 `DoctorProfile` 决定；事件分发时以会话绑定的 `doctor_id` 作为唯一目标。
- 不能以医院 ID、科室 ID 或患者 `user_id` 作为医生消息通知的广播范围。
- 会话权限变更后，REST 接口仍是最终授权校验；实时事件只做额外提示，不能构成访问授权。
- 后续如需多人协同，必须以独立“接管/转交/授权”工单定义，不在本期隐式开放。

### Q8：已打开会话在实时刷新时变为不可访问或已终结，Chat Web 如何处理？

**为什么要问：** 消息事件和权限/终结操作可能交错发生。医生页面收到提示后再拉取，有可能得到“会话已终结、绑定已失效或无权访问”。若继续保留可输入界面，可能造成医生误以为仍可回复；若直接静默清空，又会丢失对原因的理解。

请选择：

- **A. 立即按服务端权威状态刷新为只读或退出该会话，并显示原因（推荐）**  
  已终结但仍可查看历史时保留历史并禁用发送；权限失效或会话不再属于该医生时移除卡片、关闭详情并提示原因。不会因迟到事件继续尝试发送。
- **B. 保持当前页面可操作，直到医生手动刷新**  
  视觉变化最少，但可能对一个已经终结或无权限的会话继续输入，最后才在发送失败时发现。
- **C. 收到任何异常即清空消息并跳回列表，不提示原因**  
  安全保守，但医生无法区分网络问题、会话终结和权限变更，也会影响历史查看。

**确认答案：A。** 实时提示触发后的 REST 读取必须以服务端响应为最终状态：会话已终结但仍有读取权限时，保留历史并立即禁用输入，展示终结原因；权限失效、会话解绑或不再归属当前医生时，移除该会话卡片、关闭详情并提示原因。

**落实影响：**

- 复用 `resolveHospitalWriteError` 与现有 `dropConversation` 的语义，并扩展到实时定向拉取失败后的状态处理。
- 仅网络、超时和 5xx 错误保留页面与 dirty 状态并等待重试；明确的 403/404/会话终结状态不无限重试。
- 会话变为只读后禁止发送、加入、重点等级修改等写操作，历史信息仍以服务端允许范围展示。
- 迟到 WebSocket 事件不会恢复已移除会话，也不会绕过随后 REST 的权限校验。

### Q9：实时链路出现延迟、断线或拉取失败时，诊断记录保存到什么粒度？

**为什么要问：** 本问题跨 iOS、WebSocket、服务端分发、Chat Web REST 拉取四个阶段。没有可关联的诊断信息时，只能依赖人工复现；但保存完整患者消息正文又会扩大敏感医疗数据的日志暴露面和留存责任。

请选择：

- **A. 只记录关联元数据与结果，不记录消息正文（推荐）**  
  记录 `event_id`、`thread_id`、医生 ID、消息 ID、服务端发出/客户端收到/拉取完成时间、耗时、重连次数、错误码和 trace/request ID；正文仍只保留在既有业务消息表。
- **B. 仅在错误时记录完整 WebSocket 事件 payload，但不记录正文**  
  有更多现场上下文，但正常链路缺少时序样本，且需严格控制错误日志留存。
- **C. 保存完整 payload 和消息正文**  
  排障信息最完整，但会在诊断日志中额外复制患者医疗对话，安全、脱敏、访问审计和保留期限成本最高。

**确认答案：A。** 实时链路诊断只记录可关联的元数据与执行结果，不复制患者消息正文或富文本内容到日志。业务正文继续只存在于既有 `ChatMessage` 等授权业务数据中。

**落实影响：**

- 服务端记录 `event_id`、`thread_id`、目标 `doctor_id`、消息 ID、发出时间、分发结果、异常类型、trace/request ID；不记录 `text`、消息块或患者身份扩展字段。
- Chat Web 记录连接状态、事件接收时间、定向拉取开始/结束、耗时、HTTP 状态、重连次数和错误分类；前端诊断不得打印完整消息对象。
- 以 `event_id`、`thread_id`、消息 ID 与 trace/request ID 串联 iOS 发送、服务端提交、事件分发和 Web 拉取各阶段。
- 如需查看正文，应通过既有医生会话权限、审计入口和业务数据查询完成，不借由技术日志绕过授权。

### Q10：前台正常网络下，患者消息应在多久内出现在已打开的 Chat Web 会话？

**为什么要问：** 这决定 WebSocket 重连、REST 超时、重试和诊断告警的阈值。没有明确目标，就无法判断“稍慢但正常”与“实时链路故障”，也无法做验收。

请选择：

- **A. 目标 3 秒内显示；超过 3 秒静默重试并记录诊断（推荐）**  
  适合当前“事件提示 + REST 拉取”的实现；不阻断医生阅读，超时由恢复补偿兜底。
- **B. 目标 1 秒内显示；超过即显示页面级异常**  
  体验要求很高，但移动网络、代理、服务端负载下误报概率较大，且医生页面容易出现无意义提示。
- **C. 不设明确时限，只要最终能同步即可**  
  实现最宽松，但无法验收实时能力，也无法量化问题。

**确认答案：A。** 在 Chat Web 位于前台、网络正常且实时连接可用时，患者消息从服务端成功提交起，应在 3 秒内显示于医生已打开的对应会话。超过 3 秒不显示阻塞性页面错误；客户端静默重试、恢复补偿，并记录诊断元数据。

**落实影响：**

- 验收须分别测量：服务端提交完成、医生事件发出、Chat Web 接收、REST 拉取完成、消息渲染完成的端到端耗时。
- 超时判定以可关联时间戳和 `event_id`/消息 ID 为依据，不以浏览器本地时钟单独判断。
- 3 秒目标不适用于浏览器后台、离线、权限失效、服务端维护或网络恢复期间；这些情形按 Q5 补偿流程处理。
- 超时不弹出打断性提示；可在调试/诊断面板展示聚合状态，正式页面只维持正常阅读体验。

### Q11：首版收到实时提示后，消息正文采用哪一种读取接口策略？

**为什么要问：** 当前医生消息接口会返回该会话的完整可见消息列表，最容易复用；但会话变长后，每次实时事件全量读取的成本会上升。现在决定是否为本工单新增增量 cursor/after 参数，会影响服务端 API 契约、前端同步状态和测试范围。

请选择：

- **A. 首版复用现有完整消息读取接口；前端按稳定 ID 去重（推荐）**  
  不新建接口，实施和回归范围最小。结合 Q6 的请求合并，在演示及早期医生会话规模下可控；后续根据真实长度和耗时再演进增量 API。
- **B. 本期新增医生会话消息增量接口**  
  例如按 `after_message_id` 或服务端 cursor 获取增量消息；长期更省流量，但需要处理 cursor 失效、删除/撤回、排序与首次全量初始化。
- **C. WebSocket 直接下发完整消息正文，不再经 REST 读取**  
  首屏显示快，但与已经确认的 Q1“提示 + REST 权威读取”冲突，需重复实现权限和序列化。

**确认答案：A。** 首版不新增医生会话消息增量接口；收到实时事件后复用完整消息读取接口，前端使用 `server_message_id` 优先、`client_message_id` 兜底的稳定键完成去重和权威排序。

**落实影响：**

- 本期不新增 cursor、`after_message_id`、消息 delta 表或专用同步 Outbox。
- 实时事件仍以 `thread_id` 定位；一次完整读取结果是该会话当前可见消息的权威快照。
- 发送中的医生本地乐观消息在对应稳定 ID 出现在服务端快照后合并，不重复渲染。
- 若后续真实会话长度、接口耗时或 3 秒目标出现瓶颈，再以独立工单设计增量读取契约。

## 8. 完整落地方案

### 8.1 本期范围与非目标

| 范围 | 本期结论 |
| --- | --- |
| 患者消息触发 | iOS 或其他患者入口成功创建 `ChatMessage` 后触发；不改变患者端既有同步链路 |
| 医生接收者 | 仅该 `ClinicalConversationBinding.doctor` 对应的有效真实医生账号 |
| 消息读取 | 事件只提示变化；Chat Web 通过既有医生 REST 接口读取完整权威消息快照 |
| 列表变化 | 所有有效事件刷新当前队列列表与计数；不读取非当前会话正文 |
| 未读表达 | 本页面内存的“新消息”标记；不持久化，不跨刷新、标签页或设备同步 |
| 首版性能目标 | 前台正常网络下，服务端消息提交成功至当前打开会话显示，目标不超过 3 秒 |
| 明确不做 | 不推送完整消息正文；不建第二套消息表；不建医生未读表；不建消息增量接口；不开放管理员/同科医生订阅；不改变 AI Run WebSocket |

### 8.2 服务端设计

#### 8.2.1 WebSocket ticket 与路由

新增医生工作台专用 ticket API 和 WebSocket 路由，建议契约如下：

```text
POST /api/hospital/v1/doctor/conversations/ws-tickets/
GET  /ws/hospital/doctor/conversations/?ticket=<one-time-ticket>
```

ticket API 要求：

1. 使用与医生消息 REST 相同的 `DoctorConversationPermission`，先确认请求用户有有效医院医生身份。
2. 复用已有 `ChatWebSocketTicket` 的随机 token、哈希保存、短 TTL、单次消费、`web_session_id` 和 `web_session_version` 校验机制；仅将 `websocket_path` 固定为医生实时路径。
3. ticket 不携带 `thread_id`、患者 ID、医生资料或消息正文。Consumer 建连后从 ticket 对应用户重新解析有效 `DoctorProfile`，避免信任浏览器传参。
4. 用户退出、Web Session 作废、职工停用或医生档案不再有效时，连接应被拒绝或关闭；后续 REST 仍做最终权限校验。

建议新增专用 Consumer，例如 `hospital_care/realtime/doctor_conversation_consumer.py`。连接成功后：

```text
认证用户 → get_active_doctor(user) → hospital_doctor_{doctor_id} 组 → accept
```

不允许加入以下组：

- 患者通用同步组 `user_{patient_user_id}`；
- 医院级、科室级广播组；
- 前端 URL 或消息体指定的任意医生/会话组。

#### 8.2.2 事务提交后的事件分发

继续保留 `chat_sync/signals.py` 对 `ChatMessage.post_save` 的患者同步通知。为医生工作台新增独立分发器，必须在 `transaction.on_commit` 内执行：

```text
ChatMessage 保存
  → on_commit
  → 以 message.thread_id 查询 ClinicalConversationBinding
  → 确认 binding 非 ended 且医生档案/成员有效
  → 向 hospital_doctor_{binding.doctor_id} 发送提示
```

分发查询必须满足：

- `thread_id` 一对一对应会话绑定；不按患者 user、医院或科室扩大范围。
- 会话 `service_status=ended` 时不再向医生下发新消息提示。
- 绑定不存在、医生无效、事务回滚或 channel layer 不可用时，不影响消息主流程；记录不含正文的诊断结果。
- 事件可重复到达；不得依赖“恰好一次”。

#### 8.2.3 WebSocket 事件契约

```json
{
  "type": "hospital.conversation.updated",
  "payload_version": 1,
  "event_id": "e9c1f1e8-...",
  "thread_id": "bfa4237b-...",
  "message_ids": ["f0e4c34c-..."],
  "cursor": "2026-09-02T22:30:00.000000+08:00",
  "emitted_at": "2026-09-02T22:30:00.020000+08:00",
  "change_kind": "message_created"
}
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `type` | 固定为 `hospital.conversation.updated` |
| `payload_version` | 首版固定 `1`；破坏性变更须提升版本 |
| `event_id` | 每次分发唯一，用于诊断和事件级去重 |
| `thread_id` | 必填，唯一用于前端定位会话 |
| `message_ids` | 本次引起变化的稳定消息 ID 列表；只用于关联与诊断 |
| `cursor` | 消息服务端更新时间提示；首版不作为医生 REST 增量游标 |
| `emitted_at` | 服务端分发时间，用于端到端时延测量 |
| `change_kind` | 首版为 `message_created`；未来可扩展 `conversation_ended` 等值，但新增值必须兼容旧 Web |

事件禁止包含：患者姓名、手机号、成员资料、消息正文、块内容、病历、知识库片段、模型推理内容或可直接展示的患者医疗信息。

#### 8.2.4 REST 权威与状态处理

首版继续复用：

```text
GET /api/hospital/v1/doctor/conversations/
GET /api/hospital/v1/doctor/conversations/{thread_id}/
GET /api/hospital/v1/doctor/conversations/{thread_id}/messages/
```

- 事件到达当前会话：并行/顺序读取详情与完整消息列表；详情决定是否只读、终结或移除，消息接口提供正文快照。
- 事件到达非当前会话：只读取列表与计数，保持当前 `queue`、关键词、分页语义。
- REST 的 `DoctorConversationPermission` 和 `get_doctor_conversation` 是最终真相。Consumer 成功收到事件不代表会话仍可读。
- 本期不增加 `after_message_id`、cursor、消息 delta 或专用同步表。

### 8.3 Chat Web 设计

#### 8.3.1 连接生命周期

在医生工作台布局范围内挂载实时连接，不将其放入普通 AI 对话的 `RunControlContext`：

```text
医生登录成功
  → 请求医生 WebSocket ticket
  → 连接医生会话 WebSocket
  → 成功后执行一次补偿刷新
  → 进入实时事件处理
  → 退出、身份失效、组件卸载时关闭
```

重连默认策略：网络错误或非权限型关闭后指数退避 `1s → 2s → 4s → 8s → 16s → 30s（上限）`，每次加入小幅随机抖动。浏览器不可见时不持续高频重连；重新可见或 `online` 事件到来时立即尝试连接并执行补偿。认证失败、医生身份失效和明确会话权限错误不进行无限重连。

#### 8.3.2 实时事件处理矩阵

| 场景 | 列表与计数 | 当前消息正文 | 页面提示 |
| --- | --- | --- | --- |
| 事件属于当前 `selectedThreadId` | 合并刷新 | 立即进入定向读取队列 | 按滚动状态展示或更新新消息按钮 |
| 事件属于非当前会话 | 刷新当前筛选下的列表与计数 | 不读取 | 为该卡片加入页面内“新消息”标记 |
| 首次连接成功 / 重连成功 | 刷新 | 有当前会话则读取 | 静默 |
| 页面回前台 / 网络恢复 | 刷新 | 有当前会话则读取 | 静默 |
| 403/404/绑定失效 | 重新读取列表 | 不重试正文 | 移除卡片、关闭详情并说明原因 |
| 已终结但允许读取 | 刷新状态 | 保留最后可见历史 | 输入与写操作禁用，显示终结原因 |
| 网络、超时、5xx | 保留旧数据，等待调度器重试 | 保留 dirty | 无阻塞提示，仅记录诊断 |

#### 8.3.3 当前会话刷新调度器

每个 `thread_id` 至少维护：

```text
isLoading: Bool
dirty: Bool
latestEventId: String?
lastAppliedMessageIds: Set<String>
```

规则：

1. 第一条事件立即读取当前会话详情和完整消息快照。
2. 读取未结束时收到后续事件，只将该会话标记 `dirty=true`。
3. 本轮请求成功或可恢复失败后，若 `dirty=true`，清除标记并立即再跑一轮；直至没有新事件。
4. 医生自己发送触发的 `loadSelected` 与实时事件必须进入相同队列，不能独立并发覆盖状态。
5. 完整快照按 `created_at, id` 的服务端权威顺序展示。使用 `server_message_id`，缺失时使用 `client_message_id` 作为稳定键处理乐观消息去重；不按正文文本去重。
6. 非当前会话列表刷新使用独立的短时合并调度，保留当前筛选参数；它不阻塞当前正文刷新。

#### 8.3.4 页面内新消息与滚动

- 非当前会话事件将 `thread_id` 加入前端内存 `newMessageThreadIds` 集合；不写服务端、不写本地持久化。
- 医生成功打开并读到该会话消息后清除该标记；读取失败保留。
- 当前会话不显示卡片“新消息”标记，改由消息区处理。
- 当滚动容器距底部在实现阈值内（建议 `≤ 48px`）时，消息更新自动跟随底部。
- 医生正在上翻历史时保持当前位置，显示可聚合计数的“有 N 条新消息”按钮；点击后滚到底部并清零该会话的未查看计数。
- 批量合并消息一次只触发一次自动滚动，避免连跳；医生主动发送后视为回到底部。

### 8.4 权限、安全与数据最小化

1. 医生专用 Consumer 每次连接均重新验证 ticket、Web Session 和有效 `DoctorProfile`；不接受客户端声明的 doctor ID。
2. 事件只送至会话绑定医生；医院管理员、同科医生、其他医院用户和患者本人无法订阅该医生组。
3. 每次 REST 拉取继续执行医生会话权限；权限变更发生在事件之后时，以 REST 结果拒绝读取。
4. WebSocket 仅做变化提示，不携带正文，避免在 Channel Layer、浏览器内存、代理日志中扩散医疗内容。
5. 诊断日志仅记录 `event_id`、`thread_id`、医生 ID、消息 ID、时间戳、耗时、关闭码、错误分类、HTTP 状态与 trace/request ID；禁止记录正文、消息块、病历或患者扩展资料。
6. 会话终结后不再分发新提示；迟到事件不会恢复页面写权限。

### 8.5 性能、可靠性与可观测性

| 项目 | 落地规则 |
| --- | --- |
| 实时目标 | 前台、正常网络、连接可用时，患者提交成功到医生当前会话显示目标 `≤ 3s` |
| 3 秒超时 | 静默重试、保留现有界面、写入诊断；不弹阻塞错误 |
| 事件语义 | 至少一次；允许重复、乱序、短时缺失，前端靠完整 REST 快照和补偿收敛 |
| 断线补偿 | 连接成功、重连、页面可见、网络恢复时刷新列表/计数和当前会话 |
| 故障隔离 | Channel layer 或 WebSocket 故障不影响 `ChatMessage` 主写入；页面仍可手动/补偿读取 |
| 日志关联 | `event_id + thread_id + message_id + trace/request ID` 可串起各阶段 |
| 长会话边界 | 首版完整读取；观察消息数量、响应大小与 p95 耗时，超过目标后另立增量接口工单 |

### 10.2 权限与异常验收
