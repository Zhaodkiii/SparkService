## 1. 稳定模式确认规则

本工单采用一问一答式需求确认，按以下次序循环：

```text
提出 1 个问题
  -> 用户回答
  -> 将确认结论写入本文档
  -> 补齐该结论对应的产品流程
  -> 补齐数据字段、服务端契约、页面状态、异常边界和验收标准
  -> 标记决策编号和日期
  -> 再提出下 1 个问题
```

执行约束：

1. 一次只确认一个产品问题。
2. 用户未回答前，不将建议方案写成“已确认需求”。
3. 每个问题都必须记录“为什么要问”，避免只收集表面 UI 偏好。
4. 每个答案都必须转换为可落地、可测试、可验收的需求。
5. 新结论如与旧文档冲突，必须标明覆盖关系，不保留两个并行事实。
6. 所有开放问题都保留“未确认”状态，不由开发人员自行选择。
7. 在需求确认结束前，不进入业务代码实现。

## 2. 问题陈述

当前医生工作台的信息架构过度以“单条会话”为核心：医生进入工作台后会直接看到某个成员的对话。这不符合医生的实际工作方式：医生需要先确认“这是哪位患者、其基础情况是什么、其有哪些历史咨询”，再进入具体会话处理。

不调整时的主要问题：

- 同一患者的多次咨询被拆散为多条会话，医生难以建立连续认知。
- 基础资料、健康档案、风险和会话内容混在一个页面中，信息层级不清晰。
- 医生容易在没有先看患者资料的情况下直接回复。
- AI 总结、风险评估和患者画像缺少统一展示位置。
- 患者和会话的层级混淆，后续无法稳定增加就诊记录、重点标记、医生备注和随访。

```text
        -> 会话/就诊时间线
```

首屏字段清单：

| 分区 | 必显字段 | 显示规则 |
| --- | --- | --- |
| 患者头部 | 姓名、性别、年龄、患者编号、当前服务状态 | 作为患者身份确认区，页面滚动时仍应可识别当前患者 |
| 基本信息 | 手机号、证件号、地区、职业、婚姻状况 | 手机和证件号默认脱敏；本期不在列表卡片显示 |
| 健康档案 | 身高、体重、BMI、血型、吸烟史、饮酒史 | 数据不完整时逐字段显示“未填写”，不伪造默认健康值 |
| 医疗安全信息 | 过敏史、长期用药、既往病史 | 优先级高于一般人口学信息；有内容时使用明确标题和分条展示 |
| 医生工作信息 | 重点患者标记 | 与 AI 风险等级分开，不使用同一标签或同一字段 |

当前默认字段不包含：完整家庭住址、银行/医保账户资料、患者密码、平台账号权限、原始医疗附件全文和其他成员的资料。

### D-005：患者基础资料对医生完全只读

| 属性 | 确认结论 |
| --- | --- |
| 决策状态 | 已确认 |
| 确认日期 | 2026-09-03 |
| 用户答案 | A：全部只读；医生只能查看，不能修改或补充 |
| 产品结论 | 患者身份、基础资料、健康档案、过敏、用药和既往病史在医生工作台中均为只读投影 |

明确禁止：

- 页面不展示“编辑”、“修改”、“添加”、“纠错”、“保存”等基础资料写入入口。
- 不提供医生备注字段作为基础资料的补充方式。
- 不允许通过浏览器请求、隐藏接口、通用 Member API 或前端状态篡改患者资料。
- 不使用 AI 提取结果自动回写姓名、性别、年龄、过敏、用药或病史。
- 医生在会话中输入的内容只是会话消息，不得因其中包含患者资料而自动修改基础资料。

该结论不禁止医生对“会话”执行接管、回复、重点标记和结束等工作动作；这些属于会话工作状态，不是患者基础资料的编辑。

### D-006：患者资料复用现有模型，由服务端统一聚合

| 属性 | 确认结论 |
| --- | --- |
| 决策状态 | 已确认 |
| 确认日期 | 2026-09-03 |
| 用户答案 | A：复用现有 Member 和健康档案，由服务端统一聚合返回 |
| 产品结论 | 不新建医院专用患者资料表；医生工作台使用服务端生成的只读患者工作台快照 |

落地边界：

- 患者身份继续使用现有 `medical.Member`。
- 身高、体重、BMI、过敏、长期用药、既往病史、症状、手术、健康检查和检查报告等继续复用现有健康档案与医疗记录模型。
- 服务端负责聚合、字段映射、空值处理、脱敏、权限校验和更新时间计算；iOS 与 chat-web 不自行拼接多组底层接口作为最终患者资料。
- 聚合结果只读返回，不能因为医生工作台展示或会话操作而回写 `Member`、健康档案或医疗记录。
- 本期不建立第二套 `Patient`、`HospitalPatientProfile` 或医生工作台专用资料表，避免与现有成员数据形成双向同步和冲突。
- 患者列表、患者详情、会话抽屉和 AI 辅助模块都应引用同一份服务端患者工作台数据语义。

### D-007：患者列表按医生在院内已有服务关系收敛

| 属性 | 确认结论 |
| --- | --- |
| 决策状态 | 已确认 |
| 确认日期 | 2026-09-03 |
| 用户答案 | A：只展示当前医生在本院已有授权会话或服务关系的患者 |
| 产品结论 | 患者列表不是医院全量患者目录，只展示当前医生在当前医院有权服务和查看的患者 |

落地边界：

- 患者列表必须以当前登录医生、当前医院和现有授权会话/服务关系为联合筛选条件。
- 服务端负责判断可见范围；客户端不得通过修改 `member_id`、分页参数或搜索参数扩大患者范围。
- 患者详情聚合接口必须使用与患者列表一致的可见性规则，不能出现“列表看不到但详情可访问”的越权路径。
- 患者脱离医生服务关系、会话授权撤回或医院关系失效后，不再出现在下一次列表刷新结果中。
- 本期不新增“科室全部患者”和“医院全部患者”展示，不建设管理员手动分配患者流程。
- 患者缓存必须绑定医生身份、医院和 `member_id`；可见范围失效时，清理该患者基础资料与会话列表的敏感缓存。

### D-008：患者列表卡片只展示工作摘要

| 属性 | 确认结论 |
| --- | --- |
| 决策状态 | 已确认 |
| 确认日期 | 2026-09-03 |
| 用户答案 | A：姓名/脱敏标识 + 服务状态 + 最近会话时间 + 重点患者标记 |
| 产品结论 | 患者列表卡片只展示定位和工作排序所需的摘要；完整基础资料进入患者工作台后查看 |

列表卡片固定包含：

- 患者展示姓名；涉及重名时补充脱敏患者标识，不展示完整证件号或手机号。
- 当前服务状态，例如 AI 服务中、医生已接管、已结束等；状态名称复用现有会话/服务状态语义。
- 最近会话时间；没有会话时间时显示“暂无会话”，不能使用患者资料更新时间替代。
- 重点患者标记；它是医生工作状态提示，不等同于 AI 风险等级，也不扩大患者可见范围。

明确不在列表卡片展示：完整手机号、完整证件号、过敏史、长期用药、既往病史、报告内容、AI 总结正文和会话消息摘要。上述内容进入患者详情或右侧会话抽屉后按既定模块展示。

### D-009：患者列表按重点标记和最近会话时间排序

| 属性 | 确认结论 |
| --- | --- |
| 决策状态 | 已确认 |
| 确认日期 | 2026-09-03 |
| 用户答案 | A：重点患者优先，再按最近会话时间倒序 |
| 产品结论 | 在已授权患者集合内，重点患者排在普通患者之前；同一组内按最近会话时间从新到旧排列 |

排序规则：

- 第一排序键：`priority_patient=true` 优先。
- 第二排序键：`latest_conversation_at` 倒序。
- 没有会话时间的患者排在有会话时间的患者之后。
- 最近会话时间相同或为空时，使用稳定的 `member_id` 作为最终排序键，避免刷新时卡片跳动。
- 排序只改变已授权患者的展示顺序，不改变患者可见范围。
- 重点标记取消后，患者在下一次列表排序或刷新时回到普通患者分组。

2. 有缓存则立即展示并标记缓存时间；没有缓存则显示各模块加载态。
3. 后台并行请求患者资料、患者会话列表和风险结果。
4. 各请求成功后只替换对应模块，不影响其他模块。
5. 请求失败时保留旧缓存并展示局部失败/重试；无缓存时展示局部空态。
6. AI 总结不随页面进入自动请求，只展示已有结果或“生成总结”入口。

缓存属于加速手段，不代表权限授权；后台刷新和打开详情/会话仍必须由服务端重新校验医生与患者关系。

## 10. 当前开放问题

### Q-005（已回答）：患者列表卡片首屏展示哪些信息？

为什么要问：患者列表是医生进入工作台后的第一层。如果卡片直接展示过多健康和身份信息，会造成隐私暴露和视觉噪声；如果只显示姓名，又无法帮助医生快速定位重点患者和最近服务状态。本题需要与 D-004 的患者详情字段区分，明确“列表摘要”和“详情资料”的边界。

当前实现与偏差：

- 当前 chat-web 侧边栏主要显示成员/会话名称、智能体、科室和时间，尚未形成患者优先的列表卡片。
- 患者工作台已经确认患者为第一层、会话为第二层；列表不应直接退化为成员对话列表。
- 患者基础资料已确认全部只读；列表应只做摘要展示，不增加快捷编辑入口。

请选择：

- **A. 姓名/脱敏标识 + 服务状态 + 最近会话时间 + 重点患者标记（推荐）**  
  只展示定位患者和安排工作的必要摘要，点击后再查看完整基础资料与会话列表。
- **B. 直接展示完整基础资料摘要**  
  在卡片中展示年龄、性别、手机号、过敏和长期用药等，信息完整但隐私暴露和列表负担较大。
- **C. 只展示姓名和最近一条会话摘要**  
  接近现有聊天侧边栏，实现简单，但弱化患者服务状态和重点患者识别。
- **D. 只展示重点患者，普通患者不进入首屏列表**  
  便于处理高优先级患者，但不符合“展示医生可服务患者范围”的完整工作台定位。

已选择 A，具体落地方案详见“10.5 Q-005 已确认落地方案”。

### Q-028（已回答）：患者工作台缓存使用什么存储介质和生命周期？

为什么要问：隔离键解决了“谁的数据”，还需要解决“存在哪里、保存多久”。患者资料和会话内容属于敏感信息，存储方式会影响弱网首屏、设备风险、退出登录清理和系统内存压力。

当前实现与偏差：

- 当前系统已有成员健康数据的内存缓存和请求后写入缓存模式，可作为患者工作台缓存设计参考。
- 患者工作台需要区分患者列表、患者资料、会话列表、AI 总结和风险结果缓存。
- 医生工作台缓存不能只使用 member_id 作为唯一键，也不能无限期保存敏感数据。

请选择：

- **A. 复用当前客户端缓存机制，按 D-030 命名空间保存，并设置模块级过期时间和退出清理（推荐）**  
  兼顾首屏速度、弱网体验和敏感数据治理。
- **B. 只保存在内存中，应用退出后全部清空**  
  隐私边界简单，但无法支持应用重启后的缓存首屏。
- **C. 长期保存在本地，不设置过期时间**  
  首屏快，但权限撤回和旧数据泄露风险高。
- **D. 完全不保存缓存，每次实时请求**  
  一致性直观，但弱网和首屏体验较差。

### Q-003（已回答）：患者基础资料存在多个来源时，首屏以哪个来源为准？

为什么要问：当前系统中患者身份、健康档案和医疗记录分布在不同模型中，而医生工作台将它们聚合成一个患者资料视图。如果不先确定复用方式，将出现前端自行拼接来源、页面字段不一致、数据时效判断分散以及与 Q-002 “只读”相冲突的问题。本问题已通过 D-006 确认。

当前实现与偏差：

- 现有 `medical.Member` 承载患者身份信息。
- 现有 `MemberMedicalProfile` 和症状、用药、手术、检查报告等模型承载健康信息。
- 当前医生工作台还没有统一的患者工作台聚合接口，如果前端自己拼接口，将造成来源和时效判断分散。

已确认设计方向：

- **A. 复用现有 Member 和健康档案，由服务端统一聚合返回**  
  不新建患者资料表；服务端负责按字段定义来源、最后更新时间和显示值，iOS 与 chat-web 只消费统一的 workspace 快照。

### Q-002（已回答）：医生对患者基础资料可以进行哪些操作？

为什么要问：基础资料可能来自患者填写、医院系统或健康档案。医生直接修改会改变原始数据，也会带来数据来源、审计和责任边界问题。

已确认选项：

- **A. 全部只读（已选择）**  
  医生只能查看，不能修改、补充或纠错。
- **B. 原资料只读，可添加医生补充/纠错备注**  
  不覆盖患者原始资料，备注记录医生、时间、内容和来源。
- **C. 允许医生直接修改部分字段**  
  可修改职业、婚姻状况、身高、体重等，身份字段仍只读。
- **D. 允许医生修改全部资料**  
  权限最大，但必须保留完整的前后值和操作审计。

已选择 A 后的落地方案详见“10.2 Q-002 已确认落地方案”。

## 10.3 Q-003 已确认落地方案

### 10.3.1 数据聚合职责

服务端新增或扩展患者工作台聚合读取能力，具体实现应优先落在现有医院医生 API 体系内，不改变底层 `Member`、健康档案和会话模型的既有语义。

服务端聚合流程：

1. 根据登录医生身份确定当前医院和医生工作范围。
2. 校验医生是否可以访问目标患者；不能仅凭路径中的 `member_id` 放行。

6. 合并医生工作状态，例如重点患者标记；工作状态与患者原始资料分开返回。
7. 返回单个只读 `PatientWorkspaceSnapshot`，供患者资料区、患者会话列表和右侧会话抽屉共同使用。

### 10.3.3 数据规则

- 身份字段以 `Member` 为准；健康档案字段以现有健康资料模型为准；服务端负责统一组装，不由客户端决定来源。
- 缺失字段返回明确空值状态，客户端显示“未填写”或“暂无健康档案”，不能填充医学默认值。
- 过敏为空只能表达“暂无已记录过敏”，不能自动推导为“无过敏”。
- 多条用药、病史、报告按服务端返回顺序展示，并保留记录时间或来源时间。
- BMI 可以由服务端按现有身高和体重计算；若输入不完整或单位不明确，返回空值和原因，不在客户端自行猜测。
- 手机号和证件号在服务端即完成脱敏；完整敏感值不应出现在医生工作台响应中。
- 患者资料、AI 总结、风险等级和会话工作状态分区返回，不能把 AI 结果写回患者基础资料。

### 10.3.4 页面状态

- **加载中**：显示患者身份骨架和资料区占位，不先展示其他患者的缓存内容。
- **完整成功**：显示全部可用分区及各自更新时间。
- **部分成功**：已成功的分区正常展示；失败分区显示“加载失败”和局部重试，不影响会话列表和其他分区。
- **无健康档案**：保留健康档案分区，显示“暂无健康档案”。
- **资料过期**：允许查看已返回快照，但标记更新时间和刷新状态；是否允许继续会话由会话接口单独判断。
- **无权访问**：不展示本地旧敏感资料，移除患者详情并返回患者列表。
- **患者不存在或已删除**：显示明确空态，不把错误转换为普通空患者。

### 10.3.5 与客户端的落地边界

- iOS 和 chat-web 都只调用患者工作台聚合接口，不在各端分别请求并拼接 `Member`、健康档案和医疗记录。
- 客户端可以做格式化、折叠、排序和展示状态转换，但不能改变字段值或生成新的患者资料。
- 患者基础资料缓存必须与医生身份、医院、患者 `member_id` 绑定；权限失效时清理对应敏感缓存。
- 右侧会话抽屉使用同一患者上下文，但消息、AI 总结和风险工具仍复用现有对话数据与工具，不与患者资料快照混表。

### 10.3.6 验收标准

1. 选择患者后，详情页通过一次工作台聚合语义获得身份、基础资料和健康/医疗信息。
2. 不新建第二套患者资料表，不要求客户端维护患者资料副本作为事实来源。
3. 医生工作台展示的资料全部只读，任何会话操作不会改变 `Member` 或健康档案。
4. 缺少某个来源数据时只影响对应字段或分区，不导致整个患者工作台失败。
5. 无权访问患者时，服务端不返回敏感资料，客户端不继续展示旧缓存。
6. iOS、chat-web 对同一患者使用一致的字段语义、空值语义和更新时间语义。

## 10.4 Q-004 已确认落地方案

### 10.4.1 患者可见范围

患者工作台的患者集合定义为：

```text
当前登录医生
  ∩ 当前医院
  ∩ 医生已有授权会话或服务关系
  = 患者列表可见范围
```

“已有授权会话或服务关系”优先复用当前医院医生工作台已经存在的会话绑定、医生接管和服务关系数据，不在本期新建一套患者分配关系。具体关系类型由服务端根据现有模型映射，但必须形成稳定的统一判断函数，列表、详情、会话列表和会话消息接口使用同一规则。

### 10.4.2 患者列表接口

建议接口语义：

```text
GET /api/hospital/v1/doctor/patients/
```

请求必须由服务端从登录态取得医生和医院，不接受客户端传入任意 `doctor_id` 或 `hospital_id` 作为越权依据。搜索、分页、状态筛选只作用于已授权患者集合。

列表项建议返回：

```text
PatientListItem
├── member_id
├── display_name
├── masked_patient_identifier
├── service_status
├── latest_conversation_at
├── priority_patient
├── available_conversation_count
└── access_scope
```

列表项只返回患者列表所需的最小摘要；完整患者基础资料仍通过详情聚合接口按需获取，避免一次加载全量敏感信息。

### 10.4.3 详情与会话接口的统一校验

- `GET /doctor/patients/`：只返回当前医生有服务关系的患者。
- `GET /doctor/patients/{member_id}/workspace/`：再次执行同一可见范围校验，不依赖列表接口已经校验过。
- `GET /doctor/patients/{member_id}/conversations/`：只返回该医生有权查看的该患者会话。
- `GET /doctor/conversations/{thread_id}/`：校验线程所属医院、患者和医生服务关系，不能只凭 `thread_id` 返回内容。
- 医生切换医院、医生身份失效、会话授权撤回后，所有接口立即按新身份重新校验。

### 10.4.4 列表更新与缓存清理

1. 首次打开患者工作台，请求当前医生的授权患者列表。
2. 列表缓存可以用于首屏展示，但必须标记缓存时间，并在后台刷新。
3. 刷新结果不再包含某患者时，从患者列表缓存中移除该患者。
4. 同时清理该患者的基础资料、会话列表、AI 总结和风险结果等医生端敏感缓存；不要只移除列表卡片而保留详情缓存。
5. 已打开的患者详情或右侧会话抽屉收到权限失效错误后，立即停止展示敏感内容并退回患者列表。
6. 网络失败时可以继续展示尚未过期的授权列表缓存，但不应把缓存患者扩展为新可见患者；打开缓存患者的详情是否可读由后续接口和权限策略确认。

### 10.4.5 本期明确不做

- 不展示医院全部患者。
- 不展示科室全部患者。
- 不新增管理员手动分配患者页面。
- 不允许客户端通过搜索患者姓名查询未授权患者。
- 不允许通过修改 `member_id`、`thread_id`、分页游标或缓存键访问其他患者。
- 不将“重点患者”理解为额外授权；重点标记只能改变工作排序或视觉提示，不能扩大资料可见范围。

### 10.4.6 验收标准

1. 医生进入工作台后，患者列表只出现当前医院且与当前医生存在授权会话或服务关系的患者。
2. 使用同一医生身份请求一个不在授权范围内的 `member_id`，患者详情、会话列表和会话详情均不能返回患者敏感内容。
3. 搜索和分页不会突破已授权患者集合。
4. 患者服务关系撤回后，下一次刷新不再展示该患者，并清理对应敏感缓存。
5. 重点患者标记只改变展示状态，不改变可见范围。
6. 医院 A 的医生不能通过医院 B 的标识、线程标识或缓存数据访问医院 B 患者。

- 患者姓名缺失时显示“未命名患者 + 脱敏标识”，不能展示数据库主键替代姓名。

### 10.5.4 客户端实现边界

### 10.5.5 验收标准

## 10.6 Q-006 已确认落地方案

### 10.6.1 服务端排序协议

患者列表在完成 D-007 可见范围过滤后，统一由服务端按以下字段排序：

```text
priority_patient DESC
latest_conversation_at DESC NULLS LAST
member_id ASC
```

客户端不得再按本地缓存时间、消息接收时间或卡片插入时间重新排序。这样可以保证 iOS、chat-web、分页请求和后台刷新使用同一顺序。

### 10.6.2 时间字段定义

- `latest_conversation_at` 只表示当前医生可见会话的最新更新时间。
- 没有会话的患者不能使用患者资料更新时间、绑定创建时间或缓存写入时间替代。
- 服务端统一使用带时区的时间值；客户端只负责按本地时区格式化展示。
- 新消息、医生接管、医生回复和会话结束是否更新该时间，必须复用现有会话更新时间语义，不在客户端另造规则。

### 10.6.3 列表刷新、分页与缓存

- 首屏优先展示本地缓存顺序，后台刷新成功后使用服务端新顺序替换列表。
- 分页请求必须携带服务端分页游标或稳定分页参数，不能以客户端当前数组下标作为跨刷新游标。
- 重点标记变化、产生新会话消息或服务状态变化后，下一次刷新重新计算排序。
- 刷新失败时继续展示最近一次已授权列表，但标记数据时间；不因为客户端本地操作擅自调整服务端排序。
- 列表缓存必须包含排序版本或更新时间，避免旧排序与新规则混用。

### 10.6.4 验收标准

1. 已授权患者中，重点患者全部排在普通患者之前。
2. 同一分组内，最近会话时间新的患者排在前面。
3. 没有会话时间的患者排在有会话时间的患者之后。
4. 时间相同或为空时，列表顺序稳定，不因刷新随机变化。
5. iOS 和 chat-web 对同一批患者展示相同顺序。
6. 排序、分页和缓存刷新都不能展示未授权患者。

## 10.7 Q-007 已确认落地方案

### 10.7.1 请求处理顺序

患者列表请求必须按以下顺序处理：

```text
医生身份与当前医院校验
  → 授权会话/服务关系过滤
  → 姓名或脱敏标识搜索

```

任何一步都不能由客户端替代。尤其是搜索接口不能先在医院全量患者上搜索，再在客户端隐藏未授权结果。

### 10.7.2 搜索字段与筛选字段

- `keyword`：匹配患者展示姓名或脱敏患者标识。
- `status=all`：当前医生已授权的全部患者。
- `status=priority`：已授权且被标记为重点患者的患者。
- `status=pending`：已授权且当前服务状态属于待处理的患者。
- `status=ended`：已授权且当前服务状态属于已结束的患者。
- 搜索词应支持前后空格清理和大小写/全半角统一，但不能通过模糊匹配返回未授权患者。
- 服务端返回筛选后的总数时，只统计当前医生已授权集合内的结果。

### 10.7.3 页面状态与交互

- 搜索框 placeholder 使用“搜索患者姓名或标识”，不提示手机号、病史等敏感字段。
- 输入搜索词后由客户端按现有列表搜索节流规则请求服务端；具体节流时间沿用当前项目通用列表约定。
- 切换筛选项时清晰保留搜索词，除非用户主动清空；筛选项变化后重新从第一页加载。
- 搜索和筛选过程中保留当前已显示卡片，避免输入一个字符就出现整页空白；请求成功后整体替换结果。
- 无结果时显示“当前条件下暂无患者”，不显示“医院暂无患者”或其他扩大范围的提示。
- 搜索失败时保留最近一次已授权结果并显示重试状态；权限失效时清除列表缓存。

### 10.7.4 验收标准

1. 搜索只能匹配患者姓名和脱敏标识。
2. 全部、重点患者、待处理、已结束四种筛选均只作用于当前医生已授权患者。
3. 搜索接口不会因输入手机号、证件号或病史关键词而返回敏感匹配结果。
4. 搜索和筛选结果继续按 D-009 规则排序。
5. 无匹配、网络失败和权限失效均有明确页面状态。
6. 客户端无法通过搜索参数、分页参数或缓存数据看到未授权患者。

## 10.9 Q-009 已确认落地方案

### 10.9.1 会话聚合接口

建议接口语义：

```text
GET /api/hospital/v1/doctor/patients/{member_id}/conversations/
```

服务端处理顺序：

1. 校验当前医生和当前医院身份。
2. 校验目标 `member_id` 是否属于 D-007 确认的医生可见患者集合。
3. 查询该患者与当前医生有授权关系的全部院内会话。
4. 保留每个会话的 `thread_id`、智能体标识、服务状态和最近更新时间。
5. 按最近更新时间倒序、`thread_id` 稳定排序键返回。

详情接口和会话消息接口都必须重复校验医生与会话关系，不能因为会话已经出现在患者列表中就取消会话级校验。

### 10.9.2 会话隔离

- 同一患者的不同医生智能体会话分别展示、分别打开、分别加载消息。
- 不合并不同 Thread 的消息，不把不同智能体的 AI 上下文拼接到同一会话。
- 会话列表聚合只改变展示位置，不改变 Thread、ChatMessage、`ClinicalConversationBinding` 的归属。
- 已结束会话可以查看，但是否允许继续发送消息沿用现有会话状态契约，不在患者列表层重新定义。
- 当前医生无权查看的其他医生会话不得因为 `member_id` 相同而出现在列表中。

### 10.9.3 页面行为

- 患者工作台加载完成后显示会话列表，右侧会话抽屉保持关闭。
- 会话列表为空时显示“暂无可查看会话”，不自动创建新会话。
- 点击会话卡片后，将 `member_id`、`thread_id`、医院上下文和医生上下文传入现有对话框架。
- 关闭右侧抽屉后保留当前患者和会话列表；重新点击同一会话可以再次打开。
- 会话列表刷新后，如果当前打开的会话已不在可见范围，关闭抽屉并清理该会话敏感缓存。

### 10.9.4 验收标准

1. 患者会话列表包含当前医生对该患者有权查看的全部院内会话。
2. 会话按最近更新时间倒序，时间相同时顺序稳定。
3. 不同智能体和不同 Thread 不被合并。
4. 其他医生或其他服务范围的会话不会因为患者相同而展示。
5. 点击会话后右侧打开对应会话，关闭后仍停留在患者工作台。
6. 没有会话时不自动创建会话，也不跳转到普通对话。

## 10.12 Q-012 已确认落地方案

### 10.12.1 抽屉内操作

- 医生可以使用现有医生身份发送消息。
- 医生可以接管当前会话。
- 医生可以取消接管当前会话。
- 医生可以结束当前会话。
- 医生可以切换重点患者标记；该标记属于患者工作状态，不修改基础资料。
- 不在抽屉内提供患者基础资料编辑、AI 配置、知识库配置或风险规则配置。

### 10.12.2 接管后的 iOS 行为

| 会话状态 | 患者发送消息 | AI 自动回复 | 医生发送消息 |
| --- | --- | --- | --- |
| AI 服务中 | 正常进入会话 | 允许 | 按现有医生权限 |
| 医生接管中 | 正常进入会话 | 禁止自动回复 | 允许 |
| 已结束 | 按现有结束规则处理 | 禁止新自动回复 | 禁止继续发送，除非现有服务端契约明确允许 |

服务端必须在收到患者消息时重新读取会话接管状态，再决定是否创建 AI 回复任务。客户端不能通过隐藏 AI 消息、停止轮询或本地标志实现“暂停 AI”。

### 10.12.3 状态同步与竞态处理

- 接管和取消接管操作必须返回服务端最新会话状态。
- iOS 发送患者消息前后都可能遇到医生状态变化，最终以服务端接收消息时的状态为准。
- 接管成功后，已在队列中的 AI 任务是否取消由服务端现有任务机制决定；客户端不得假设已经生成或已经取消。
- 取消接管成功后，新的患者消息可以触发 AI；接管期间的历史消息不由客户端重复提交。
- 网络失败时保留原状态，按钮恢复可重试；不能乐观地把 AI 状态切换为暂停或恢复。
- 收到实时事件或重新进入会话时，以服务端状态覆盖本地状态。

### 10.12.4 验收标准

### 10.14.1 输入区状态

| 会话状态 | 输入区提示 | 医生发送 | 患者新消息触发 AI |
| --- | --- | --- | --- |

### 10.14.2 发送流程

1. iOS 打开会话抽屉时读取服务端当前会话状态。
2. 根据状态更新输入区提示和发送按钮。

5. 发送成功后将医生消息追加到现有消息流，并更新会话最近更新时间。
6. 发送失败时保留草稿内容，展示失败原因并允许重试。

输入区的提示只用于帮助医生理解当前状态，不能代替服务端对 AI 是否回复的判断。接管状态下患者消息仍必须进入原会话，不能被 iOS 丢弃或隐藏。

### 10.14.3 状态变化竞态

- 医生打开输入区后，其他端可能改变接管状态；发送时仍以服务端实时状态为准。
- 如果服务端返回“会话已接管/已结束/无权发送”，iOS 立即刷新抽屉状态并保留未发送内容。
- 接管成功但本地网络断开时，恢复连接后以服务端状态覆盖本地状态。
- 医生取消接管后，患者后续消息可以触发 AI；客户端不重放接管期间的旧消息。

### 10.14.4 验收标准

1. 接管中输入区显示“当前由医生回复”，医生可以发送医生身份消息。
2. AI 服务中输入区显示“AI 将自动回复”。
3. 医生消息始终发送到当前会话，不创建额外 Thread。
4. 患者消息在接管中进入会话但不触发 AI。
5. 已结束、无权或状态未知的会话不能发送医生消息。
6. 发送失败或状态冲突时，不丢失医生输入内容。

### 12.2 患者列表流程

1. 客户端从当前登录态获得医生工作台上下文，不允许用户手动伪造医院或医生 ID。
2. 服务端根据当前身份确定医院、职工关系和医生资料。
3. 服务端从现有医生服务关系/会话绑定中生成患者集合。
4. 按 D-010 执行姓名/脱敏标识搜索和状态筛选。
5. 按 D-009 执行重点患者优先、最近会话倒序和稳定键排序。
6. 返回 D-008 规定的最小患者卡片字段。
7. 客户端缓存列表，但每次详情进入仍重新校验权限。

建议接口：


### 12.3 患者工作台加载流程

1. 使用 D-030 的缓存键读取患者资料、会话列表、AI 总结和风险结果。
2. 先显示缓存或模块级加载态。
3. 后台并行请求患者资料、患者会话列表和风险结果。
4. AI 总结只显示已有结果，不自动生成。
5. 每个请求成功后只替换对应模块；失败模块保留旧值并提供重试。

### 12.4 会话抽屉流程

1. 医生点击患者会话列表中的某条会话。
2. 客户端将 hospital_id、doctor_id、member_id、thread_id 和 agent_id 作为上下文传给现有对话框架。
3. 服务端通过医生会话权限再次校验。
4. 读取现有消息流并打开右侧抽屉。
5. 根据会话状态显示 AI 服务中、医生接管中或已结束。
6. 医生执行回复、接管、取消接管、结束或重点标记。
7. 操作成功后刷新会话状态、患者列表摘要和缓存。

### 12.5 接管与 AI 回复流程

~~~text
AI 服务中
  患者发送消息 → 服务端允许 AI 回复

医生接管中
  患者发送消息 → 消息进入原 Thread → 服务端禁止 AI 自动回复
  医生发送消息 → 以真人医生身份写入原 Thread

医生取消接管
  后续患者消息 → 服务端允许 AI 回复

已结束
  历史消息可读 → 输入区禁用
  新建咨询 → 新 Thread + 当前患者 + 当前智能体
~~~

### 12.6 AI 总结与风险评估流程

~~~text
患者工作台进入
  → 展示已有 AI 总结（不自动生成）
  → 医生点击生成/刷新
  → 服务端重新校验当前医生可见资料和会话
  → 复用现有 AI 工具
  → 保存生成版本与输入快照
  → 返回四个分区结果
  → 医生可标记“已了解”

风险评估
  → 独立读取现有风险工具结果
  → 可查看/刷新
  → 人工调整进入现有风险工具独立流程
  → AI 总结不能覆盖风险等级
~~~

4. 验证患者列表不出现未授权患者。
5. 验证医生接管后患者消息不触发 AI。

## 17. 完整验收场景

1. 医生登录后只能看到当前医院和当前医生服务范围内的患者。
2. 患者列表按照重点患者优先、最近会话倒序展示。
3. 搜索只匹配姓名和脱敏标识。
4. 点击患者后默认看到资料和会话列表，不自动打开会话。
5. 患者资料全部只读。
6. 会话列表只显示当前医生有权查看的全部院内会话。
7. 点击会话后右侧打开现有消息流。
8. AI 服务中时输入区提示 AI 将自动回复。
9. 医生接管后输入区提示当前由医生回复，患者消息不触发 AI。
10. 医生取消接管后，后续患者消息恢复 AI 回复。
11. 已结束会话历史可读，输入禁用。
12. 新建咨询创建新 Thread 并绑定当前患者和当前智能体。
13. AI 总结按四个分区展示，医生只能标记已了解。
14. 风险卡片独立展示并复用现有风险工具。
15. 患者资料、会话、总结和风险缓存按医生/医院/患者/模块隔离。
16. 退出登录、身份切换、权限撤回后敏感缓存清理。
