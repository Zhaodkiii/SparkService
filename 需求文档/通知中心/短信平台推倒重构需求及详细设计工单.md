# SparkService 全渠道通知中心——短信渠道专项需求及详细设计工单

> 文档状态：方案评审  
> 工单编号：`NC-SMS-000001`  
> 优先级：P0  
> 更新时间：2026-07-13  
> 适用范围：SparkService、Celery、后台管理系统  
> 建设原则：按全新系统设计和交付；不迁移历史数据、不双写、不兼容旧短信记录，不在本需求中讨论旧系统改造。

## 1. 决策摘要

现有短信能力由 OTP、通知、邀请和后台活动分别调用 Provider，数据散落在 `PhoneOTP`、`NotificationMessage`、业务日志和阿里云响应中，无法形成统一、可信的发送台账。新系统在全渠道通知中心内建立短信渠道能力，所有短信必须经过同一个入口、同一套幂等与限流、同一套发送记录和回执状态机。

| 项目 | 决策 |
| --- | --- |
| 平台边界 | 作为 `notification_center` 内的 SMS Channel Adapter，不建立独立短信领域 |
| 首个供应商 | 阿里云短信 Dysmsapi 2017-05-25 |
| 默认签名 | `梦原鲸苏州科技服务` |
| 已知模板 | `SMS_508370089`，用途及变量上线前确认 |
| 发送入口 | 所有业务统一调用 `NotificationCenter.create_intent` 或发布标准事件 |
| 执行方式 | 业务事务提交后进入 Celery 队列，消费者发送 |
| 权威台账 | `NotificationMessage` + `ChannelDelivery(channel=sms)` + `DeliveryAttempt` + `ProviderEvent` |
| 幂等 | 平台强制幂等，供应商不提供幂等 |
| 状态 | 业务状态、提交状态、送达状态分离 |
| 回执 | 使用 `QuerySendDetails` 主动同步，保留未来回调扩展 |
| 后台 | 深度融入通知中心，共享活动、模板、收件人和统计，短信保留渠道专属能力 |
| 敏感数据 | 手机号加密保存，检索用哈希，展示用掩码；验证码不落短信台账 |
| 历史数据 | 不迁移、不回填、不合并统计；新系统启用日作为数据起点 |

### 1.1 与主文档的模型对齐

| 原短信独立设计概念 | 全渠道通知中心统一概念 | 处理结果 |
| --- | --- | --- |
| SmsApplicationService | NotificationCenter Application API | 删除独立发送入口 |
| SmsTemplate | ChannelTemplateVersion(channel=sms) | 并入统一模板版本 |
| SmsMessage | NotificationMessage + ChannelDelivery(channel=sms) | 拆分逻辑消息与渠道投递 |
| SmsAttempt | DeliveryAttempt | 复用统一供应商调用事实 |
| SmsReceipt | ProviderEvent | 复用统一回执事件模型 |
| SmsAuditLog | NotificationAuditLog | 复用统一审计体系 |
| Sms后台 | 通知中心/发送记录/短信 | 并入统一信息架构 |
| sms Celery队列 | notification.security.high/transactional/bulk/receipt | 按业务优先级共享队列体系 |

短信专项不得重新创建上述平行模型。短信特有信息通过ChannelTemplateVersion配置、ContactEndpoint(channel=sms)、DeliveryAttempt供应商字段和ProviderEvent规范化字段表达。

## 2. 建设背景

### 2.1 当前结构性问题

1. 验证码短信不创建 `NotificationMessage`，后台无法查询。
2. `NotificationMessage` 要求用户必填，无法覆盖注册前、登录前短信。
3. Provider 只返回 RequestId，没有保存 BizId，无法精确查询回执。
4. `sent` 同时被理解为“接口调用成功”和“用户收到短信”，状态语义错误。
5. 不同业务分别决定日志、降级和异常处理，行为不一致。
6. 缺少统一幂等记录，超时与 Celery 重试可能造成重复计费发送。
7. 手机号、验证码和模板参数的脱敏规则不统一。
8. 后台页面只是通用通知记录，不具备短信模板、BizId、回执和费用排障能力。

### 2.2 全新建设边界

本文是[全渠道通知中心重构需求及详细设计工单](./全渠道通知中心重构需求及详细设计工单.md)的短信渠道专项设计。主文档定义通用领域模型、状态机、Outbox、活动、模板、偏好和后台；本文只补充短信业务规则、阿里云协议、号码安全、频控、防盗刷和回执。若两份文档冲突，以主文档为准。

新系统启用后只认全渠道通知中心台账；旧数据不导入、不补齐 BizId、不参与新统计，也不提供新旧混合列表。认证域和其他业务域只保存自身状态及 NotificationIntent/Message ID。

## 3. 建设目标

### 3.1 核心目标

1. OTP、通知、邀请和系统告警需要短信时，全部创建统一 NotificationIntent 并由短信 ChannelDelivery 执行。
2. 每条短信从业务受理、排队、供应商提交到运营商回执全程可追踪。
3. 提交成功不等于送达成功，后台准确展示两个阶段。
4. 任何重试都不产生非预期重复短信。
5. 平台支持多模板、多业务、单发和受控批量发送。
6. 支持按 BizId 调用 `QuerySendDetails` 查询最近 30 天回执。
7. 不保存验证码明文，不在日志和页面展示完整手机号或短信 Content。
8. 供应商可替换，但首期只实现阿里云。

### 3.2 非目标

1. 不允许管理员自由编辑并发送未审核短信正文。
2. 不让客户端直接调用短信供应商。
3. 不在首期实现营销自动化、用户画像触达或跨供应商智能路由。
4. 不通过短信台账承担 OTP 校验；OTP 生成与校验仍属于认证域。
5. 不处理任何启用前短信数据；历史查询和历史统计不属于本系统。

## 4. 业务场景

| 场景 | 业务代码 | 用户是否必需 | 发送方式 | 关键要求 |
| --- | --- | --- | --- | --- |
| 手机登录验证码 | `auth_login_otp` | 否 | 单发 | 高强度限流、验证码不落台账 |
| 绑定手机号验证码 | `auth_bind_phone_otp` | 是 | 单发 | 防账号接管、审计 |
| 后台通知 | `admin_notification` | 是 | 拆分单发 | 活动审批、退订策略 |
| 成员邀请 | `member_invite` | 否 | 单发 | 业务幂等、关联邀请 ID |
| 安全告警 | `security_alert` | 是 | 单发 | 高优先级、禁止静默降级 |

### 5.1 模块目录建议

```text
notification_center/
```

## 6. 核心领域模型

### 6.1 ChannelTemplateVersion

复用主文档的 `NotificationTemplate → NotificationTemplateVersion → ChannelTemplateVersion`。短信只是 `channel=sms` 的渠道版本，不建立短信模板主表。

| 字段 | 说明 |
| --- | --- |
| `template_version_id` | 关联统一业务模板版本 |
| `channel` | 固定 `sms` |
| `provider` | `aliyun` |
| `provider_template_code` | 如 `SMS_508370089` |
| `sign_name` | 如 `梦原鲸苏州科技服务` |
| `sms_category` | `verification/notification/marketing` |
| `variable_mapping` | 业务变量到阿里云变量的显式映射 |
| `content_snapshot_masked` | 审核模板描述，不含可变敏感值 |
| `provider_approved_at` | 阿里云审核确认时间 |
| `config` | 受 schema 约束的渠道扩展配置 |

模板发布、审批、语言和版本生命周期使用通知中心通用能力。签名、模板编码或变量发生变化时创建新的统一模板版本，不原地修改已发布版本。

### 6.2 NotificationMessage

复用主文档的收件人级逻辑消息。它不保存手机号、BizId或短信供应商状态；同一 Message 可以按 parallel/fallback 策略同时拥有 APNs、邮箱和短信 Delivery。

| 通用字段 | 短信场景说明 |
| --- | --- | --- |
| recipient_type/id | 登录前OTP和匿名邀请允许没有User |
| template_version_id | 指向统一业务模板版本 |
| render_context_ciphertext | OTP等变量短期加密，发送或过期后清除 |
| idempotency_key | 收件人级幂等，参与全渠道聚合 |
| status | 由所有ChannelDelivery聚合，不等同短信状态 |
| expires_at | OTP必须设置短有效期 |

### 6.3 ContactEndpoint 与 ChannelDelivery

手机号存入通用 `ContactEndpoint(channel=sms)`：地址密文供发送与回执查询，HMAC供精确检索，掩码供后台展示。登录前OTP可创建短生命周期匿名endpoint；已登录用户关联用户endpoint。

`ChannelDelivery(channel=sms)`保存短信渠道状态：

| 通用字段 | 短信含义 |
| --- | --- |
| provider | `aliyun` |
| route_order/required | 由全渠道路由策略决定 |
| success_threshold | 通常 `provider_delivered`；OTP可按产品定义使用accepted |
| status | PLANNED/QUEUED/SENDING/ACCEPTED/DELIVERED/DELIVERY_FAILED/UNKNOWN等 |
| endpoint_count | 首期固定1 |
| accepted_at/delivered_at | 提交受理与最终送达时间分开 |

### 6.4 DeliveryAttempt

每次SendSms调用创建通用DeliveryAttempt，并保存短信专属规范化字段：Code、脱敏Message、BizId、RequestId、OutId、耗时、outcome和error_category。BizId放在可索引provider_message_id或受约束扩展字段中，RequestId放provider_request_id；二者禁止混用。

禁止覆盖旧Attempt。每次受控重试新增Attempt；`timeout_unknown`不自动新建下一次发送尝试。

### 6.5 ProviderEvent

每次QuerySendDetails结果形成通用ProviderEvent：

| 字段 | 说明 |
| --- | --- |
| `provider/external_event_id` | aliyun + 回执指纹，唯一去重 |
| `attempt_id` | 关联具体DeliveryAttempt |
| `normalized_type` | delivered/delivery_failed/receipt_unknown |
| `provider_code` | ErrCode |
| `provider_status` | SendStatus原值 |
| `occurred_at` | ReceiveDate或供应商事件时间 |
| `payload_fingerprint` | 回执摘要，不保存Content |

不保存 QuerySendDetails 返回的 `Content` 和完整 `PhoneNum`。

### 6.6 NotificationAuditLog

复用通知中心通用审计表，记录短信渠道模板发布、人工查询回执、受控重试、解除抑制和敏感详情访问，不建立短信专属审计表。

## 7. 状态机

### 7.1 SMS ChannelDelivery 状态

```text
CREATED -> QUEUED -> PROCESSING -> SUBMITTED -> DELIVERED
    |         |          |             -> DELIVERY_FAILED
    |         |          -> SUBMIT_FAILED
    |         |          -> SUBMIT_UNKNOWN
    |         -> CANCELLED
    -> EXPIRED
```

### 7.2 状态定义

| 状态 | 含义 |
| --- | --- |
| `CREATED` | 已持久化，尚未入队 |
| `QUEUED` | 已提交任务队列 |
| `PROCESSING` | Worker 已原子抢占 |
| `SUBMITTED` | 阿里云 `Code=OK`，不代表送达 |
| `DELIVERED` | 回执确认送达 |
| `DELIVERY_FAILED` | 运营商回执明确失败 |
| `SUBMIT_FAILED` | 阿里云同步拒绝或本地明确失败 |
| `SUBMIT_UNKNOWN` | 超时等导致是否受理未知 |
| `CANCELLED` | 发送前被授权业务取消 |
| `EXPIRED` | 超过业务有效期，未调用供应商 |

这是主文档通用ChannelDelivery状态机在短信渠道的具体解释。NotificationMessage总状态仍由APNs、短信、邮箱等所有Delivery聚合。状态转换必须通过通知中心领域服务完成，短信Adapter不得直接update Message状态。

## 8. 统一发送接口

### 8.1 内部命令

```python
@dataclass(frozen=True)
class CreateNotificationIntentCommand:
    topic: str
    business_type: str
    business_id: str
    template_key: str
    template_params: dict[str, str]
    recipient: RecipientReference
    routing: RoutingPolicy
    idempotency_key: str
    request_id: str
    scheduled_at: datetime | None = None
    expires_at: datetime | None = None
    priority: int = 50
```

返回：

```python
@dataclass(frozen=True)
class CreateIntentResult:
    intent_id: str
    accepted: bool
    duplicate: bool
    status: str
```

业务层得到的是“平台已接受任务”，不是“短信已发送”。

### 8.2 入队事务

1. 通知中心校验topic、业务模板、变量、收件人、routing和有效期。
2. 创建Intent和Outbox；Outbox Relay保证事务提交后的任务投递。
3. 解析收件人并创建统一NotificationMessage。
4. 路由阶段读取短信偏好、Suppression和ContactEndpoint；需要短信时创建ChannelDelivery(channel=sms)。
5. 短信发送前执行号码校验、限流、防盗刷和费用策略。
6. 入队失败由通用Outbox/repair任务恢复，不建立短信独立补偿机制。

### 8.3 幂等键

```text
HMAC(server_key,
  business_type | business_id | template_key | template_version |
  normalized_phone | semantic_action
)
```

同一幂等键永远返回同一个 message_id。人工重发必须创建带有明确 `resend_sequence` 的新业务动作，并经过权限与审计，不能删除旧键。

## 9. 阿里云 Provider 设计

### 9.1 配置

```dotenv
NOTIFICATION_CENTER_SMS_ENABLED=true
NOTIFICATION_PROVIDER_SMS=aliyun
ALIYUN_SMS_ACCESS_KEY_ID=<secret manager>
ALIYUN_SMS_ACCESS_KEY_SECRET=<secret manager>
ALIYUN_SMS_ENDPOINT=dysmsapi.aliyuncs.com
ALIYUN_SMS_CONNECT_TIMEOUT_SECONDS=3
ALIYUN_SMS_READ_TIMEOUT_SECONDS=5
SMS_PHONE_ENCRYPTION_KEY_ID=<kms-key-id>
SMS_PHONE_HASH_KEY=<secret manager>
```

签名和模板不再以多个随意环境变量散落，由 ChannelTemplateVersion 注册表管理；Secret 仍只从安全配置注入。

### 9.2 SendSms 映射

| 参数 | 来源 | 规则 |
| --- | --- | --- |
| PhoneNumbers | 解密后的规范手机号 | OTP 单号码；首期所有业务单发 |
| SignName | ChannelTemplateVersion | 必须已启用 |
| TemplateCode | ChannelTemplateVersion | 必须已审核确认 |
| TemplateParam | 短期解密变量 | 变量键必须完全匹配；空变量时不传 |
| OutId | ChannelDelivery/DeliveryAttempt 外部流水摘要 | 不包含手机号、用户 ID 等明文 |

读取并分别保存 `Code`、`Message`、`BizId`、`RequestId`。HTTP 200 但 Code 非 OK 仍是提交失败。

### 9.3 超时与重试

1. 超时不低于 1 秒，默认连接 3 秒、读取 5 秒。
2. 参数、权限、签名和模板错误不重试。
3. 明确连接前失败可有限重试。
4. 请求已发出后超时标记 `SUBMIT_UNKNOWN`，不得自动再次发送。
5. 每次重试复用同一ChannelDelivery和OutId，并新增DeliveryAttempt。
6. 任何可能重复计费的人工重试必须二次确认并审计。

### 9.4 RAM 权限

最小权限仅包含：

```text
dysms:SendSms
dysms:QuerySendDetails
```

资源范围按阿里云接口模型为 `*`。发送与查询调用均设置远低于官方 5000 QPS 的应用级限流。

## 10. 回执同步

### 10.1 QuerySendDetails 请求

1. PhoneNumber 来自 `ContactEndpoint(channel=sms)` 解密值，只允许一个号码。
2. BizId 来自成功 DeliveryAttempt，只允许一个值。
3. SendDate 使用原提交时间的 `yyyyMMdd`。
4. 只查询最近 30 天。
5. PageSize 1–50，精确 BizId 查询默认 20、CurrentPage=1。

### 10.2 响应处理

1. Query RequestId 单独保存，不覆盖 SendSms RequestId。
2. 校验 PhoneNum、TemplateCode、OutId 和时间窗口与本地记录一致。
3. `ErrCode=DELIVERED` 且状态一致时更新为 DELIVERED。
4. 其他状态按阿里云完整映射表转换；未知值保存原值并保持 UNKNOWN。
5. Content 不落库、不写日志。
6. TotalCount 是提交维度数量，不作为计费条数。

### 10.3 调度策略

首次查询延迟执行，未完成时按 1、5、15、30 分钟递增，随后降低频率。终态停止查询；超过 30 天标记回执过期。查询失败绝不触发重新发送。

## 11. OTP 接入标准

1. 认证域生成随机验证码并只保存哈希。
2. 调用通知中心时传入验证码变量；平台仅在任务执行所需的短窗口内加密保存。
3. 任务完成或过期后清除 `parameter_ciphertext`，仅保留变量键。
4. NotificationIntent.business_id 使用 otp_id，NotificationMessage 和 Delivery 均不保存验证码。
5. OTP 短信设置 expires_at；Worker 取到过期消息直接标记 EXPIRED。
6. 白名单固定验证码不调用供应商，但创建 `SKIPPED_TEST` 台账，后台明确显示未真实发送。
7. 生产环境配置缺失或发送失败不得返回伪成功。

## 12. 限流与防盗刷

### 12.1 OTP 限流维度

按手机号、IP、设备、账号和业务类型分别设置秒、分钟、小时和日配额。认证域先做请求级限流，通知中心在创建短信ChannelDelivery和实际SendSms前再次限流；命中后返回429且不调用供应商。

### 12.2 后台通知限流

后台群发必须具有统一Campaign审批、AudienceSnapshot、目标人数预览、批次上限、发送窗口和取消能力。首期每个收件人建立NotificationMessage并创建单号码短信Delivery，不直接使用最多1000号码的SendSms群发，以保证全渠道聚合、单用户回执、幂等和费用核算。

### 12.3 平台保护

1. 全局发送 QPS、供应商 QPS、模板 QPS 独立限制。
2. OTP 与普通通知使用不同 Celery 队列，避免通知挤占验证码。
3. 费用或失败率异常时自动熔断普通通知，安全类短信单独决策。
4. 禁止以提高阿里云配额代替业务防盗刷。

## 13. 通知中心融合设计

短信不是独立于通知中心的孤立后台，而是通知中心中的标准渠道。通知中心负责“给谁、何时、为什么发送”，短信域负责“如何安全提交、是否送达、供应商发生了什么”。

### 13.1 统一信息架构

```text
通知中心
  总览
    全渠道发送趋势
    APNs / 邮箱 / 短信渠道健康度
    待处理异常
  通知任务
    新建通知
    任务列表
    任务详情与各渠道结果
  收件人
    用户与可用渠道
    短信触达资格
  模板中心
    业务模板
    渠道版本
      APNs 模板
      邮件模板
      短信模板
  发送记录
    全渠道记录
    APNs
    短信
    邮箱
  统计分析
    全渠道统计
    短信提交与送达
    模板与业务统计
  渠道设置
    APNs
    阿里云短信
    邮箱
```

通知中心的活动、模板、收件人、NotificationMessage、DeliveryAttempt和ProviderEvent都是共享能力；短信只提供 `ChannelDelivery(channel=sms)` 的Adapter、策略和渠道扩展字段。全渠道页面展示统一摘要，进入短信详情后展示BizId和运营商回执等短信专属信息。

### 13.2 通知任务融合

一次通知任务可以选择 APNs、短信和邮箱中的一个或多个渠道，并明确渠道策略：

| 策略 | 行为 |
| --- | --- |
| `parallel` | 所选渠道同时发送，各自记录结果 |
| `fallback` | 按 APNs → 邮箱 → 短信顺序兜底，前一渠道成功后停止 |
| `required_channels` | 指定渠道必须执行，不因其他渠道成功跳过 |

通知任务保存业务目的和受众定义，统一受众物化按收件人创建NotificationMessage；路由器再为需要短信的Message创建ChannelDelivery。Campaign和Message状态从所有渠道聚合，但不能覆盖短信Delivery自身的提交与送达事实。

全渠道聚合状态建议：

```text
DRAFT / SCHEDULED / RUNNING / COMPLETED / PARTIAL / FAILED / CANCELLED
```

“COMPLETED”表示任务执行完成，不等于每条短信已送达。任务详情必须分别展示“短信已受理数量”和“短信已送达数量”。

### 13.3 模板中心融合

统一业务模板描述通知目的，一个业务模板可以配置多个渠道版本：

```text
业务模板：登录验证码
  APNs：不适用
  Email：login_otp_email_v1
  SMS：auth_login_otp_v1 -> SMS_xxx
```

短信渠道版本必须配置签名、阿里云模板编码、模板类型、变量白名单、版本和启用状态。短信正文由阿里云审核模板决定，后台不提供自由正文编辑器。

模板发布流程：草稿 → 待审核确认 → 已启用 → 已停用。启用短信模板前必须验证签名、模板编码和变量；修改变量或供应商模板编码必须创建新版本。

### 13.4 收件人与渠道资格

通知中心收件人列表统一展示 APNs、短信、邮箱可用性。短信资格至少包括：

1. 是否存在有效手机号。
2. 手机号是否通过业务要求的验证。
3. 是否允许对应类型短信。
4. 是否命中退订、黑名单或风险限制。
5. 是否处于本地/供应商频控窗口。

“有手机号”不等于“可发送短信”。创建通知任务时必须预估目标人数、各渠道可达人数、短信预计条数和可能费用。

### 13.5 通知中心总览

总览展示：

1. 今日通知任务、目标人数和各渠道发送量。
2. 短信已提交、已受理、已送达、送达失败和状态未知数量。
3. 短信接受率、送达率、P95 提交延迟和回执延迟。
4. OTP 与普通通知队列积压。
5. 模板错误、权限错误、频控、费用和发送量异常。

全渠道统计与短信统计口径必须明确：任务数、提交次数、运营商送达数和计费估算不能混为一个指标。

### 13.6 短信发送记录列表

标准字段：

| 字段 | 说明 |
| --- | --- |
| 消息 ID | NotificationMessage ID |
| 业务类型 | 验证码、通知、邀请、安全告警 |
| 用户 | 可为空，显示“登录前用户” |
| 手机号 | 始终掩码 |
| 模板 | 内部模板名和阿里云模板编码 |
| 总状态 | 排队中、处理中、已受理、已送达、失败、未知、过期 |
| 提交状态 | 单独显示供应商提交结果 |
| 送达状态 | 单独显示运营商回执 |
| Code/ErrCode | 阿里云结果摘要 |
| BizId | 受权限控制的复制 |
| 创建/提交/回执时间 | 三个阶段时间 |
| 操作 | 详情、查询回执、受控重试 |

支持按手机号精确搜索、用户、业务类型、模板、状态、BizId、RequestId 和时间范围筛选。手机号查询由服务端计算 HMAC，不允许明文模糊匹配。

### 13.7 短信详情

展示业务信息、模板信息、状态时间线、每次 DeliveryAttempt、最新 ProviderEvent 和审计记录。不展示验证码、完整手机号、TemplateParam、短信 Content、设备 ID、IP 或云密钥。

### 13.8 主动查询回执

```http
POST /api/admin/v1/notification-center/deliveries/sms/{delivery_id}/query-receipt/
```

服务端从台账读取手机号、BizId 和发送日期；前端不传供应商查询参数。接口具有独立 RBAC、30 秒防重复、分布式锁、审计和最近 30 天校验。

### 13.9 通知中心 API

```text
GET  /api/admin/v1/notification-center/deliveries/sms/
GET  /api/admin/v1/notification-center/deliveries/sms/{id}/
POST /api/admin/v1/notification-center/deliveries/sms/{id}/query-receipt/
POST /api/admin/v1/notification-center/deliveries/sms/{id}/resend/
GET  /api/admin/v1/notification-center/channel-templates/sms/
POST /api/admin/v1/notification-center/channel-templates/sms/{id}/activate/
POST /api/admin/v1/notification-center/channel-templates/sms/{id}/deactivate/
GET  /api/admin/v1/notification-center/statistics/sms/
```

所有写操作和敏感读取必须写 NotificationAuditLog。

通知任务和模板中心另外使用统一通知中心资源：

```text
GET/POST /api/admin/v1/notification-center/campaigns/
GET      /api/admin/v1/notification-center/campaigns/{id}/
GET/POST /api/admin/v1/notification-center/templates/
GET      /api/admin/v1/notification-center/recipients/
GET      /api/admin/v1/notification-center/overview/
```

统一通知 API 返回各渠道聚合摘要；短信专属 API 返回提交尝试、BizId 和回执详情，避免把所有渠道字段塞进一个通用 JSON。

### 13.10 RBAC 权限

| 权限 | 能力 |
| --- | --- |
| `notification:view` | 查看通知中心总览和普通记录 |
| `notification:campaign:create` | 创建通知任务 |
| `notification:campaign:approve` | 审批批量通知 |
| `notification:sms:view` | 查看短信台账与掩码号码 |
| `notification:sms:query_receipt` | 主动查询运营商回执 |
| `notification:sms:resend` | 受控重发 |
| `notification:sms:template_manage` | 管理短信模板版本与启停 |
| `notification:sms:sensitive_access` | 经审批访问必要敏感信息 |

创建、审批、发送不得默认由同一低权限角色全部完成。批量短信和人工重发需要更高权限与完整审计。

## 14. 安全与隐私

1. 手机号使用应用层加密保存，密钥版本可轮换。
2. 精确检索使用 HMAC，不使用普通 SHA-256 防止号码枚举。
3. 日志只记录 message_id、掩码号码、状态、Code、BizId/RequestId 摘要。
4. 验证码、TemplateParam 和 Content 禁止进入日志、审计和普通数据库字段。
5. 参数密文设置最短保留期，发送完成或过期立即清除。
6. 后台完整号码原则上不可见；确需查看采用单独权限、二次确认和审计。
7. 阿里云凭证使用独立 RAM 身份和 Secret Manager，定期轮换。
8. 管理接口执行 CSRF、防重放、RBAC 和操作审计。

## 15. 可观测性与告警

指标至少包括：

1. 创建、排队、处理和提交数量。
2. 阿里云接受率、运营商送达率和回执失败率。
3. P50/P95/P99 提交延迟和端到端送达延迟。
4. 按业务、模板和错误码聚合的失败数。
5. SUBMIT_UNKNOWN、回执过期和队列积压数。
6. 幂等命中数、限流数和防盗刷拦截数。
7. 当日发送量和费用估算。

配置缺失、接受率或送达率突降、验证码队列积压、未知状态增长、发送量或费用异常必须告警。

## 17. 全新系统启用方案

本项目不执行历史数据迁移、不影子双写、不提供旧记录兼容查询。新系统以明确的启用时间为数据边界：启用后的短信全部进入新平台，启用前的数据不进入新后台、不参与统计。

### 17.1 建设顺序

1. 创建 `notification_center` App、领域模型、模板注册表和安全基础设施。
2. 实现统一发送服务、状态机、幂等和队列。
3. 实现阿里云 SendSms 与 QuerySendDetails Adapter。
4. 实现通知中心的任务、模板、收件人和短信记录 API。
5. 实现通知中心页面、RBAC、审计、统计和告警。
6. 接入 OTP、通知、邀请和安全告警业务。
7. 完成真实短信联调、容量测试、安全测试和故障演练。
8. 在约定启用时间一次性开放新系统。

### 17.2 数据起点

1. `SMS_PLATFORM_LAUNCHED_AT` 记录新系统正式启用时间。
2. 后台默认只查询新系统 NotificationMessage，不展示历史占位行。
3. 统计报表明确标注“数据自启用时间起”。
4. 不从旧 PhoneOTP、NotificationMessage 或日志推断历史发送与送达结果。
5. 新系统内禁止出现指向旧短信记录的兼容字段。

### 17.3 启用前检查

1. 所有业务代码通过架构检查确认只调用 NotificationCenter。
2. 签名、模板和变量在阿里云控制台审核通过。
3. RAM、密钥、队列、Worker、Redis、数据库和告警配置就绪。
4. 通知中心能够完整展示新短信的提交和送达状态。
5. OTP 超时、供应商限流、网络超时、重复任务和回执延迟演练通过。
6. 平台总开关与分业务开关均经过验证。

### 17.4 回滚原则

启用后的回滚只暂停新发送或关闭具体业务，不切回任何旧短信实现。已生成的 NotificationMessage、DeliveryAttempt 和 ProviderEvent 永久保留，恢复后根据原状态继续处理；SUBMIT_UNKNOWN 不得自动重发。

## 18. 测试策略

### 18.1 单元测试

覆盖模板变量、手机号规范化、HMAC、加解密、幂等、状态机、过期、限流、错误映射、Content 丢弃和敏感日志检查。

### 18.2 集成测试

1. Mock SendSms 的 OK、非 OK、异常和超时。
2. 验证 BizId 与 RequestId 分开保存。
3. Mock QuerySendDetails 的已送达、失败、未就绪和未知状态。
4. 验证号码、模板、OutId 不匹配时不更新状态。
5. 验证重复 Celery 任务不会重复发送。
6. 验证事务回滚不会留下可执行孤儿任务。

### 18.3 真实联调

在阿里云测试号码环境发送，保存 message_id、BizId、Send RequestId、Query RequestId 和最终回执作为证据。不得在自动化测试中真实发送。

### 18.4 安全测试

检查数据库、日志、Celery 参数、Sentry、后台 API 和页面源代码中不存在验证码、完整手机号、AccessKey Secret 和短信 Content。

## 19. 发布与回滚

每个业务使用独立Feature Flag。回滚只暂停对应topic或短信渠道，不删除统一NotificationMessage、DeliveryAttempt或ProviderEvent。已提交短信不得因回滚再次发送；UNKNOWN必须人工或回执确认后处理。

上线顺序：创建新数据库结构 → Worker → 管理 API → 通知中心页面 → 业务入口启用。回滚顺序相反，但保留回执同步能力处理已经提交的消息。

## 23. 工程技术设计细化

### 23.1 共享模型中的短信字段落位

短信不建平行主表，但需要在主文档共享模型中明确字段落位：

| 共享模型 | 通用字段 | 短信用途 |
| --- | --- | --- |
| ContactEndpoint | address_ciphertext/address_hash/address_masked | 加密手机号、HMAC检索、掩码展示 |
| ContactEndpoint | scope | `region_code + sms_provider_scope` |
| ChannelTemplateVersion | provider/provider_template_id/config | aliyun、SMS模板编码、签名和变量映射 |
| ChannelDelivery | provider/status/accepted_at/delivered_at | 短信提交与送达主状态 |
| DeliveryAttempt | provider_message_id | 保存BizId |
| DeliveryAttempt | provider_request_id | 保存SendSms RequestId |
| DeliveryAttempt | provider_code/provider_message | Code和脱敏Message |
| DeliveryAttempt | external_reference | OutId |
| ProviderEvent | external_event_id/provider_code/provider_status | 回执指纹、ErrCode和SendStatus |
| ProviderEvent | occurred_at/received_at | 运营商回执时间和系统接收时间 |

必须为以下组合建立索引或唯一约束：

```text
ContactEndpoint(channel, address_hash, scope) UNIQUE
ChannelDelivery(message_id, channel, route_order) UNIQUE
DeliveryAttempt(delivery_endpoint_id, attempt_no) UNIQUE
DeliveryAttempt(provider, provider_message_id) INDEX
DeliveryAttempt(provider, provider_request_id) INDEX
ProviderEvent(provider, external_event_id) UNIQUE
ChannelDelivery(channel, status, created_at, id) INDEX
```

### 23.2 ChannelTemplateVersion短信配置Schema

```json
{
  "provider": "aliyun",
  "provider_template_code": "SMS_508370089",
  "sign_name": "梦原鲸苏州科技服务",
  "sms_category": "notification",
  "variable_mapping": {},
  "supports_empty_template_param": true,
  "region_policy": ["CN"],
  "max_variable_length": {
    "code": 6
  },
  "receipt_policy": {
    "enabled": true,
    "query_window_days": 30
  }
}
```

发布校验：

1. provider固定为已注册Adapter。
2. 签名和模板编码非空且已由人工确认审核状态。
3. variable_mapping的目标键集合与阿里云模板变量完全一致。
4. 验证码模板必须分类为verification，不能被后台普通活动选择。
5. notification/marketing模板不能被OTP topic引用。
6. 无变量模板发送时省略TemplateParam，不发送空字符串或空JSON。
7. 已发布版本不可修改config，只能创建新版本。

### 23.3 手机号规范化

内部统一使用E.164：

```text
输入 13800138000       -> +8613800138000
输入 8613800138000     -> +8613800138000
输入 +8613800138000    -> +8613800138000
输入 852XXXXXXXX       -> +852XXXXXXXX
```

处理顺序：去除允许的空格和分隔符 → 解析显式国家码 → 缺省国家码按业务配置补齐 → 使用号码库校验长度和区域 → 输出E.164。不能只依赖字符串长度或正则判断所有国家号码。

阿里云参数转换：国内号码按Adapter明确规则转换为其接受格式；QuerySendDetails国内号码使用11位号码，国际/港澳台保留国际区号。转换逻辑只存在于Aliyun Adapter。

### 23.4 手机号加密与检索

建议使用信封加密：

```text
address_ciphertext = version | key_id | nonce | ciphertext | tag
address_hash = HMAC-SHA256(search_key, canonical_e164)
address_masked = region-aware mask(canonical_e164)
```

1. 加密使用AEAD算法，每行随机nonce。
2. HMAC密钥与加密密钥分离，禁止普通SHA-256防止号码字典枚举。
3. key_id支持密钥轮换；读取旧密钥、写入当前密钥。
4. 后台按完整号码精确搜索时，服务端规范化并计算HMAC。
5. 禁止前缀/后缀模糊搜索完整号码；运营查询使用掩码显示。
6. 解密仅允许发送Worker、回执查询Worker和经审批的安全用例。

### 23.7 SendSms构造算法

```text
1. 校验ChannelTemplateVersion仍为PUBLISHED
2. 解密ContactEndpoint并转换供应商号码格式
3. 解密短期渲染变量
4. 校验变量键集合与模板schema完全相等
5. 生成稳定OutId
6. 创建DeliveryAttempt(outcome=pending)
7. 构造SendSmsRequest
8. 调用send_sms_with_options
9. 读取HTTP状态、Code、Message、BizId、RequestId
10. 事务更新Attempt和ChannelDelivery
11. 清除不再需要的敏感渲染参数
12. 调度回执查询
```

### 23.8 OutId和幂等

OutId不包含手机号、用户ID或业务明文：

```text
out_id = "nc_" + base32(HMAC(out_id_key, delivery_id | attempt_semantic_id))[:32]
```

平台幂等层级：

| 层级 | 唯一键 |
| --- | --- |
| Intent | event_id / intent idempotency_key |
| Message | intent + recipient |
| Delivery | message + channel + route_order |
| Attempt | delivery_endpoint + attempt_no |
| ProviderEvent | provider + external_event_id |

阿里云不保证幂等，数据库幂等只能阻止本系统正常重复执行。请求发出后超时仍可能已被受理，因此timeout_unknown禁止自动创建新Attempt。

### 23.9 Delivery并发抢占

发送Worker使用条件更新：

```text
UPDATE notification_delivery
SET status='SENDING', lease_owner=?, lease_expires_at=?
WHERE id=?
  AND channel='sms'
  AND status IN ('QUEUED','WAITING_RETRY')
  AND (lease_expires_at IS NULL OR lease_expires_at < now)
```

受影响行数为1才允许调用Provider。仅使用Redis锁不够，数据库状态与唯一约束必须是最终防线。

### 23.11 QuerySendDetails任务

任务参数只传delivery_id：

```python
@shared_task(bind=True, queue="notification.receipt")
def sync_sms_delivery_receipt(self, delivery_id: str):
    ReceiptApplicationService.sync_sms(delivery_id=delivery_id)
```

Application Service执行：

1. 锁定并读取Delivery、accepted Attempt和ContactEndpoint。
2. 校验BizId非空、发送日期未超过30天、状态仍需查询。
3. 解密手机号并调用QuerySendDetails。
4. 校验PhoneNum、TemplateCode、OutId和时间窗口。
5. 创建幂等ProviderEvent。
6. 由通用事件归一化器更新ChannelDelivery。
7. 记录查询RequestId，不覆盖SendSms RequestId。
8. 丢弃Content和完整PhoneNum。

### 23.12 回执查询节奏

建议首次查询在提交后1分钟，未终态时按5、15、30分钟、2小时、6小时递增；之后每日低频查询直到终态或30天窗口结束。具体节奏配置化，并加入随机抖动防止批量活动产生查询尖峰。

主动查询接口30秒内返回缓存结果；同一Delivery使用分布式锁和数据库lease，避免后台点击与定时任务并发调用。

### 23.13 Redis限流键

```text
nc:sms:otp:phone:{phone_hmac}:minute
```

### 23.14 建议初始限流口径

具体数值需产品与安全确认，首期可按以下保守基线配置：

| 维度 | OTP建议 | 普通通知建议 |
| --- | --- | --- |
| 同号码 | 60秒1次、小时5次、日10次 | 同模板按业务频控 |
| 同IP | 分钟10次、小时50次 | 后台活动不使用公网IP维度 |
| 同设备 | 分钟5次、小时20次 | 不适用 |
| 同模板 | 独立QPS | 独立QPS及日预算 |
| 全局 | 远低于供应商5000 QPS | 按Worker容量和费用预算 |

不能把这些建议硬编码在Service常量中，应进入版本化策略配置并记录变更审计。

### 23.15 OTP敏感数据生命周期

```text
OTP生成
  -> 认证域保存code_hash
  -> 通知中心短期加密variables.code
  -> 发送Worker内存解密并调用Adapter
  -> Provider调用完成或消息过期
  -> 物理清除render_context_ciphertext中的code
```

Celery参数、结构化日志、Sentry、NotificationAuditLog、后台API和ProviderEvent中均不得出现code。

### 23.16 短信模板与业务Topic约束

| Topic类别 | 允许短信模板类别 | 用户偏好 |
| --- | --- | --- |
| security OTP | verification | 不按营销退订处理，但受防盗刷限制 |
| transactional | notification | 按必要性政策和渠道偏好 |
| reminder | notification | 尊重静默时段和用户偏好 |
| campaign | notification/marketing | 必须同意、退订和审批 |

路由器在创建Delivery前校验Topic与模板类别，Adapter不负责业务分类。

### 23.17 群发决策

虽然SendSms支持最多1000个相同参数号码，首期仍坚持单号码Delivery和单号码Provider请求，原因：

1. NotificationMessage是收件人级事实，需要独立状态。
2. QuerySendDetails只支持单号码详情。
3. 单号码便于偏好、抑制、取消、幂等和费用归属。
4. OTP官方也建议单发。

未来容量确有需要时，可以在Adapter内部合并兼容的Delivery形成临时批次，但不能改变上层数据模型；批次必须能把BizId/回执重新映射回每个Delivery。

### 23.18 错误映射

| 供应商/本地场景 | error_category | Delivery处理 |
| --- | --- | --- |
| Code=OK | accepted | ACCEPTED并保存BizId |
| 模板变量错误 | validation | SUBMIT_FAILED，不重试 |
| 签名/模板未审核 | authorization/configuration | 熔断模板或渠道 |
| RAM权限错误 | authorization | 渠道熔断并告警 |
| 供应商频控 | rate_limit | WAITING_RETRY |
| 明确连接前失败 | transient_before_submit | 有限重试 |
| 请求后读取超时 | timeout_unknown | UNKNOWN，不自动重发 |
| ErrCode=DELIVERED | delivered | DELIVERED |
| 明确运营商失败 | delivery_failed | DELIVERY_FAILED |
| 未知ErrCode/SendStatus | receipt_unknown | 保留原值并告警 |

原始Message只能脱敏截断后保存，不能原样返回客户端。

### 23.23 数据保留

1. OTP变量密文：发送或过期后立即清除。
2. endpoint手机号密文：endpoint有效期间保留，注销后按主文档匿名化政策处理。
3. Delivery/Attempt/ProviderEvent：遵循主文档统一保留期。
4. QuerySendDetails Content：永不落库。
5. 聚合统计：不含完整手机号和可逆标识。
