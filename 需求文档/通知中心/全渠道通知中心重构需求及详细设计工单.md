# SparkService 全渠道通知中心重构需求及详细设计工单

> 文档状态：方案评审  
> 工单编号：`NOTIFICATION-CENTER-000001`  
> 优先级：P0  
> 更新时间：2026-07-13  
> 建设方式：全新建设，不迁移历史数据，不兼容旧通知记录  
> 首期渠道：APNs、短信、邮箱  
> 扩展目标：Android/FCM、站内信、Web Push、微信及其他供应商可通过适配器接入

## 1. 决策摘要

建设一个完整、通用、可扩展的通知中心，将系统通知、验证码、医疗业务提醒、成员邀请和后台运营活动统一纳入同一套通知意图、受众、模板、偏好、渠道路由、投递、回执、审计和统计模型。

| 决策项 | 结论 |
| --- | --- |
| 系统形态 | Django 模块化单体 + Celery 异步 Worker |
| 一致性 | 业务事务 + Transactional Outbox，至少一次任务投递，业务幂等消除重复副作用 |
| 核心模型 | 通知意图 → 收件人消息 → 渠道投递 → 发送尝试 → 供应商事件 |
| 渠道扩展 | Ports & Adapters；核心域不依赖 APNs、阿里云或邮件 SDK |
| 模板 | 业务模板与渠道模板分离，模板不可变版本化 |
| 受众 | 查询条件与不可变受众快照分离，不把大量用户 ID 存在 Campaign JSON 中 |
| 偏好 | 事务性、安全性、运营性通知分级；按主题和渠道管理同意、退订和抑制 |
| 状态 | 活动、消息、投递、尝试和回执各自拥有状态机，不使用一个 `sent` 表示全部语义 |
| 敏感数据 | 接收地址加密、HMAC 精确检索、页面掩码；验证码和敏感模板参数不落普通日志 |
| 后台 | 通知用户列表、通知模板、发送活动、APNs/短信/邮箱记录融为一个通知中心 |
| 历史数据 | 不迁移、不回填、不参与新统计；新系统启用时间为数据起点 |

## 2. 当前系统审计与不足

### 2.1 当前实现概况

现有系统在 `accounts` 内定义 `NotificationTemplate`、`NotificationCampaign` 和 `NotificationMessage`，由 `NotificationService` 同时完成用户筛选、模板渲染、任务编排和三个渠道的 Provider 调用。后台分别复用同一个 `NotificationLogsView` 展示 APNs、短信和邮箱记录。

当前业务调用包括：

1. 后台面向用户发送 APNs、短信和邮箱通知。
2. 手机和邮箱 OTP 直接调用各自 Provider。
3. 成员邀请按 APNs → 邮件 → 短信兜底，部分匿名联系人又直接调用 Provider。
4. 健康资源与用药计划变化发送 APNs。
5. 后台部分医疗操作直接同步调用 `NotificationService.send_to_user_sync`。

### 2.2 结构性不足

| 问题 | 当前表现 | 后果 |
| --- | --- | --- |
| 领域混杂 | 模型和服务位于 accounts | 通知规则被账号域绑架，其他业务只能跨层调用 |
| Provider 可绕过 | OTP、匿名邀请直接调用 Provider | 台账缺失、策略不一致、后台查不到 |
| 模板模型过于通用 | 所有渠道共用 title/body/payload | 无法表达 APNs headers、邮件 HTML/主题、短信模板编码 |
| 模板不版本化 | 修改记录直接影响当前模板 | 无法重现历史发送内容和审批版本 |
| 活动受众存 JSON | `target_user_ids` 全量保存 | 大受众扩展差、缺少快照状态与逐人原因 |
| 同步遍历 | Campaign Worker 循环用户和渠道 | 单任务过大、失败隔离差、无法独立扩容 |
| 状态语义错误 | `sent/failed/partial/skipped` | APNs 接受、邮件投递、短信受理和最终送达无法区分 |
| 记录过度聚合 | APNs 多设备放 JSON，短信/邮件单字段 | 不可索引、不可分页、难以重试单个 endpoint |
| 缺少偏好与抑制 | 仅判断有没有手机号/邮箱/token | 无法处理退订、投诉、硬退信、无效设备 token |
| 缺少可靠事件 | 事务提交与 Celery 入队非原子 | 可能数据库成功但通知任务丢失 |
| 缺少标准回执 | 没有统一 ProviderEvent | 无法处理邮件退信、短信回执、APNs token 失效 |
| 敏感字段边界弱 | body/payload/delivery_details 任意存储展示 | 验证码、手机号和业务敏感数据可能泄漏 |
| 后台通用化过度 | 三个渠道复用同一张表和详情 | 字段不匹配，无法专业排障 |

### 2.3 需要保留的业务能力

全新系统仍须支持：

1. 通知用户列表与各渠道可达性判断。
2. 通知模板、预览、启停和渠道默认设置。
3. 单用户、用户集合和筛选受众活动。
4. 立即发送与定时发送。
5. APNs、短信、邮箱独立记录与详情。
6. OTP、成员邀请、健康资源变化、用药计划和后台运营活动。
7. APNs → 邮件 → 短信等业务兜底策略。

## 3. 行业标准与设计依据

### 3.1 通用事件契约

内部领域事件采用 CloudEvents 风格元数据：`id`、`source`、`type`、`subject`、`time`、`datacontenttype`、`data`、`trace_id`。这样能统一不同业务发布通知意图的格式，并为未来消息总线、审计和跨服务演进保留稳定契约。

### 3.2 APNs

1. 设备 token 与具体 App/topic 绑定，不能跨 App 使用。
2. 每次请求记录 `apns-id`、HTTP 状态和 reason。
3. `BadDeviceToken`、`Unregistered`、`DeviceTokenNotForTopic` 等不可重试错误使 endpoint 失效。
4. 5xx 可退避重试，429 按限流策略延迟；4xx 先修复请求，禁止盲目重试。
5. APNs 200 表示 Apple 接受请求，不证明用户看到或点击通知；打开、点击需由客户端埋点事件补全。

### 3.3 邮件

1. 必须配置 SPF、DKIM、DMARC，并持续监控发件域信誉。
2. 区分供应商接受、投递、软退信、硬退信、投诉、打开和点击。
3. 硬退信与投诉进入抑制名单，禁止持续重试损害信誉。
4. 运营/订阅类邮件支持 RFC 8058 一键退订；事务性安全邮件不提供误导性退订。
5. HTML 与纯文本版本同时生成，链接使用受控域名和签名参数。

### 3.4 短信

1. SendSms 不具备业务幂等，平台必须自行保证。
2. BizId 与 RequestId 分开保存；提交成功不等于运营商送达。
3. 使用 QuerySendDetails 获取最近 30 天单手机号、单 BizId 回执。
4. 验证码逐号码发送；所有短信受业务限流、防盗刷和费用保护。

## 4. 目标与非目标

### 4.1 目标

1. 所有业务只能通过统一通知中心创建通知。
2. 支持事务性、安全性、运营性和系统性通知分类。
3. 支持单渠道、并行多渠道、优先级兜底和必达渠道策略。
4. 支持模板版本、变量 schema、多语言和渠道差异。
5. 支持用户偏好、同意、退订、静默时段、抑制和 endpoint 健康度。
6. 支持完整投递生命周期、独立重试、回执和审计。
7. 新增渠道时不修改通知核心模型和状态机。
8. 后台能够回答：为什么发、发给谁、用了什么模板、每个渠道发生了什么、是否送达。

### 4.2 非目标

1. 不迁移历史通知数据。
2. 不在首期建设复杂营销自动化旅程、A/B 实验或机器学习最佳发送时间。
3. 不保证 APNs 的“用户已阅读”；只能记录 APNs 接受和客户端上报的打开事件。
4. 不允许后台自由输入短信正文绕过供应商模板审核。
5. 不在首期拆分独立微服务。

## 5. 架构选择与权衡

### 5.1 方案比较

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 继续扩展现有 Service | 改动小 | 领域继续混杂，无法解决可靠性和状态问题 | 不采用 |
| 独立通知微服务 | 隔离和独立扩容强 | 当前团队运维、分布式事务和治理成本高 | 暂不采用 |
| 模块化单体 + 异步 Worker | 保持部署简单，边界清晰，可独立扩容 Worker | 需严格模块依赖和数据库边界 | 采用 |

### 5.2 模块边界

新建 `notification_center` Django App，内部使用六边形架构：

```text
notification_center/
  domain/          # 实体、值对象、策略、状态机、领域事件
  application/     # 用例：创建意图、解析受众、路由、发送、回执
  ports/           # Provider、Queue、Clock、Crypto、Preference 接口
  adapters/        # APNs、SMS、Email、Celery、ORM
  admin_api/       # 后台接口
  tasks/           # 异步任务入口，只调用 application use case
  models.py        # ORM 映射
```

依赖方向只能从 Adapter 指向 Application/Domain。业务模块只能调用公开 Application API 或发布领域事件。

### 5.3 Transactional Outbox

业务在自身事务内写入 `NotificationOutbox`，事务提交后 Relay 投递任务。Relay 可重复投递，消费者使用事件 ID 和幂等键去重。这样避免“业务已成功但 Celery 任务没入队”的不一致。

## 6. 统一领域语言

| 名称 | 含义 |
| --- | --- |
| NotificationIntent | 一次业务通知意图，说明为什么通知 |
| Campaign | 后台创建的批量或定时活动，是 Intent 的一种来源 |
| Audience | 目标受众定义 |
| AudienceSnapshot | 活动执行时冻结的收件人集合 |
| NotificationMessage | 某个收件人的逻辑通知 |
| ChannelDelivery | 某条 Message 在某个渠道上的投递 |
| Endpoint | 可发送地址，如 APNs token、手机号、邮箱 |
| DeliveryAttempt | 一次供应商请求 |
| ProviderEvent | 供应商回执、退信、投诉或 token 失效事件 |
| UserPreference | 用户对主题和渠道的偏好 |
| Suppression | 因退订、投诉、硬退信、无效地址而禁止发送 |

## 7. 数据模型

### 7.1 NotificationTopic

定义业务主题，如 `security.login_otp`、`medical.resource_changed`、`medication.reminder`、`member.invite`、`content.update`、`marketing.campaign`。

字段：`key`、名称、类别、是否强制事务通知、允许渠道、默认路由策略、默认优先级、偏好规则、数据保留策略、启用状态。

### 7.2 NotificationTemplate 与 TemplateVersion

`NotificationTemplate` 表示稳定业务模板；`NotificationTemplateVersion` 是发布后不可变版本。

版本字段：语言、变量 JSON Schema、主题、版本号、状态、创建人、审批人、发布时间。一个版本关联多个 `ChannelTemplateVersion`：

| 渠道 | 专属配置 |
| --- | --- |
| APNs | title/body、sound、badge 策略、category、thread-id、collapse-id、interruption-level、custom data schema |
| Email | subject、HTML、纯文本、from/reply-to、headers、退订策略 |
| SMS | sign name、provider template code、变量映射、短信类型 |
| 未来渠道 | 由 Adapter capability schema 声明 |

模板从 DRAFT → REVIEW → PUBLISHED → RETIRED。已发布版本不可原地修改。

### 7.3 NotificationIntent

字段：ID、event_id、topic、business_type、business_id、template/version、发送策略、优先级、计划时间、过期时间、幂等键、trace_id、来源、创建时间。

### 7.4 Campaign 与 AudienceSnapshot

Campaign 保存名称、目标定义、模板、渠道策略、计划、审批、预算上限和状态。AudienceSnapshot 按行保存 recipient，不使用 JSON 用户 ID 数组。

| 模型 | 关键字段 |
| --- | --- |
| AudienceDefinition | 筛选条件、版本、创建人 |
| AudienceSnapshot | campaign_id、recipient_type/id、解析状态、排除原因 |
| CampaignApproval | 审批人、人数、预计渠道量、预计费用、审批意见 |

受众冻结后，用户资料变化不改变该次活动目标；发送前仍重新校验偏好、抑制和 endpoint 有效性。

### 7.5 NotificationMessage

一位收件人的逻辑消息。`recipient_type` 支持 user 和匿名联系目标，`user_id` 可空。

关键字段：intent、campaign、recipient、template_version、locale、render_context_ciphertext、幂等键、总状态、计划/过期时间、创建/完成时间。

### 7.6 ContactEndpoint

统一端点索引：

| 字段 | 说明 |
| --- | --- |
| channel | `apns/email/sms/...` |
| owner_type/owner_id | 用户、匿名业务实体或系统目标 |
| address_ciphertext | 加密 token/邮箱/手机号 |
| address_hash | HMAC 精确检索 |
| address_masked | 后台展示 |
| scope | APNs topic、邮箱发件域、短信区域等 |
| verified_at | 已验证时间 |
| status | active/invalid/suppressed/revoked |
| invalid_reason | 无效原因 |
| last_success_at/last_failure_at | 健康度 |

APNs token 必须按 device installation + bundle/topic 唯一，不按用户单字段存储。

### 7.7 ChannelDelivery

每条 Message 每个渠道一条投递，可关联一个或多个 endpoint 子投递。字段包括：channel、route_order、required、状态、rendered_content_ciphertext/expiry、provider、endpoint_count、成功/失败/抑制数和时间。

### 7.8 DeliveryAttempt

每次实际供应商调用单独建行：delivery、endpoint、attempt_no、provider、provider_message_id、provider_request_id、HTTP/provider code、结果、耗时、可重试时间、错误分类、创建时间。禁止覆盖旧尝试。

### 7.9 ProviderEvent

统一保存供应商事实：事件类型、provider、external_event_id、delivery/attempt、原始状态码、规范化状态、发生时间、接收时间、去重键和脱敏 payload 摘要。

事件类型示例：`accepted/delivered/bounced/complained/unsubscribed/opened/clicked/token_invalid/receipt_unknown`。

### 7.10 Preference、Consent 与 Suppression

| 模型 | 用途 |
| --- | --- |
| NotificationPreference | 用户按 topic/category/channel 的允许、静音和静默时段 |
| NotificationConsent | 同意来源、版本、时间、撤回证据 |
| SuppressionEntry | endpoint/用户/主题/渠道级禁止发送及原因 |

安全验证码和必要服务通知按产品与法规规则定义是否可关闭；营销通知必须尊重退订和同意。

### 7.11 NotificationOutbox 与 AuditLog

Outbox 保存事件 ID、类型、payload、状态、尝试次数和下次投递时间。AuditLog 保存后台模板发布、活动审批、取消、重发、敏感信息访问和回执查询。

## 8. 状态机

### 8.1 Campaign

```text
DRAFT -> PENDING_APPROVAL -> APPROVED -> SCHEDULED -> RUNNING
                                             |          -> COMPLETED
                                             |          -> PARTIAL
                                             |          -> FAILED
                                             -> CANCELLED
```

### 8.2 Message

```text
CREATED -> ROUTED -> PROCESSING -> COMPLETED
    |          |           -> PARTIAL
    |          |           -> FAILED
    |          -> SUPPRESSED
    -> EXPIRED / CANCELLED
```

### 8.3 ChannelDelivery

```text
PLANNED -> QUEUED -> SENDING -> ACCEPTED -> DELIVERED
     |        |         |          |      -> DELIVERY_FAILED
     |        |         |          -> UNKNOWN
     |        |         -> SUBMIT_FAILED
     |        -> EXPIRED
     -> SKIPPED / SUPPRESSED / CANCELLED
```

不同渠道的 `ACCEPTED` 含义不同，但都不能等同于最终送达。

## 9. 通知路由策略

### 9.1 策略类型

| 策略 | 行为 | 适用业务 |
| --- | --- | --- |
| parallel | 多渠道并行，各自独立 | 重要系统公告 |
| fallback | 按顺序尝试，达到成功条件后停止 | 成员邀请 |
| required | 指定渠道必须执行 | 登录 OTP 指定短信或邮箱 |
| best_effort | 有可用 endpoint 才发送 | 普通资源变化提醒 |
| delayed_fallback | 主渠道一段时间未成功再启用备用 | 后期可选 |

### 9.2 成功条件

路由必须声明 success threshold：`provider_accepted`、`provider_delivered` 或 `client_opened`。例如成员邀请首期可将 APNs accepted 视为路由成功，但后台必须明确这不是用户已读。

### 9.3 决策顺序

主题政策 → 用户偏好/同意 → Suppression → endpoint 可用性 → 静默时段 → 频控 → 渠道策略 → Provider 健康度 → 创建 Delivery。

## 10. 模板渲染

1. 使用受限模板语法和 JSON Schema 校验变量，禁止任意 Python `format_map`。
2. 变量分为公开、个人信息、认证秘密三个敏感等级。
3. OTP 等认证秘密只在短期加密上下文中存在，发送或过期后清除。
4. 渲染在 Worker 内完成，日志只记录模板版本和变量键。
5. 提供测试数据预览，但真实用户敏感数据必须掩码。
6. 多语言按收件人 locale → 模板默认语言 → 系统默认语言回退。
7. 渲染产物保留期限按主题配置；安全消息正文尽快清除。

## 11. 可靠投递与队列

### 11.1 队列分层

```text
notification.security.high     # OTP、安全告警
notification.transactional     # 邀请、业务状态
notification.reminder          # 用药等提醒
notification.bulk              # 后台活动
notification.receipt           # 回执处理
notification.dead_letter       # 人工处理
```

### 11.2 幂等

创建 Intent、Message、Delivery、Attempt 和 ProviderEvent 均有独立唯一幂等键。Celery 至少一次投递是允许的，但重复任务不能产生第二次非预期供应商调用。

### 11.3 重试分类

| 分类 | 策略 |
| --- | --- |
| validation/permanent | 不重试 |
| auth/configuration | 熔断渠道并告警 |
| rate_limited | 遵循 Retry-After 或指数退避 |
| transient_5xx/network_before_send | 有限退避重试 |
| timeout_unknown | 不自动重复发送，等待查询或人工处理 |
| invalid_endpoint | 失效 endpoint，不重试 |

### 11.4 过期与取消

Worker 发送前必须检查 expires_at、活动取消状态、最新偏好和抑制。OTP 过期后禁止发送；活动取消只阻止尚未提交的投递。

## 12. 渠道详细设计

### 12.1 APNs

1. Endpoint 按 device installation、bundle/topic、environment 存储。
2. 使用 Token-based authentication，私钥由 Secret Manager 管理。
3. 发送保存 apns-id、HTTP status、reason、topic、push type 和环境。
4. `410/Unregistered` 及明确坏 token 使 endpoint invalid。
5. 429 与 5xx 有限退避；不可重试 4xx 直接终止。
6. 支持 collapse-id、thread-id、category、sound、badge 和静默推送，但由模板 schema 控制。
7. App 上报 `opened/actioned` 事件，与 Message ID 关联；不把 APNs 200 当已读。

### 12.2 短信

1. 首期阿里云 SendSms，签名和模板编码来自已发布渠道模板。
2. 每条单号码发送，平台生成 OutId 和幂等键。
3. 分别保存 Code、Message、BizId、RequestId。
4. QuerySendDetails 使用单手机号、单 BizId、原发送日期，查询最近 30 天。
5. 保存 ErrCode、SendStatus、发送/回执时间；不保存返回 Content。
6. OTP 队列、频控和费用保护独立于普通通知。
7. 后期供应商切换通过 SmsProvider Adapter，不改变核心模型。

### 12.3 邮箱

1. Email Adapter 首期兼容现有 SMTP/服务商，接口必须返回 provider message ID。
2. 正式环境配置 SPF、DKIM、DMARC 和受控 From/Reply-To。
3. 支持 HTML + text/plain multipart。
4. Provider webhook 进入 ProviderEvent，处理 delivered、soft/hard bounce、complaint、open、click。
5. hard bounce 和 complaint 写 SuppressionEntry；soft bounce 有限重试。
6. 运营订阅邮件加入 RFC 8058 List-Unsubscribe 与 List-Unsubscribe-Post，并由 DKIM 覆盖。
7. 打开率受隐私保护影响，只作为辅助指标，不作为关键业务成功条件。

### 12.4 未来渠道接入规范

新 Adapter 必须声明能力：是否支持回执、批量、富文本、动作按钮、折叠、过期、优先级、退订和最大 payload。核心路由只依赖能力，不写 `if channel == ...` 的供应商逻辑。

## 13. 当前业务接入方案

| 当前业务 | Topic | 推荐路由 |
| --- | --- | --- |
| 手机登录 OTP | `security.login_otp.sms` | required SMS，高优先级、短过期 |
| 邮箱登录 OTP | `security.login_otp.email` | required Email，高优先级、短过期 |
| 成员邀请 | `member.invite` | APNs → Email → SMS fallback |
| 健康资源变化 | `medical.resource_changed` | APNs best_effort，可按偏好扩展邮件 |
| 用药计划变化/提醒 | `medication.reminder` | APNs required/best_effort，后期多渠道 |
| 后台运营活动 | `campaign.admin` | 经审批的 parallel 或指定渠道 |
| 安全告警 | `security.alert` | required channels，绕过普通静默但不绕过无效 endpoint |

业务只提交 topic、business_id、recipient、模板键和变量，不直接选择 Provider、不拼装供应商参数。

### 14.1 总览

展示今日/近 7 日活动、逻辑消息、渠道投递量、接受率、送达率、失败率、队列积压、异常、退信/投诉、无效 token、短信费用估算和渠道健康。

### 14.2 通知用户列表

字段建议：用户、账号状态、locale、时区、APNs endpoint 数、短信资格、邮箱资格、偏好摘要、抑制状态、最近成功通知、最近失败。支持按用户、掩码联系方式、渠道可达性、主题偏好、抑制原因筛选。

“有联系方式”与“可通知”分开：可通知需要地址有效、已验证、用户允许、未抑制且符合主题政策。

### 14.3 通知模板

列表展示业务模板、topic、版本、语言、各渠道版本、状态、审批人和发布时间。支持创建草稿、变量 schema、渠道预览、测试发送、审批、发布、停用和复制新版本。已发布版本不可编辑。

### 14.4 发送活动

活动创建流程：基本信息 → 受众定义 → 模板/语言 → 渠道策略 → 计划与频控 → 预估人数/条数/费用 → 测试发送 → 审批 → 调度。

活动详情展示不可变受众快照、排除原因、各渠道漏斗、失败分类和取消状态。大活动异步解析受众并分页创建 Message。

### 14.5 全渠道发送记录

字段：Message ID、业务/topic、收件人、模板版本、路由策略、总状态、渠道摘要、创建时间、完成时间。详情以时间线展示每个渠道 Delivery。

### 14.6 APNs 发送记录

字段：Delivery ID、用户、设备/应用、topic、环境、状态、apns-id、HTTP 状态、reason、尝试次数、接受时间、打开时间、操作。

支持失效 token 原因筛选，不显示完整 device token。

### 14.7 短信发送记录

字段：Delivery ID、业务类型、用户/登录前用户、掩码号码、模板编码、提交状态、送达状态、Code/ErrCode、BizId、提交时间、回执时间、操作。

详情支持权限受控的 QuerySendDetails 主动查询。页面禁止显示 OTP、TemplateParam 和短信 Content。

### 14.8 邮箱发送记录

字段：Delivery ID、用户、掩码邮箱、模板/主题、提交状态、投递状态、退信类型、投诉、退订、provider message ID、发送/事件时间、操作。

详情展示事件时间线和脱敏 SMTP/Provider 结果，不展示认证秘密。

### 14.9 异常与抑制

统一管理坏 token、硬退信、投诉、退订、短信频控、地址无效、渠道熔断和死信。解除抑制必须有权限、理由和审计；投诉产生的抑制原则上不允许普通管理员解除。

### 14.10 后台设计原则

1. 先展示业务结论，再展示供应商技术字段。
2. “已受理、已送达、已打开”严格分开，不使用笼统“成功”。
3. 用户、活动、Message、Delivery、Attempt和ProviderEvent之间可以双向追踪。
4. 敏感数据默认掩码，查看完整值属于独立高风险操作。
5. 所有列表支持可复制的稳定ID、固定筛选条件和可分享的查询URL。
6. 大数据查询、导出和统计异步执行，不阻塞普通列表。
7. 页面显示数据口径、更新时间和统计延迟，避免把异步统计误认为实时事实。
8. 未知状态和新状态必须可见，不允许前端默认归类为成功或失败。

### 14.11 全局页面框架


### 14.13 通用筛选区

所有记录页面统一使用：

1. 时间范围，默认最近7天，提供今天、24小时、7天、30天快捷选项。
2. Topic、模板版本、活动、渠道、Provider、状态和错误分类。
3. 用户、业务ID、供应商ID精确搜索。
4. “仅异常”“仅未终态”“仅人工可处理”快捷筛选。
5. 筛选条件同步到URL query，刷新和分享链接后不丢失。
6. 提供“重置筛选”和当前生效条件标签。

高基数字段采用远程搜索Select，不一次加载全部模板、活动或用户。

### 14.14 通用表格规范

1. 默认按`created_at DESC, id DESC`稳定排序。
2. 使用服务端游标分页；不提供任意跳转到极深页。
3. ID、状态、时间、渠道和操作列固定宽度；业务摘要列自适应。
4. 状态标签同时使用文字和颜色，不能只靠颜色表达。
5. 时间默认显示管理员时区，悬停显示UTC原值。
6. 空值统一显示`-`，禁止显示`undefined/null`。
7. 长ID提供截断、复制和查看完整值按钮。
8. 表格列可以按页面预设切换，但关键状态列不可隐藏。
9. 列表只返回摘要；大JSON和事件时间线按需加载详情。

### 14.15 状态展示体系

状态分为四组视觉语义：

| 语义 | 示例 | 展示原则 |
| --- | --- | --- |
| 处理中 | CREATED、QUEUED、SENDING、WAITING_RECEIPT | 蓝色/中性，显示等待原因 |
| 成功事实 | ACCEPTED、DELIVERED、OPENED | 分阶段标签，不能合并 |
| 可恢复异常 | RATE_LIMITED、WAITING_RETRY、UNKNOWN | 橙色，显示下次动作 |
| 终止异常 | FAILED、SUPPRESSED、EXPIRED、CANCELLED | 红色或灰色，显示稳定reason |

聚合状态旁必须提供组成数量，例如“部分成功：APNs 1/1、邮箱 0/1、短信未执行”。

第三层为趋势和漏斗：Intent → Message → Delivery → Accepted → Delivered/Open。不同渠道缺少最终送达能力时单独标记，不伪造统一漏斗。

第四层为待办：待审批活动、失败模板、UNKNOWN投递、死信、投诉、费用异常和即将过期凭证。

总览卡片可点击进入已预置筛选条件的对应列表。

### 14.19 模板列表与详情

模板列表字段：模板Key、Topic、当前发布版本、支持语言、APNs/短信/邮箱渠道状态、变量数、状态、最近发布人和时间。

模板详情Tabs：

1. 基本信息与Topic政策。
2. 版本历史和版本差异。
3. 变量JSON Schema。
4. APNs渠道模板。
5. 短信渠道模板。
6. 邮箱渠道模板。
7. 预览与测试发送。

发布确认弹窗必须展示版本差异、渠道配置、变量变化、受影响Topic和审批人。若删除变量会导致现有调用不兼容，发布门禁拒绝并显示契约测试结果。

### 14.20 模板预览与测试发送

预览必须选择：模板版本、语言、渠道和测试数据集。敏感变量使用模拟值，不允许自动载入真实用户医疗数据。

测试发送要求：

1. 只能发送到配置的测试Endpoint或管理员本人已验证Endpoint。
2. 明确标记TEST，不进入生产活动统计。
3. 仍创建完整Message/Delivery/Attempt，便于验证Adapter。
4. 短信测试可能产生费用，发送前显示确认。
5. 测试发送具有独立RBAC和审计。

### 14.21 发送活动列表

字段建议：活动ID、名称、Topic、模板版本、受众规模、渠道策略、状态、计划时间、进度、创建人、审批人和创建时间。

进度同时展示：受众解析、Message物化、渠道投递、终态完成。不能只显示单一百分比掩盖哪个阶段阻塞。

快捷操作按状态控制：草稿可编辑/删除，待审批可撤回，已审批可调度，运行中可取消未提交投递，终态只允许查看和复制为新活动。

### 14.22 活动创建向导

步骤与校验：

1. 基本信息：名称、Topic、目的和负责人。
2. 受众：用户/筛选器、排除条件和预估。
3. 模板：已发布版本、语言回退和变量来源。
4. 渠道路由：parallel/fallback/required及成功阈值。
5. 计划：立即/定时、时区、过期、静默时段。
6. 预算与频控：人数、短信条数、费用上限和发送速率。
7. 测试发送：必须完成的渠道测试。
8. 审核摘要：不可变快照和风险提示。

每一步保存草稿。离开页面后可继续；进入审批后冻结受众条件、模板版本、路由、计划和预算。

### 14.23 活动预估

预估结果至少包括：

```text
原始受众人数
排除人数及原因
可生成Message人数
APNs可达人数
邮箱可达人数
短信可达人数
预计各渠道Delivery数
预计短信条数和费用区间
静默时段延迟人数
Suppression人数
```

预估带`calculated_at`和数据版本。超过配置时间后审批前必须重新计算；变化超过阈值使旧审批失效。

### 14.24 活动详情

顶部展示业务摘要和紧急取消按钮。主体Tabs：概览、受众快照、Message、渠道投递、异常、统计、审批和审计。

概览中使用时间线展示：创建 → 预估 → 测试 → 审批 → 调度 → 开始 → 完成/取消。每个节点显示操作人、时间和request_id。

### 14.25 全渠道消息详情

Message详情布局：

1. 业务信息：Topic、business_type/id、Intent、Campaign、模板版本。
2. 收件人：用户或匿名联系人摘要、locale、时区。
3. 路由决策：偏好、Suppression、Endpoint和选中渠道。
4. Delivery卡片：APNs、短信、邮箱各自状态和摘要。
5. 统一时间线：Attempt和ProviderEvent按时间排序。
6. 聚合结果：为什么Message最终是COMPLETED/PARTIAL/FAILED。

详情提供关联资源链接，但业务资源访问仍执行对应业务权限，通知权限不能越权查看医疗内容。

### 14.26 渠道详情抽屉规范

三种渠道共用基础区：Delivery ID、Message、Topic、模板、Provider、Endpoint掩码、状态、Attempt数、创建/终态时间。

渠道专属区：

| 渠道 | 专属字段 |
| --- | --- |
| APNs | topic、environment、push type、apns-id、HTTP status、reason、token失效时间、打开/动作事件 |
| 短信 | sign、template code、Code、BizId、Send RequestId、ErrCode、SendStatus、回执时间 |
| 邮箱 | subject摘要、provider message ID、accepted/delivered、bounce类型、complaint、unsubscribe、open/click |

原始供应商响应不直接渲染，使用字段白名单和脱敏后的诊断信息。

### 14.27 异常中心

异常中心按可处置性分组：

1. 平台异常：Outbox积压、死信、状态卡住。
2. 渠道异常：凭证、熔断、Provider错误率。
3. 模板异常：变量不匹配、模板失效、payload超限。
4. Endpoint异常：坏token、硬退信、投诉、号码无效。
5. 投递异常：UNKNOWN、持续重试、回执过期。
6. 业务异常：受众为零、预算超限、活动被取消。

每条异常展示severity、first_seen、last_seen、affected_count、owner、状态和运行手册链接。支持确认、指派、添加备注和关闭；关闭异常不等于修改Delivery事实。

### 14.28 Suppression管理

列表字段：Scope、渠道、掩码Endpoint、原因、来源事件、创建时间、是否允许解除、解除人和解除时间。

解除流程：权限校验 → 显示风险与来源 → 输入理由 → 必要时二人审批 → 创建新审计事实。不得物理删除原Suppression记录；使用active/cleared状态保留历史。

### 14.29 渠道设置

渠道设置页面默认只读展示：启用状态、Provider、环境、凭证标识/到期时间、Endpoint、限流、超时、队列、最近健康探测和熔断状态。

密钥值永不展示。配置修改优先通过部署/Secret Manager完成；后台若提供开关，只能操作经过白名单的运行时开关并完整审计。

提供“健康探测”操作，但不得向真实用户发送。真实测试发送走模板测试功能。

### 14.30 统计分析

统计页面分为：业务Topic、活动、模板、渠道、Provider、失败原因和用户偏好趋势。

所有图表显示指标定义。支持按日/小时粒度和时间范围筛选。跨渠道对比时区分accepted和delivered；APNs不能验证最终送达时不绘制虚假送达率。

### 14.31 导出中心

导出属于异步任务：创建导出申请 → 权限校验 → 生成脱敏文件 → 临时下载URL → 到期删除。导出字段使用白名单，不导出完整Endpoint、OTP、TemplateParam、医疗正文或Provider密钥。

大范围导出需要更高权限和理由，生成、下载和过期清理均写审计。

### 14.32 批量操作

允许的批量操作应非常有限：批量取消未开始活动、批量指派异常、批量停用模板草稿等。禁止批量重发Delivery、批量解除投诉Suppression或批量查看完整联系方式。

任何批量操作先显示影响数量和不可逆影响，并通过后台任务执行，提供Job ID和结果报告。

### 14.33 RBAC反馈

无权限的危险操作默认不展示；通过深链访问时返回403并说明缺少的权限代码。按钮禁用时显示原因，例如“活动已开始，不能修改模板”或“投诉抑制不可由当前角色解除”，不能只显示灰色按钮。

### 14.34 审计查看器

资源详情提供审计时间线：actor、action、resource、前后状态摘要、request_id、IP/User-Agent摘要和结果。敏感字段仅记录是否访问，不把被访问值写入审计。

审计记录不可由后台普通用户编辑或删除。

### 14.35 加载、空状态和错误状态

1. 首次加载使用骨架屏，筛选刷新保留旧数据并显示局部loading。
2. 无数据时区分“系统尚无数据”和“当前筛选无结果”。
3. API失败保留用户筛选，提供重试和request_id。
4. 部分统计延迟时标注“数据更新中”，不清空整页。
5. 渠道不可用时顶部展示告警，但记录查询仍应可用。

### 14.36 实时刷新

运行中活动、队列健康和异常数量可以采用15–30秒轮询；普通历史列表不自动刷新，避免行位置跳动。详情抽屉可手动刷新。后期如引入SSE/WebSocket，也只传状态变化通知，客户端仍通过API读取权威数据。

### 14.37 响应式与可访问性

后台以桌面为主，最小支持常见笔记本宽度。窄屏下次要列进入详情，不压缩关键状态和操作。表格、标签、弹窗和图表必须支持键盘操作、可见焦点、文本状态、合理对比度和屏幕阅读器标签。

### 14.38 后台性能要求

1. 列表首屏P95≤800ms，不含异步统计生成。
2. 详情基础信息P95≤500ms，事件时间线可独立分页加载。
3. 筛选Select远程搜索P95≤500ms。
4. 普通列表每页默认20、最大100。
5. 图表查询设置最大时间范围和粒度，超限提示使用异步导出。
6. 前端取消过期请求，避免快速切换筛选导致旧响应覆盖新数据。

### 14.39 后台错误码与文案

后台显示稳定中文说明，同时保留可复制的机器错误码和request_id。例如：

```text
notification_campaign_budget_exceeded
notification_template_contract_changed
notification_delivery_retry_not_allowed
notification_sms_receipt_expired
notification_suppression_release_forbidden
```

供应商原始Message不直接面向普通管理员，安全角色可查看脱敏诊断摘要。

### 14.40 页面级验收标准

- [ ] 总览能从异常卡片跳转到正确预置筛选列表。
- [ ] 用户列表能解释每个渠道为什么可达或不可达。
- [ ] 模板发布前显示版本差异和契约测试结果。
- [ ] 活动创建具备预估、测试发送、审批、预算和取消。
- [ ] 全渠道详情能串联Intent、Message、Delivery、Attempt和ProviderEvent。
- [ ] APNs、短信、邮箱页面均展示各自专业字段。
- [ ] 所有敏感字段默认掩码，访问和导出经过权限及审计。

## 17. 安全与隐私

3. OTP、token、手机号、邮箱、TemplateParam 和 Content 不进入普通日志。
4. Provider webhook 验证签名、时间戳和重放，事件 ID 唯一去重。
5. APNs 私钥、短信 AK、SMTP/邮件 API Key 使用 Secret Manager 和最小权限。
6. 后台实施 RBAC、操作审批、CSRF、防重放和审计。
7. 数据保留按 topic/category 配置；统计尽量使用聚合数据。
8. 用户注销时按政策匿名化通知数据，但安全审计保留必要不可逆摘要。

## 19. 可观测性

### 19.1 指标

1. Intent、Message、Delivery、Attempt 各阶段数量和延迟。
2. 每渠道接受率、送达率、失败率和未知率。
3. APNs 失效 token、429、5xx；邮件硬/软退信、投诉、退订；短信 Code/ErrCode 与费用估算。
4. Outbox 积压、队列积压、重试、死信和幂等命中。
5. 按 topic、模板版本、Provider、App、环境聚合。

### 19.2 追踪

贯穿 `trace_id → intent_id → message_id → delivery_id → attempt_id → provider_id`。日志使用结构化字段，不记录敏感 payload。

### 19.3 告警

渠道配置失效、接受率/送达率突降、投诉率/退信率升高、OTP 延迟、队列积压、死信增长、短信费用异常和模板错误必须告警并关联运行手册。

## 20. 容量与性能

1. Campaign 受众异步解析、批量落库，不把用户列表放进任务参数。
2. 每个渠道独立队列和并发；安全通知隔离资源。
3. 发送记录按 created_at、channel、status、topic、provider ID 建复合索引。
4. 大表按时间归档或分区作为容量达到阈值后的演进，不在首期过早引入。
5. 统计使用异步聚合表，不对 Attempt/ProviderEvent 大表实时全扫描。
6. Provider QPS 限制由分布式令牌桶控制，不能依赖 Worker 数量碰运气。

## 25. 架构决策记录

### ADR-001：采用模块化单体而非微服务

状态：拟接受。当前团队和部署基础以 Django/Celery 为主，模块化单体可以获得清晰边界、独立 Worker 扩容和事务 Outbox，同时避免服务发现、跨服务事务和独立运维成本。未来当通知吞吐或团队边界明确时，可按现有 Ports 和事件契约拆出服务。

### ADR-002：至少一次任务 + 业务幂等

状态：拟接受。端到端 exactly-once 在外部 Provider 场景不可实现。系统接受任务可能重复，用数据库唯一键、状态抢占和供应商副作用边界实现有效一次业务效果；超时未知不自动重发。

### ADR-003：业务模板与渠道模板分离

状态：拟接受。同一业务通知在 APNs、邮件和短信上的能力、审核和内容结构不同。分离后增加渠道无需污染业务模板，但模板管理 UI 和发布流程更复杂。

### ADR-004：不把 Provider 回执塞进通用 JSON

状态：拟接受。核心字段规范化建模，渠道扩展字段可使用受 schema 约束的 JSON。这样可查询、统计和索引，但增加模型数量。

### 27.2 功能不丢失原则

每个业务完成整合必须同时满足：

1. 原触发条件不变：业务成功后仍在相同语义点产生通知意图。
2. 原目标人群不变：特别是成员本人绑定、管理员角色和匿名联系人选择逻辑。
3. 原导航能力不变：APNs payload 的 route、resource_id、member_id 等有版本化 schema。
4. 原时效不下降：OTP 和安全通知进入独立高优先级队列。
5. 原业务事务不被通知阻塞：业务提交成功后通过 Outbox 异步执行。
6. 通知失败可见但不反向篡改已成功的核心业务状态。
7. fallback 只有在明确定义的成功条件下停止，不再把模糊 `sent` 当作所有渠道成功。
8. 新系统为每个跳过、抑制和失败给出稳定 reason，后台可解释。

### 27.3 业务功能对照验收

每个业务建立“旧行为规格”而不是迁移旧数据，使用固定测试场景验证新实现：

| 验收维度 | 必测内容 |
| --- | --- |
| 触发 | 创建、更新、通过、拒绝、定时到期等事件是否仅触发一次 |
| 收件人 | 用户、成员本人、管理员、匿名联系人是否与业务规则一致 |
| 模板 | 标题、正文、变量、语言及 App 路由是否正确 |
| 渠道 | required/parallel/fallback 顺序及停止条件 |
| 无渠道 | 缺手机号、邮箱或 token 时正确 SKIPPED，不伪报成功 |
| 业务失败 | 业务事务回滚时不创建可执行通知 |
| 通知失败 | Provider 失败不回滚已完成业务，但产生可检索异常 |
| 重复事件 | 相同 business_id/event_id 不重复发送 |
| 过期 | OTP、提醒在过期后不发送 |
| 注销 | endpoint 失效、偏好与历史记录按策略匿名化 |

### 27.5 TaskNotification 的处理

`TaskNotification` 同时表达“任务提醒规则”和“远程发送结果”，需要拆开：

1. 任务域新建或保留 `TaskReminderPolicy`：task、reminder_time、repeat rule、enabled、template key、业务变量。
2. 远程调度进入通知中心 `NotificationSchedule`，到期创建 Intent。
3. iOS 本地通知配置继续由任务 API 返回 ReminderPolicy，不创建虚假的 Provider Delivery。
4. 任务完成、取消、修改时间时，调用 `cancel_by_business_key` 或重建 schedule。
5. 新系统启用时不导入旧 TaskNotification；仍未到期的旧提醒不自动补发。上线前应明确告知这是数据边界，并通过产品验收。

### 27.9 为什么需要墓碑任务

Celery 消息序列化时保存任务名称。直接删除旧任务代码后，Broker 中的 ETA/reserved 消息会成为 `unregistered task`，既无法安全确认业务状态，也可能持续报错。墓碑任务以相同名称注册一个发布周期，明确丢弃旧消息，保证不会重复通知。

### 28.3 索引与查询原则

1. 所有后台时间列表使用 `(status, created_at, id)` 或 `(channel, status, created_at, id)` 复合索引。
2. Provider ID、BizId、RequestId、apns-id 建精确索引，不做模糊查询。
3. 联系地址只通过 HMAC 精确检索，不在密文上查询。
4. AudienceSnapshot 和 Message 禁止使用无界 offset 深分页；使用 `(created_at,id)` 游标。
5. JSON 只存受 schema 约束的扩展配置，不把核心状态、错误码和 Provider ID 藏进 JSON。
6. 数据库时间统一 UTC，API 按用户或管理员时区格式化。

### 28.4 CloudEvents 风格事件契约

```json
{
  "specversion": "1.0",
  "id": "018f-event-id",
  "source": "sparkservice.medical",
  "type": "medical.medication_plan.changed.v1",
  "subject": "medication-plan/12345",
  "time": "2026-07-13T10:00:00Z",
  "datacontenttype": "application/json",
  "trace_id": "req-abc",
  "data": {
    "business_id": "12345",
    "member_id": "678",
    "actor_user_id": "10",
    "action": "updated"
  }

```

规则：

1. `type` 必须版本化；破坏性字段变化发布 v2。
2. data 只包含解析受众和模板变量所需的最小业务引用。
3. 禁止在事件中放 OTP、完整手机号、邮箱、APNs token 和医疗正文。
4. 消费者根据 event id 幂等；事件顺序不能依赖 Broker 全局顺序。
5. 事件 schema 纳入契约测试和兼容性检查。

### 28.5 Outbox Relay 实现

推荐批量抢占算法：

```text
1. SELECT pending rows
   WHERE available_at <= now
   ORDER BY id
   LIMIT 100
   FOR UPDATE SKIP LOCKED
2. 原子更新为 publishing，并设置 lease_owner/lease_expires_at
3. 事务提交
4. 逐条发布 Celery 任务
5. 发布成功更新 published
6. 发布失败递增 attempts，设置 available_at 退避
7. lease 超时由 repair task 重新置 pending
```

禁止在持有数据库锁时执行网络调用。Outbox payload 只保存通知事件，不保存解密后的 endpoint 或认证秘密。

### 28.6 Message 路由并发控制

Worker 通过条件更新抢占：

```sql
UPDATE ... SET status='PROCESSING', lease_owner=?, lease_expires_at=?
WHERE id=? AND status IN ('CREATED','ROUTED') AND lease_expires_at < now
```

受影响行数为 0 时说明已被其他 Worker 处理。每个 Message 的 Delivery 创建使用数据库唯一约束兜底，不能只依赖 Redis 锁。

### 28.7 Provider Adapter 契约

```python
class NotificationProvider(Protocol):
    channel: str

    def capabilities(self) -> ProviderCapabilities: ...
    def validate(self, request: ProviderRequest) -> None: ...
    def send(self, request: ProviderRequest) -> ProviderSendResult: ...
    def normalize_error(self, exc: Exception) -> ProviderError: ...
    def verify_event(self, headers: Mapping, body: bytes) -> VerifiedProviderEvent: ...
```

`ProviderSendResult` 必须区分：

```text
accepted
permanent_rejection
transient_failure_before_submit
rate_limited
timeout_unknown
```

Adapter 不负责用户偏好、业务路由、幂等和数据库状态机。核心域不读取供应商 SDK 对象。

### 28.8 Provider 能力声明

```json
{
  "supports_delivery_receipt": true,
  "supports_batch": false,
  "supports_expiration": true,
  "supports_collapse": true,
  "supports_unsubscribe": false,
  "supports_open_event": false,
  "max_payload_bytes": 4096
}
```

模板发布和路由规划阶段根据能力拒绝不支持的配置，不能等到发送时才失败。

### 28.9 活动执行分片

1. AudienceDefinition 解析为 Snapshot，记录 included/excluded 和原因。
2. Snapshot 按主键游标每批 500–1000 人物化 Message，批次大小可配置。
3. 每个 Message 独立路由和发送，不由一个 Campaign Task 循环所有用户。
4. Campaign 进度来自计数器和周期校准，不在每条 Message 完成时锁同一 Campaign 行。
5. 取消活动设置 `cancel_requested_at`；Worker 发送前检查，已提交外部供应商的无法撤回。
6. 活动完成条件：受众解析完成且所有 Message 进入终态。

### 28.10 聚合状态算法

Message 状态按 Delivery 事实计算：

| 条件 | Message 状态 |
| --- | --- |
| 全部 suppressed/skipped | SUPPRESSED |
| required Delivery 任一失败且无允许 fallback | FAILED |
| 至少一个达到 success threshold，其他均终态 | COMPLETED 或 PARTIAL |
| 仍有非终态 Delivery | PROCESSING |
| 所有可执行 Delivery 失败 | FAILED |

Campaign 状态按 Message 聚合。后台必须同时展示分母：目标人数、快照人数、有效消息、Delivery 数量，避免“100人活动、300次渠道投递”口径混淆。

### 28.14 错误分类

| error_category | 示例 | 处理 |
| --- | --- | --- |

### 28.15 SLO 建议

| 场景 | 指标 | 首期目标 |
| --- | --- | --- |
| OTP | Intent 创建至首次供应商请求 P95 | ≤ 3秒 |
| 事务通知 | Intent 至首次请求 P95 | ≤ 30秒 |
| 定时活动 | 计划时间至开始处理 P95 | ≤ 60秒 |
| Outbox | pending 最老年龄 | 高优先级 ≤ 5秒，普通 ≤ 60秒 |
| 后台查询 | 列表 API P95 | ≤ 800ms |
| 回执 | Provider事件接收到状态更新 P95 | ≤ 60秒 |
| 可用性 | 通知中心创建 Intent API | 月度 ≥ 99.9% |

供应商不可用不等于创建 Intent API 不可用；系统可以接受并排队未过期的普通通知，但 OTP 超过有效期必须失败而不是延迟发送。

### 28.16 数据保留建议

| 数据 | 建议保留 |
| --- | --- |
| OTP渲染参数密文 | 发送或过期后立即清除 |
| 普通渲染产物 | 7–30天，按 topic 配置 |
| Message/Delivery/Attempt | 180天在线，之后聚合或删除 |
| ProviderEvent | 180天，敏感 payload 不保存 |
| Campaign和审批 | 2年或按合规要求 |
| AuditLog | 至少2年，不允许普通管理员删除 |
| 聚合统计 | 长期保留，不含直接标识符 |

### 28.17 渠道熔断

1. 认证/配置错误立即打开渠道熔断器并通知值班人员。
2. 短时间 5xx/超时率超过阈值进入 open，冷却后 half-open 探测。
3. 熔断粒度为 provider + credential scope + environment，不能因测试环境故障关闭生产。
4. fallback 是否启用由 topic policy 决定；OTP 不得擅自切换到用户未选择渠道。
5. 熔断期间新 Delivery 标记 WAITING_PROVIDER 或按过期策略失败。

### 28.18 运行手册最低内容

每个渠道必须有：凭证失效、429、5xx、队列积压、未知提交、错误模板、无效 endpoint 激增、退信/投诉升高、短信费用异常的诊断步骤、止损开关、恢复步骤和证据留存要求。

### 28.20 故障场景决策表

| 故障 | 系统动作 | 禁止动作 |
| --- | --- | --- |
| Redis/Celery不可用 | Outbox保留pending，恢复后投递 | 在业务请求内直接调用Provider |
| 数据库短暂不可用 | 创建Intent失败并返回稳定错误 | 只发外部通知不留台账 |
| Provider 5xx | 退避、熔断、按策略fallback | 无限重试 |
| Provider超时未知 | 标记UNKNOWN，查询或人工确认 | 自动再发 |
| 模板被供应商停用 | 停用渠道模板并告警 | 换成自由文本绕过审核 |
| APNs token失效 | endpoint invalid | 对同token持续重试 |
| 邮件投诉 | suppression | 普通管理员解除后继续发送 |
| 回执乱序 | 按状态优先级和occurred_at幂等应用 | 用旧事件覆盖新终态 |
| 活动误发 | 取消未提交Delivery、关闭队列生产者 | 宣称可撤回已提交消息 |

### 28.21 回执乱序规则

ProviderEvent 可能重复或乱序。状态更新遵循：

1. external_event_id 去重。
2. 终态不被非终态覆盖。
3. 同级事件按 provider occurred_at 判断；缺失时使用 received_at 并标记时间可信度。
4. delivered 与 later bounce/complaint 可同时存在：Delivery 保留投递事实，Suppression 记录后续信誉事件。
5. 所有原始规范化事件保留，便于重新聚合。

### 28.22 定时提醒正确性

1. NotificationSchedule 保存 fire_at、timezone、recurrence、business_key 和 next_fire_at。
2. 周期规则计算使用用户/成员时区，最终时间转 UTC。
3. 夏令时地区明确处理不存在时间和重复时间。
4. 修改计划使用版本号；旧 schedule fire 时发现版本不匹配即跳过。
5. 任务完成或取消事务内写 cancel outbox，避免旧 ETA 消息继续执行。
6. 调度器按数据库 due rows 扫描，而不是为长期计划堆积大量 Celery ETA 消息。

### 28.23 API与前端兼容策略

新API从 `/notification-center/` 独立发布，不复用旧响应结构。前端类型必须使用明确枚举，不把未知状态直接当成功。状态字典由前端版本内置并对未知值显示“未知状态”，避免后端新增状态导致空白页面。

### 28.24 Definition of Done

每个 topic 的接入工单只有同时满足以下条件才算完成：

1. topic政策、模板变量schema和路由策略已评审。
2. 业务事务通过Outbox产生Intent。
3. 幂等、过期、无endpoint、偏好、suppression测试通过。
4. 各目标渠道契约测试和真实联调通过。
5. 后台能按business_id和trace_id追踪。
6. 指标、日志、告警和运行手册存在。
7. 旧调用入口已删除并由CI禁止回归。
8. 安全扫描未发现敏感数据泄漏。

## 29. 通用实现与APNs/邮箱技术细化

短信渠道的字段、阿里云Adapter、号码安全、限流和回执实现详见[短信渠道专项需求及详细设计](./短信平台推倒重构需求及详细设计工单.md)。本章补齐通知中心通用实现以及APNs、邮箱的同等级技术细节。

### 29.1 Django模型组织

建议按功能拆分ORM文件，避免单个models.py继续膨胀：

```text
notification_center/models/
  topic.py
  template.py
  intent.py
  audience.py
  message.py
  endpoint.py
  delivery.py
  preference.py
  schedule.py
  outbox.py
  audit.py
```

Model只表达持久化结构；状态转换、路由、重试和聚合放在Domain/Application层。Django signal不得承担外部发送，避免隐式副作用和事务边界不清。

### 29.2 主聚合边界

| 聚合 | 一致性边界 | 禁止跨边界强事务 |
| --- | --- | --- |
| TemplateVersion | 模板内容、变量schema、渠道版本、发布状态 | 不与Campaign发送记录同事务 |
| NotificationIntent | 业务意图、幂等、计划和过期 | 不在创建Intent时同步创建所有Delivery |
| NotificationMessage | 单收件人状态和Delivery规划 | 不锁Campaign主行更新每条进度 |
| ChannelDelivery | endpoint、Attempt和渠道状态 | Provider网络调用不在数据库锁事务内 |
| Campaign | 受众定义、审批、预算和聚合状态 | 不直接包含全量用户ID |
| ContactEndpoint | 地址、验证、健康度和失效状态 | 偏好与Consent独立建模 |

### 29.3 状态转换服务

所有状态转换使用显式命令：

```python
message.mark_routed()
delivery.queue()
delivery.start_sending(lease)
delivery.record_acceptance(attempt)
delivery.record_failure(error)
delivery.apply_provider_event(event)
campaign.request_cancel(actor)
```

每个方法校验允许的前置状态并产生领域事件。Serializer、View、Celery Task和Adapter禁止直接修改status。

### 29.4 Outbox写入示例

```python
with transaction.atomic():
    business_row = service.apply_business_change(...)
    outbox = NotificationOutbox.objects.create(
        event_id=uuid7(),
        event_type="medical.medication_plan.changed.v1",
        aggregate_type="medication_plan",
        aggregate_id=str(business_row.id),
        payload=minimal_event_payload,
        status="PENDING",
        available_at=timezone.now(),
    )
```

Outbox和业务变更必须写入同一数据库事务。`transaction.on_commit(task.delay)`只能作为Relay唤醒优化，不能作为唯一可靠投递机制。

### 29.5 Outbox Relay任务

```python
@shared_task(queue="notification.maintenance")
def relay_notification_outbox():
    OutboxRelay(batch_size=100).run_once()
```

Relay使用`SELECT ... FOR UPDATE SKIP LOCKED`抢占，网络发布在事务外执行。记录`lease_owner/lease_expires_at/attempts/last_error`；repair任务回收超时lease。发布成功不删除Outbox，按保留期清理。

### 29.6 受众解析实现

AudienceDefinition必须使用版本化白名单筛选器，不接受前端任意ORM字段或SQL：

```json
{
  "schema_version": 1,
  "operator": "and",
  "rules": [
    {"field": "is_active", "op": "eq", "value": true},
    {"field": "has_reachable_channel", "op": "in", "value": ["apns", "email"]}
  ]
}
```

解析流程：校验schema → 生成受控QuerySet → 游标分页 → 写AudienceSnapshot → 记录included/excluded reason → 生成统计摘要。审批后Definition和Snapshot均不可修改。

### 29.7 Message物化与路由

```text
AudienceSnapshot(included)
  -> 每收件人NotificationMessage
  -> 读取TopicPolicy
  -> 读取Preference/Consent/Suppression
  -> 解析ContactEndpoint
  -> 选择ChannelTemplateVersion
  -> 创建ChannelDelivery
  -> 推送对应优先级队列
```

同一Message下各Delivery使用`message_id + channel + route_order`唯一约束。fallback后续Delivery可以先创建为BLOCKED，前一渠道未达到success_threshold时再解锁。

### 29.8 fallback状态推进

```text
APNs Delivery终态
  ├─ 达到阈值 -> 后续Email/SMS标记SKIPPED_FALLBACK_SUCCEEDED
  └─ 未达到阈值 -> 原子解锁下一route_order Delivery
```

解锁使用条件更新与唯一事件键，防止两个Worker同时启动下一渠道。required渠道不受其他渠道成功影响。

### 29.9 APNs Endpoint字段

ContactEndpoint(channel=apns)的scope至少包含：

```json
{
  "installation_id": "device-installation-id",
  "bundle_id": "com.sparkclient.ios",
  "topic": "com.sparkclient.ios",
  "environment": "production",
  "push_type_capabilities": ["alert", "background"]
}
```

唯一约束建议：`channel + address_hash(token) + topic + environment`。同一设备重新注册新token时，旧endpoint设为REVOKED；不能假设token永久不变。

### 29.10 APNs Adapter接口

```python
class ApnsProvider(Protocol):
    def send(
        self,
        *,
        device_token: str,
        topic: str,
        environment: str,
        payload: dict,
        headers: ApnsHeaders,
    ) -> ApnsSendResult: ...
```

结果字段：outcome、apns_id、http_status、reason、token_invalid_at、retry_after和latency_ms。Adapter只映射Apple协议，不处理用户偏好和fallback。

### 29.11 APNs请求构造

Headers由ChannelTemplateVersion和Delivery策略生成：

```text
apns-topic
apns-push-type
apns-priority
apns-expiration
apns-collapse-id（可选）
apns-id（平台生成，便于幂等追踪）
```

payload在发送前计算UTF-8字节长度并校验Apple上限；自定义字段放在aps之外，并携带message_id、topic和route等最小导航字段，不携带医疗正文或认证秘密。

### 29.12 APNs错误映射

| HTTP/reason | 分类 | 处理 |
| --- | --- | --- |
| 200 | accepted | Delivery=ACCEPTED，保存apns-id |
| 400 BadDeviceToken | endpoint_invalid | endpoint=INVALID，不重试 |
| 410 Unregistered | endpoint_invalid | 按timestamp失效，不重试 |
| 403 ExpiredProviderToken | authentication | 刷新JWT后有限重试；持续失败熔断 |
| 413 PayloadTooLarge | validation | 不重试，模板告警 |
| 429 TooManyRequests | rate_limit | 延迟重试 |
| 500/503 | transient_provider | 指数退避 |

APNs 200只表示Apple接受。客户端`opened/actioned`通过独立事件API上报，不篡改accepted事实。

### 29.13 APNs客户端事件API

```http

Authorization: Bearer <token>
Idempotency-Key: <client-event-id>
```

```json
{
  "message_id": "message_01J...",
  "event": "opened",
  "action_id": "view_medication_plan",
  "occurred_at": "2026-07-13T10:00:00Z",
```

### 29.14 邮件Endpoint与规范化

邮箱内部保存规范化地址密文、HMAC和掩码。域名转小写并IDNA规范化；本地部分原则上保持原值，不能未经策略统一转小写破坏少数大小写敏感系统。验证状态与账号email字段分离。

### 29.15 Email Provider Port

```python
class EmailProvider(Protocol):
    def send(
        self,
        *,
        to: str,
        subject: str,
        text_body: str,
        html_body: str,
        headers: Mapping[str, str],
        tags: Mapping[str, str],
    ) -> EmailSendResult: ...

    def verify_webhook(self, headers, body) -> list[ProviderEventDTO]: ...
```

EmailSendResult区分accepted、rejected、rate_limited、transient_failure和timeout_unknown，并返回provider_message_id、request_id和响应码。

### 29.16 邮件生成

1. subject、text和html分别使用受限模板渲染。
2. HTML经过安全模板和链接白名单，不允许任意管理员脚本。
3. 生成multipart/alternative，纯文本不是从HTML粗暴去标签的不可读内容。
4. 设置Message-ID、Date、From、Reply-To和业务追踪header。
5. 运营邮件加入List-Unsubscribe和List-Unsubscribe-Post。
6. 退订token包含recipient、topic、版本、过期时间并签名，不暴露原始用户ID。
7. DKIM/SPF/DMARC由发件基础设施配置和上线检查验证。

### 29.17 邮件Provider事件

统一规范化：

| Provider事件 | normalized_type | 后续动作 |
| --- | --- | --- |
| delivered | delivered | Delivery=DELIVERED |
| soft bounce | soft_bounce | 有限重试/观察endpoint健康度 |
| hard bounce | hard_bounce | endpoint SUPPRESSED |
| complaint | complained | 写高优先级Suppression，不普通解除 |
| unsubscribe | unsubscribed | 更新对应topic/category偏好 |
| open | opened | 辅助指标 |
| click | clicked | 辅助指标并验证安全链接 |

Webhook必须验证供应商签名、时间戳、来源和事件ID；原始payload进入受限日志存储前脱敏，核心字段写ProviderEvent。

### 29.18 一键退订端点

```http
POST /api/public/v1/notification-center/email/unsubscribe/{signed_token}/
Content-Type: application/x-www-form-urlencoded

List-Unsubscribe=One-Click
```

不得跳转、不得要求登录或二次确认；重复请求幂等成功。事务性安全邮件不得错误更新为“用户全部通知关闭”。

### 29.19 Suppression优先级

```text
legal/global suppression
  > complaint/hard bounce endpoint suppression
  > topic unsubscribe
  > channel preference off
  > quiet hours
  > routing strategy
```

每次发送前重新评估。活动审批时的可达人数只是估计，最终发送数可能因新退订或endpoint失效减少。

### 29.20 Preference解析算法

```text
Topic强制政策
  -> Category偏好
  -> Topic覆盖
  -> Channel覆盖
  -> QuietHours
  -> Endpoint系统权限和状态
```

解析输出不是boolean，而是`ALLOW / DELAY_UNTIL / DENY`及稳定reason。后台用户列表展示最终可达性和理由，不只显示是否有联系方式。

### 29.21 NotificationSchedule扫描

```text
SELECT due schedules
WHERE status='ACTIVE' AND next_fire_at <= now
ORDER BY next_fire_at,id
FOR UPDATE SKIP LOCKED
LIMIT 500
```

事务内推进next_fire_at并写Outbox，事务外由Relay执行。周期提醒不使用大量Celery ETA长期驻留Broker。schedule使用version避免修改/取消后的旧执行。

### 29.22 Celery任务契约

任务参数统一：

```json
{
  "resource_id": "01J...",
  "event_id": "01J...",
  "trace_id": "req-abc",
  "schema_version": 1
}
```

禁止传User对象、QuerySet、endpoint明文、渲染正文和Provider凭证。任务必须验证schema_version，未知版本进入死信而不是猜测执行。

### 29.23 Celery确认与超时

Provider任务建议late acknowledgement，仅在状态安全落库后ack；Worker进程丢失会重投，因此数据库lease和幂等必需。soft/hard time limit必须大于Provider连接/读取超时并留出状态落库时间，不能让Celery硬杀死发生在外部请求已提交但Attempt尚未记录的窗口。

### 29.24 ProviderEvent接收事务

```text
验证签名
  -> 解析为DTO
  -> external_event_id唯一插入ProviderEvent
  -> 锁定对应Attempt/Delivery
  -> 应用单调状态转换
  -> 更新Endpoint/Suppression/Preference
  -> 写审计与指标事件
  -> 返回2xx
```

重复事件返回2xx且不重复副作用。无法匹配的合法事件进入orphan事件表/状态，告警后人工关联，不能直接丢弃。

### 29.25 API权限和审计中间件

通知中心后台API统一注入actor、request_id、IP摘要和User-Agent摘要。模板发布、活动审批/取消、Delivery重试、短信回执查询、Suppression解除和敏感信息访问必须写NotificationAuditLog；审计写入失败时高风险写操作失败关闭。

### 29.26 分页响应

```json
{
  "items": [],
  "page": {
    "next_cursor": "base64url-signed-cursor",
    "has_more": false,
    "limit": 50
  }
}
```

cursor包含排序字段和ID并签名，防止用户篡改任意查询位置。报表导出走异步任务，不允许把limit无限放大。

### 29.27 统计口径

| 指标 | 分母/定义 |
| --- | --- |
| audience_count | AudienceSnapshot included |
| message_count | 实际逻辑收件人消息 |
| delivery_count | 渠道投递数量 |
| acceptance_rate | accepted Deliveries / submitted Deliveries |
| delivery_rate | delivered / accepted且具备回执能力的Deliveries |
| suppression_rate | suppressed / planned Deliveries |
| fallback_rate | 启用后续渠道的Messages / fallback Messages |

APNs没有运营商式最终送达回执时，不与短信/邮件送达率强行合并；全渠道总览分别展示accepted和可验证delivered。

### 29.28 聚合修复任务

定期从事实表重新计算Delivery、Message和Campaign摘要，发现差异时修复并记录audit/metric。修复任务不得改写Attempt和ProviderEvent事实，也不得触发再次发送。

### 29.29 数据清理任务

按topic保留策略游标删除/匿名化：先清敏感render context，再处理在线明细，最后保留无标识聚合。每批限制行数，避免长事务；记录扫描、删除、失败数量和最老待清数据年龄。

### 29.30 开发环境Provider

提供FakeAPNs/FakeSMS/FakeEmail Adapter：写入测试Attempt和可控ProviderEvent，不连接真实供应商。开发环境不得使用“配置缺失也视为成功”的逻辑；Fake Provider必须显式启用并在后台标记模拟数据。

### 29.31 契约测试基类

每个Provider必须通过相同测试：

```text
accepted映射
永久失败映射
临时失败映射
rate limit及retry_after
timeout_unknown
Provider ID/Request ID保存
敏感日志扫描
重复回执幂等
乱序回执单调状态
endpoint失效或suppression副作用
```

### 29.32 跨渠道端到端测试

1. parallel：APNs成功、Email硬退信、SMS送达，Message聚合为PARTIAL/COMPLETED按policy。
2. fallback：APNs坏token后解锁Email，Email delivered后SMS保持SKIPPED。
3. required：SMS失败时即使APNs成功，Message仍按required规则失败。
4. quiet hours：普通提醒延迟，OTP立即执行。
5. campaign取消：未提交Delivery取消，已accepted事实保留。
6. 用户退订发生在活动审批后：发送前重新检查并suppressed。
7. Outbox重复发布：只创建一份Message/Delivery。
8. Provider回执重复/乱序：不回退终态、不重复写Suppression。

### 29.33 技术验收补充

- [ ] Domain/Application不导入Django View、Celery或Provider SDK。
- [ ] Provider网络调用不发生在数据库锁事务内。
- [ ] Outbox Relay、Schedule扫描和受众物化支持SKIP LOCKED并发。
- [ ] 所有状态修改经过显式状态机。
- [ ] APNs token按topic/environment隔离并正确失效。
- [ ] 邮件硬退信、投诉、退订和RFC8058端点完成。
- [ ] Provider webhook验签、去重、乱序和orphan处理完成。
- [ ] Celery参数不包含敏感数据。
- [ ] 统计口径区分Audience、Message、Delivery、Attempt和ProviderEvent。
- [ ] Fake Provider显式启用且不会与生产记录混淆。
- [ ] 三渠道parallel/fallback/required端到端测试通过。
