# SparkService 通知业务类型与全渠道业务场景接入规范需求及详细设计工单

> 文档状态：待评审  
> 工单编号：`NOTIFICATION-CENTER-000003`  
> 优先级：P0  
> 更新时间：2026-07-13  
> 关联工单：`NOTIFICATION-CENTER-000001`、短信渠道专项工单  
> 涉及项目：`SparkService`、`SparkClient`  
> 建设原则：新通知体系直接采用本规范；不迁移旧通知数据

## 1. 决策摘要

通知中心增加一套受控、可注册、可版本化的“业务场景”能力。业务调用方不得再用自由文本 `topic_key`、标题、payload `type` 或模板名称表达业务含义。

一次通知必须明确回答四个问题：

1. `business_domain`：属于哪个稳定业务域，例如账号、医疗、会员权益。
2. `business_type`：通知的业务对象类型，例如认证、账号生命周期、医疗资源、Pro 试用。
3. `business_scene`：发生了什么具体业务事件，例如注册验证码、注销完成、试用申请通过。
4. `business_id`：关联哪一个业务实例，例如申请 ID、邀请 ID、医疗资源 ID；没有业务实体时可空。

`business_scene` 是服务端路由、模板、偏好、客户端动作、幂等、统计和审计的最小稳定键。首期格式为 `<domain>.<object>.<event>`，只允许小写字母、数字和下划线，以点分段，例如：

```text
account.auth.login_otp_requested
account.lifecycle.deactivation_completed
medical.resource.updated
membership.pro_trial.application_approved
```

## 2. 背景与当前问题

### 2.1 当前模型有字段但没有规范

现有 `NotificationIntent` 已包含 `topic_key`、`business_type`、`business_id`，但存在以下问题：

| 问题 | 当前表现 | 影响 |
| --- | --- | --- |
| `business_type` 无约束 | 可空自由字符串，没有注册表 | 同一场景产生多个拼法，无法统计和治理 |
| 缺少 `business_scene` | 只能依靠 `topic_key` 或 payload `type` 猜测动作 | 不能区分申请、通过、拒绝、到期等生命周期 |
| Topic 与 Scene 混用 | `medical.resource_changed` 既像订阅主题又像业务事件 | 用户偏好、模板选择和业务审计耦合 |
| payload 动作不统一 | 业务自行设置 `type` 和业务字段 | iOS 只能散落 switch，无法演进和兼容 |
| 调用入口过宽 | `send_to_user_sync` 接受自由标题、正文和 payload | 可绕过场景注册、模板和变量校验 |
| 场景覆盖不完整 | OTP、医疗更新、邀请、Pro 试用各自实现 | 通知记录无法按业务闭环查询 |
| 生命周期不成对 | 有“申请通过”，未必有“已申请/拒绝/到期/撤销” | 用户体验和后台审计不完整 |

### 2.2 术语边界

| 字段 | 稳定性 | 示例 | 职责 |
| --- | --- | --- | --- |
| `topic_key` | 产品策略级，低频变化 | `security.authentication` | 偏好、同意、静默、默认渠道策略 |
| `business_domain` | 组织业务域，极低频变化 | `account`、`medical` | 权限、归属、统计分组 |
| `business_type` | 业务对象类别，低频变化 | `auth`、`resource`、`pro_trial` | 后台筛选、对象聚合 |
| `business_scene` | 业务事件，追加式演进 | `medical.resource.updated` | 模板、路由、客户端动作、幂等 |
| `business_id` | 单次业务实例 | `trial_application:123` | 关联详情与排障 |
| `template_key/version` | 展现版本 | `pro_trial_approved/3` | 渠道内容渲染 |
| `client_action` | 客户端交互命令 | `open_medical_resource` | 点击后的安全导航 |

禁止把模板 key、客户端页面名、供应商模板 Code 当作业务场景。

## 3. 目标与非目标

### 3.1 目标

1. 找齐 SparkService 和 SparkClient 已有通知业务，并纳入统一场景目录。
2. 新增业务场景必须先注册，再接模板和渠道，不能直接调用 Provider。
3. 服务端能够按场景执行校验、幂等、路由、降级、偏好与审计。
4. 客户端以统一 Envelope 解析通知，以白名单动作导航，并支持未知场景安全降级。
5. 后台能按业务域、业务类型、业务场景、业务 ID 查询完整投递链路。
6. 场景目录可追加、可停用、不可随意改义或复用旧编码。

### 3.2 非目标

1. 本工单不迁移历史通知记录，也不为历史记录推断业务场景。
2. 本工单不把营销旅程或规则引擎作为首期范围。
3. 本工单不允许客户端根据任意服务端 URL 或类名直接跳转。
4. “用户已读”只适用于站内消息或客户端明确上报，不由 APNs/SMS/邮件受理状态推断。

## 4. 业务场景编码规范

### 4.1 编码结构

```text
business_scene = <domain>.<object>.<event>
```

规则：

1. 总长度不超过 128，正则 `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*){2,4}$`。
2. `domain` 与 Django App 不强绑定，避免代码目录调整导致协议变化。
3. `object` 使用稳定业务对象，不使用页面名称。
4. `event` 使用已经发生或需要执行的业务事实；建议过去式/明确动作，如 `approved`、`expiring`。
5. 已发布编码永久保留语义；改义时创建新编码，旧编码标记 `retired`。
6. 渠道不是场景的一部分；同一场景可路由到 APNs、短信、邮件、站内信。

### 4.2 业务类型编码

`business_type` 使用 `<domain>.<object>`，例如 `membership.pro_trial`。它是场景前缀的规范化投影，不允许调用方单独传入互相矛盾的值：

```text
business_scene: membership.pro_trial.application_approved
business_domain: membership
business_type: membership.pro_trial
```

服务端由场景注册表填充 `business_domain` 与 `business_type`，调用方只提交 `business_scene`。

### 4.3 业务 ID 规范

1. `business_id` 保存业务主键的稳定字符串，不含手机号、邮箱、验证码等敏感数据。
2. 多对象场景使用主对象 ID，其他关联放在受 schema 约束的 `references` 中。
3. 推荐同时保存 `business_reference = <resource_type>:<id>`，例如 `trial_application:123`。
4. 对登录 OTP 等没有持久业务对象的场景，使用服务端生成的 challenge ID，不使用验证码本身。

## 5. 场景注册中心

### 5.1 NotificationBusinessScene

新增模型：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `key` | varchar(128), unique | 完整场景编码 |
| `domain` | varchar(32), index | 业务域 |
| `business_type` | varchar(64), index | `<domain>.<object>` |
| `event_name` | varchar(64) | 事件名称 |
| `display_name` | varchar(128) | 后台中文名称 |
| `description` | varchar(500) | 触发条件和业务含义 |
| `topic` | FK | 偏好与策略主题 |
| `category` | enum | security/transactional/system/operational/marketing |
| `severity` | enum | info/success/warning/critical |
| `default_template_key` | varchar(128) | 默认业务模板 |
| `default_routing` | JSON | 默认渠道、并行/兜底、送达阈值 |
| `variable_schema` | JSON Schema | 模板变量契约 |
| `reference_schema` | JSON Schema | 业务引用契约 |
| `client_action_schema` | JSON Schema | 客户端动作参数契约 |
| `idempotency_strategy` | enum | event/subject/window/custom |
| `dedupe_window_seconds` | int | 时间窗去重 |
| `preference_policy` | enum | mandatory/opt_out/opt_in |
| `quiet_hour_policy` | enum | respect/bypass_critical/bypass |
| `retention_days` | int | 内容与事件保留策略 |
| `status` | enum | draft/active/deprecated/retired |
| `contract_version` | int | 场景契约版本 |
| `owner_team` | varchar(64) | 业务负责人 |
| `created_at/updated_at` | datetime | 审计时间 |

约束：`key` 的前两段必须与 `domain/business_type` 一致；`active` 场景必须绑定已发布模板或明确声明无内容渠道；发布后关键语义字段不可直接修改。

### 5.2 为什么 Topic 不能替代 Scene

Topic 是用户订阅策略。例如注册 OTP、登录 OTP、换绑 OTP 都可属于 `security.authentication`，但三者的模板变量、风控、幂等和客户端行为不同。反过来，同一个 `medical.resource.updated` 场景可根据资源类型使用不同模板变体，但仍是同一业务事件。

| `system.app_version.update_available` | 新版本可用 | 版本发布且满足用户条件 | APNs/InApp | 扩展 |
| `system.app_version.force_update_required` | 必须升级 | 客户端版本低于强制版本 | InApp/APNs | 扩展 |
| `system.announcement.published` | 系统公告 | 后台活动批准并发布 | APNs/Email/InApp | 后台活动归一 |
| `operation.campaign.published` | 运营活动 | 运营活动批准并发送 | 配置 | 现有后台活动 |

### 6.7 候选场景评审矩阵

不能把每次 CRUD 都自动变成用户通知。以下代码中已有相应业务能力，但是否通知、通知谁和打扰强度必须由产品与业务负责人逐项确认：

| 业务事件候选 | 建议场景 | 默认建议 | 待确认项 |
| --- | --- | --- | --- |
| 成员角色改变 | `medical.member.role_changed` | 仅受影响成员，APNs + InApp | 管理者是否同步收到 |
| 成员权限改变 | `medical.member.permission_changed` | 仅权限被修改者，APNs + InApp | 降权是否提升为 warning |
| 成员被移除 | `medical.member.removed` | 被移除者与所有者，APNs + InApp | 是否邮件留证 |
| 所有者转移 | `medical.member.ownership_transferred` | 双方，APNs + Email + InApp | 是否强制不可退订 |
| 分享票据接受/撤销 | `medical.share.accepted/revoked` | 发起人，APNs + InApp | 是否仅首次接受通知 |
| 报告生成完成 | `medical.report.ready` | 资源所有者/授权管理者，APNs + InApp | 敏感摘要范围 |
| 异常指标识别 | `medical.exam.abnormal_detected` | 默认只站内，谨慎推送 | 医疗风险文案与免责声明 |
| 随访到期 | `medical.follow_up.due` | APNs + InApp | 提醒频次与关闭权限 |
| 任务被分配/改变/取消 | `task.lifecycle.assigned/changed/cancelled` | InApp，必要时 APNs | 哪些变化值得打扰 |
| 科普文章发布/推荐 | `content.article.published/recommended` | opt-in 运营通知 | 频控、画像依据、退订 |
| 系统维护 | `system.maintenance.scheduled/started/completed` | InApp + 必要渠道 | 影响范围和强度 |

每个候选场景启用前必须填写：触发事实、收件人规则、默认渠道、级别、可退订性、静默策略、模板、客户端动作、幂等键、过期时间、数据敏感等级和负责人。

## 7. 服务端统一事件契约

### 7.1 业务模块提交 DTO

业务模块只能调用 `NotificationCommandBus.publish()` 或写入同事务 Outbox：

```json
{
  "event_id": "01J...ULID",
  "business_scene": "membership.pro_trial.application_approved",
  "subject": {"type": "user", "id": "123"},
  "business_reference": {"type": "trial_application", "id": "456"},
  "occurred_at": "2026-07-13T10:20:30+08:00",
  "actor": {"type": "admin", "id": "9"},
  "variables": {
    "display_name": "用户",
    "expires_at": "2026-07-20T10:20:30+08:00"
  },
  "client_action": {
    "type": "open_pro_trial",
    "params": {"application_id": "456"}
  },
  "trace_id": "request-trace-id",
  "idempotency_key": "membership.pro_trial.application_approved:456:v1"
}
```

### 7.2 校验顺序

1. 场景必须存在且为 `active`。
2. subject、reference、variables、client_action 通过场景 JSON Schema。
3. 服务端从注册表派生 domain、business_type、topic、模板和默认路由。
4. 校验业务调用方是否拥有该 domain/scene 的发布权限。
5. 在业务事务内写 Outbox；唯一键拦截重复事件。
6. 异步消费者创建 Intent、RecipientMessage、ChannelDelivery。
7. 发送前再次校验 endpoint、偏好、抑制、静默、过期时间。

### 7.3 幂等键

| 类型 | 规则示例 |
| --- | --- |
| 状态变更 | `<scene>:<business_id>:<state_version>` |
| OTP | `<scene>:<challenge_id>:<send_generation>` |
| 定时提醒 | `<scene>:<occurrence_id>` |
| 资源更新聚合 | `<scene>:<resource_type>:<resource_id>:<revision>` |
| 后台活动 | `<scene>:<campaign_id>:<recipient_id>` |

数据库必须同时约束 Outbox event_id、Intent idempotency_key 和每个 recipient 的消息幂等键。Celery 重试不能生成新业务事件 ID。

### 7.4 事务边界

```python
with transaction.atomic():
    application = approve_trial(...)
    notification_publisher.enqueue_in_transaction(
        scene="membership.pro_trial.application_approved",
        subject=UserRef(application.user_id),
        business_ref=BusinessRef("trial_application", application.id),
        variables={"expires_at": application.expires_at.isoformat()},
        idempotency_key=f"trial-approved:{application.id}:{application.version}",
    )
```

禁止在数据库事务中同步调用 APNs、阿里云短信或 SMTP。Worker 只消费持久化 Outbox，并使用短任务扇出。

## 8. NotificationIntent 数据模型调整

在现有模型基础上增加并收紧：

| 字段 | 调整 |
| --- | --- |
| `business_scene` | 新增 varchar(128)、索引、FK/逻辑关联 Scene.key；新数据非空 |
| `business_domain` | 新增 varchar(32)、索引，由注册表快照生成 |
| `business_type` | 改为非空 varchar(64)，由注册表生成 |
| `business_id` | 保留，标准化为主业务对象 ID |
| `business_reference_type` | 新增 varchar(64)、索引 |
| `scene_contract_version` | 新增 positive int，保存发送时契约版本 |
| `scene_snapshot` | 新增 JSON，保存名称、策略的非敏感最小快照 |
| `client_action_ciphertext` | 新增加密字段；普通索引不存参数全文 |
| `event_id` | 新增唯一 ULID/UUID，区别于 Intent 主键 |
| `occurred_at` | 新增业务事实发生时间，区别于创建时间 |
| `actor_type/actor_id` | 新增，可空，支持审计 |

索引建议：

```text
(business_domain, created_at DESC)
(business_type, created_at DESC)
(business_scene, created_at DESC)
(business_reference_type, business_id, created_at DESC)
(subject_type, subject_id, created_at DESC)
UNIQUE(event_id)
UNIQUE(idempotency_key)
```

不将 Scene 外键设置为级联删除。注册场景只能退役，不能物理删除已经被 Intent 引用的编码。

## 9. 客户端统一通知协议

### 9.1 Notification Envelope

APNs 与站内信共用逻辑 Envelope；短信、邮件中的安全链接也映射到同一 action：

```json
{
  "schema_version": 1,
  "notification_id": "01J...",
  "business_scene": "medical.resource.updated",
  "business_type": "medical.resource",
  "occurred_at": "2026-07-13T10:20:30+08:00",
  "action": {
    "type": "open_medical_resource",
    "params": {
      "member_id": "12",
      "resource_type": "medication_plan",
      "resource_id": "98"
    }
  },
  "presentation": {
    "thread_key": "member:12:medical",
    "interruption_level": "active"
  }
}
```

约束：APNs custom data 控制在安全余量内；不携带访问令牌、手机号、邮箱、验证码和医疗详情；所有资源打开后重新鉴权。

### 9.2 客户端类型

SparkClient 新增独立基础模块或放入通知基础设施层：

```swift
struct NotificationEnvelope: Decodable, Sendable {
    let schemaVersion: Int
    let notificationID: String
    let businessScene: String
    let businessType: String
    let occurredAt: Date?
    let action: NotificationAction?
}

enum NotificationAction: Sendable {
    case openNotificationCenter
    case openProTrial(applicationID: String?)
    case openMember(memberID: String)
    case openMedicalResource(memberID: String, resourceType: String, resourceID: String)
    case openMedicationPlan(memberID: String, planID: String)
    case openTask(taskID: String)
    case openAppUpdate
    case unknown(type: String)
}
```

不要把 `business_scene` 生成为封闭 Swift enum；服务端可新增场景，旧客户端必须能解码未知字符串。`action.type` 使用白名单 enum 并提供 `.unknown` 降级。

### 9.3 统一处理流程

1. App 收到远程通知，先解码 Envelope；解码失败记录脱敏遥测并打开通知中心。
2. 校验 `schema_version`。高于客户端支持版本时只展示，不执行未知导航。
3. 前台收到通知时刷新通知中心数据，不直接假定当前页面有相应状态。
4. 用户点击后由 `NotificationActionRouter` 统一导航。
5. Router 检查登录态、成员权限、资源存在性；失败时给出可理解提示并回退通知中心。
6. 上报 `received/opened/action_succeeded/action_failed`，使用 notification_id 去重。
7. 冷启动动作进入统一 Pending Route，完成登录和应用初始化后执行一次。

### 9.4 客户端兼容矩阵

| 情况 | 行为 |
| --- | --- |
| 已知 scene + 已知 action | 正常展示并导航 |
| 未知 scene + 已知 action | 可导航，同时记录未知场景 |
| 已知 scene + 未知 action | 展示通知，点击进入通知中心 |
| schema_version 过高 | 不执行 action，进入通知中心 |
| 资源已删除/无权限 | 提示“内容已不可用”，不得泄露存在性细节 |
| 未登录 | 保存一次性 pending action，登录后重新鉴权执行 |

## 13. Celery 与 Outbox 设计

新增队列建议：

```text
notification.outbox.relay
notification.intent.expand
notification.delivery.apns
notification.delivery.sms
notification.delivery.email
notification.receipt.poll
notification.lifecycle
```

1. Relay 使用 `select_for_update(skip_locked)` 小批量取 Outbox。
2. 任务参数只传 ID，不传手机号、正文、验证码和整个业务 payload。
3. 每个任务先检查数据库终态和幂等记录，再产生副作用。
4. 重试采用指数退避 + jitter，并按 Provider 错误分类决定是否重试。
5. OTP 过期后直接标记 expired，不发送迟到验证码。
6. 场景的定时生命周期（试用到期、邀请到期）由业务事实任务产生事件，不由通知中心修改业务状态。
7. 旧通知 Celery 任务停止生产后，等待队列清空；确认无在途任务，再移除 beat 配置和 worker 路由。

## 14. 安全、隐私与合规

1. 业务场景和业务 ID不应包含个人信息。
2. 医疗资源 payload 只含不敏感定位键；服务端详情接口再次做成员权限校验。
3. OTP 明文只在受控短生命周期上下文中使用，不进入普通 NotificationMessage body、日志和后台详情。
4. 客户端 action 参数不能是任意 URL、任意类名或脚本。
5. 后台敏感信息访问需单独权限、二次确认和审计。
6. 营销场景必须 opt-in/opt-out 合规；安全和必要事务通知按产品规则设置 mandatory。
7. 所有客户端事件接口防重放、限流，并校验 notification 与当前用户归属。

## 15. 可观测性与指标

所有指标至少带低基数标签 `business_domain/business_type/business_scene/channel/provider/status`；不得把 user_id、business_id、手机号作为指标标签。

关键指标：

1. 场景事件发布量、Outbox 积压时间、Intent 创建失败率。
2. 各场景 recipient 数、抑制率、无可用端点率。
3. 各渠道受理率、送达率、终态失败率、P50/P95/P99 延迟。
4. 客户端 received/opened/action success 转化漏斗。
5. 未知 scene、未知 action、schema 解码失败数量。
6. 场景无已发布模板、模板变量校验失败、重复事件拦截量。

日志统一包含 `event_id/intent_id/recipient_message_id/delivery_id/trace_id/business_scene`，敏感值只输出掩码或 HMAC。

## 16. 实施阶段

### 阶段 A：契约与基础模型（P0）

1. 建 Scene 注册表、字段约束、种子目录和后台只读页。
2. 为 Intent 增加 scene/domain/type/event/reference 字段和索引。
3. 实现发布 DTO、JSON Schema 校验、Outbox 与幂等。
4. 建立客户端 Envelope、ActionRouter、未知场景降级和埋点。

### 阶段 B：安全与核心事务（P0）

1. 注册/登录/绑定/换绑 OTP 统一接入。
2. Pro 试用申请、通过、拒绝、发放、回收接入。
3. 邮件 OTP 移除 Provider 直调，保证全部可查。

### 阶段 C：医疗与提醒（P0/P1）

1. 医疗资源变化、成员邀请、绑定权限变化接入。
2. 用药计划、本地提醒和服务端提醒统一 occurrence_id。
3. 通用任务与 AI 长任务接入。

### 阶段 D：后台与旧入口下线（P1）

1. 后台增加 Scene、Intent、全链路详情。
2. 禁止自由业务 payload 和同步发送入口。
3. 清空旧通知队列，删除旧 beat/worker 路由和遗留数据表。
4. 增加 CI 静态检查，禁止业务模块 import Provider 或调用 deprecated 方法。

## 17. 测试设计

### 17.1 服务端

1. Scene 编码、状态、契约版本与不可变规则测试。
2. 每个 active 场景的 variables/reference/action 合约测试。

1. 已知、未知 scene/action/schema version 解码测试。
2. 前台、后台、冷启动、未登录四种打开路径测试。
3. 成员切换、资源删除、权限撤销、网络失败的降级测试。
4. received/opened/action 事件去重与离线补报测试。

### 17.3 契约测试

服务端导出 active Scene Catalog JSON，SparkClient CI 用固定 schema 验证：

1. 所有 `client_action.type` 均在当前客户端支持集或显式声明最低版本。
2. action 必填参数与客户端 Decoder 一致。

## 18. 验收标准

1. 新通知 Intent 的 `business_scene/business_domain/business_type` 填充率为 100%。
2. 所有 active 场景可在后台查看负责人、模板、路由、schema 和版本。
3. 注册、登录、注销、医疗更新、Pro 申请/通过/拒绝/发放/到期均有明确场景。
4. 手机与邮箱 OTP、匿名邀请、后台审批通知全部进入统一台账。
5. 业务代码不再直接调用 APNs/SMS/Email Provider。
6. Celery 重投不会造成重复短信、邮件或推送。
