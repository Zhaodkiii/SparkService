# SparkService 会员试用通知全渠道并发改为顺序降级修复工单

创建日期：2026-07-16  
关联模块：通知中心、会员试用、Pro 权益、APNs、邮件、短信、后台管理系统  
优先级：P0  
修复类型：通知路由策略错误 / 多渠道重复触达 / 会员通知体验问题

## 1. 背景

后台通知记录中，同一次会员试用通知出现多渠道同时投递：

```text
email  会员试用  apple_000920.7dfc34cca  149***@qq.com  已受理  已发放 Pro 试用权限  1/1  2026-07-16 17:08:51
81     apns   会员试用  apple_000920.7dfc34cca  ***             已受理  已发放 Pro 试用权限  1/1  2026-07-16 17:08:51
```

同一用户、同一业务事件、同一时间既发了 Email，又发了 APNs。

这不符合会员试用通知的预期策略。会员通知不应该默认全渠道触达，而应该按优先级顺序尝试：

```text
APNs -> Email -> 手机短信
```

只有当前一个渠道失败、不可达或被抑制时，才进入下一个渠道。

## 2. 问题现象

### 2.1 后台记录表现

1. 同一条会员试用事件产生多条渠道通知记录。
2. APNs 与 Email 在同一时间均显示“已受理”。
3. 用户可能同时收到 App 推送和邮件，造成重复打扰。

### 2.2 业务期望

会员试用通知属于事务性权益通知，但不是“所有渠道都必须通知一次”。

正确策略应为：

1. 用户有可用 APNs 设备且 APNs 提交成功，则停止。
2. APNs 失败、无 token、token 无效、用户关闭推送或被抑制时，再尝试 Email。
3. Email 失败、无邮箱、退信抑制或不可达时，再尝试手机短信。
4. 三个渠道都失败后，本次会员通知才算触达失败。

## 3. 根因分析

### 3.1 会员试用场景默认路由被自动生成为 parallel

当前 `notification_center/business_scenes.py` 中，场景目录默认生成路由：

```python
"default_routing": {
    "mode": "parallel",
    "steps": [{"channel": channel, "required": False} for channel in self.channels],
}
```

会员试用相关场景配置了多个渠道，例如：

```python
_scene("membership.pro_trial.application_approved", "Pro 试用申请通过", channels=("apns", "in_app", "email"))
_scene("membership.pro_trial.manually_granted", "系统发放试用", channels=("apns", "in_app", "email"))
```

因此这些场景的默认语义变成了“并行多渠道发送”，而不是“按优先级降级发送”。

补充约束：`membership.pro_trial.expiring`（试用即将到期）和 `membership.pro_trial.revoked`（试用已收回）本阶段不触发用户通知，不应纳入本次顺序降级发送链路。

### 3.2 执行层已经支持 fallback，但会员场景没有使用

`notification_center/services.py` 中已有路由执行逻辑：

```python
if mode == "fallback" and NotificationCenterService._delivery_meets_threshold(
    delivery,
    step.get("success_threshold", "provider_accepted"),
):
    break
```

也就是说，只要路由配置为：

```json
{
  "mode": "fallback",
  "steps": [
    {"channel": "apns", "route_order": 1, "required": false, "success_threshold": "provider_accepted"},
    {"channel": "email", "route_order": 2, "required": false, "success_threshold": "provider_accepted"},
    {"channel": "sms", "route_order": 3, "required": false, "success_threshold": "provider_accepted"}
  ]
}
```

执行层就可以在 APNs 成功后停止，不再继续 Email 和短信。

当前问题不是完全缺能力，而是会员场景默认路由策略配置错误。

### 3.3 `in_app` 不应参与外部触达降级链路

会员试用通知里，`in_app` 更适合作为站内消息或通知中心 inbox 记录，不应该和 APNs、Email、SMS 放在同一个外部触达链路里判断成功。

如果 `in_app` 被放入 fallback 链路，可能出现：

1. 站内消息创建成功后直接停止，导致用户没有收到 APNs/Email/SMS。
2. 或者 parallel 模式下站内消息与外部渠道一起产生，进一步扩大“全渠道”问题。

因此会员外部通知链路应只包含：

```text
apns -> email -> sms
```

站内消息如需保留，应作为独立 inbox 记录，不参与“是否已触达用户”的渠道降级判断。

## 4. 影响范围

1. 会员试用通过、系统发放试用等场景可能重复触达用户。
2. 邮件、短信等成本渠道被不必要触发。
3. 后台统计会把同一业务事件记录为多渠道成功，影响真实触达率分析。
4. 用户体验变差：同一权益变化被 App 推送和邮件重复提醒。
5. 如果未来加入短信到会员场景，在 parallel 策略下会进一步造成短信费用浪费。
6. `expiring`、`revoked` 如果误触发，会制造不必要的权益焦虑或误解，本阶段应保持不通知。

## 5. 修复目标

1. 会员试用通知默认不再使用全渠道并发。
2. 会员试用外部触达按固定顺序降级：

```text
apns -> email -> sms
```

3. 第一个渠道提交成功或达到配置的成功阈值后，不再触发后续渠道。
4. 当前渠道失败、不可达、被抑制或没有可用 endpoint 时，才进入下一个渠道。
5. 后台通知记录中，同一会员事件默认只应产生一个成功外部渠道记录。
6. 三个渠道都失败时，才能标记该收件人的会员通知触达失败。

## 6. 修复方案

### 6.1 为会员场景新增显式 fallback 路由配置

不要继续让会员场景走 `SceneDefinition.defaults()` 的通用 parallel 默认值。

建议为会员试用相关场景显式配置：

```json
{
  "mode": "fallback",
  "steps": [
    {
      "channel": "apns",
      "route_order": 1,
      "required": false,
      "success_threshold": "provider_accepted"
    },
    {
      "channel": "email",
      "route_order": 2,
      "required": false,
      "success_threshold": "provider_accepted"
    },
    {
      "channel": "sms",
      "route_order": 3,
      "required": false,
      "success_threshold": "provider_accepted"
    }
  ]
}
```

首批至少覆盖：

| 场景 | 当前问题 | 修复后 |
|---|---|---|
| `membership.pro_trial.application_approved` | APNs/InApp/Email parallel | APNs -> Email -> SMS fallback |
| `membership.pro_trial.manually_granted` | 中文名称为“管理员发放试用”，且 APNs/InApp/Email parallel | 改为“系统发放试用”，APNs -> Email -> SMS fallback |

可按产品确认继续覆盖：

- `membership.pro_trial.application_submitted`
- `membership.pro_trial.application_rejected`
- `membership.pro_trial.activated`
- `membership.pro_trial.expired`
- `membership.pro.entitlement_changed`

明确不触发通知：

| 场景 | 处理方式 | 原因 |
|---|---|---|
| `membership.pro_trial.expiring` | 不创建用户通知，不进入 APNs/Email/SMS 路由 | 本阶段不做试用即将到期提醒 |
| `membership.pro_trial.revoked` | 不创建用户通知，不进入 APNs/Email/SMS 路由 | 本阶段不对用户发送试用收回通知 |

### 6.2 更新场景目录生成逻辑，支持按场景声明 routing

建议扩展 `SceneDefinition`，允许单个场景传入 `default_routing` 或 `routing_mode`。

示例：

```python
MEMBERSHIP_FALLBACK_ROUTING = {
    "mode": "fallback",
    "steps": [
        {"channel": "apns", "route_order": 1, "required": False, "success_threshold": "provider_accepted"},
        {"channel": "email", "route_order": 2, "required": False, "success_threshold": "provider_accepted"},
        {"channel": "sms", "route_order": 3, "required": False, "success_threshold": "provider_accepted"},
    ],
}
```

会员场景使用：

```python
_scene(
    "membership.pro_trial.manually_granted",
    "系统发放试用",
    severity=SUCCESS,
    channels=("apns", "email", "sms"),
    default_routing=MEMBERSHIP_FALLBACK_ROUTING,
)
```

注意：这里的 `channels` 应与外部触达链路一致，不再把 `in_app` 混入同一条路由。

### 6.3 修复已有数据库中的场景配置

仅修改代码目录不足以修复已经入库的 `NotificationBusinessScene.default_routing`。

需要提供数据迁移或管理命令，把已存在会员场景更新为 fallback：

```python
NotificationBusinessScene.objects.filter(
    key__in=[
        "membership.pro_trial.application_approved",
        "membership.pro_trial.manually_granted",
    ]
).update(default_routing=MEMBERSHIP_FALLBACK_ROUTING)
```

如果已有模板、后台配置或缓存读取了旧路由，也需要同步刷新。

同时需要将 `membership.pro_trial.manually_granted` 的 `display_name` 更新为“系统发放试用”。

`membership.pro_trial.expiring` 和 `membership.pro_trial.revoked` 不更新为 fallback 路由，应标记为本阶段不触发用户通知；如果系统中已有自动任务调用这两个场景，需要停用调用入口或在业务层直接跳过通知创建。

### 6.4 调用方不能再只传单渠道覆盖默认策略

当前 `ai_config/tasks.py` 中自动审批通过通知调用：

```python
NotificationCenterService.send_to_user_sync(
    channels=[NotificationMessage.Channel.APNS],
    business_scene="membership.pro_trial.application_approved",
    ...
)
```

这类调用如果只传 `channels=[apns]`，会导致 APNs 失败后没有机会降级到 Email/SMS。

修复后，会员业务调用应交给场景路由决定渠道：

```python
NotificationCenterService.send_to_user_sync(
    channels=[NotificationMessage.Channel.APNS, NotificationMessage.Channel.EMAIL, NotificationMessage.Channel.SMS],
    business_scene="membership.pro_trial.application_approved",
    ...
)
```

或者进一步优化 `send_to_user_sync`：当传入 `business_scene` 且未显式传 `routing` 时，以 `scene.default_routing.steps` 作为渠道来源，而不是只使用调用方的 `channels`。

推荐后者，避免每个业务调用方重复维护渠道顺序。

### 6.5 明确失败后才进入下一渠道

执行层需要确认以下状态会进入下一渠道：

| 状态 | 是否进入下一渠道 |
|---|---|
| `accepted` | 否 |
| `delivered` | 否 |
| `submit_unknown` | 建议否，等待回执或重试，不立即降级 |
| `submit_failed` | 是 |
| `delivery_failed` | 是 |
| `cancelled` | 是 |
| `expired` | 是 |
| 无可用 endpoint | 是 |
| 用户退订/抑制 | 是 |

如果当前实现中“无可用 endpoint”没有产生 `ChannelDelivery`，需要补一条 skipped/cancelled delivery，或者让 fallback 执行器把该渠道视为失败并继续下一步。

### 6.6 成功阈值建议

会员权益通知默认使用：

```text
success_threshold = provider_accepted
```

理由：

1. APNs 200 只能表示 Apple 接受，不代表用户已读，但足以表示系统已完成一次外部触达尝试。
2. 邮件供应商受理也不等于最终阅读，不应阻塞后续业务。
3. 短信提交成功通常也只能代表供应商受理，最终回执可能延迟。

如果某个会员场景未来要求强保证，可单独改成 `provider_delivered`，但不建议默认使用，避免等待回执导致链路过慢。

### 6.7 业务流程设计

#### 6.7.1 Pro 试用申请通过

触发场景：

```text
membership.pro_trial.application_approved
```

业务时点：

1. 用户提交 Pro 试用申请。
2. 系统审核或后台审批将申请状态更新为 `ACTIVE`。
3. Pro 权益写入或更新成功。
4. 业务事务提交后创建通知意图。
5. 通知中心按 `apns -> email -> sms` 顺序尝试外部触达。

建议流程：

```text
TrialApplication 状态更新
  -> Pro 权益生效
  -> transaction.on_commit
  -> create NotificationIntent
  -> create NotificationRecipientMessage
  -> execute fallback route
  -> APNs 成功则结束
  -> APNs 失败则 Email
  -> Email 失败则 SMS
  -> 更新 recipient_message / intent 终态
```

幂等键建议：

```text
membership.pro_trial.application_approved:{trial_application_id}
```

同一个申请 ID 只能产生一次申请通过通知。重复审批、任务重试、接口重放都应该复用同一条 `NotificationIntent`，不能再次触发渠道发送。

#### 6.7.2 系统发放试用

触发场景：

```text
membership.pro_trial.manually_granted
```

展示文案：

```text
系统发放试用
```

业务时点：

1. 系统基于规则、运营配置、补偿任务或后台动作发放 Pro 试用。
2. 对用户展示时统一表达为“系统发放试用”，不暴露“管理员”概念。
3. 权益写入成功后触发通知。
4. 通知中心按同样的 fallback 路由触达。

幂等键建议：

```text
membership.pro_trial.manually_granted:{grant_record_id}
```

如果当前没有独立的发放记录 ID，短期可使用：

```text
membership.pro_trial.manually_granted:user:{user_id}:trial:{trial_id}:started_at:{yyyyMMddHHmmss}
```

中长期建议补充稳定的权益发放流水表，避免只用 user ID 导致同一用户多次试用无法区分。

#### 6.7.3 不触发通知场景

以下场景本阶段不创建用户通知：

```text
membership.pro_trial.expiring
membership.pro_trial.revoked
```

业务处理规则：

1. 如果已有定时任务扫描即将到期试用，不调用通知中心。
2. 如果已有后台收回试用能力，收回动作只更新权益状态和审计日志，不发用户通知。
3. 如果未来产品要求开启提醒，必须新开工单确认触达策略、文案、频率、是否允许短信。

### 6.8 技术流程设计

#### 6.8.1 场景配置读取

会员通知入口调用 `send_to_user_sync` 时，必须保证：

1. 传入 `business_scene`。
2. 未显式传入 `routing` 时，从 `NotificationBusinessScene.default_routing` 读取路由。
3. 渠道列表优先从 `routing.steps` 推导，而不是由调用方手写单渠道列表决定。

推荐解析顺序：

```python
scene = NotificationCenterService.ensure_business_scene(business_scene, topic_key=topic_key)
routing = explicit_routing or payload.get("_routing") or scene.default_routing
steps = normalize_route_steps(routing)
channels = [step["channel"] for step in steps]
```

如果调用方传入的 `channels` 与 `routing.steps` 不一致，建议以 `routing.steps` 为准，并记录 warning 日志：

```text
notification.route.channels_overridden scene=membership.pro_trial.application_approved input_channels=apns resolved_channels=apns,email,sms
```

这样可以修复 `ai_config/tasks.py` 当前只传 `channels=[APNS]` 导致无法降级的问题。

#### 6.8.2 fallback 执行器伪代码

建议将当前内联循环整理为清晰的内部方法：

```python
def _execute_fallback_route(*, recipient_message, user, steps, content, context):
    for step in sorted(steps, key=lambda x: x["route_order"]):
        channel = step["channel"]
        delivery = ensure_delivery_row(
            recipient_message=recipient_message,
            channel=channel,
            route_order=step["route_order"],
            required=False,
            success_threshold=step["success_threshold"],
        )

        if not endpoint_available(user=user, channel=channel):
            mark_delivery_cancelled(delivery, reason="endpoint_unavailable")
            continue

        if is_suppressed(user=user, channel=channel, topic_key=context.topic_key):
            mark_delivery_cancelled(delivery, reason="suppressed")
            continue

        result = send_channel(channel=channel, user=user, content=content, context=context)
        update_delivery_from_result(delivery, result)

        if meets_threshold(delivery, step["success_threshold"]):
            mark_recipient_accepted(recipient_message)
            return delivery

        if delivery.status in {"submit_unknown", "processing"}:
            mark_recipient_processing(recipient_message)
            return delivery

    mark_recipient_failed(recipient_message, reason="all_channels_failed")
    return None
```

关键点：

1. fallback 不是“只发第一个渠道”，而是“第一个成功后停止”。
2. 无可用 endpoint、退订、抑制、Provider 明确失败都要继续下一渠道。
3. `submit_unknown` 不应立即降级，避免 APNs/Email/SMS 供应商超时后又继续发送，造成重复触达。
4. 每一步都要落 `ChannelDelivery`，否则后台无法解释为什么跳到下一个渠道。

#### 6.8.3 无可用 endpoint 的落库策略

如果用户没有某渠道可达地址，不应静默跳过。建议创建投递记录：

| 字段 | 建议值 |
|---|---|
| `ChannelDelivery.channel` | 当前渠道 |
| `status` | `cancelled` |
| `error_code` | `endpoint_unavailable` |
| `error_message` | `apns token missing` / `email missing` / `phone missing` |
| `route_order` | 当前顺序 |
| `required` | `false` |
| `success_threshold` | `provider_accepted` |

这样后台可以展示：

```text
APNs 跳过：无可用设备 token
Email 已受理
SMS 未执行：前序 Email 已成功
```

对于“前序已成功所以未执行”的后续渠道，不建议创建 `ChannelDelivery`，避免后台误解为失败；可以在详情页根据路由策略展示“未执行，原因：前序渠道已成功”。

#### 6.8.4 状态流转

单收件人状态建议：

```text
created
  -> processing
  -> accepted      # 任一渠道达到 provider_accepted
  -> delivered     # 任一渠道后续确认 delivered，可选推进
  -> failed        # 所有渠道失败、跳过或不可达
```

渠道投递状态建议：

```text
created
  -> processing
  -> accepted / delivered
  -> submit_failed / delivery_failed / submit_unknown / cancelled
```

会员 fallback 场景下，`NotificationRecipientMessage` 的成功判定是：

```text
任一已执行渠道满足该 step.success_threshold
```

失败判定是：

```text
所有可尝试 step 均未满足 success_threshold，且不存在 processing/submit_unknown
```

### 6.9 代码改造点

#### 6.9.1 `notification_center/business_scenes.py`

改造目标：

1. `SceneDefinition` 增加可选字段 `default_routing`。
2. `defaults()` 优先使用显式 `default_routing`。
3. 会员可通知场景使用 `MEMBERSHIP_FALLBACK_ROUTING`。
4. `membership.pro_trial.manually_granted` 的 `display_name` 改成“系统发放试用”。
5. `expiring/revoked` 保留在场景目录时，应加注释说明本阶段不由业务触发通知；如已有注册表同步机制，不应误把它们变成可发送场景。

示例结构：

```python
@dataclass(frozen=True)
class SceneDefinition:
    key: str
    display_name: str
    channels: tuple[str, ...] = ("in_app",)
    default_routing: dict[str, Any] | None = None

    def defaults(self, topic=None):
        routing = self.default_routing or {
            "mode": "parallel",
            "steps": [{"channel": channel, "required": False} for channel in self.channels],
        }
        return {
            ...
            "default_routing": routing,
            ...
        }
```

#### 6.9.2 `notification_center/services.py`

改造目标：

1. `_route_steps` 支持只从 routing 推导步骤。
2. `send_to_user_sync` 在有 `business_scene` 时优先使用 `scene.default_routing`。
3. 如果 `routing.steps` 存在，使用 steps 推导渠道，不被调用方单渠道覆盖。
4. fallback 循环中对“无 endpoint / 被抑制”创建可解释的 cancelled delivery。
5. `submit_unknown` 状态不继续降级，避免重复触达。
6. `_recipient_route_succeeded` 继续按 mode 判断，fallback 下任一 step 成功即可。

建议新增或整理以下内部方法：

```python
_resolve_scene_routing(...)
_route_channels_from_steps(...)
_ensure_cancelled_delivery(...)
_execute_route_step(...)
_should_continue_fallback(...)
```

短期也可以先在 `send_to_user_sync` 内完成最小改造，但必须补测试覆盖。

#### 6.9.4 后台接口与展示

1. 列表默认展示实际执行的渠道记录。
2. 详情页展示路由策略：

3. 如果 APNs 失败后 Email 成功，展示：

### 6.10 数据迁移与存量修复

需要新增数据迁移或一次性管理命令，至少完成：

1. 更新 `membership.pro_trial.application_approved.default_routing` 为 fallback。
2. 更新 `membership.pro_trial.manually_granted.default_routing` 为 fallback。
3. 更新 `membership.pro_trial.manually_granted.display_name` 为“系统发放试用”。
4. 不把 `membership.pro_trial.expiring`、`membership.pro_trial.revoked` 更新为 fallback。
5. 如数据库里存在这两个场景的定时触发配置、Campaign 草稿或系统任务配置，需要停用。

迁移示例：

```python
def forwards(apps, schema_editor):
    NotificationBusinessScene = apps.get_model("notification_center", "NotificationBusinessScene")
    routing = {
        "mode": "fallback",
        "steps": [
            {"channel": "apns", "route_order": 1, "required": False, "success_threshold": "provider_accepted"},
            {"channel": "email", "route_order": 2, "required": False, "success_threshold": "provider_accepted"},
            {"channel": "sms", "route_order": 3, "required": False, "success_threshold": "provider_accepted"},
        ],
    }
    NotificationBusinessScene.objects.filter(
        key__in=[
            "membership.pro_trial.application_approved",
            "membership.pro_trial.manually_granted",
        ]
    ).update(default_routing=routing)
    NotificationBusinessScene.objects.filter(
        key="membership.pro_trial.manually_granted"
    ).update(display_name="系统发放试用")
```

回滚策略：

1. 不建议自动回滚到 parallel，避免再次重复触达。
2. 如需回滚代码，应保留数据库 fallback 配置。
3. 如需临时停发会员通知，应在业务调用入口加开关，而不是改回 parallel。

### 6.11 幂等、并发与重试

#### 6.11.1 幂等

会员通知必须以业务实例为幂等边界：

| 场景 | 幂等键 |
|---|---|
| 申请通过 | `membership.pro_trial.application_approved:{trial_application_id}` |
| 系统发放 | `membership.pro_trial.manually_granted:{grant_record_id}` |

不得使用纯 `request_id` 作为唯一幂等来源，因为后台重试、Celery 重试、接口重放可能带来不同 request_id。

#### 6.11.2 并发

同一用户同一权益实例可能由多个任务同时触发。创建通知时应：

1. 对 `NotificationIntent.idempotency_key` 建唯一约束或依赖已有唯一索引。
2. 使用 `get_or_create`。
3. 对同一 `NotificationRecipientMessage` 使用稳定唯一条件。
4. 渠道投递使用 `(message, channel)` 或等价条件避免重复创建。

#### 6.11.3 重试

重试策略：

| 情况 | 处理 |
|---|---|
| APNs 明确 4xx 不可重试 | 标记失败，进入 Email |
| APNs 5xx / 网络超时 | 标记 `submit_unknown` 或 retry，不立即进入 Email |
| Email provider accepted | 停止，不进入 SMS |
| Email 硬退信 | 标记失败并加入抑制，再进入 SMS |
| SMS 提交成功 | 停止 |
| SMS 流控 | 标记失败或延迟重试，按费用策略决定是否重试 |

本工单建议短期对 `submit_unknown` 不降级，先避免重复触达；后续可单独设计“未知状态超时后补偿降级”。

### 6.12 日志与监控

新增结构化日志，便于排查：

```text
notification.membership.route.start scene=membership.pro_trial.manually_granted user_id=1 routing_mode=fallback steps=apns,email,sms business_id=123
notification.membership.route.step scene=membership.pro_trial.manually_granted user_id=1 channel=apns route_order=1 status=accepted stop=true reason=provider_accepted
notification.membership.route.step scene=membership.pro_trial.manually_granted user_id=1 channel=email route_order=2 status=cancelled reason=previous_channel_succeeded
notification.membership.route.done scene=membership.pro_trial.manually_granted user_id=1 final_status=accepted winning_channel=apns
```

建议指标：

| 指标 | 说明 |
|---|---|
| `membership_notification_route_total` | 会员通知路由总数 |
| `membership_notification_winning_channel_total` | 最终成功渠道分布 |
| `membership_notification_all_channels_failed_total` | 三渠道均失败次数 |
| `membership_notification_duplicate_channel_total` | 同一业务事件多成功渠道数量 |
| `membership_notification_suppressed_total` | 被抑制或无 endpoint 的次数 |

报警建议：

1. 同一 `business_scene + business_id + user_id` 在 5 分钟内出现两个成功外部渠道，报警。
2. `all_channels_failed` 连续升高，报警。
3. SMS fallback 比例异常升高，提示 APNs 或 Email 渠道可能异常。

### 6.15 接口与数据契约

#### 6.15.1 业务调用契约

会员业务调用通知中心时，最少需要传入：

```python
NotificationCenterService.send_to_user_sync(
    campaign_id=None,
    user_id=user_id,
    channels=[APNS, EMAIL, SMS],
    title=title,
    body=body,
    payload=payload,
    created_by_id=None,
    request_id=request_id,
    business_scene="membership.pro_trial.application_approved",
    business_reference_type="trial_application",
    business_id=str(trial_application_id),
    idempotency_key=f"membership.pro_trial.application_approved:{trial_application_id}",
    source="ai_config.tasks",
)
```

契约要求：

1. `business_scene` 必填。
2. `business_id` 必须是业务实例 ID，不是用户 ID。
3. `idempotency_key` 必须稳定，不能每次任务重试都变化。
4. 不允许通过 `payload["_routing"]` 覆盖会员场景默认路由，除非是测试代码。
5. 调用方不判断渠道成功，不自行补发 Email/SMS，由通知中心统一处理。

#### 6.15.2 Payload 契约

建议会员通知 payload 保持最小化：

```json
{
  "type": "membership_pro_trial",
  "scene": "membership.pro_trial.application_approved",
  "trial_application_id": 123,
  "refresh_ai_config": true,
  "route": "ai_settings"
}
```

禁止放入：

- 邮箱明文
- 手机号明文
- 管理员 ID 或姓名
- 内部审批备注
- 权益计算细节

#### 6.15.3 后台记录字段期望

每条实际执行的外部渠道投递记录应至少可看到：

| 字段 | 说明 |
|---|---|
| `business_scene` | `membership.pro_trial.application_approved` 或 `membership.pro_trial.manually_granted` |
| `business_id` | 申请 ID 或发放流水 ID |
| `channel` | 实际执行渠道 |
| `route_order` | 1/2/3 |
| `routing_mode` | `fallback` |
| `status` | 渠道投递状态 |
| `stop_reason` | `provider_accepted` / `all_channels_failed` / `submit_unknown_waiting` |

如果现有模型没有 `stop_reason` 字段，短期可以写入 `delivery_details` 或日志；长期建议规范化字段。

### 6.16 边界场景矩阵

| 用户状态 | APNs | Email | SMS | 期望结果 |
|---|---|---|---|---|
| 三渠道均可用 | 成功 | 不执行 | 不执行 | APNs 胜出 |
| APNs token 缺失 | 跳过 | 成功 | 不执行 | Email 胜出 |
| APNs token 无效 | 失败 | 成功 | 不执行 | Email 胜出 |
| APNs 超时未知 | `submit_unknown` | 不执行 | 不执行 | 等待重试或回执，不重复触达 |
| APNs 失败、Email 退信抑制 | 失败 | 跳过 | 成功 | SMS 胜出 |
| APNs 失败、Email 无地址、SMS 无手机号 | 失败 | 跳过 | 跳过 | 整体失败 |
| 用户关闭推送、邮箱存在 | 跳过 | 成功 | 不执行 | Email 胜出 |
| 邮箱格式无效、手机号存在 | APNs 失败 | 跳过 | 成功 | SMS 胜出 |
| 用户只有邮箱 | 跳过 | 成功 | 不执行 | Email 胜出 |
| 用户只有手机号 | 跳过 | 跳过 | 成功 | SMS 胜出 |
| `expiring` 事件 | 不执行 | 不执行 | 不执行 | 不创建通知 |
| `revoked` 事件 | 不执行 | 不执行 | 不执行 | 不创建通知 |

## 7. 回归测试建议

### 7.1 APNs 成功时不再发送 Email/SMS

构造用户：

- 有可用 APNs token
- 有邮箱
- 有手机号

触发：

```text
membership.pro_trial.manually_granted
```

期望：

- 只产生 APNs 外部投递成功记录。
- 不产生 Email 发送记录。
- 不产生 SMS 发送记录。
- `NotificationRecipientMessage.status` 为 `accepted` 或 `delivered`。

### 7.2 APNs 失败后发送 Email，Email 成功后停止

构造用户：

- APNs token 无效或 Provider 返回失败
- 有邮箱
- 有手机号

期望：

- APNs 记录为失败。
- Email 记录为已受理。
- SMS 不发送。
- 收件人逻辑消息判定为成功。

### 7.3 APNs 和 Email 都失败后发送 SMS

构造用户：

- APNs 失败
- Email 失败或无邮箱
- 有手机号

期望：

- APNs 失败。
- Email 失败或跳过。
- SMS 已受理。
- 不再继续其他渠道。

### 7.4 三个渠道都失败时才整体失败

构造用户：

- 无可用 APNs
- 无邮箱或邮件被抑制
- 无手机号或短信失败

期望：

- 三个步骤均失败或跳过。
- `NotificationRecipientMessage.status=failed`。
- 业务侧可在后台看到完整失败原因。

### 7.5 复现样例回归

使用同一用户 `apple_000920.7dfc34cca` 触发“已发放 Pro 试用权限”通知。

期望：

- 如果 APNs 已受理，则不会再出现同时间 Email 已受理记录。
- 后台同一业务事件只展示 APNs 成功外部触达。

### 7.6 不触发通知场景回归

触发或模拟以下业务事件：

```text
membership.pro_trial.expiring
membership.pro_trial.revoked
```

期望：

- 不创建 `NotificationIntent`。
- 不创建 `NotificationMessage`。
- 不创建 APNs/Email/SMS 渠道投递记录。
- 后台通知记录列表中不出现“试用即将到期”或“试用已收回”的用户触达记录。

## 8. 验收标准

1. 会员试用通知默认路由为 `fallback`，不是 `parallel`。
2. 默认外部渠道顺序为 `apns -> email -> sms`。
3. APNs 成功时，Email 和短信不会发送。
4. APNs 失败时，才发送 Email。
5. Email 失败时，才发送短信。
6. 后台通知记录能展示每一步失败或成功原因。
7. `membership.pro_trial.manually_granted` 的展示名称改为“系统发放试用”。
8. `membership.pro_trial.expiring` 和 `membership.pro_trial.revoked` 不触发用户通知。
9. 历史已入库的会员场景 `default_routing` 被迁移为新策略。
10. 新增自动化测试覆盖 APNs 成功、APNs 失败转 Email、Email 失败转 SMS、全失败、不触发通知五类场景。
