# SparkService 短信验证码发送用户归属问题修复工单

创建日期：2026-07-13  
关联模块：账户登录、OTP、通知中心、短信发送记录  
优先级：P0  
修复类型：身份归属错误 / 审计记录错误 / 通知中心数据准确性

## 1. 背景

当前 `/api/v1/otp/phone/request/` 用于提交手机号验证码发送请求。客户端已上送：

```json
{
  "phone_number": "+8615385056020",
  "device_id": "680783DA-E49E-4C68-BBE9-2939FFC7897F",
  "bundle_id": "cn.Zhaodk.Health",
  "provider_uid": ""
}
```

接口响应：

```json
{
  "code": 0,
  "msg": "otp_sent",
  "data": {
    "otp_id": "06afd742-7bf1-4584-af56-cb48e87dad09",
    "expires_in": 300
  }
}
```

目前问题是：短信验证码发送记录里的“用户/登录前用户”归属不能只按手机号查找用户，更不能在相同手机号存在多个内部账号时取第一个用户。登录唯一身份不在 `auth_user.username`，而在 `accounts_socialidentity`。

## 2. 问题现象

同一个手机号 `+8615385056020` 当前存在多个内部用户：

| 用户 ID | username | 设备 bundle_id | 说明 |
|---:|---|---|---|
| 695 | phone_15385056020 | `cn.Zhaodk.Health` | 健康 App 用户 |
| 811 | phone_15385056020_2 | `cn.zhaodk.SupportClient` | SupportClient 用户 |

当客户端以：

```json
{
  "phone_number": "+8615385056020",
  "bundle_id": "cn.Zhaodk.Health",
  "device_id": "680783DA-E49E-4C68-BBE9-2939FFC7897F"
}
```

请求短信验证码时，短信发送记录应归属到 `bundle_id=cn.Zhaodk.Health` 下的手机号身份，即用户 `695`；不能因为手机号相同而错误关联到 `811` 或其他账号。

## 3. 根因

### 3.1 错误认知

把手机号当成全局唯一用户标识是错误的。

`auth_user.username` 只是内部技术账号名，例如：

- `phone_15385056020`
- `phone_15385056020_2`

它不能作为登录唯一介质。

### 3.2 正确身份模型

登录唯一身份由 `accounts_socialidentity` 决定：

```python
models.UniqueConstraint(
    fields=["bundle_id", "provider", "provider_uid"],
    name="uniq_social_identity_bundle_provider_uid",
)
```

真正唯一键是：

| 字段 | 含义 | 手机号登录取值 |
|---|---|---|
| `bundle_id` | 哪个 App | `cn.Zhaodk.Health` |
| `provider` | 登录渠道 | `phone` |
| `provider_uid` | 渠道唯一 ID | 标准化 E.164 手机号，如 `+8615385056020` |

所以手机号短信验证码请求阶段的用户归属必须使用：

```text
bundle_id + provider=phone + provider_uid=normalized_phone
```

如果是 SparkClient 注销账户等登录态敏感验证场景，客户端必须上送 `user_id`；普通登录和注册/首次登录场景客户端不需要上送 `user_id`。

## 4. 当前接口分析

### 4.1 当前请求参数

接口：

```http
POST /api/v1/otp/phone/request/
```

当前请求体：

| 字段 | 当前状态 | 说明 |
|---|---|---|
| `phone_number` | 必填 | 手机号，服务端标准化为 E.164 |
| `device_id` | 可选 | 客户端安装级设备 ID |
| `bundle_id` | 可选 | App 包标识 |
| `provider_uid` | 可选 | 当前对手机号登录无实际必要，手机号 provider_uid 应由服务端标准化手机号得出 |

### 4.2 当前返回参数

```json
{
  "otp_id": "06afd742-7bf1-4584-af56-cb48e87dad09",
  "expires_in": 300
}
```

| 字段 | 说明 |
|---|---|
| `otp_id` | 本次验证码请求 ID，后续 verify 使用 |
| `expires_in` | 有效期秒数 |

### 4.3 当前不足

1. `bundle_id` 在 serializer 中仍是可选字段，不利于准确归属身份。
2. 请求阶段没有 `user_id` 字段，SparkClient 注销账户等登录态敏感场景无法显式提交当前用户。
3. OTP 请求到通知中心短信记录的链路没有可靠传递已解析的用户。
4. 如果服务端按手机号反查用户，可能错误命中同手机号在其他 `bundle_id` 下的账号。
5. 短信验证码属于敏感通知，发送记录可以展示 BizId、状态、掩码手机号，但不能展示 OTP、TemplateParam、短信 Content。

## 5. 修复目标

1. `/api/v1/otp/phone/request/` 支持 SparkClient 注销账户等登录态敏感场景上送 `user_id`。
2. 服务端以 `bundle_id + provider=phone + normalized_phone` 精确确认登录身份。
3. 注销账户场景如果上送 `user_id`，必须校验该用户是否匹配当前登录用户和 `bundle_id + phone` 身份；不匹配时不能强行归属。
4. 短信验证码通知记录正确展示：
   - 已匹配身份：显示对应用户。
   - 未匹配身份：显示“登录前用户”。
5. 新发送的短信验证码记录中保留 `bundle_id`、`device_id`、`otp_id`、`request_id` 等审计上下文。
6. 不做历史数据迁移；历史缺失归属的数据按“登录前用户”展示。

## 6. 修复方案

### 6.1 接口请求参数调整

接口不变：

```http
POST /api/v1/otp/phone/request/
```

请求体调整为：

```json
{
  "phone_number": "+8615385056020",
  "device_id": "680783DA-E49E-4C68-BBE9-2939FFC7897F",
  "bundle_id": "cn.Zhaodk.Health",
  "user_id": 695,
  "scene": "account_deactivation"
}
```

字段定义：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `phone_number` | 是 | 手机号，服务端标准化为 E.164 |
| `bundle_id` | 是 | App 维度；手机号身份归属必须依赖它 |
| `device_id` | 是 | 安装实例维度；用于设备审计、风控、通知上下文 |
| `user_id` | 视场景 | 仅登录态敏感操作需要上送，例如 SparkClient 注销账户；普通登录/注册验证码不要求客户端上送 |
| `provider_uid` | 废弃 | 手机号登录场景不再依赖客户端传入，服务端统一使用标准化手机号 |

兼容策略：

- 短期可保留 `provider_uid` 字段但忽略其值。
- `bundle_id`、`device_id` 建议从“可选”升级为“必填”。
- 如果担心旧客户端，可设置灰度开关：
  - 第一阶段：缺失时 warning + 仍发送，但记录为“登录前用户”。
  - 第二阶段：缺失时返回 `400 bundle_id_required` 或 `400 device_id_required`。

### 6.2 服务端用户归属规则

手机号验证码请求必须区分三类业务场景，不能一刀切要求客户端上送 `user_id`。

| 场景 | 客户端是否上送 `user_id` | 服务端是否绑定用户 | 归属规则 |
|---|---|---|---|
| SparkClient 注销账户 / 登录态敏感验证 | 必须上送 | 必须绑定 | 校验 `user_id + bundle_id + phone` 是否匹配当前登录身份或 SocialIdentity |
| 用户登录场景 | 不上送 | 服务端匹配绑定 | 服务端用 `bundle_id + provider=phone + normalized_phone` 查 SocialIdentity，命中则绑定该用户 |
| 注册 / 首次登录场景 | 不上送 | 不绑定 | SocialIdentity 不存在时记录为“登录前用户”，verify 成功后才创建身份 |

服务端收到手机号 OTP 请求后：

```text
normalized_phone = normalize_e164(phone_number)
identity = SocialIdentity.objects.filter(
    bundle_id=bundle_id,
    provider=SocialIdentity.Provider.PHONE,
    provider_uid=normalized_phone,
).select_related("user").first()
```

归属决策：

| 场景 | 处理 |
---|---|
| 注销账户场景缺少 `user_id` | 返回 `400 user_id_required_for_account_deactivation`，不发送短信 |
| 注销账户场景 `user_id` 与当前登录用户不一致 | 返回 `403 user_context_mismatch`，不发送短信 |
| 注销账户场景 `identity` 存在且匹配 `user_id` | 使用该 `user_id` 作为短信记录用户 |
| 注销账户场景 `identity` 不存在或不匹配 `user_id` | 返回 `409 user_identity_mismatch`，不发送短信 |
| 登录场景 `identity` 存在，客户端未上送 `user_id` | 服务端使用 `identity.user_id` 作为短信记录用户 |
| 登录场景 `identity` 不存在，客户端未上送 `user_id` | 视为注册/首次登录，记录为“登录前用户” |
| 登录/注册场景客户端误上送 `user_id` | 不建议使用；服务端可忽略并 warning，或按灰度策略校验 |

注意：验证码请求阶段不能因为客户端传了 `user_id` 就建立登录态或创建身份绑定。真正登录仍必须发生在 `/api/v1/otp/phone/verify/` 验证码校验通过之后。

### 6.2.1 三类业务场景详细规则

#### A. SparkClient 注销账户场景

注销账户属于登录态敏感操作。客户端必须上送：

```json
{
  "phone_number": "+8615385056020",
  "bundle_id": "cn.Zhaodk.Health",
  "device_id": "680783DA-E49E-4C68-BBE9-2939FFC7897F",
  "user_id": 695,
  "scene": "account_deactivation"
}
```

服务端必须校验：

1. 请求处于登录态，`request.user.id == user_id`。
2. `SocialIdentity(bundle_id, provider=phone, provider_uid=normalized_phone).user_id == user_id`。
3. 如该用户当前没有 phone SocialIdentity，但注销流程允许用新手机号验证，必须由注销业务显式授权，不能在通用 OTP 请求里默认通过。

短信记录必须绑定 `NotificationMessage.user_id = user_id`。

#### B. 用户登录场景

登录场景客户端不需要上送 `user_id`，因为用户可能尚未完成身份认证。请求示例：

```json
{
  "phone_number": "+8615385056020",
  "bundle_id": "cn.Zhaodk.Health",
  "device_id": "680783DA-E49E-4C68-BBE9-2939FFC7897F",
  "scene": "login"
}
```

服务端处理：

1. 用 `bundle_id + phone + normalized_phone` 查询 SocialIdentity。
2. 命中则把短信记录绑定到 `identity.user_id`。
3. 未命中则不绑定用户，记录为“登录前用户”。

#### C. 注册 / 首次登录场景

注册或首次手机号登录时，客户端不上送 `user_id`，服务端也不绑定用户。请求示例：

```json
{
  "phone_number": "+8613999999999",
  "bundle_id": "cn.Zhaodk.Health",
  "device_id": "new-device-id",
  "scene": "login"
}
```

服务端处理：

1. 查询 SocialIdentity 不存在。
2. 发送验证码。
3. `NotificationMessage.user_id = NULL`。
4. 后台展示“登录前用户”。
5. `/api/v1/otp/phone/verify/` 成功后，才创建新的用户和 SocialIdentity。

### 6.3 代码改造点

| 文件 | 改造内容 |
|---|---|
| `accounts/otp/serializers.py` | `PhoneOTPRequestSerializer` 增加 `user_id`、`scene`；`bundle_id/device_id` 改为必填或灰度必填 |
| `accounts/otp/views.py` | 从 serializer 读取 `user_id`、`scene` 并传给 `OTPService.request_phone_otp` |
| `accounts/services/otp_service.py` | `request_phone_otp` 增加 `user_id`、`scene` 参数；按场景解析身份：注销必须校验 user_id，登录服务端匹配，注册不绑定 |
| `notification_center/services.py` | `send_phone_otp` 接收已解析的 `user_id`，写入 `NotificationMessage.user`、`ContactEndpoint.user`、metadata |
| `notification_center/serializers.py` | 短信记录的 `用户/登录前用户` 字段从 `message.user` 和 metadata 派生，不能按手机号反查第一个用户 |
| `notification_center/models.py` | 如当前 `PhoneOTP` 无 `user` 字段，可新增 `requested_user` 或在通知 intent/message metadata 保存 `user_id` |
| `backoffice-web/src/views/NotificationLogsView.vue` | 短信发送记录继续展示“用户/登录前用户”，不展示 OTP、TemplateParam、Content |

### 6.4 推荐伪代码

```python
def resolve_phone_otp_request_user(
    *,
    bundle_id: str,
    phone_number: str,
    user_id: int | None,
    scene: str,
    request_user=None,
):
    normalized_phone = PhoneNumberService.normalize_e164(phone_number)
    identity = (
        SocialIdentity.objects
        .select_related("user")
        .filter(
            bundle_id=bundle_id,
            provider=SocialIdentity.Provider.PHONE,
            provider_uid=normalized_phone,
        )
        .first()
    )

    if scene == "account_deactivation":
        if not user_id:
            raise APIError("user_id_required_for_account_deactivation", code=40061, status_code=400)
        if request_user is None or not request_user.is_authenticated or request_user.id != user_id:
            raise APIError("user_context_mismatch", code=40361, status_code=403)
        if identity is None or identity.user_id != user_id:
            raise APIError("user_identity_mismatch", code=40901, status_code=409)
        if not identity.user.is_active:
            raise APIError("user_inactive", code=40103, status_code=401)
        return identity.user

    # 登录场景：客户端不上送 user_id，服务端按 bundle + phone 尝试匹配。
    if identity is None:
        # 注册 / 首次登录：不绑定用户。
        return None

    # 非注销场景下，如果客户端误上传 user_id，不能盲信。
    if user_id and identity.user_id != user_id:
        raise APIError("user_identity_mismatch", code=40901, status_code=409)

    if not identity.user.is_active:
        raise APIError("user_inactive", code=40103, status_code=401)

    return identity.user
```

### 6.5 通知中心短信记录字段规则

短信验证码发送记录字段：

| 字段 | 来源 |
|---|---|
| Delivery ID | `ChannelDelivery.id` |
| 业务类型 | `NotificationIntent.business_type=phone_otp` |
| 用户/登录前用户 | `NotificationMessage.user`；为空则显示“登录前用户” |
| 掩码号码 | `ContactEndpoint.address_masked` / `NotificationMessage.receiver_phone` |
| 模板编码 | `ChannelDelivery.details.template_code` |
| 提交状态 | `ChannelDelivery.status` 映射 |
| 送达状态 | `QuerySendDetails` 或轮询回执映射 |
| Code/ErrCode | `provider_code` / `error_code` |
| BizId | `provider_message_id` |
| 提交时间 | `accepted_at` / `sent_at` |
| 回执时间 | `delivered_at` |
| 操作 | 查看、权限受控 QuerySendDetails |

禁止展示：

- OTP 验证码明文。
- `TemplateParam`。
- 阿里云返回的短信 `Content`。
- `NotificationMessage.body` 中的验证码。
- `NotificationMessage.payload.template_param` 中的验证码。

## 7. 安全要求

1. `user_id` 是归属 hint，不是认证凭证。
2. 服务端必须以 `SocialIdentity(bundle_id, phone, normalized_phone)` 作为身份真相。
3. `bundle_id` 必须参与手机号身份解析，不能只用手机号。
4. 不能在发送验证码阶段创建新的 `SocialIdentity`。
5. 不能因为 `user_id` 存在就把短信记录归属给该用户；必须校验匹配。
6. 日志可以记录 `bundle_id/device_id/user_id/request_id/otp_id`，但不能记录验证码明文。
7. 通知中心短信记录页和详情接口都不得返回 OTP、TemplateParam、Content。

## 9. 验收标准

1. 同一手机号在不同 `bundle_id` 下绑定不同用户时，短信验证码发送记录归属正确。
2. `cn.Zhaodk.Health + +8615385056020` 归属到用户 `695`，不能归属到 `811`。
3. `cn.zhaodk.SupportClient + +8615385056020` 归属到用户 `811`。
4. SparkClient 注销账户场景未上送 `user_id` 时拒绝发送验证码。
5. SparkClient 注销账户场景上送错误 `user_id` 时，服务端返回错误，不能将短信记录错误绑定到该用户。
6. 用户登录场景客户端不上送 `user_id`，服务端命中 SocialIdentity 时自动绑定对应用户。
7. 注册 / 首次登录场景客户端不上送 `user_id`，服务端未命中 SocialIdentity 时不绑定用户，后台显示“登录前用户”。
8. 缺失 `bundle_id` 时按灰度策略处理；最终状态应拒绝请求。
9. 缺失 `device_id` 时按灰度策略处理；最终状态应拒绝请求。
10. 通知中心短信发送记录页不展示 OTP、TemplateParam、Content。
11. QuerySendDetails 主动查询仍可用，且只更新状态、BizId、ErrCode、回执时间等安全字段。
12. `/api/v1/otp/phone/verify/` 登录签发 token 的逻辑仍只以验证码校验成功和 `SocialIdentity(bundle_id, phone)` 为准。
13. 新增单元测试覆盖同手机号多 bundle 多用户、注销、登录、注册三类场景。

## 11. 实施顺序

1. 更新 `PhoneOTPRequestSerializer`，增加 `user_id`、`scene`，并灰度要求 `bundle_id/device_id`。

## 12. 详细实现方案

### 12.1 请求 DTO 设计

`PhoneOTPRequestSerializer` 增加两个字段：

```python
class PhoneOTPRequestSerializer(serializers.Serializer):
    phone_number = serializers.CharField(max_length=32)
    provider_uid = serializers.CharField(max_length=128, required=False, allow_blank=True)
    bundle_id = serializers.CharField(max_length=128, required=False, allow_blank=True)
    device_id = serializers.CharField(max_length=128, required=False, allow_blank=True)
    user_id = serializers.IntegerField(required=False, allow_null=True)
    scene = serializers.ChoiceField(
        choices=("login", "account_deactivation"),
        required=False,
        default="login",
    )
```

字段处理原则：

| 字段 | 服务端处理 |
|---|---|
| `phone_number` | 必须标准化为 E.164 |
| `provider_uid` | 手机号 OTP 场景忽略，避免客户端污染登录唯一键 |
| `bundle_id` | 身份解析必需字段；灰度期允许缺失但记录 warning |
| `device_id` | 设备审计必需字段；灰度期允许缺失但记录 warning |
| `user_id` | 仅 `scene=account_deactivation` 必填 |
| `scene` | 默认 `login`，用于区分登录、注册、注销账户 |

后续如果 OTP 场景继续增多，不建议继续堆布尔字段，应扩展 `scene`：

```text
login
account_deactivation
phone_change
security_verify
```

### 12.2 业务场景枚举

建议在 `OTPService` 中定义常量，避免字符串散落：

```python
class PhoneOTPScene:
    LOGIN = "login"
    ACCOUNT_DEACTIVATION = "account_deactivation"
```

如果后续增加数据库字段，可同步到 `PhoneOTP.scene`。

### 12.3 身份解析服务

新增内部方法：

```python
@staticmethod
def _resolve_phone_otp_user(
    *,
    normalized_phone: str,
    bundle_id: str,
    user_id: int | None,
    scene: str,
    request_user=None,
    request_id: str = "",
):
    normalized_bundle_id = (bundle_id or "").strip()
    identity = None
    if normalized_bundle_id:
        identity = (
            SocialIdentity.objects.select_related("user")
            .filter(
                bundle_id=normalized_bundle_id,
                provider=SocialIdentity.Provider.PHONE,
                provider_uid=normalized_phone,
            )
            .first()
        )

    if scene == PhoneOTPScene.ACCOUNT_DEACTIVATION:
        if not user_id:
            raise APIError("user_id_required_for_account_deactivation", code=40061, status_code=400)
        if request_user is None or not request_user.is_authenticated or request_user.id != user_id:
            raise APIError("user_context_mismatch", code=40361, status_code=403)
        if identity is None or identity.user_id != user_id:
            raise APIError("user_identity_mismatch", code=40901, status_code=409)
        if not identity.user.is_active:
            raise APIError("user_inactive", code=40103, status_code=401)
        return identity.user

    if user_id:
        flow_logger.warning(
            "auth.phone_otp.request.user_id_ignored_for_login",
            extra={"request_id": request_id, "bundle_id": normalized_bundle_id, "user_id": user_id},
        )

    if identity is None:
        return None
    if not identity.user.is_active:
        raise APIError("user_inactive", code=40103, status_code=401)
    return identity.user
```

注意：

- 登录场景不使用客户端上送的 `user_id`。
- 注册场景不是显式 scene，而是 `scene=login` 且查不到 SocialIdentity。
- 注销账户场景必须有登录态，因此 view 需要把 `request.user` 传入 service。

### 12.4 View 层改造

`PhoneOTPRequestView` 需要传递 `request.user`：

### 12.6 OTPService 改造流程

推荐流程：

```text
request_phone_otp
  -> normalize phone
  -> validate bundle_id/device_id by rollout policy
  -> resolve user by scene
      account_deactivation:
        require user_id + authenticated request_user
        require SocialIdentity matches
      login:
        ignore client user_id
        query SocialIdentity(bundle_id, phone)
        if found -> resolved_user
        if not found -> None
  -> create PhoneOTP(scene, requested_user, bundle_id, device_id)
  -> NotificationCenterService.send_phone_otp(user_id=resolved_user.id if exists else None)
  -> return otp_id/expires_in
```

关键点：

- 先解析用户，再创建通知记录。
- 发送失败时，`PhoneOTP` 仍可存在，但需要记录发送失败原因。
- 白名单手机号也要走同样的用户归属解析，否则测试环境看不到归属问题。

### 12.9 错误码设计

| code | msg | HTTP | 场景 |
|---:|---|---:|---|
| 40061 | `user_id_required_for_account_deactivation` | 400 | 注销账户 OTP 未传 user_id |
| 40062 | `scene_invalid` | 400 | scene 非法 |
| 40063 | `bundle_id_required` | 400 | 强制期缺少 bundle_id |
| 40064 | `device_id_required` | 400 | 强制期缺少 device_id |
| 40361 | `user_context_mismatch` | 403 | request.user 与 user_id 不一致 |
| 40901 | `user_identity_mismatch` | 409 | user_id 与 SocialIdentity 不一致 |
| 40103 | `user_inactive` | 401 | 命中用户已停用 |

### 12.10 灰度开关

建议增加 settings：

```python
PHONE_OTP_REQUIRE_BUNDLE_ID = env_bool("PHONE_OTP_REQUIRE_BUNDLE_ID", False)
PHONE_OTP_REQUIRE_DEVICE_ID = env_bool("PHONE_OTP_REQUIRE_DEVICE_ID", False)

```

灰度期：

- 缺少 `bundle_id`：warning，发送但不绑定用户。
- 缺少 `device_id`：warning，发送但风险日志标记。
- 登录场景误传 `user_id`：warning，默认忽略。

强制期：

- 缺少 `bundle_id` 直接 400。
- 缺少 `device_id` 直接 400。
- 登录场景误传 `user_id` 可按 `PHONE_OTP_STRICT_USER_HINT` 决定忽略或校验。

### 12.14 回滚方案

回滚分两层：

1. 配置回滚：
   - 关闭 `PHONE_OTP_REQUIRE_BUNDLE_ID`。
   - 关闭 `PHONE_OTP_REQUIRE_DEVICE_ID`。
   - 关闭 `PHONE_OTP_STRICT_USER_HINT`。
2. 代码回滚：
   - 保留 serializer 的 `user_id/scene` 向后兼容字段。
   - 回滚 service 的严格校验逻辑。
   - 不删除新增数据库字段，避免迁移回滚风险。

即使回滚严格校验，也必须保留一条底线：不能按手机号全局查第一个用户。

### 12.15 发布步骤

1. 后端先上线兼容版本：支持 `user_id/scene`，但登录场景不要求客户端传。
2. SparkClient 注销账户流程开始上送 `user_id` 和 `scene=account_deactivation`。
3. 观察日志：
   - `identity_not_found`
   - `user_context_mismatch`
   - `user_identity_mismatch`
   - 缺失 `bundle_id/device_id`
4. 确认无异常后，开启 `PHONE_OTP_REQUIRE_BUNDLE_ID`。
5. 再开启 `PHONE_OTP_REQUIRE_DEVICE_ID`。
6. 最后按需要开启 `PHONE_OTP_STRICT_USER_HINT`。

### 12.16 开发注意事项

1. 不要使用 `User.objects.filter(username__contains=phone)`。
2. 不要使用 `SocialIdentity.objects.filter(provider_uid=phone).first()`。
3. 不要在请求验证码阶段创建 SocialIdentity。
4. 不要把客户端 `user_id` 当认证凭证。
5. 不要在任何日志、payload、attempt request_payload 中保存验证码明文。
6. 不要让前端根据手机号反查用户；归属必须由后端返回。

## 13. 风险与兼容

| 风险 | 处理 |
|---|---|
| 老客户端未传 `bundle_id` | 第一阶段 warning + 登录前用户；第二阶段拒绝 |
| 老客户端未传 `device_id` | 第一阶段 warning；第二阶段拒绝 |
| 注销场景客户端传错 `user_id` | 返回 `409 user_identity_mismatch` |
| 登录/注册场景客户端误传 `user_id` | 不作为认证依据；可忽略并记录 warning，或灰度校验 |
| 同手机号跨 App 多用户 | 必须按 `bundle_id` 区分 |
| 敏感字段泄露 | API 序列化层和前端双层隐藏 |

4. 不改变 `/otp/phone/verify/` 的登录唯一键模型。
