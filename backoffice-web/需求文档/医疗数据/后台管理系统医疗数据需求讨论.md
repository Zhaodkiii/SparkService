# 后台管理系统医疗数据需求讨论

## 1. 背景

当前后台管理系统已有以下功能：

| 模块 | 说明 |
| --- | --- |
| 仪表盘 | 后台首页数据概览 |
| 异步任务 | 任务看板、任务管理 |
| 用户管理 | 用户、设备、注销相关管理 |
| 通知中心 | 通知用户、模板、发送活动、发送日志 |
| 版本控制 | 版本配置、检查日志 |
| AI 场景配置 | 场景、模型、Provider、小任务、试用期 |
| 权限管理 | 后台菜单、角色、权限 |
| 审计日志 | 管理员操作留痕 |

为了支持服务端后台管理系统查看系统内用户给 AI 发起的对话内容、分析 AI 回复质量、定位识别与医疗数据整理问题，后台还需要能围绕“用户 -> 成员 -> 医疗数据”查看结构化医疗数据。

本需求建议单独建立一级菜单：`医疗数据`。不要放在 `用户管理` 下，也不要放在 `AI 场景配置` 下。原因是医疗数据既关联用户与家庭成员，也关联 AI 识别、附件、病例、体检、检查、用药、随访、隐私权限、审计和合规，独立成大菜单更清晰。

## 2. 总体目标

1. 新增后台一级菜单 `医疗数据`。
2. 支持以用户维度查看有医疗数据的用户列表。
3. 支持进入某个用户后查看其成员列表。
4. 支持进入某个成员后查看医疗数据总览、分类列表、详情和附件。
5. 支持基础可视化：数量统计、时间线、分类分布、用药执行摘要、附件识别状态。
6. 支持与 AI 对话分析联动：从医疗数据看到来源、识别任务、AI 生成字段和用户手动修改痕迹。
7. 补充权限、隐私脱敏、审计日志、数据导出、异常数据、性能分页、附件预览等常见基础问题。

## 2.1 已确认产品原则

| 问题 | 当前结论 |
| --- | --- |
| 医疗数据是否允许后台修改 | 当前阶段只读；后期再考虑错误修正，本期不做编辑、修正、删除、合并等写操作 |
| 医疗附件是否允许下载 | 允许下载，但需要权限控制、短期签名 URL、审计日志；批量下载后期再评估 |
| 是否展示管理员水印 | 不展示水印 |
| 是否需要单独医疗数据管理员角色 | 不需要新增单独角色，沿用现有后台 RBAC 角色体系，通过菜单/接口/按钮权限控制 |
| 家庭成员共享关系是否可视化 | 需要，在用户成员页和成员详情页展示共享关系、入口用户、成员绑定关系 |
| 大用户数据量很大时如何加载 | 分页加载；成员页先加载用户摘要与成员分页，成员医疗数据分类列表也分页加载 |
| `complete-data` 是否直接复用客户端接口 | 后台建议建设独立聚合接口，复用客户端模型口径和字段命名思路，但不要直接依赖客户端接口形态 |

## 2.3 工单 `BACKOFFICE-MED-000001`：用户医疗数据大数据量加载性能优化

### 2.3.1 背景

`医疗数据 / 用户医疗数据` 页面会聚合用户、成员、病例、体检、检查检验、药盒、处方、用药计划、附件、AI 识别任务等多类数据。随着数据量增长，直接实时聚合容易出现：

1. 首屏加载慢。
2. 请求超时或加载失败。
3. 数据库聚合查询消耗大量 CPU、内存和 IO。
4. 大用户进入成员页或成员医疗数据页时，一次返回过多数据。
5. 前端表格渲染压力大，页面卡顿。
6. 管理员重复筛选和翻页导致同类重查询。
7. 导出或查看详情与列表查询抢占资源。

本工单目标是把用户医疗数据后台从“实时全量聚合”改为“轻量列表 + 分页明细 + 预聚合统计 + 按需详情”的模式。

### 2.3.2 目标

1. 用户医疗数据列表首屏只加载轻量字段，不加载成员完整医疗数据。
2. 用户、成员、分类列表全部分页加载，默认 `page_size` 建议 20，最大不超过 100。
3. 列表统计优先使用预聚合表、缓存或异步统计结果，避免每次请求跨多张大表实时 count。
4. 成员医疗数据页先加载总览摘要，再按 tab 分页加载分类列表。
5. 详情、附件、原始 JSON、AI 识别输出全部按需加载。
6. 大查询要有超时、降级、错误提示和可重试能力。
7. 后端接口要能监控慢查询、超时率、错误率和资源消耗。

### 2.3.3 后端优化方案

| 优化项 | 方案 |
| --- | --- |
| 专用列表接口 | `GET /api/admin/v1/medical-data/users/` 只返回用户摘要和预聚合统计，不返回成员明细 |
| 成员分页接口 | `GET /api/admin/v1/medical-data/users/{user_id}/members/` 支持分页、排序、轻量统计 |
| 分类分页接口 | `GET /api/admin/v1/medical-data/users/{user_id}/members/{member_id}/{resource_type}/` 每个分类独立分页 |
| 详情按需加载 | 详情接口只在点击详情抽屉时请求 |
| 字段裁剪 | 列表接口不要返回附件 URL、原始 JSON、大文本、AI 原始输出、明细项数组 |
| 统计预聚合 | 建议建立用户/成员维度统计表或物化统计缓存，存储成员数、各类数据数量、附件数、最近更新时间、异常数 |
| 异步刷新统计 | 医疗数据创建/更新/删除后通过异步任务刷新统计；允许短时间最终一致 |
| 缓存策略 | 用户列表筛选结果可短 TTL 缓存，成员摘要和分类计数可按用户/成员维度缓存 |
| 慢查询保护 | 接口设置查询超时；超时返回可理解错误，不拖垮后台服务 |
| 限制深分页 | 大数据翻页建议支持 cursor/keyset pagination；普通页码分页只允许合理页数 |
| 分离导出 | 导出走异步任务，不在列表接口同步生成 |
| 附件隔离 | 附件预览和下载使用短期签名 URL，生成 URL 不参与列表查询 |

### 2.3.4 数据库与索引建议

必须评估并补充索引：

| 表/数据 | 索引建议 |
| --- | --- |
| 成员表 | `user_id`、`updated_at`、共享关系相关字段 |
| 病例 | `member_id`、`updated_at`、`occurred_at`、`source` |
| 体检报告 | `member_id`、`exam_date`、`updated_at`、`source` |
| 检查检验报告 | `member_id`、`report_date`、`updated_at`、`category` |
| 药盒 | `member_id`、`updated_at`、`expires_at` |
| 处方 | `member_id`、`prescribed_at`、`updated_at` |
| 用药计划 | `member_id`、`status`、`start_date`、`end_date`、`updated_at` |
| 用药记录 | `member_id`、`plan_id`、`scheduled_at`、`status` |
| 附件 | `owner_type`、`owner_id`、`member_id`、`created_at` |
| AI 任务/识别记录 | `user_id`、`member_id`、`resource_type`、`resource_id`、`status`、`created_at` |

注意：

1. 不要为了列表页在运行时做多张大表 `COUNT DISTINCT`。
2. 不要在列表页 join 大文本字段、附件表原始 URL、AI 原始输出。
3. 默认排序字段必须有索引，例如 `last_medical_updated_at desc, user_id desc`。
4. 如果存在软删除字段，常用查询需要组合软删除条件或使用部分索引。

### 2.3.5 前端优化方案

| 优化项 | 方案 |
| --- | --- |
| 首屏轻量加载 | 先展示筛选栏、统计卡 skeleton、表格 skeleton，再加载数据 |
| 分页加载 | 表格使用服务端分页，不在前端持有全量数据 |
| 筛选防抖 | 关键词搜索 300-500ms debounce，避免每输入一个字请求一次 |
| 请求取消 | 筛选条件变化时取消上一个未完成请求，避免旧请求覆盖新结果 |
| 局部刷新 | 切换 tab 只刷新当前 tab，不重新加载整个成员完整数据 |
| 错误恢复 | 加载失败展示 `a-result` / `a-alert`，提供“重试”和“复制 request_id” |
| 空状态 | 无数据用 `a-empty`，区分“无医疗数据”和“筛选无结果” |
| 详情懒加载 | 点击详情后再加载详情、附件、原始 JSON |
| 大表格滚动 | 宽表格使用横向滚动；大量行坚持分页，不做无限加载全量 |
| 避免重复请求 | 同一用户成员摘要、同一成员统计可做短时间前端缓存 |

### 2.3.6 接口返回策略

用户医疗数据列表只返回：

| 字段类型 | 是否返回 |
| --- | --- |
| 用户基础摘要 | 返回 |
| 成员数量、数据数量、附件数量、AI 任务数量 | 返回预聚合结果 |
| 最近更新时间、最近来源 | 返回 |
| 风险/异常数量 | 返回摘要 |
| 成员明细 | 不返回 |
| 分类明细 | 不返回 |
| 附件 URL | 不返回 |
| 原始 JSON | 不返回 |
| AI 原始输出 | 不返回 |

成员医疗数据总览只返回：

1. 成员摘要。
2. 分类数量。
3. 最近更新时间。
4. 异常摘要。
5. 共享关系摘要。
6. 当前管理员权限信息。

分类列表只返回列表字段；详情字段按详情接口获取。

### 2.3.7 降级与失败处理

| 场景 | 处理 |
| --- | --- |
| 统计缓存未命中 | 返回列表基础信息，统计字段显示计算中或 `-`，后台异步补算 |
| 统计刷新中 | 展示旧统计和 `统计刷新中` tag |
| 列表查询超时 | 返回明确错误码，前端展示重试 |
| 某个分类加载失败 | 只影响当前 tab，不影响成员页其它区域 |
| 附件签名失败 | 详情中提示附件暂不可预览/下载 |
| 后端限流 | 前端提示操作过快，请稍后重试 |

### 2.3.8 监控与验收标准

建议验收指标：

| 指标 | 目标 |
| --- | --- |
| 用户医疗数据列表首屏接口 P95 | 小于 2 秒 |
| 用户成员列表接口 P95 | 小于 2 秒 |
| 分类列表接口 P95 | 小于 2 秒 |
| 详情接口 P95 | 小于 3 秒，附件签名除外 |
| 列表接口错误率 | 小于 1% |
| 单次列表最大返回行数 | 不超过 100 |
| 慢查询 | 有日志和告警 |
| 超时请求 | 有 request_id，前端可展示并用于排查 |

需要记录：

1. 接口耗时。
2. SQL 查询耗时。
3. 返回数据大小。
4. 分页参数。
5. 管理员 ID。
6. request_id。
7. 是否命中缓存。
8. 是否使用预聚合统计。

### 8.5 常见问题

1. 一个成员是否可以被多个用户共享？
2. 后台查看共享成员数据时，权限归属按创建者、当前绑定用户，还是所有共享用户？
3. 成员被删除或解绑后，后台是否仍可查历史数据？
4. 注销用户下的成员与医疗数据是否匿名化、软删除或物理删除？
5. 成员姓名、生日、性别是否属于敏感信息，是否需要默认脱敏？
6. 家庭药箱 `familyMedicineBoxes` 是按家庭、按用户，还是按入口成员聚合？
7. 成员关系变更后，历史数据是否保持原关系快照？

## 15. 接口设计建议

### 15.1 用户列表

`GET /api/admin/v1/medical-data/users/`

该接口是 `BACKOFFICE-MED-000001` 的核心优化对象。必须保持轻量返回，只返回用户摘要和预聚合统计，不允许在接口内实时加载成员完整数据、分类明细、附件 URL、AI 原始输出。

查询参数：

| 参数 | 说明 |
| --- | --- |
| `user_id` | 用户 ID 精确查询 |
| `keyword` | 用户名/邮箱/手机号搜索 |
| `data_type` | 医疗数据类型 |
| `source` | 来源 |
| `has_attachment` | 是否有附件 |
| `has_ai_task` | 是否有 AI 识别 |
| `updated_after` / `updated_before` | 更新时间范围 |
| `status` | 用户状态 |
| `ordering` | 排序 |
| `page` / `page_size` | 分页 |
| `cursor` | 可选；大数据深分页时优先使用 cursor/keyset pagination |

返回要求：

1. 默认 `page_size` 建议 20。
2. 最大 `page_size` 不超过 100。
3. 默认排序建议 `last_medical_updated_at desc, user_id desc`。
4. 统计字段来自预聚合结果或短 TTL 缓存。
5. 如果统计暂不可用，不阻塞列表返回。

### 15.2 用户成员

`GET /api/admin/v1/medical-data/users/{user_id}/members/`

返回用户摘要和成员统计。该接口必须分页，不允许一次性返回该用户下全部成员和全部医疗数据。

建议查询参数：

| 参数 | 说明 |
| --- | --- |
| `keyword` | 成员姓名/关系搜索 |
| `binding_status` | 绑定状态 |
| `share_status` | 共享状态 |
| `ordering` | 排序 |
| `page` / `page_size` | 分页 |

### 15.3 成员完整医疗数据

`GET /api/admin/v1/medical-data/users/{user_id}/members/{member_id}/complete-data/`

参考客户端 `RemoteMemberCompleteData`，但后台接口不返回全量深层明细，默认只返回总览摘要和必要的首屏数据。后台可额外返回：

| 字段 | 说明 |
| --- | --- |
| `stats` | 分类数量、附件数、异常数 |
| `source_summary` | 来源统计 |
| `ai_task_summary` | AI 识别任务统计 |
| `quality_flags` | 异常标记 |
| `permissions` | 当前管理员可见字段/可执行动作 |

接口策略：

1. 后台不建议直接复用客户端 `complete-data` 接口作为管理端接口。
2. 后台应新增 admin 专用聚合接口，返回口径参考 `RemoteMemberCompleteData`，但允许增加统计、质量标记、来源链路、权限信息和审计辅助字段。
3. 这样后期可以兼容更多后台分析需求，例如数据质检、AI 识别链路、共享关系、导出、脱敏控制，而不影响客户端接口性能和兼容性。
4. 成员完整接口只返回总览与必要摘要；各分类列表仍走分页接口，避免大用户一次性加载过多数据。

### 15.4 分类列表

为了性能，成员页 tabs 不建议一次拉全部大列表。已确认采用分页加载，提供分类分页接口：

`GET /api/admin/v1/medical-data/users/{user_id}/members/{member_id}/{resource_type}/`

`resource_type` 建议：

- `medical-cases`
- `health-exam-reports`
- `examination-reports`
- `medicine-boxes`
- `family-medicine-boxes`
- `prescriptions`
- `medication-plans`
- `medication-records`
- `symptoms`
- `visits`
- `surgeries`
- `follow-ups`
- `attachments`

### 15.5 详情

`GET /api/admin/v1/medical-data/resources/{resource_type}/{resource_id}/`

返回详情、附件、AI 识别信息、关联数据、审计摘要。

| `api:medical_data:member:complete` | 查询成员完整医疗数据 |

| `button:medical_data:raw_json:view` | 查看原始 JSON |
| `button:medical_data:attachment:view` | 预览附件 |
| `button:medical_data:attachment:download` | 下载单个附件 |
| `button:medical_data:sensitive:view` | 查看未脱敏敏感字段 |
| `button:medical_data:export` | 导出 |

审计要求：

1. 查看成员完整医疗数据需要写审计日志。
2. 查看附件原图/PDF 需要写审计日志。
3. 下载单个附件需要写审计日志。
4. 查看原始 JSON 需要写审计日志。
5. 查看未脱敏字段需要写审计日志。

8. 审计日志中不要记录完整敏感医疗内容，只记录资源类型和 ID。

1. 不新增单独的“医疗数据管理员”角色。
2. 继续使用现有 RBAC，按菜单、接口、按钮权限控制可见范围。

## 17. 隐私与合规策略

已确认与仍需评审的隐私合规点：

1. 管理员是否默认可以看到完整医疗数据？
2. 是否需要按角色区分“运营可看统计，客服可看脱敏，研发/超级管理员可看完整”？
3. 成员姓名、生日、性别、诊断、报告结论、附件原图是否默认脱敏？
4. 附件 URL 是否应使用短期签名 URL？
5. 原始 JSON 是否可能包含身份证号、手机号、医院号、条形码、二维码？
6. 附件允许单个下载，但必须权限控制、短期签名 URL、审计记录；批量下载后期再评估。
7. 不展示管理员水印。
8. 是否需要限制同一管理员短时间查看大量用户医疗数据？
9. 用户注销后医疗数据如何处理：删除、匿名化、保留审计？
10. 家庭共享成员数据，管理员查看时是否需要同时审计被共享成员和入口用户？
11. AI 识别原始输出是否可能包含模型幻觉内容，应如何标记？
12. 是否需要医疗免责声明：后台数据仅用于运营分析和问题排查，不用于诊断？

## 18. 数据质量与异常状态

建议后台主动展示异常，避免只做“看数据”：

| 异常 | 说明 |
| --- | --- |
| 附件缺失 | 数据有附件 ID，但文件不可访问 |
| 明细未加载 | 报告存在但 `medExamDetails` 为空 |
| 识别失败 | AI 任务失败 |
| 识别结果未保存 | 任务成功但无对应医疗资源 |
| 重复报告 | 同成员同日期同机构疑似重复 |
| 日期异常 | 未来日期、过早日期、开始晚于结束 |
| 药品过期 | 药盒有效期已过 |
| 库存异常 | 库存为负、单位缺失 |
| 用药计划无药品 | 计划未关联药盒/药品 |
| 处方无计划 | 处方未关联用药计划 |
| 报告异常值未标记 | 明细有超参考范围但未标异常 |
| 病例孤岛 | 病例没有关联任何就诊/报告/处方 |

## 19. 与 AI 对话/异步任务联动

因为背景目标包含“查看用户给 AI 发起对话内容，方便分析”，医疗数据模块建议保留联动：

| 联动 | 行为 |
| --- | --- |
| 医疗资源 -> AI 对话 | 如果数据来自对话或上传识别，展示对话/消息 ID，并可跳转对话详情 |
| 医疗资源 -> 异步任务 | 展示识别任务 ID、状态、耗时、错误 |
| AI 任务 -> 医疗资源 | 从任务页跳转保存后的医疗资源 |
| 用户 -> 对话 | 用户医疗数据列表可跳转用户对话页 |
| 附件 -> 识别结果 | 附件详情展示 OCR/识别原始结果和结构化字段差异 |

需要讨论：

1. 当前服务端是否保留 `resource_id` 与 AI 任务/对话消息的映射？
2. 如果没有映射，是否需要新增 `source_trace` 或 `origin` 字段？
3. AI 识别后用户手动修改字段，是否保留修改前后 diff？
4. 管理员是否能看到完整 prompt、模型返回和工具调用？

| 医疗附件是否允许后台下载 | 允许单个下载，需要权限、短期签名 URL 和审计 |
| 是否需要对管理员展示水印 | 不展示 |
| 是否需要单独的医疗数据管理员角色 | 不需要，沿用现有 RBAC |
| 家庭成员共享关系是否需要可视化 | 需要 |
| `complete-data` 是否适合后台复用 | 后台建设 admin 专用聚合接口，复用客户端模型口径，不直接依赖客户端接口 |
| 大用户数据量很大时如何加载 | 分页加载，成员页和分类列表都不要一次性加载全部 |

### 21.2 推荐方案

以下问题按最符合当前项目和大众后台系统的方式先给出推荐方案：

1. 检查检验明细 `medExamDetails` 建议保留统一基础模型，同时按报告类型增加扩展字段。体检、检验、影像、病理共用“项目、结果、单位、参考范围、异常标记、备注”基础字段，类型特有内容放入 `extra` 或类型详情结构。
2. 处方、药盒、用药计划三者建议建立稳定关联：处方可关联多个用药计划，用药计划可关联一个药盒药品，药盒药品可被多个计划复用。后台列表要允许关联缺失，并展示“未关联”异常。
3. AI 识别失败的数据也要展示，但放在“附件与识别”或数据质检视角中；成员医疗数据列表只展示已保存为结构化医疗资源的数据。
4. 数据可信度建议标记为：用户手动、AI 自动、AI 后人工修改、导入、系统同步、未知。后台列表和详情都展示来源。
5. 搜索一期支持用户、成员、资源标题、医院/机构、医生、药品名、疾病/诊断；二期再做更重的全文搜索。
6. 报告结论和检查指标全文搜索建议二期做，避免一期引入复杂索引和敏感内容检索风险。
7. 未成年人或特殊成员数据不建议默认屏蔽，否则客服排查困难；建议通过脱敏、权限、审计、频控控制风险。如后续有合规要求，再按年龄或成员标签限制。
8. 附件下载一期只做单个文件下载，不做批量下载和批量导出附件。
9. 后台默认只读，所有“编辑、删除、合并、纠错、重新识别并覆盖”都放到后续版本评估。
10. 管理员查看大量医疗数据建议加频控和异常审计告警，但一期可以先记录审计，二期再做告警。
