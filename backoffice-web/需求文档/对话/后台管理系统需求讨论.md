# 后台管理系统对话查看需求讨论

## 1. 背景

当前后台管理系统已有以下一级或二级功能：

| 模块 | 说明 |
| --- | --- |
| 仪表盘 | 后台首页数据概览 |
| 异步任务 | 任务看板、任务管理 |
| 用户管理 | 用户、设备、注销相关管理 |
| 通知中心 | 通知用户、模板、发送活动、发送日志 |
| 版本控制 | 版本配置、检查日志 |
| AI 场景配置 | 场景、模型、Provider、小任务、试用期 |
| 权限管理 | 后台菜单、角色、权限 |
| 审计日志 | 管理员操作留痕 |

为了分析 AI 服务效果、排查用户问题、观察模型回复质量，需要支持服务端后台管理系统查看系统内用户向 AI 发起的对话内容。

本需求建议单独建立一级菜单：`对话`，不要放在 `用户管理` 或 `AI 场景配置` 下面。原因是对话查看既涉及用户，也涉及 AI 模型、工具调用、健康数据、内容安全、隐私合规和审计，独立成菜单更清晰。

## 2. 目标

1. 新增后台一级菜单 `对话`。
2. `对话` 下新增子模块 `用户对话`。
3. 支持查看“有对话的用户列表”。
4. 支持查看某个用户的会话列表。
5. 支持查看某个会话内的消息详情。
6. 页面基础 UI 参考 `/Users/hua/Downloads/Reference/NextChat-main` 的侧边栏会话列表与消息气泡布局。
7. 消息数据模型参考客户端 `ChatMessage` / `ChatMessageBlock` 设计，不把消息简单当作纯文本处理。
8. 需要补充系统管理员权限、分页、搜索、删除状态、注销用户匿名化展示、异常状态等基础问题。

## 3. 需求范围

### 3.1 菜单规划

建议新增：

| 菜单层级 | 菜单名 | 路由建议 | 权限码建议 |
| --- | --- | --- | --- |

- `backoffice-web/src/router/routes.ts`
- `backoffice-web/src/layouts/AdminLayout.vue`
- 后台 RBAC 菜单初始化或权限配置接口

建议页面文件：

- `backoffice-web/src/views/ConversationUsersView.vue`
- `backoffice-web/src/api/modules/conversations.ts`

### 3.2 页面结构

用户对话模块建议采用两级进入：

1. 用户对话列表页：展示有对话的用户列表。
2. 用户会话详情页：左侧展示该用户的会话列表，右侧展示选中会话消息详情。

如果后台当前 tabs 路由体系更适合单页，建议使用：

- `/conversations/users`：用户列表。
- `/conversations/users/:userId`：某用户会话与消息详情。

## 4. 用户对话列表

### 4.1 列表目标

展示系统内“有 AI 对话记录的用户”，用于系统管理员快速定位用户对话行为、分析服务质量和排查问题。

### 4.2 列表字段

| 字段 | 说明 | 口径建议 |
| --- | --- | --- |
| 用户 ID | Django User 主键 | `auth_user.id` |
| 用户名 | 用户名 | `username` |
| 邮箱 | 用户邮箱 | 直接展示原始值；注销/匿名化用户展示匿名化后的用户信息 |
| 状态 | 启用/禁用 | `is_active` |
| 会话数 | 该用户全部会话数量，同时展示已删除会话数 | `ChatThread` |
| 消息总数 | 用户和助手消息总数 | 统计全部消息，同时展示 tombstone 数量 |
| 用户发送次数 | 用户向 AI 发起消息次数 | `role=user`，统计全部用户消息 |
| 助手回复次数 | AI 回复消息次数 | `role=assistant`，统计全部助手消息 |
| 最近对话时间 | 最近一条消息时间 | `max(ChatMessage.created_at)` 或 `ChatThread.updated_at` |
| 最近使用模型 | 最近助手消息模型 | `ChatMessage.model_name` |
| 最近会话标题 | 最近更新会话标题 | `ChatThread.title` |
| 操作 | 查看会话 | 进入用户会话列表 |

你已提出的字段需要保留：

- 展示用户列表。
- 只展示有对话的用户列表。
- 展示最近对话时间。
- 展示创建会话列表。
- 展示发送会话总次数。
- 操作：查看会话。

建议把“创建会话列表”理解为“会话列表入口”和“会话数量”，具体文案可在评审时确认。

### 4.3 筛选与搜索

建议支持：

| 条件 | 说明 |
| --- | --- |
| 用户 ID | 精确搜索 |
| 用户名/邮箱 | 模糊搜索 |
| 最近对话时间 | 时间范围 |
| 是否有用户消息 | 避免只有系统初始化会话 |
| 模型名称 | 过滤某模型产生的对话 |
| 用户状态 | 启用/禁用 |
| 会话数量范围 | 例如会话数大于 10 的用户 |
| 消息数量范围 | 例如消息数大于 100 的重度用户 |

### 4.4 排序

默认排序：

1. 最近对话时间倒序。
2. 用户 ID 倒序作为稳定兜底。

可选排序：

- 最近对话时间。
- 会话数。
- 消息总数。
- 用户发送次数。
- 注册时间。

### 4.5 操作列

| 操作 | 行为 |
| --- | --- |
| 查看会话 | 打开该用户会话列表页面 |

如执行了“后台表格操作列悬浮统一需求文档”，本页面操作列也需要使用统一右侧悬浮操作列组件。

### 5.2 用户会话列表字段

| 字段 | 说明 | 来源 |
| --- | --- | --- |
| 会话 ID | `ChatThread.id` | UUID |
| 标题 | `ChatThread.title` | 为空时显示“未命名会话” |
| 场景 | `ChatThread.scenario` | 当前只有 `chat`，后续可扩展 |
| 当前模型 | `ChatThread.current_model_name` | 会话维度模型 |
| 消息数 | 会话内非 tombstone 消息数 | `ChatMessage` |
| 用户消息数 | 会话内用户发送次数 | `role=user` |
| 助手消息数 | 会话内助手回复次数 | `role=assistant` |
| 最近消息时间 | 最近一条消息创建时间 | `ChatMessage.created_at` |
| 创建时间 | 会话创建时间 | `ChatThread.created_at` |
| 是否置顶 | `ChatThread.is_pinned` | 后台只读展示 |
| 是否删除 | `ChatThread.is_deleted` | 已删除会话也展示，并在会话卡片打标 |

### 5.3 会话筛选

建议支持：

- 会话标题搜索。
- 会话 ID 精确搜索。
- 时间范围。
- 是否已删除。
- 模型名称。
- 是否包含附件。
- 是否包含工具调用。
- 是否包含失败消息。

### 5.4 消息详情基础展示

消息详情按时间线展示：

| 字段 | 说明 |
| --- | --- |
| 消息角色 | `system` / `user` / `assistant` |
| 消息时间 | `created_at` |
| 消息状态 | `delivery_state` |
| 模型 | `model_name` |
| client_message_id | 客户端消息 ID |
| server_message_id | 服务端消息 ID |
| 消息块 | `blocks` |
| 是否 tombstone | 删除占位 |
| server_updated_at | 服务端更新时间 |

展示形态：

- 用户消息靠右或带用户色标。
- 助手消息靠左或带助手色标。
- 系统消息使用中性提示块。
- 消息块之间保留顺序，按 `order_key`、`created_at`、`id` 排序。
- 支持 Markdown 渲染，但必须提供“查看原始文本/JSON”的入口。
- 失败、发送中、流式中断等状态需要有明显 tag。

## 8. 权限与审计

### 8.1 权限口径

当前后台对话查看仅面向系统管理员开放，暂不拆分客服、运营、研发等细粒度角色。系统管理员进入该模块后，所有查看操作全部允许。

| 权限码 | 说明 |
| --- | --- |
| 系统管理员 | 可查看对话菜单、用户对话列表、用户会话列表、消息详情、附件/图片、调试数据、system prompt、role prompt |
| 非系统管理员 | 不展示对话菜单，不允许访问对话相关接口 |

实现要求：

1. 前端菜单只对系统管理员展示。
2. 后端接口必须再次校验系统管理员身份，不能只依赖前端菜单隐藏。
3. 不做按钮级权限拆分，避免重复造轮子和增加不必要复杂度。
4. 当前版本不支持导出、删除、编辑、标注等写操作，因此不需要导出/删除类按钮权限。

### 8.2 审计日志

当前需求重点是系统管理员只读查看。建议保持后台现有审计能力的基础口径：

| 行为 | 说明 |
| --- | --- |
| 进入用户会话列表 | 可记录管理员、目标用户、筛选条件 |
| 查看会话消息详情 | 可记录管理员、目标用户、thread_id |
| 查看调试数据 | 可记录管理员、目标用户、thread_id、message_id |
| 查看附件或图片 | 可记录管理员、附件 ID 或 URL 标识 |

不需要：

1. 不要求填写查看原因。
2. 不需要查看明文二次确认。
3. 不需要单独的敏感内容权限。
4. 不支持导出，因此没有导出审计。

## 9. 隐私与安全

用户已签署协议，本模块用于系统管理员分析服务质量和排查问题，当前需求确认：后台不对会话和消息内容做脱敏、隐藏、水印、改写或额外处理。

### 9.1 展示口径

明确要求：

1. 不脱敏任何对话数据。
2. 不对消息、工具参数、健康数据、医疗数据、附件信息做内容改写。
3. 不在页面展示“正在查看用户隐私数据”等提示。
4. 不给消息详情页面加水印。
5. 不支持按用户请求从后台导出对话。
6. 不支持按用户请求从后台删除对话。

### 9.2 用户删除与注销后的展示

用户删除或注销后的对话仍然需要展示，方便服务端排查历史问题。

处理规则：

| 场景 | 展示规则 |
| --- | --- |
| 会话被删除 | 会话仍展示；会话卡片上增加明显的 `已删除` 标记 |
| 消息 tombstone | 默认在消息时间线中展示删除状态；可用筛选切换是否只看正常消息 |
| 用户注销 | 会话数据保留；用户身份信息按系统已有匿名化结果展示 |
| 用户匿名化 | 用户列表和会话页展示匿名化用户，例如“匿名用户 #123”或系统已有匿名化字段 |
| 注销用户的消息 | 消息内容照常展示，不做二次处理 |

会话卡片删除标记建议：

- 在会话标题右侧展示 `已删除` tag。
- 使用中性色或警示色 tag，不影响点击查看。
- 会话列表支持 `全部 / 正常 / 已删除` 分段筛选。
- 右侧会话信息栏展示 `deleted_at`。

### 9.3 XSS 与富文本

`html` block 不能直接渲染未净化 HTML。

即使不做业务数据脱敏，也不能执行不可信 HTML。安全渲染不属于数据改写，而是前端展示安全要求。

- 默认代码块展示 HTML 源码。
- 如要预览，使用 sandbox iframe 或严格 sanitize。
- 所有 Markdown 渲染禁用危险 HTML。

### 9.4 附件访问

实现要求：

1. 图片优先使用服务端已有附件 URL 或文件服务 URL 展示。
2. 如果 URL 过期或文件不存在，卡片展示 `附件不可访问`，保留原始附件 JSON。
3. 第一阶段支持图片大图预览；其它文件展示文件卡片和原始信息。
4. 不额外隐藏文件名、URL、大小、类型等字段。

## 10. UI 细节建议

### 10.1 用户列表

- 使用后台现有 Ant Design Vue 表格风格。
- 顶部筛选区不要过重，常用筛选第一行展示，高级筛选可折叠。
- 时间统一为中国常用格式，参考已有后台时间展示统一需求。
- 操作列使用统一右侧悬浮操作列。

### 10.2 会话详情页

最终建议采用“独立详情页 + 左侧会话栏 + 右侧消息时间线”的布局，不使用弹窗或抽屉作为主流程。

原因：

1. 对话查看属于高频阅读和分析场景，需要足够横向空间。
2. 会话列表与消息详情需要同时可见，弹窗/抽屉容易拥挤。
3. 当前后台已有 tabs + content 区域，独立页面最符合现有框架。
4. NextChat 的主流对话布局也是左侧会话列表、右侧消息内容，用户认知成本低。

推荐布局：

```text
┌─────────────────────────────────────────────────────────────┐
│ 用户摘要 / 筛选 / 返回用户列表                               │
├───────────────┬─────────────────────────────────────────────┤
│ 会话列表       │ 会话信息                                    │
│ - 标题         ├─────────────────────────────────────────────┤
│ - 消息数       │ 消息时间线                                  │
│ - 最近时间     │ user message                                │
│ - 模型         │ assistant message                           │
│               │ tool / deep thought / attachment / cards     │
└───────────────┴─────────────────────────────────────────────┘
```

Ant Design Vue 组件建议：

| 区域 | 组件 |
| --- | --- |
| 顶部用户摘要 | `a-page-header` 风格区域或普通 flex header、`a-descriptions`、`a-tag` |
| 会话筛选 | `a-input-search`、`a-segmented`、`a-select` |
| 左侧会话列表 | 自定义轻量列表，不使用表格 |
| 会话卡片 | 自定义 div + `a-tag` + `a-typography-text` |
| 消息详情 | 自定义消息时间线，不使用 `a-timeline` 强行套聊天 UI |
| 折叠内容 | `a-collapse` |
| 调试数据 | `a-modal` 或右侧局部 `a-drawer`，只用于排查问题，不承载主流程 |
| 图片预览 | `a-image` / `a-image-preview-group` |
| 加载状态 | `a-spin`、骨架屏 |
| 空状态 | `a-empty` |

页面尺寸：

- 左侧会话栏宽度建议 `300px - 360px`。
- 右侧消息区自适应。
- 顶部用户摘要高度控制在一屏内，不做大卡片堆叠。
- 页面整体使用白底、浅灰分隔线、低饱和 tag，简洁大方。
- 不做营销式大标题、渐变背景、装饰卡片。

### 10.3 消息气泡

参考客户端：

- `ChatMessageBubbleContentView` 中消息气泡包含 padding、背景色、块列表。
- `ChatMessageBlock+Render` 根据 block payload 渲染不同组件。

实现原则：

1. 消息会话必须以正常 Web 对话方式展示，不能做成原始数据表、JSON 浏览器或 block 调试面板。
2. 主界面参考客户端 `ChatMessageBubbleContentView.body` 和 `ChatMessageBlock.render(context:)`：先投影消息时间线，再按 block 类型渲染为用户能读懂的卡片。
3. `payload`、`kind`、`revision`、`order_key`、`tool_call_id` 等字段属于调试信息，不作为默认主视觉。
4. 底层数据只能作为“查看调试数据”的辅助能力，不能代替可视化卡片。
5. 后台需要尽量还原客户端消息卡片处理方式，让系统管理员看到的内容接近用户在 App 里看到的对话内容。

后台第一期可视化展示：

| 类型 | 展示方式 |
| --- | --- |
| 用户文本 | 右侧气泡，浅色背景 |
| 助手文本 | 左侧气泡，白底或灰底 |
| 思考过程 | 折叠面板 |
| 工具调用 | 工具过程卡片，展示工具名、状态、可读输入摘要、可读结果摘要 |
| 图片 | 缩略图网格 |
| 文件 | 文件卡片 |
| 错误 | 红色提示块 |
| 健康/医疗卡片 | 完整可视化卡片，按指标/结论/建议排版 |
| 未知块 | 展示“暂不支持的消息内容”占位卡片，提供调试数据入口 |

消息卡片完整性要求：

1. 每条消息主视觉展示角色、时间、状态、模型；message id 默认收进操作区或调试信息里，避免干扰阅读。
2. 消息正文按 block 顺序完整展示，不能只取第一段文本。
3. 每个 block 默认按客户端卡片方式可视化展示，不在主界面暴露 kind、revision、payload。
4. 消息操作区提供复制 message id、复制 thread id、查看调试数据。
5. 工具调用默认显示可读过程摘要；点击“查看过程”后展示工具名、状态、输入摘要、结果摘要，完整原始数据放调试入口。
6. 支持“一键展开全部工具调用 / 收起全部工具调用”。
7. 图片支持缩略图和大图预览。
8. Markdown 样式参考主流 Web 对话页面：代码块、列表、表格、引用都要可读。
9. 不显示输入框，不支持管理员在后台发消息。

## 11. 统计口径

需要提前确认统计口径，避免后续前后端理解不一致。

| 指标 | 建议口径 |
| --- | --- |
| 有对话用户 | 至少存在一条 `ChatMessage` 的用户 |
| 会话数 | 默认统计全部会话，同时单独给出正常会话数、已删除会话数 |
| 消息总数 | 默认统计全部消息，同时单独给出 tombstone 消息数 |
| 用户发送次数 | `role=user` 的消息数；这是“发送会话总次数”的第一阶段口径 |
| AI 回复次数 | `role=assistant` 的消息数 |
| 最近对话时间 | 最近消息 `created_at`，无消息时用会话 `updated_at` |
| 最近模型 | 最近一条 assistant 消息 `model_name`，为空时用 thread `current_model_name` |
| 失败消息数 | `delivery_state=failed` 或 block `status=failed` |
| 工具调用次数 | block `kind=tool` 数量 |
| 附件消息数 | block `kind in imageGallery/fileAttachments` 或 metadata attachments 非空 |

已定口径：

1. “发送会话总次数”按用户消息数统计，即 `role=user`。
2. AI 回复失败不计入用户发送次数，但计入失败消息数。
3. 同一 `client_message_id` 只保留服务端当前消息记录，统计当前表状态。
4. tombstone 消息需要展示删除状态，不做物理隐藏；页面提供筛选。
5. 已删除会话需要展示，会话卡片增加 `已删除` 标记。

## 12. 性能与分页

### 12.1 后端查询

需要避免在列表中 N+1 查询。

用户列表建议使用聚合查询：

- 按 `ChatMessage.user_id` 聚合消息数、用户消息数、助手消息数、最近对话时间。
- 会话数按 `ChatThread.user_id` 聚合。
- 最近会话可用子查询。

会话列表建议：

- 按用户过滤。
- 注解消息数量、最近消息时间。
- 分页返回。

消息详情建议：

- 只查询指定用户、指定 thread。
- `prefetch_related("blocks")`。
- 长会话分页。

### 12.2 索引检查

现有模型已有部分索引：

- `ChatMessage(user, server_updated_at, id)`
- `ChatMessage(thread, created_at, id)`
- `ChatMessageBlock(message, order_key, created_at)`
- `ChatMessageBlock(user, server_updated_at, id)`

可能需要补充评估：

- `ChatMessage(user, created_at, id)` 用于用户最近对话聚合。
- `ChatMessage(user, role, created_at)` 用于用户发送次数统计。
- `ChatThread(user, is_deleted, updated_at)` 用于会话列表。
- `ChatMessageBlock(kind, status)` 是否需要取决于筛选使用频率。

问题：

1. 当前线上对话量级是多少？用户数、会话数、消息数、block 数分别多大？
2. 是否需要将用户对话统计做成异步汇总表？
3. 用户列表统计是否接受分钟级延迟？
4. 是否需要限制最大 page_size？

## 13. 导出、删除与运营分析

当前版本明确不支持后台导出或删除对话。

不做：

- 不导出单个会话 JSON。
- 不导出单个会话 Markdown。
- 不导出某用户一段时间内对话。
- 不提供后台删除会话或消息能力。
- 不提供按用户请求导出或删除对话数据的后台入口。

原因：

1. 第一阶段目标是只读查看和问题排查。
2. 导出和删除属于更高风险能力，容易扩大需求范围。
3. 后续如要做导出，需要单独评审文件存储、下载有效期、操作审计和权限。

## 14. 内容分析扩展

后续可以考虑：

- 高频问题统计。
- 模型回复失败率。
- 用户满意/重试/删除行为。
- 工具调用成功率。
- 会话标签。

## 15. 已定方案与剩余问题

### 15.1 产品问题

已定：

1. `对话` 建议作为一级菜单。
2. 子模块第一期只做 `用户对话`。
3. 用户列表中“发送会话总次数”按用户消息数统计，即 `role=user`。
4. 最近对话时间优先使用最近消息时间。
5. 已删除会话也展示，并在会话卡片标记 `已删除`。
6. tombstone 消息展示删除状态，不做物理隐藏。
7. 用户详情页和用户对话页建议互相跳转。

剩余可实现时确定：

1. 会话标题为空时展示“未命名会话”还是“新会话”。
2. 第一阶段是否需要按患者/家庭成员筛选。

### 15.2 权限最终方案

当前只有系统管理员拥有对话查看权限，权限操作全部允许。

具体结论：

1. 只有系统管理员可以看到 `对话` 一级菜单和 `用户对话` 子菜单。
2. 系统管理员可以查看用户列表、会话列表、消息详情、附件、图片、调试数据、system prompt、role prompt。
3. 不做客服、运营、研发等角色拆分。
4. 不做敏感内容查看二次确认。
5. 不要求填写查看原因。
6. 不做字段级明文权限开关。
7. 当前版本不支持导出。
8. 当前版本不支持后台删除会话或消息。
9. 后端所有接口必须校验系统管理员身份，防止绕过前端菜单直接访问接口。

### 15.3 隐私合规最终方案

用户已签署协议，当前查看需求完全合规。后台展示对话时不脱敏、不改写、不额外处理任何会话和消息数据。

具体结论：

1. 不脱敏任何数据。
2. 不对健康、医疗、工具参数、图片、文件、system prompt、role prompt 做隐藏或摘要替换。
3. 不在页面展示“正在查看用户隐私数据”。
4. 不加水印。
5. 用户删除后的对话也要展示。
6. 已删除会话在会话卡片上增加 `已删除` 标记。
7. 用户注销后，会话数据保留；用户身份信息按已有匿名化结果展示，消息内容照常展示。
8. 暂不支持按用户请求导出对话数据。
9. 暂不支持按用户请求删除对话数据。

### 15.4 技术问题解决方案

#### 15.4.1 现有 `chat_sync` 数据是否完整同步所有客户端 block

现状分析：

- 服务端 `ChatRemoteMessageSerializer.blocks` 要求上传 `blocks` 数组。
- 服务端 `_upsert_message_blocks` 将每个 block 原样保存到 `ChatMessageBlock.payload`。
- 服务端 `kind`、`status`、`revision`、`order_key`、`tool_call_id`、`node_role`、`anchor` 等字段会从 block 中提取成独立列。
- 客户端 `ChatMessageBlockKind` 当前包含 text、deepThought、tool、imageGallery、fileAttachments、healthCards、structuredHealthCards、nutritionCards、medicalRiskNotice 等多种类型。

解决方案：

1. 后台接口直接读取 `ChatMessage.blocks` 关联数据，不重新推断消息内容。
2. 前端按 `block.kind` 做渲染分发，未识别的类型使用“暂不支持的消息内容”可视化占位兜底，并提供调试数据入口。
3. 后端响应保留完整 `payload`，避免后台遗漏客户端新类型。
4. 后续新增客户端 block 类型时，后台不需要阻塞上线，先通过“暂不支持的消息内容”占位卡片兜底，再补专用卡片。

#### 15.4.2 是否存在客户端本地有、服务端没有的 block 类型

可能存在，尤其是客户端自动追加、旧版本迁移、远端暂未支持的 block。

现有线索：

- 客户端已有 `mergingRemotePreservingLocalHealthResourceBlocks`，说明历史上存在远端 push/拉取尚未支持部分 block 的情况。
- 服务端当前 `ChatMessageBlock.kind` 是字符串，不限制枚举，具备兼容新类型的基础。

解决方案：

1. 后台以服务端已入库数据为准展示。
2. 对未入库的客户端本地-only 内容，后台无法展示；这是同步链路问题，不在后台页面补造数据。
3. 在需求中增加“block 同步完整性检查”：研发可用客户端样例对比服务端 `ChatMessageBlock` 是否缺失。
4. 后台页面提供 `blocks_count` 和调试数据查看，方便发现缺失类型。

#### 15.4.3 `metadata.attachments` 与 `blocks` 内附件是否重复

现状分析：

- 服务端 `_to_payload` 会返回 `metadata.attachments`。
- 同时消息 block 可能包含 `imageGallery` 或 `fileAttachments`。
- 旧消息或兼容消息可能只在 `metadata.attachments` 有附件。

解决方案：

1. 展示优先级：先展示 `blocks` 中的 `imageGallery` / `fileAttachments`。
2. 如果 `blocks` 中没有附件 block，但 `metadata.attachments` 非空，则渲染一个“历史附件”block。
3. 如果两边都有，前端按附件 URL、文件 ID、文件名+大小生成去重 key，避免重复展示。
4. 调试数据里仍完整展示 `metadata.attachments` 和 block payload，不做删除。

#### 15.4.4 `server_message_id` 是否总是非空

现状分析：

- 服务端模型 `server_message_id` 是 `CharField`，并有唯一约束。
- 序列化入参允许 `server_message_id` 为空或缺失。
- 实际入库逻辑需要保证生成服务端 ID，否则唯一约束和排查链路都会受影响。

解决方案：

1. 后台展示时同时展示服务端自增 `id`、`client_message_id`、`server_message_id`。
2. 如果 `server_message_id` 为空，页面显示 `未生成` tag，不阻塞消息展示。
3. 后端接口返回 `message_db_id` 作为兜底定位字段。
4. 后续服务端应统一在入库时补齐 `server_message_id`，建议格式保持现有逻辑，不在后台页面生成。

#### 15.4.5 消息流式更新中 `revision` 如何展示

现状分析：

- `ChatMessageBlock.revision` 是单调本地版本，用于幂等 upsert。
- `status` 可能是 `pending`、`streaming`、`ready`、`failed`。
- 后台看到的是服务端当前落库态，不是实时流式过程。

解决方案：

1. 主界面展示 block 对应的可视化状态，例如“流式中”“失败”“已完成”。
2. `streaming` 状态显示为“流式中/未完成”，但仍保持聊天卡片样式。
3. `failed` 状态显示为“失败”提示卡片，并保留错误内容。
4. 消息级 `delivery_state` 在消息头部轻量展示，block 级 `status` 放入调试数据。
5. 调试数据保留完整 revision，方便排查覆盖更新。

#### 15.4.6 block 的 `order_key` 为空时排序如何兜底

现状分析：

- 服务端 `ChatMessageBlock.Meta.ordering = ["order_key", "created_at", "id"]`。
- 数据库中空值排序在不同数据库表现可能不完全一致。
- 客户端合并逻辑中已有 `orderKey` 优先，否则按 `createdAt` 兜底的思路。

解决方案：

1. 后端接口返回消息块时显式排序，不完全依赖模型默认 ordering。
2. 推荐排序：有 `order_key` 的 block 按 `order_key asc` 在前；没有 `order_key` 的 block 按 `created_at asc, id asc` 兜底。
3. 如果要完全贴近客户端展示，可使用：`order_key is null`、`order_key`、`created_at`、`id` 的组合排序。
4. 前端不要自行重排后端返回结果，只按接口顺序渲染。

#### 15.4.7 是否需要兼容旧版本消息结构

需要兼容。

解决方案：

1. 新结构：优先渲染 `ChatMessageBlock`。
2. 旧结构：如果没有 blocks，但 `metadata.attachments`、`reasoning_content`、普通文本字段存在，则后端生成兼容展示字段或前端生成虚拟 block。
3. 未知 payload：统一展示 JSON。
4. 缺失字段：前端全部按可选字段处理，不因为单个 block 缺字段导致整条消息渲染失败。

#### 15.4.8 后台接口放在哪个模块

推荐放在现有 `backoffice` app 内，不新增 `conversation_admin` 模块。

原因：

1. 当前后台管理相关接口集中在 `backoffice`。
2. 对话查看是后台只读能力，不是 chat_sync 面向客户端同步协议的一部分。
3. 放在 `backoffice` 可以复用现有后台权限、响应格式、审计和路由风格。
4. 避免新增 app 带来迁移、配置和维护成本。

建议文件：

- `backoffice/views.py`：新增 conversation admin views 或拆分后再引入。
- `backoffice/serializers.py`：新增对话后台 serializer。
- `backoffice/urls.py`：新增 `/api/admin/v1/conversations/...` 路由。

如果后续代码过大，再在 `backoffice` 内拆出 `conversation_views.py`、`conversation_serializers.py`，仍归属 `backoffice` app。

#### 15.4.9 大 JSON payload 是否需要截断展示

业务数据不做处理，但 UI 需要避免大 JSON 撑爆页面。

解决方案：

1. 接口返回完整 JSON。
2. 消息卡片默认展示可读摘要。
3. 调试数据放在弹窗或抽屉中查看。
4. 调试数据容器设置最大高度和滚动，不截断数据。
5. 提供复制调试数据按钮。
6. 如果浏览器渲染明显卡顿，再增加“点击加载调试数据”的懒加载交互，但不改变数据内容。

#### 15.4.10 是否需要后端提供 block 摘要字段

建议后端提供轻量摘要字段，前端仍保留完整 payload。

原因：

1. 用户列表和会话列表需要快速展示最近消息摘要。
2. 不同 block 类型的摘要规则放在后端更稳定，避免多个前端重复实现。
3. 摘要只用于列表预览，不替代消息详情完整展示。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `message_preview` | 消息文本预览或 block 摘要 |
| `block_summary` | 单个 block 的展示摘要 |
| `block_kinds` | 会话包含的 block 类型集合 |
| `has_tool` | 是否包含工具调用 |
| `has_attachment` | 是否包含图片/文件 |
| `has_failed_message` | 是否有失败消息 |

摘要生成规则：

1. `text`：取前 120 字用于列表。
2. `deepThought`：显示“AI 思考过程”。
3. `tool`：显示“工具调用：工具名”。
4. `imageGallery`：显示“图片 N 张”。
5. `fileAttachments`：显示“文件 N 个”。
6. 健康/医疗卡片：显示 block 类型中文名。
7. 未知类型：显示 `未知内容：kind`。

### 15.5 UI 最终方案

#### 15.5.1 会话列表形态

采用新页面左侧栏，不使用弹窗/抽屉承载会话列表。

最终方案：

1. `/conversations/users` 展示有对话用户列表。
2. 点击“查看会话”进入 `/conversations/users/:userId`。
3. 用户会话页左侧是会话列表，右侧是消息详情。
4. 会话列表使用自定义轻量卡片，参考 NextChat 的会话列表信息密度，但视觉上贴合当前后台 Ant Design Vue。

#### 15.5.2 移动端与窄屏

后台以桌面为主，但窄屏不能错乱。

方案：

1. 桌面端使用左右分栏。
2. 宽度不足时左侧会话栏可折叠为窄栏或顶部选择器。
3. 不要求做完整移动端聊天体验。
4. 最低保证 1280px 桌面宽度体验优秀，1024px 不错乱。

#### 15.5.3 会话列表是否拖拽

不支持拖拽。

原因：

1. 后台是只读分析场景，不需要改变会话顺序。
2. 拖拽会暗示可编辑，不符合后台查看语义。
3. 排序统一由最近对话时间、创建时间、消息数等筛选控制。

#### 15.5.4 消息搜索

需要支持消息搜索，但第一阶段做轻量实现。

方案：

1. 会话列表支持标题搜索。
2. 消息区顶部支持关键词搜索当前会话消息。
3. 命中关键词高亮。
4. 支持上一条/下一条命中跳转。
5. 跨全部会话全文搜索可后续单独做，不放入第一阶段。

#### 15.5.5 一键复制 ID

需要支持。

复制项：

- user_id。
- thread_id。
- message_db_id。
- client_message_id。
- server_message_id。
- block_id。
- tool_call_id。

UI：

- 使用 Ant Design Vue 图标按钮。
- 默认只显示复制图标，hover tooltip 展示含义。
- 复制成功使用 `message.success`。

#### 15.5.6 调试数据

需要提供调试数据查看能力，并支持复制，但不能影响正常对话阅读。

方案：

1. 每条消息提供“查看调试数据”按钮。
2. 每个 block 在调试数据弹窗中提供完整 block 数据。
3. 调试数据使用等宽字体、浅灰背景、可滚动容器。
4. 调试数据弹窗宽度建议 `960px` 或 `80vw`。
5. 不截断、不改写底层数据。

#### 15.5.7 工具调用展开

工具调用默认折叠，需要支持展开全部。

方案：

1. 单个 tool block 使用工具过程卡片或 `a-collapse`。
2. tool header 展示工具名称、可读状态、耗时或更新时间。
3. 展开后优先展示可读参数摘要、可读结果摘要、父 tool 关系；完整底层数据在调试入口查看。
4. 消息区顶部提供“展开全部工具 / 收起全部工具”。

#### 15.5.8 图片大图预览

需要支持。

方案：

1. 图片 block 使用缩略图网格。
2. 点击缩略图打开 `a-image-preview-group` 大图预览。
3. 图片加载失败展示失败占位和原始 URL/JSON。
4. 多图支持左右切换。

#### 15.5.9 视觉风格

页面 UI 需要简洁大方，和主流 Web 对话页面看齐，同时符合当前后台框架。

视觉要求：

1. 使用 Ant Design Vue 作为基础组件，不重复造轮子。
2. 左侧会话卡片简洁，包含标题、最近时间、消息数、模型、删除 tag。
3. 消息卡片完整展示，但视觉上不堆满边框。
4. 用户消息和助手消息用轻微背景差异区分，避免高饱和颜色。
5. block 卡片使用统一圆角、统一间距、统一标题行。
6. Markdown、代码块、表格、图片、文件卡片需要完整可读。
7. 不做渐变背景、装饰图形、大面积彩色卡片。
8. 整体贴近主流 ChatGPT / NextChat 类 Web 对话阅读体验，但保持后台管理系统的克制和密度。

## 18. 工单 `CONVERSATION-000002`：医疗数据加载性能与稳定性优化

### 18.1 背景

对话消息中可能包含大量医疗数据、用户健康数据、检查报告、处方、用药记录、家庭成员健康资料、工具调用结果、结构化健康卡片等内容。

这些数据具有以下特点：

1. 数据量大：单个用户可能有多份报告、多次问诊、多条健康记录和大量附件。
2. 嵌套深：医疗数据可能以 block payload、tool result、health resource reference、structured health cards 等多种形式存在。
3. 加载慢：如果进入会话详情时一次性加载完整医疗数据，接口容易变慢。
4. 容易失败：大 payload、大附件、跨表查询、外部文件访问都可能造成超时或失败。
5. 消耗资源：后端查询、JSON 序列化、网络传输、前端渲染都会被大数据拖慢。

本工单目标是修复“医疗数据 / 用户医疗数据加载慢、加载失败、资源消耗过高”的问题，同时保持后台消息主界面仍以正常对话卡片方式展示，不退化成原始数据浏览器。

### 18.2 问题表现

| 问题 | 表现 |
| --- | --- |
| 首屏慢 | 打开用户会话详情时等待很久，甚至白屏 |
| 接口超时 | 消息详情接口因为大 payload 或跨表查询超时 |
| 前端卡顿 | 浏览器渲染大量医疗 JSON、报告内容、图片附件时卡顿 |
| 内存占用高 | 一次性加载完整用户医疗数据导致浏览器内存上涨 |
| 失败不可恢复 | 某个医疗数据块加载失败后整条消息或整个会话不可用 |
| 重复加载 | 切换会话、展开卡片、返回页面时重复请求同一批大数据 |
| 无降级 | 医疗数据不可用时没有摘要、占位和重试入口 |

### 18.3 优化目标

1. 对话首屏优先加载会话结构和消息可视化摘要。
2. 大型医疗数据默认不随消息详情首包全量返回。
3. 健康/医疗卡片先展示可读摘要，再按需加载完整详情。
4. 单个医疗数据块加载失败不能影响整条消息时间线展示。
5. 后端接口避免大范围跨表查询和 N+1 查询。
6. 前端避免一次性渲染大 JSON、大表格、大附件列表。
7. 增加缓存、分页、懒加载、局部重试、加载状态和失败占位。
8. 保持数据不脱敏、不改写；优化的是加载方式和展示方式，不改变数据内容。

### 18.4 总体方案

采用“轻量首包 + 按需详情 + 分块加载 + 局部失败降级”的方案。

```text
进入会话详情
    ↓
加载会话列表 + 消息时间线基础数据
    ↓
每条消息展示正常对话卡片
    ↓
医疗/健康 block 先展示摘要卡片
    ↓
管理员点击“展开详情”
    ↓
按 block_id / resource_id 单独加载完整医疗数据
    ↓
成功：替换为完整可视化卡片
失败：保留摘要 + 显示失败原因 + 提供重试
```

### 18.5 后端接口优化

#### 18.5.1 消息详情接口分层

现有消息详情接口建议只返回消息基础字段、block 基础字段和可视化摘要，不返回大型医疗详情。

```http
GET /api/admin/v1/conversations/users/{user_id}/threads/{thread_id}/messages/
```

返回建议：

| 字段 | 说明 |
| --- | --- |
| `message` | 消息基础信息 |
| `blocks` | block 基础信息 |
| `block_summary` | 可视化摘要 |
| `has_heavy_detail` | 是否存在大型详情数据 |
| `detail_load_mode` | `inline` / `lazy` |
| `detail_endpoint` | 懒加载详情接口 |
| `detail_status` | `not_loaded` / `loaded` / `failed` |

医疗数据详情单独提供接口：

```http
GET /api/admin/v1/conversations/users/{user_id}/threads/{thread_id}/blocks/{block_id}/detail/
```

用于按需加载：

- `structuredHealthCards`
- `healthCards`
- `nutritionCards`
- `healthResourceReference`
- `sleepVisualization`
- `workoutVisualization`
- 大型 tool result
- 大型附件 metadata

#### 18.5.2 医疗数据摘要字段

后端需要为大型医疗数据生成轻量摘要，供首屏展示。

| 类型 | 摘要内容 |
| --- | --- |
| 体检报告 | 报告名称、报告时间、机构、异常指标数量、结论摘要 |
| 处方 | 药品数量、开具时间、用药提醒摘要 |
| 用药记录 | 药品名、剂量、最近记录时间 |
| 健康指标 | 指标名称、最近值、趋势、是否异常 |
| 睡眠 | 总时长、深睡/浅睡摘要、睡眠评分 |
| 运动 | 运动类型、时长、消耗、心率摘要 |
| 营养 | 热量、蛋白质、脂肪、碳水、建议摘要 |
| 工具结果 | 工具名、状态、结果摘要、是否有完整详情 |

摘要要求：

1. 摘要必须足够小，适合会话首屏展示。
2. 摘要不是脱敏，不改变数据含义，只是减少首包体积。
3. 完整数据可通过详情接口按需加载。

#### 18.5.3 分页与游标

大型医疗数据详情必须分页或分段。

建议：

| 场景 | 策略 |
| --- | --- |
| 报告列表 | `page/page_size` 或 cursor |
| 指标历史 | 按时间范围分页 |
| 工具结果长列表 | 分段返回 |
| 附件列表 | 分页返回 |
| 大型结构化 JSON | 按 section 返回 |

示例：

```http
GET /api/admin/v1/conversations/users/{user_id}/medical/resources/{resource_type}/{resource_id}/sections/
GET /api/admin/v1/conversations/users/{user_id}/medical/resources/{resource_type}/{resource_id}/sections/{section_key}/
```

#### 18.5.4 查询优化

后端需要避免大范围查询。

要求：

1. 所有医疗详情接口必须按 `user_id`、`member_id`、`resource_id` 精确过滤。
2. 列表页不查询完整医疗详情，只查询摘要字段。
3. 消息详情接口不跨表加载完整医疗资源。
4. 避免在 serializer 中循环查询医疗资料。
5. 对高频筛选字段补充索引。
6. 对大型 JSONField 避免无条件反序列化和返回。

可能需要评估的索引：

| 模型/数据 | 索引建议 |
| --- | --- |
| 医疗资源 | `user_id, member_id, created_at` |
| 报告/检查 | `user_id, resource_type, resource_id` |
| 健康指标 | `user_id, member_id, metric_type, measured_at` |
| 聊天 block | `message_id, kind, order_key` |
| 工具调用 | `tool_call_id, parent_tool_call_id` |

### 18.6 缓存与预计算

#### 18.6.1 摘要缓存

为大型医疗数据生成摘要缓存。

缓存内容：

- 医疗资源标题。
- 时间。
- 类型。
- 关键指标。
- 异常数量。
- 简短结论。
- block 可视化摘要。

缓存更新策略：

1. 医疗数据写入或同步后更新摘要。
2. block payload 更新后更新 block 摘要。
3. 缓存失效时接口可同步生成一次，但必须限制耗时。
4. 生成失败时返回基础占位摘要。

#### 18.6.2 会话级统计缓存

用户会话列表中的消息数、医疗 block 数、附件数、失败消息数等可做汇总缓存，避免每次进入列表实时聚合。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `medical_block_count` | 医疗/健康 block 数 |
| `heavy_block_count` | 大型详情 block 数 |
| `attachment_count` | 附件数量 |
| `failed_detail_count` | 详情加载失败数量 |
| `last_medical_resource_at` | 最近医疗资源时间 |

### 18.7 前端加载与渲染优化

#### 18.7.1 首屏加载策略

页面进入时只加载：

1. 用户摘要。
2. 会话列表第一页。
3. 当前会话最近消息第一页。
4. 消息可视化摘要。
5. 医疗/健康卡片摘要。

不在首屏加载：

- 完整体检报告。
- 完整工具结果。
- 大型结构化健康数据。
- 全量附件 metadata。
- 大型调试数据。

#### 18.7.2 懒加载策略

以下内容必须点击或进入可视区域后再加载：

| 内容 | 触发方式 |
| --- | --- |
| 医疗卡片完整详情 | 点击“展开详情” |
| 工具完整过程 | 点击“查看过程” |
| 图片大图 | 点击缩略图 |
| 附件完整信息 | 点击文件卡片 |
| 调试数据 | 点击“查看调试数据” |
| 历史消息 | 点击“向上加载历史消息”或滚动到顶部 |

#### 18.7.3 局部 loading 与失败降级

每个大型医疗卡片独立 loading，不能阻塞整个消息时间线。

卡片状态：

| 状态 | UI |
| --- | --- |
| 未加载 | 显示摘要 + `展开详情` |
| 加载中 | 卡片内部 skeleton/loading |
| 加载成功 | 展示完整可视化详情 |
| 加载失败 | 保留摘要 + 显示失败原因 + `重试` |
| 数据不存在 | 显示 `数据不可用`，保留 resource id |

#### 18.7.4 前端渲染保护

1. 长消息列表使用分页或虚拟滚动，避免一次渲染全部 DOM。
2. 大型卡片展开后再挂载内容，收起时可释放重型 DOM。
3. Markdown 代码块、表格、大文本设置最大高度和滚动。
4. 图片使用缩略图，避免直接加载原图。
5. 调试数据弹窗点击后再请求，不随消息首包返回。
6. 切换会话时取消未完成请求，避免旧请求覆盖新会话。

### 18.8 超时、重试与降级

后端接口建议：

| 接口 | 超时策略 |
| --- | --- |
| 消息列表 | 必须快，超时前返回基础消息和摘要 |
| 医疗详情 | 可单独超时，不影响消息列表 |
| 附件详情 | 可失败占位 |
| 调试数据 | 可懒加载，失败可重试 |

前端重试：

1. 每个医疗卡片提供局部重试。
2. 会话消息列表提供整体刷新。
3. 调试数据加载失败后可重试。
4. 重试按钮不能造成重复并发请求。

降级策略：

1. 摘要可用、详情失败：继续展示摘要。
2. 详情接口超时：提示 `详情加载超时，请重试`。
3. 数据不存在：提示 `医疗数据不可用`。
4. 附件失效：提示 `附件不可访问`。
5. 未支持类型：展示占位卡片，不影响其它消息。

### 18.9 可观测性与排查

需要增加性能埋点或日志，便于确认优化效果。

后端记录：

| 指标 | 说明 |
| --- | --- |
| 消息列表接口耗时 | p50 / p90 / p99 |
| 医疗详情接口耗时 | p50 / p90 / p99 |
| 单次返回 payload 大小 | 避免首包过大 |
| 查询次数 | 发现 N+1 |
| 慢查询 | 定位索引问题 |
| 详情加载失败原因 | 超时、权限、数据不存在、序列化异常 |

前端记录：

| 指标 | 说明 |
| --- | --- |
| 首屏可见时间 | 进入会话到看到消息摘要 |
| 医疗卡片展开耗时 | 点击展开到详情展示 |
| 详情加载失败率 | 按 block kind 统计 |
| 前端渲染错误 | 卡片渲染异常 |
| 请求取消次数 | 切换会话时取消旧请求 |

### 18.10 实施阶段

#### 阶段一：止血优化

1. 消息详情接口不返回大型医疗详情。
2. 医疗 block 先展示摘要卡片。
3. 调试数据改为点击后加载。
4. 医疗详情卡片增加局部 loading、失败占位、重试。
5. 前端切换会话时取消旧请求。

#### 阶段二：结构优化

1. 新增 block detail 接口。
2. 新增医疗资源 section 接口。
3. 增加摘要缓存。
4. 优化后端查询和索引。
5. 会话列表增加医疗数据统计摘要。

#### 阶段三：体验与稳定性优化

1. 长消息列表虚拟滚动或分页增强。
2. 大型卡片展开后按 section 加载。
3. 图片缩略图和附件预览优化。
4. 增加性能监控和慢接口告警。

### 18.11 验收标准

1. 打开用户会话详情时，不因医疗数据量大导致整页加载失败。
2. 消息时间线首屏先展示可视化摘要，不等待完整医疗详情。
3. 医疗/健康卡片可点击展开详情，详情加载失败时有局部错误提示和重试。
4. 单个医疗 block 加载失败不影响其它消息展示。
5. 调试数据不随首包返回，点击后再加载。
6. 会话切换时不会出现旧请求覆盖新会话内容。
7. 大型附件、图片、报告不会一次性全部加载。
8. 后端消息列表接口无明显 N+1 查询。
9. 首屏接口 payload 大小明显下降。
10. 前端长会话滚动和展开大型医疗卡片时不明显卡顿。
