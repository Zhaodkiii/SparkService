## 工单 `ACCOUNTS-000001`：单账号仅允许一个有效设备登录

### 1. 背景

### Q：现在要解决什么问题？

A：当前 `TrustedDevice` 是“安装实例维度”的可信设备记录：

```text
SparkService/accounts/models.py:17-61
```

现有模型能记录：

1. `user`：设备当前关联的用户。
2. `bundle_id + device_id`：安装实例唯一键。
3. `push_token` / `notifications_enabled`：推送能力。
4. `is_revoked`：设备是否吊销。

但它还不能表达“某个用户当前唯一有效登录设备是哪一台”。因此在 A1、A2 两台设备都登录同一个用户时，会出现：

1. A1 和 A2 都可能继续持有可刷新的 refresh token。
2. A1 没有手动退出时，A2 登录不会自动让 A1 的刷新链路失效。
3. APNs 通知可能投递到该用户关联的多台设备，而不是只投递当前有效设备。

本需求要求：**一个用户同一时间只有一个设备有效登录。后登录设备取代先登录设备。旧设备再次刷新 token、打开 App 恢复会话，或提交任何需要登录态的业务请求时，服务端必须返回未授权，触发客户端强制退出。**

### 2. 目标场景

### Q：A1、A2 两台设备应该如何表现？

A：

```text
用户1先在 A1 登录
  -> A1 成为用户1当前有效登录设备
  -> A1 refresh token 正常刷新
  -> 通知只发 A1

用户1未退出 A1，又在 A2 登录
  -> A2 成为用户1当前有效登录设备
  -> A1 的登录会话被服务端标记为失效
  -> 通知只发 A2

A1 再次打开 App，尝试刷新 token
  -> 服务端发现 A1 不是当前有效登录设备
  -> refresh 失败，返回 401 / token_not_valid / device_session_revoked
  -> 客户端强制退出登录

A1 如果没有先触发 refresh，而是直接提交任意登录态业务请求
  -> 服务端仍然发现 A1 不是当前有效登录设备
  -> 业务请求返回 401 / device_session_revoked / device_session_replaced
  -> 客户端强制退出登录

A2 正常使用
  -> A2 refresh token 正常
  -> A2 登录态业务请求正常
  -> 通知继续只发 A2

用户1重新在 A1 登录
  -> A1 成为当前有效登录设备
  -> A2 的登录会话被服务端标记为失效
  -> A2 下次 refresh token 失败并退出
  -> 通知只发 A1
```

### Q：这个需求是否只改服务端？

A：是。本工单只要求服务端实现规则。

客户端行为只依赖现有未授权处理：

1. refresh token 或任意登录态业务请求返回 401。
2. 客户端收到认证失效后清理本地登录态。
3. 客户端回到登录页。

服务端不需要新增客户端接口才能满足核心要求，但登录、刷新和登录态业务接口需要能根据 `device_id + bundle_id` 或 token 中的设备会话标识判断当前请求来自哪台设备。

### 3. 当前问题

### Q：为什么不能只靠 `TrustedDevice.is_revoked`？

A：不建议直接把“被踢下线”和 `TrustedDevice.is_revoked` 混用。

原因：

1. `TrustedDevice` 是设备安装实例，不是登录会话。
2. `is_revoked=True` 更适合表达设备被管理员吊销、账号注销、风控封禁等长期状态。
3. A1 被 A2 顶掉登录，并不代表 A1 这台设备永远不能登录。
4. 如果把 A1 设备直接 `is_revoked=True`，用户重新在 A1 登录时还要额外解除吊销，语义容易混乱。

因此推荐新增“当前有效登录设备 / 登录会话”状态，而不是把所有逻辑塞进 `TrustedDevice`。

### Q：为什么不能只清空旧设备 push_token？

A：清空旧设备 `push_token` 只能阻止通知，不会阻止旧设备刷新 token，也不会阻止旧设备继续提交其他登录态业务请求。

本需求有两个独立目标：

1. 登录会话唯一：旧设备不能继续 refresh，也不能继续调用任何登录态业务 API。
2. 通知设备唯一：APNs 只发当前有效设备。

前者需要会话校验；后者需要通知投递过滤。只处理推送不够。

### 4. 推荐数据模型

### Q：服务端应该新增什么模型？

A：推荐新增账号当前设备会话模型，例如 `AccountDeviceSession`。

示例字段：

```python
class AccountDeviceSession(models.Model):
    class Status(models.TextChoices):
        ACTIVE = "active", "有效"
        REVOKED = "revoked", "已失效"
        LOGGED_OUT = "logged_out", "已退出"

    user = models.ForeignKey(User, related_name="device_sessions", on_delete=models.CASCADE)
    trusted_device = models.ForeignKey(TrustedDevice, related_name="account_sessions", on_delete=models.CASCADE)
    bundle_id = models.CharField(max_length=255, db_index=True, default="")
    device_id = models.CharField(max_length=255, db_index=True, default="")
    session_version = models.PositiveIntegerField(default=1, db_index=True)
    refresh_jti = models.CharField(max_length=255, blank=True, default="", db_index=True)
    status = models.CharField(max_length=32, choices=Status.choices, default=Status.ACTIVE, db_index=True)
    revoked_reason = models.CharField(max_length=64, blank=True, default="")
    replaced_by = models.ForeignKey("self", null=True, blank=True, on_delete=models.SET_NULL)
    last_refreshed_at = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True, db_index=True)
    updated_at = models.DateTimeField(auto_now=True)
```

推荐约束：

```text
同一 user 同一时间最多一个 ACTIVE session
```

如果数据库支持条件唯一约束：

```python
models.UniqueConstraint(
    fields=["user"],
    condition=Q(status="active"),
    name="uniq_active_device_session_per_user",
)
```

### Q：为什么不直接在 `TrustedDevice` 上加 `is_active_login`？

A：可以做最小实现，但长期不推荐。

缺点：

1. `TrustedDevice` 会同时承担“设备画像、推送能力、登录会话、风控吊销”多种职责。
2. 无法记录历史登录会话、替换关系、失效原因。
3. refresh token 的 `jti/session_version` 与设备画像耦合太强。
4. 后续支持后台查看登录历史、主动踢设备、登录安全提醒时会继续膨胀。

因此推荐新增 `AccountDeviceSession`，让 `TrustedDevice` 继续保持设备画像职责。

### 5. 登录签发流程

### Q：登录成功时服务端应该做什么？

A：所有登录入口成功认证后，必须进入统一的设备会话激活流程。

涉及入口：

```text
SparkService/accounts/auth/views.py
SparkService/accounts/services/login_service.py
SparkService/accounts/otp/views.py
SparkService/accounts/services/otp_service.py
```

推荐流程：

```text
login_success(user, bundle_id, device_id)
  -> 找到或创建 TrustedDevice(bundle_id, device_id)
  -> 关联 TrustedDevice.user = user
  -> transaction.atomic()
       -> 查询 user 当前 ACTIVE AccountDeviceSession
       -> 如果当前 ACTIVE 不是本次 device:
            标记旧 session = REVOKED
            revoked_reason = "replaced_by_new_device"
            可选：加入 SimpleJWT blacklist
       -> 为本次 device 创建/激活新的 ACTIVE AccountDeviceSession
       -> 生成 refresh token，并把 session 标识写入 token claim
  -> 返回 access_token / refresh_token
```

### Q：token 中需要写入什么？

A：推荐在 refresh token 中写入至少一个服务端可校验的会话标识：

```text
device_id
bundle_id
device_session_id
session_version
```

关键是 refresh 时服务端能判断：

```text
这个 refresh token 是否属于用户当前 ACTIVE 设备会话
```

如果只从请求 body 读取 `device_id`，有被伪造风险；如果 token claim 和 body 都有，则需要双重校验：

```text
token.device_session_id == active_session.id
token.device_id == request.device_id
token.bundle_id == request.bundle_id
```

### 6. 登录态请求校验

### Q：旧设备为什么会在刷新 token 或提交业务请求时被强制退出？

A：因为服务端不能只在 refresh token 接口校验设备会话。旧设备可能打开 App 后先触发设备登记、最新用户会话刷新、聊天同步、医疗同步、AI 配置刷新等业务请求，如果这些请求仍然通过，就会出现“旧设备虽然 refresh 已失效，但还能继续使用一部分业务能力”的漏洞。

因此需要两层校验：

1. refresh token 接口校验：旧设备不能换取新的 access token。
2. 所有登录态业务 API 校验：旧设备即使暂时持有未过期 access token，也不能继续访问业务接口。

refresh 入口：

```text
SparkService/accounts/auth/views.py: TokenRefreshView
```

推荐校验流程：

```text
TokenRefreshView.post
  -> 校验 refresh token 基础有效性
  -> 解析 user_id / device_session_id / device_id / bundle_id
  -> 查询 AccountDeviceSession
  -> 如果不存在：401 device_session_not_found
  -> 如果 status != ACTIVE：401 device_session_revoked
  -> 如果该 session 不是 user 当前 ACTIVE session：401 device_session_replaced
  -> 如果 request.device_id 与 token.device_id 不一致：401 device_mismatch
  -> 校验通过：签发新的 access token / refresh token
  -> 更新 last_refreshed_at
```

登录态业务 API 推荐校验流程：

```text
Authenticated request
  -> JWTAuthentication 解析 user
  -> 解析请求中的 device_id / bundle_id，或从 access token claim 中读取 device_session_id
  -> 查询 user 当前 ACTIVE AccountDeviceSession
  -> 如果不存在：401 device_session_not_found
  -> 如果请求 session 不是当前 ACTIVE：401 device_session_replaced
  -> 如果 session.status != ACTIVE：401 device_session_revoked
  -> 如果 request.device_id 与 token.device_id 不一致：401 device_mismatch
  -> 校验通过：继续进入业务 view/service
```

建议实现位置：

```text
自定义 Authentication / Permission / Middleware
```

优先建议放在认证/权限层，避免每个业务 view 手写校验导致遗漏。所有 `IsAuthenticated` 的业务接口都应被覆盖；登录、匿名设备登记、验证码发送等匿名接口不走该校验。

### Q：A1 被 A2 顶掉后，A1 的旧 refresh token 是否还需要进 blacklist？

A：建议需要。

实现上可以有两层：

1. 主校验：`AccountDeviceSession.status != ACTIVE` 时拒绝 refresh。
2. 保险校验：如果能拿到旧 refresh token 的 `jti`，把旧 token 加入 SimpleJWT blacklist。

即使 blacklist 因 token rotation 配置或历史 token 处理不完整，也能通过 `AccountDeviceSession` 拒绝旧设备刷新和旧 access token 的业务请求。

### 7. 设备登记流程

### Q：设备登记接口需要怎么调整？

A：`/api/v1/device/register/` 仍然保留设备画像 upsert 能力，但需要配合当前有效登录设备规则。

当前入口：

```text
SparkService/accounts/device/views.py
SparkService/accounts/services/device_service.py
```

建议：

1. 匿名登记：只 upsert `TrustedDevice`，不创建 `AccountDeviceSession`。
2. 登录态登记：可以更新 `TrustedDevice.user` 和画像，但不应单独把设备变成 ACTIVE 登录设备。
3. ACTIVE 登录设备只能由登录成功流程创建/切换。
4. 如果登录态登记来自非当前 ACTIVE 设备，必须返回 401，触发客户端强制退出。

推荐策略：

```text
旧设备打开 App 后如果先调用 /device/register/：
  -> 服务端返回 401 device_session_revoked / device_session_replaced
  -> 客户端强制退出

匿名 /device/register/：
  -> 可以继续登记设备画像
```

即：匿名 `/device/register/` 可以继续登记设备画像；登录态 `/device/register/` 必须遵循单设备会话校验。

### 8. APNs 通知投递

### Q：如何保证一个用户只通知一个设备？

A：通知服务查询 APNs 目标设备时，只能选用户当前 ACTIVE `AccountDeviceSession` 关联的 `TrustedDevice`。

当前相关位置：

```text
SparkService/accounts/services/notification_service.py
```

当前 APNs 查询大致按：

```text
TrustedDevice.objects.filter(user_id=user.id, notifications_enabled=True)
  .exclude(push_token="")
```

这会命中用户多台可推送设备。

需要改为：

```text
active_session = AccountDeviceSession.objects.filter(
    user=user,
    status=ACTIVE,
    trusted_device__notifications_enabled=True,
).exclude(
    trusted_device__push_token=""
).select_related("trusted_device").first()

仅向 active_session.trusted_device.push_token 发送 APNs
```

### Q：后台用户列表里的 APNs 可达状态怎么判断？

A：`NotificationService` 中用户筛选、列表展示、`has_apns` 判断也要切到“当前有效设备”口径。

旧口径：

```text
用户任意 TrustedDevice 有 push_token 即认为 APNs 可达
```

新口径：

```text
用户当前 ACTIVE AccountDeviceSession 对应 TrustedDevice 有 push_token 且 notifications_enabled=True，才认为 APNs 可达
```

### 9. 登出与失效

### Q：用户手动退出登录时怎么处理？

A：服务端应提供或复用登出接口，把当前设备会话标记为 `LOGGED_OUT`。

如果当前没有登出接口，本工单至少要求：

1. refresh token 被新设备替换时返回 401。
2. 用户重新登录其他设备时旧 session 被 `REVOKED`。

后续可补充登出接口：

```text
POST /api/v1/auth/logout/
body: refresh_token, device_id, bundle_id
```

处理：

```text
当前 device_session.status = LOGGED_OUT
refresh token 加入 blacklist
不影响 TrustedDevice 画像
```

### 11. 数据迁移说明

### Q：是否需要考虑历史数据迁移？

A：不需要。

当前按全新项目处理，本工单不要求兼容历史旧会话或历史多设备数据。

需要做的只有：

1. 新增 `AccountDeviceSession` 表结构和约束迁移。
2. 新登录用户从第一次登录开始创建 ACTIVE 设备会话。
3. 不需要为历史 `TrustedDevice` 选择初始 ACTIVE session。
4. 不需要回填历史 session、`refresh_jti` 或替换关系。
5. 不需要兼容老 refresh token 的多设备共存状态；新逻辑上线后按新登录/新 refresh 口径执行。

仍需保持概念区分：

```text
登录唯一性看 AccountDeviceSession
推送可达性看 active_session.trusted_device.push_token + notifications_enabled
```

两者不要混为一谈。

### 12. 错误码与响应

### Q：旧设备 refresh 或提交业务请求应该返回什么？

A：推荐统一返回 401，并使用明确业务 code/msg：

```json
{
  "code": 40104,
  "msg": "device_session_revoked",
  "data": null
}
```

可选错误：

| msg | 含义 |
| --- | --- |
| `device_session_revoked` | 当前设备会话已失效 |
| `device_session_replaced` | 当前设备已被另一台设备登录替代 |
| `device_session_not_found` | token 对应设备会话不存在 |
| `device_mismatch` | 请求设备与 token 设备不一致 |
| `token_not_valid` | refresh token 本身无效 |

客户端不需要区分所有细节，收到 401 即可强制退出；服务端日志和排障需要区分原因。

### 13. 验收标准

1. 用户1在 A1 登录成功后，A1 成为用户1唯一 ACTIVE `AccountDeviceSession`。
2. 用户1在 A2 登录成功后，A1 的 `AccountDeviceSession` 被标记为 `REVOKED`，A2 成为唯一 ACTIVE。
3. A1 未手动退出，重新打开 App 并 refresh token 时，服务端返回 401，原因可识别为 `device_session_revoked` 或 `device_session_replaced`。
4. A1 如果先提交设备登记、用户会话刷新、聊天同步、医疗同步、AI 配置刷新或任意登录态业务 API，也必须返回 401，原因可识别为设备会话失效。
5. A2 refresh token 正常成功。
6. A2 任意登录态业务请求正常成功。
7. 用户1重新在 A1 登录后，A2 的会话被标记为 `REVOKED`，A1 成为唯一 ACTIVE。
8. A2 再 refresh token 或提交任意登录态业务请求时返回 401。
9. APNs 通知只向当前 ACTIVE 会话绑定的 `TrustedDevice.push_token` 投递。
10. 如果旧设备仍有 `push_token`，通知服务也不能向旧设备投递。
11. 如果当前 ACTIVE 设备没有开启通知或没有 `push_token`，APNs 渠道应 `SKIPPED`，不能退回旧设备。
12. `TrustedDevice` 仍保持 `bundle_id + device_id` 唯一，不因多次登录创建重复设备。
13. 旧设备被替换不应永久吊销 `TrustedDevice`，用户重新在旧设备登录后可重新成为 ACTIVE。
