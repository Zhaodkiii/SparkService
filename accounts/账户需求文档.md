## 工单 `ACCOUNTS-000001`：单账号仅允许一个有效设备登录

### 1. 背景

### Q：现在要解决什么问题？

A：当前 `TrustedDevice` 是“安装实例维度”的可信设备记录：

```text
SparkService/accounts/models.py:17-61
```

现有模型能记录：

1. `user`：设备当前关联的用户。
2. `bundle_id + device_id`：安装实例唯一键。
3. `push_token` / `notifications_enabled`：推送能力。
4. `is_revoked`：设备是否吊销。

但它还不能表达“某个用户当前唯一有效登录设备是哪一台”。因此在 A1、A2 两台设备都登录同一个用户时，会出现：

1. A1 和 A2 都可能继续持有可刷新的 refresh token。
2. A1 没有手动退出时，A2 登录不会自动让 A1 的刷新链路失效。
3. APNs 通知可能投递到该用户关联的多台设备，而不是只投递当前有效设备。

本需求要求：**一个用户同一时间只有一个设备有效登录。后登录设备取代先登录设备。旧设备再次刷新 token、打开 App 恢复会话，或提交任何需要登录态的业务请求时，服务端必须返回未授权，触发客户端强制退出。**

### 2. 目标场景

### Q：A1、A2 两台设备应该如何表现？

A：

```text
用户1先在 A1 登录
  -> A1 成为用户1当前有效登录设备
  -> A1 refresh token 正常刷新
  -> 通知只发 A1

用户1未退出 A1，又在 A2 登录
  -> A2 成为用户1当前有效登录设备
  -> A1 的登录会话被服务端标记为失效
  -> 通知只发 A2

A1 再次打开 App，尝试刷新 token
  -> 服务端发现 A1 不是当前有效登录设备
  -> refresh 失败，返回 401 / token_not_valid / device_session_revoked
  -> 客户端强制退出登录

A1 如果没有先触发 refresh，而是直接提交任意登录态业务请求
  -> 服务端仍然发现 A1 不是当前有效登录设备
  -> 业务请求返回 401 / device_session_revoked / device_session_replaced
  -> 客户端强制退出登录

A2 正常使用
  -> A2 refresh token 正常
  -> A2 登录态业务请求正常
  -> 通知继续只发 A2

用户1重新在 A1 登录
  -> A1 成为当前有效登录设备
  -> A2 的登录会话被服务端标记为失效
  -> A2 下次 refresh token 失败并退出
  -> 通知只发 A1
```

### Q：这个需求是否只改服务端？

A：是。本工单只要求服务端实现规则。

客户端行为只依赖现有未授权处理：

1. refresh token 或任意登录态业务请求返回 401。
2. 客户端收到认证失效后清理本地登录态。
3. 客户端回到登录页。

服务端不需要新增客户端接口才能满足核心要求，但登录、刷新和登录态业务接口需要能根据 `device_id + bundle_id` 或 token 中的设备会话标识判断当前请求来自哪台设备。

### 3. 当前问题

### Q：为什么不能只靠 `TrustedDevice.is_revoked`？

A：不建议直接把“被踢下线”和 `TrustedDevice.is_revoked` 混用。

原因：

1. `TrustedDevice` 是设备安装实例，不是登录会话。
2. `is_revoked=True` 更适合表达设备被管理员吊销、账号注销、风控封禁等长期状态。
3. A1 被 A2 顶掉登录，并不代表 A1 这台设备永远不能登录。
4. 如果把 A1 设备直接 `is_revoked=True`，用户重新在 A1 登录时还要额外解除吊销，语义容易混乱。

因此推荐新增“当前有效登录设备 / 登录会话”状态，而不是把所有逻辑塞进 `TrustedDevice`。

### Q：为什么不能只清空旧设备 push_token？

A：清空旧设备 `push_token` 只能阻止通知，不会阻止旧设备刷新 token，也不会阻止旧设备继续提交其他登录态业务请求。

本需求有两个独立目标：

1. 登录会话唯一：旧设备不能继续 refresh，也不能继续调用任何登录态业务 API。
2. 通知设备唯一：APNs 只发当前有效设备。

前者需要会话校验；后者需要通知投递过滤。只处理推送不够。

### 4. 推荐数据模型

### Q：服务端应该新增什么模型？

A：推荐新增账号当前设备会话模型，例如 `AccountDeviceSession`。

示例字段：

```python
class AccountDeviceSession(models.Model):
    class Status(models.TextChoices):
        ACTIVE = "active", "有效"
        REVOKED = "revoked", "已失效"
        LOGGED_OUT = "logged_out", "已退出"

    user = models.ForeignKey(User, related_name="device_sessions", on_delete=models.CASCADE)
    trusted_device = models.ForeignKey(TrustedDevice, related_name="account_sessions", on_delete=models.CASCADE)
    bundle_id = models.CharField(max_length=255, db_index=True, default="")
    device_id = models.CharField(max_length=255, db_index=True, default="")
    session_version = models.PositiveIntegerField(default=1, db_index=True)
    refresh_jti = models.CharField(max_length=255, blank=True, default="", db_index=True)
    status = models.CharField(max_length=32, choices=Status.choices, default=Status.ACTIVE, db_index=True)
    revoked_reason = models.CharField(max_length=64, blank=True, default="")
    replaced_by = models.ForeignKey("self", null=True, blank=True, on_delete=models.SET_NULL)
    last_refreshed_at = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True, db_index=True)
    updated_at = models.DateTimeField(auto_now=True)
```

推荐约束：

```text
同一 user 同一时间最多一个 ACTIVE session
```

如果数据库支持条件唯一约束：

```python
models.UniqueConstraint(
    fields=["user"],
    condition=Q(status="active"),
    name="uniq_active_device_session_per_user",
)
```

### Q：为什么不直接在 `TrustedDevice` 上加 `is_active_login`？

A：可以做最小实现，但长期不推荐。

缺点：

1. `TrustedDevice` 会同时承担“设备画像、推送能力、登录会话、风控吊销”多种职责。
2. 无法记录历史登录会话、替换关系、失效原因。
3. refresh token 的 `jti/session_version` 与设备画像耦合太强。
4. 后续支持后台查看登录历史、主动踢设备、登录安全提醒时会继续膨胀。

因此推荐新增 `AccountDeviceSession`，让 `TrustedDevice` 继续保持设备画像职责。

### 5. 登录签发流程

### Q：登录成功时服务端应该做什么？

A：所有登录入口成功认证后，必须进入统一的设备会话激活流程。

涉及入口：

```text
SparkService/accounts/auth/views.py
SparkService/accounts/services/login_service.py
SparkService/accounts/otp/views.py
SparkService/accounts/services/otp_service.py
```

推荐流程：

```text
login_success(user, bundle_id, device_id)
  -> 找到或创建 TrustedDevice(bundle_id, device_id)
  -> 关联 TrustedDevice.user = user
  -> transaction.atomic()
       -> 查询 user 当前 ACTIVE AccountDeviceSession
       -> 如果当前 ACTIVE 不是本次 device:
            标记旧 session = REVOKED
            revoked_reason = "replaced_by_new_device"
            可选：加入 SimpleJWT blacklist
       -> 为本次 device 创建/激活新的 ACTIVE AccountDeviceSession
       -> 生成 refresh token，并把 session 标识写入 token claim
  -> 返回 access_token / refresh_token
```

### Q：token 中需要写入什么？

A：推荐在 refresh token 中写入至少一个服务端可校验的会话标识：

```text
device_id
bundle_id
device_session_id
session_version
```

关键是 refresh 时服务端能判断：

```text
这个 refresh token 是否属于用户当前 ACTIVE 设备会话
```

如果只从请求 body 读取 `device_id`，有被伪造风险；如果 token claim 和 body 都有，则需要双重校验：

```text
token.device_session_id == active_session.id
token.device_id == request.device_id
token.bundle_id == request.bundle_id
```

### 6. 登录态请求校验

### Q：旧设备为什么会在刷新 token 或提交业务请求时被强制退出？

A：因为服务端不能只在 refresh token 接口校验设备会话。旧设备可能打开 App 后先触发设备登记、最新用户会话刷新、聊天同步、医疗同步、AI 配置刷新等业务请求，如果这些请求仍然通过，就会出现“旧设备虽然 refresh 已失效，但还能继续使用一部分业务能力”的漏洞。

因此需要两层校验：

1. refresh token 接口校验：旧设备不能换取新的 access token。
2. 所有登录态业务 API 校验：旧设备即使暂时持有未过期 access token，也不能继续访问业务接口。

refresh 入口：

```text
SparkService/accounts/auth/views.py: TokenRefreshView
```

推荐校验流程：

```text
TokenRefreshView.post
  -> 校验 refresh token 基础有效性
  -> 解析 user_id / device_session_id / device_id / bundle_id
  -> 查询 AccountDeviceSession
  -> 如果不存在：401 device_session_not_found
  -> 如果 status != ACTIVE：401 device_session_revoked
  -> 如果该 session 不是 user 当前 ACTIVE session：401 device_session_replaced
  -> 如果 request.device_id 与 token.device_id 不一致：401 device_mismatch
  -> 校验通过：签发新的 access token / refresh token
  -> 更新 last_refreshed_at
```

登录态业务 API 推荐校验流程：

```text
Authenticated request
  -> JWTAuthentication 解析 user
  -> 解析请求中的 device_id / bundle_id，或从 access token claim 中读取 device_session_id
  -> 查询 user 当前 ACTIVE AccountDeviceSession
  -> 如果不存在：401 device_session_not_found
  -> 如果请求 session 不是当前 ACTIVE：401 device_session_replaced
  -> 如果 session.status != ACTIVE：401 device_session_revoked
  -> 如果 request.device_id 与 token.device_id 不一致：401 device_mismatch
  -> 校验通过：继续进入业务 view/service
```

建议实现位置：

```text
自定义 Authentication / Permission / Middleware
```

优先建议放在认证/权限层，避免每个业务 view 手写校验导致遗漏。所有 `IsAuthenticated` 的业务接口都应被覆盖；登录、匿名设备登记、验证码发送等匿名接口不走该校验。

### Q：A1 被 A2 顶掉后，A1 的旧 refresh token 是否还需要进 blacklist？

A：建议需要。

实现上可以有两层：

1. 主校验：`AccountDeviceSession.status != ACTIVE` 时拒绝 refresh。
2. 保险校验：如果能拿到旧 refresh token 的 `jti`，把旧 token 加入 SimpleJWT blacklist。

即使 blacklist 因 token rotation 配置或历史 token 处理不完整，也能通过 `AccountDeviceSession` 拒绝旧设备刷新和旧 access token 的业务请求。

### 7. 设备登记流程

### Q：设备登记接口需要怎么调整？

A：`/api/v1/device/register/` 仍然保留设备画像 upsert 能力，但需要配合当前有效登录设备规则。

当前入口：

```text
SparkService/accounts/device/views.py
SparkService/accounts/services/device_service.py
```

建议：

1. 匿名登记：只 upsert `TrustedDevice`，不创建 `AccountDeviceSession`。
2. 登录态登记：可以更新 `TrustedDevice.user` 和画像，但不应单独把设备变成 ACTIVE 登录设备。
3. ACTIVE 登录设备只能由登录成功流程创建/切换。
4. 如果登录态登记来自非当前 ACTIVE 设备，必须返回 401，触发客户端强制退出。

推荐策略：

```text
旧设备打开 App 后如果先调用 /device/register/：
  -> 服务端返回 401 device_session_revoked / device_session_replaced
  -> 客户端强制退出

匿名 /device/register/：
  -> 可以继续登记设备画像
```

即：匿名 `/device/register/` 可以继续登记设备画像；登录态 `/device/register/` 必须遵循单设备会话校验。

### 8. APNs 通知投递

### Q：如何保证一个用户只通知一个设备？

A：通知服务查询 APNs 目标设备时，只能选用户当前 ACTIVE `AccountDeviceSession` 关联的 `TrustedDevice`。

当前相关位置：

```text
SparkService/accounts/services/notification_service.py
```

当前 APNs 查询大致按：

```text
TrustedDevice.objects.filter(user_id=user.id, notifications_enabled=True)
  .exclude(push_token="")
```

这会命中用户多台可推送设备。

需要改为：

```text
active_session = AccountDeviceSession.objects.filter(
    user=user,
    status=ACTIVE,
    trusted_device__notifications_enabled=True,
).exclude(
    trusted_device__push_token=""
).select_related("trusted_device").first()

仅向 active_session.trusted_device.push_token 发送 APNs
```

### Q：后台用户列表里的 APNs 可达状态怎么判断？

A：`NotificationService` 中用户筛选、列表展示、`has_apns` 判断也要切到“当前有效设备”口径。

旧口径：

```text
用户任意 TrustedDevice 有 push_token 即认为 APNs 可达
```

新口径：

```text
用户当前 ACTIVE AccountDeviceSession 对应 TrustedDevice 有 push_token 且 notifications_enabled=True，才认为 APNs 可达
```

### 9. 登出与失效

### Q：用户手动退出登录时怎么处理？

A：服务端应提供或复用登出接口，把当前设备会话标记为 `LOGGED_OUT`。

如果当前没有登出接口，本工单至少要求：

1. refresh token 被新设备替换时返回 401。
2. 用户重新登录其他设备时旧 session 被 `REVOKED`。

后续可补充登出接口：

```text
POST /api/v1/auth/logout/
body: refresh_token, device_id, bundle_id
```

处理：

```text
当前 device_session.status = LOGGED_OUT
refresh token 加入 blacklist
不影响 TrustedDevice 画像
```

### 11. 数据迁移说明

### Q：是否需要考虑历史数据迁移？

A：不需要。

当前按全新项目处理，本工单不要求兼容历史旧会话或历史多设备数据。

需要做的只有：

1. 新增 `AccountDeviceSession` 表结构和约束迁移。
2. 新登录用户从第一次登录开始创建 ACTIVE 设备会话。
3. 不需要为历史 `TrustedDevice` 选择初始 ACTIVE session。
4. 不需要回填历史 session、`refresh_jti` 或替换关系。
5. 不需要兼容老 refresh token 的多设备共存状态；新逻辑上线后按新登录/新 refresh 口径执行。

仍需保持概念区分：

```text
登录唯一性看 AccountDeviceSession
推送可达性看 active_session.trusted_device.push_token + notifications_enabled
```

两者不要混为一谈。

### 12. 错误码与响应

### Q：旧设备 refresh 或提交业务请求应该返回什么？

A：推荐统一返回 401，并使用明确业务 code/msg：

```json
{
  "code": 40104,
  "msg": "device_session_revoked",
  "data": null
}
```

可选错误：

| msg | 含义 |
| --- | --- |
| `device_session_revoked` | 当前设备会话已失效 |
| `device_session_replaced` | 当前设备已被另一台设备登录替代 |
| `device_session_not_found` | token 对应设备会话不存在 |
| `device_mismatch` | 请求设备与 token 设备不一致 |
| `token_not_valid` | refresh token 本身无效 |

客户端不需要区分所有细节，收到 401 即可强制退出；服务端日志和排障需要区分原因。

### 13. 验收标准

1. 用户1在 A1 登录成功后，A1 成为用户1唯一 ACTIVE `AccountDeviceSession`。
2. 用户1在 A2 登录成功后，A1 的 `AccountDeviceSession` 被标记为 `REVOKED`，A2 成为唯一 ACTIVE。
3. A1 未手动退出，重新打开 App 并 refresh token 时，服务端返回 401，原因可识别为 `device_session_revoked` 或 `device_session_replaced`。
4. A1 如果先提交设备登记、用户会话刷新、聊天同步、医疗同步、AI 配置刷新或任意登录态业务 API，也必须返回 401，原因可识别为设备会话失效。
5. A2 refresh token 正常成功。
6. A2 任意登录态业务请求正常成功。
7. 用户1重新在 A1 登录后，A2 的会话被标记为 `REVOKED`，A1 成为唯一 ACTIVE。
8. A2 再 refresh token 或提交任意登录态业务请求时返回 401。
9. APNs 通知只向当前 ACTIVE 会话绑定的 `TrustedDevice.push_token` 投递。
10. 如果旧设备仍有 `push_token`，通知服务也不能向旧设备投递。
11. 如果当前 ACTIVE 设备没有开启通知或没有 `push_token`，APNs 渠道应 `SKIPPED`，不能退回旧设备。
12. `TrustedDevice` 仍保持 `bundle_id + device_id` 唯一，不因多次登录创建重复设备。
13. 旧设备被替换不应永久吊销 `TrustedDevice`，用户重新在旧设备登录后可重新成为 ACTIVE。
14. 单元测试覆盖 A1/A2 登录替换、refresh 失效、旧设备任意登录态业务请求失效、通知只发当前设备；不要求历史数据迁移测试。

## 工单 `ACCOUNTS-000002`：设备登记按用户隔离并拒绝旧设备登录态登记

### 1. 背景

### Q：为什么要新增这个工单？

A：`ACCOUNTS-000001` 已经要求“一个账号同一时间只有一个有效设备登录”，但当前设备画像模型仍然是：

```text
SparkService/accounts/models.py:19-62
TrustedDevice 以 bundle_id + device_id 唯一
```

这会带来两个问题：

1. 同一台物理设备/同一安装标识如果登录过不同用户，后登录用户会复用并覆盖同一条 `TrustedDevice.user`、推送 token、通知权限和终端画像。
2. A1 设备已经被 A2 顶掉后，A1 前台恢复时仍可能先成功调用 `/api/v1/device/register/`，把旧设备画像写成成功，随后其他业务请求或 refresh token 才触发 401 退出。

从日志可以看到错误时序：

```text
A1 前台恢复
  -> POST /api/v1/device/register/ status=200 msg=device_registered
  -> GET /api/v1/tasks/sync/ status=401 msg=device_session_replaced
  -> POST /api/v1/auth/token/refresh/ status=401 msg=token_not_valid
  -> 客户端强制退出
```

这个流程的问题不是“最终没有退出”，而是：**旧设备在已经失效后仍先成功登记了用户设备信息**。设备登记接口本身也应该成为旧设备强制退出的触发点。

### 2. 目标

### Q：本工单要达到什么状态？

A：

1. `TrustedDevice` 不再以全局 `bundle_id + device_id` 唯一，而是以 `bundle_id + device_id + user_id` 唯一。
2. 一台设备可以登记不同用户，各用户拥有各自的设备画像记录。
3. 用户 A 的设备画像不能被用户 B 登录或匿名登记覆盖。
4. 匿名设备登记仍然允许，用于未登录冷启动，但不能覆盖任何已绑定用户的设备记录。
5. 登录态 `/api/v1/device/register/` 必须校验当前 `AccountDeviceSession`。
6. 旧设备 A1 被 A2 替换后，A1 再调用 `/device/register/` 必须直接返回 401 `device_session_replaced` 或 `device_session_revoked`，不能先写入成功。
7. APNs 投递、设备会话、账号注销、数据导出等所有读取 `TrustedDevice` 的地方都要按新的“用户维度设备记录”处理。

### 3. 数据模型调整

### Q：`TrustedDevice` 唯一约束怎么改？

A：从：

```python
models.UniqueConstraint(fields=["bundle_id", "device_id"], name="uniq_bundle_device")
```

改为：

```python
models.UniqueConstraint(
    fields=["bundle_id", "device_id", "user"],
    name="uniq_bundle_device_user",
)
```

同时需要处理 `user = NULL` 的匿名登记。由于多数数据库中 `NULL` 不参与普通唯一约束冲突，建议增加两类约束：

```python
# 已绑定用户：同一用户下 bundle_id + device_id 唯一
models.UniqueConstraint(
    fields=["bundle_id", "device_id", "user"],
    condition=Q(user__isnull=False),
    name="uniq_bundle_device_user_bound",
)

# 匿名登记：同一安装只保留一条匿名画像
models.UniqueConstraint(
    fields=["bundle_id", "device_id"],
    condition=Q(user__isnull=True),
    name="uniq_bundle_device_anonymous",
)
```

这样可以同时满足：

1. 未登录冷启动：同一安装只有一条匿名设备记录。
2. 用户1登录：创建或更新 `(bundle_id, device_id, user1)`。
3. 用户2登录：创建或更新 `(bundle_id, device_id, user2)`，不覆盖用户1设备画像。

### Q：是否影响 `AccountDeviceSession`？

A：有影响，但方向是正向的。

当前 `AccountDeviceSession.trusted_device` 指向 `TrustedDevice`：

```text
SparkService/accounts/models.py:63-117
```

当 `TrustedDevice` 改成用户维度后，`AccountDeviceSession.trusted_device` 将天然指向“该用户自己的设备画像”，不会再出现：

```text
用户1的 AccountDeviceSession.trusted_device
  -> 指向后来被用户2覆盖 user 字段的 TrustedDevice
```

需要注意：

1. `AccountDeviceSession.user` 必须与 `trusted_device.user` 一致。
2. `DeviceSessionService._get_or_create_trusted_device` 不能再用 `bundle_id + device_id` 全局查询。
3. 登录激活会话时，应查询或创建 `TrustedDevice(bundle_id, device_id, user)`。
4. 匿名 `TrustedDevice(user=None)` 不能直接“改 user”为登录用户，否则仍会把匿名记录搬走；登录态登记应读取同一 `bundle_id + device_id + user=NULL` 的当前设备匿名画像，并覆盖/补全到当前用户维度记录，匿名记录可保留或后续清理。

### 4. 服务端流程调整

### Q：设备登记接口应该怎么改？

A：`/api/v1/device/register/` 要分三种情况：

```text
无 Authorization
  -> 匿名登记
  -> upsert TrustedDevice(user=None, bundle_id, device_id)
  -> 不覆盖任何 user != None 的 TrustedDevice

Authorization 有效且设备会话 ACTIVE
  -> 登录态登记
  -> upsert TrustedDevice(user=request.user, bundle_id, device_id)
  -> 如果存在同一 bundle_id + device_id + user=NULL 的匿名记录，用该匿名记录覆盖/补全当前用户设备画像
  -> 更新当前用户自己的设备画像、push_token、notifications_enabled

Authorization 无效、过期、或设备会话已被替换/吊销
  -> 返回 401
  -> msg=device_session_replaced / device_session_revoked / token_not_valid
  -> 不执行 DeviceService.register_device
```

关键原则：**只要请求带了登录态意图，就不能在鉴权失败时降级成匿名设备登记。**

当前 `DeviceRegisterView` 注释里仍有旧语义：

```text
JWT 无效/过期：不会返回 401，仅跳过用户绑定逻辑
```

本工单要求修正为：

```text
无 Authorization：允许匿名登记
有 Authorization 但无效：返回 401
有 Authorization 且设备会话失效：返回 401
```

### Q：DeviceService.register_device 怎么改？

A：当前逻辑是：

```text
TrustedDevice.objects.filter(bundle_id=bundle_id, device_id=device_id).first()
```

需要改为：

```text
if user is None:
    lookup = {bundle_id, device_id, user=None}
else:
    lookup = {bundle_id, device_id, user=user}
```

并且：

1. 匿名登记只更新匿名行。
2. 登录态登记只 upsert 当前用户行，但要以当前设备匿名行作为覆盖/补全来源。
3. 不允许 `obj.user = user` 把其他用户或匿名行直接改绑。
4. 登录态请求体显式携带的字段优先级最高；请求体未携带的设备画像字段，可由同一 `bundle_id + device_id + user=NULL` 匿名记录补齐。
5. 匿名行不能移动主键，也不能被改绑为当前用户。

### Q：未登录登记后，用户登录再登记，会不会出现两条设备信息？

A：会出现两条不同语义的设备记录，这是符合本工单设计的，不是重复脏数据：

```text
匿名设备记录：
bundle_id + device_id + user = NULL

登录态用户设备记录：
bundle_id + device_id + user = 当前登录用户
```

原因：

1. 匿名记录表达“这个安装实例在未登录状态下出现过”，用于冷启动、国家地区、版本、设备画像等基础信息。
2. 用户记录表达“这个安装实例属于某个已登录账号”，用于当前用户的 push_token、通知权限、设备会话、APNs 投递和排障。
3. 两者不能混成一条，否则未登录匿名登记或其他用户登录可能覆盖当前用户设备信息。

避免问题的方式不是强行只保留一条，而是明确隔离：

```text
未登录 /device/register/
  -> 只 upsert user=NULL 的匿名记录

登录后 /device/register/
  -> 只 upsert user=当前用户 的用户记录
  -> 覆盖/补全来源：当前设备 user=NULL 的匿名记录
  -> 不改绑、不删除匿名记录

用户A /device/register/
  -> 不能覆盖用户B记录

匿名 /device/register/
  -> 不能覆盖任何 user != NULL 的用户记录
```

如果后续不希望匿名记录长期保留，可以增加清理策略：

1. 登录成功创建/更新用户设备记录后，把当前设备匿名记录的非敏感画像覆盖/补全到用户记录。
2. 匿名记录继续保留用于最近未登录设备画像，或异步标记/定期清理。
3. 清理不能影响用户维度 `TrustedDevice` 和 `AccountDeviceSession`。

### Q：未登录情况下重复打开 App，会不会登记多条匿名设备信息？

A：不应该。

服务端必须通过匿名唯一约束保证同一安装实例只有一条匿名记录：

```python
models.UniqueConstraint(
    fields=["bundle_id", "device_id"],
    condition=Q(user__isnull=True),
    name="uniq_bundle_device_anonymous",
)
```

重复未登录冷启动时：

```text
第一次：
  -> create TrustedDevice(user=NULL, bundle_id, device_id)

第二次及以后：
  -> update 同一条 TrustedDevice(user=NULL, bundle_id, device_id)
  -> 更新 app_version / build_version / country_code / last_seen / request_id 等
```

验收要求：

1. 同一 `bundle_id + device_id` 未登录重复调用 `/device/register/`，数据库仍只有一条 `user=NULL` 记录。
2. `created` 第一次为 `true`，后续为 `false`。
3. 后续请求只更新匿名记录的设备画像字段，不创建多条匿名记录。

### Q：未登录调用 `/device/register/` 会不会返回 401？

A：不应该。未登录匿名登记是允许场景。

必须区分：

```text
没有 Authorization header
  -> 这是匿名请求
  -> 允许登记
  -> 返回 200 device_registered

有 Authorization header，但 token 无效/过期
  -> 这是登录态意图失败，不是匿名请求
  -> 返回 401
  -> 不允许降级匿名登记

有 Authorization header，token 有效但 device_session 已失效
  -> 旧设备请求
  -> 返回 401 device_session_replaced / device_session_revoked
  -> 不登记
```

避免误 401 的关键：

1. 客户端未登录状态调用 `/device/register/` 时不要携带 Authorization。
2. 服务端 `DeviceRegisterView` 只在完全没有 Authorization 时走匿名登记。
3. 服务端不能因为“没有用户”就直接 401；只有“带了无效登录态”才 401。

这与 `ACCOUNTS-000002` 的整体设计一致：**匿名登记允许，登录态失效拒绝，匿名记录和用户记录隔离。**

### Q：DeviceSessionService._get_or_create_trusted_device 怎么改？

A：当前逻辑遇到同一 `bundle_id + device_id` 已归属其他用户时只打 warning：

```text
device.session.trusted_device_user_conflict
```

新逻辑不应该把这当冲突，因为同一设备登录不同用户是允许场景。应改成：

```text
TrustedDevice.objects.filter(
    user=user,
    bundle_id=bundle_id,
    device_id=device_id,
).first()
```

找不到就创建当前用户自己的 `TrustedDevice`。如果存在同一 `bundle_id + device_id + user=NULL` 的匿名行，应使用匿名画像作为当前用户行的覆盖/补全来源；但不能把匿名行直接改绑成当前用户。

### 5. 风险点分析

### Q：改成 `bundle_id + device_id + user_id` 唯一有什么风险？

A：

1. **APNs 多用户投递风险**  
   同一设备登录过多个用户后，可能存在多条 `TrustedDevice` 持有同一个 `push_token`。通知投递必须继续以 `AccountDeviceSession.ACTIVE` 为准，不能按 `push_token` 或 `device_id` 全局发送。

2. **匿名记录膨胀风险**  
   匿名冷启动会保留 `user=None` 行，登录后又创建用户行。需要接受这是一条“安装匿名画像”，或增加定期清理长期未更新匿名行的任务。

3. **注销/封禁处理风险**  
   `TrustedDevice.objects.filter(user=user)` 仍能处理用户自己的设备记录，但不能再假设同一 `device_id` 只有一行。

4. **后台排障展示风险**  
   后台按 `device_id` 搜索会出现多用户记录，需要展示 `user_id`、最近有效 `AccountDeviceSession`、last_seen，避免误判“重复设备”。

5. **推送 token 清空风险**  
   用户1拒绝通知时，只应清空用户1这条 `TrustedDevice.push_token`。不能按 `bundle_id + device_id` 清空用户2记录。

6. **会话外键一致性风险**  
   `AccountDeviceSession.trusted_device.user_id` 必须等于 `AccountDeviceSession.user_id`。建议在服务层保证，并增加测试。

### Q：对 `AccountDeviceSession` 的具体影响是什么？

A：

1. `AccountDeviceSession` 表结构本身可以不改。
2. 登录激活逻辑必须拿到当前用户维度的 `TrustedDevice`。
3. `apns_trusted_device_for_user(user)` 更安全，因为 active session 指向当前用户设备行。
4. 替换登录仍然按 `AccountDeviceSession.user` 单用户维度处理，不受同设备多用户记录影响。
5. 测试要覆盖：同一 `bundle_id + device_id` 登录用户1和用户2，分别产生不同 `TrustedDevice`，且各自 `AccountDeviceSession.trusted_device_id` 不相同。

### 6. A1/A2 错误流程修正

### Q：为什么日志中的流程是错的？

A：日志显示：

```text
A1 已经被 A2 顶掉
A1 前台恢复先 POST /device/register/ 成功
随后 Task.Sync 返回 401 device_session_replaced
再 refresh 返回 401 token_not_valid
最后客户端退出
```

问题是：A1 已经不是当前有效设备，任何带登录态的服务端请求都应该先触发退出。`/device/register/` 也是登录态请求，不能例外。

### Q：服务端应该如何处理？

A：

```text
DeviceRegisterView.post
  -> 检查是否存在 Authorization header
  -> 如果没有：匿名登记
  -> 如果有：必须使用 SparkJWTAuthentication 认证
       -> token 无效：401，不登记
       -> token 有效但 device_session 失效：401，不登记
       -> token 有效且 session ACTIVE：继续登记当前用户设备画像
```

注意：不要 catch `AuthenticationFailed` 后继续匿名登记。旧设备的 Authorization 虽然失效，但这不是匿名请求。

### 8. 验收标准

1. 同一 `bundle_id + device_id` 可以分别登记用户1和用户2，数据库中存在两条不同 `TrustedDevice`。
2. 用户1设备登记不会覆盖用户2的 `push_token`、`notifications_enabled`、`country_code`、`last_seen`。
3. 匿名冷启动登记只 upsert `user=None` 的设备记录，不覆盖用户记录。
4. 同一 `bundle_id + device_id` 未登录重复调用 `/device/register/`，只保留一条 `user=None` 匿名记录，后续调用只更新该记录。
5. 登录态 `/device/register/` 只 upsert 当前用户记录，并把同一设备匿名记录的设备画像覆盖/补全到当前用户记录；匿名记录仍保留 `user=NULL`。
6. 未登录且不带 Authorization 调用 `/device/register/` 返回 200，不返回 401。
7. 带无效 Authorization 调用 `/device/register/` 返回 401，不降级匿名登记。
8. 登录成功后创建设备会话时，`AccountDeviceSession.trusted_device.user_id == AccountDeviceSession.user_id`。
9. A1 登录后，A2 登录同一账号，A1 session 被替换。
10. A1 前台恢复如果先调用 `/api/v1/device/register/`，服务端直接返回 401 `device_session_replaced` 或 `device_session_revoked`。
11. A1 的 `/device/register/` 401 后不应产生 `device_registered` 成功日志，也不应更新 `TrustedDevice.last_seen/request_id/push_token`。
12. A2 的 `/device/register/` 正常成功并更新 A2 对应用户设备画像。
13. APNs 只投递给当前 ACTIVE `AccountDeviceSession.trusted_device`。
14. 同一设备登录过多个用户后，通知不会误投到非当前用户或非 ACTIVE 会话记录。
15. 单元测试覆盖同设备多用户隔离、匿名/登录态隔离、登录态用匿名画像覆盖/补全当前用户行、匿名重复登记幂等、无 Authorization 匿名登记 200、无效 Authorization 登记 401、旧设备登记 401、APNs ACTIVE 会话投递。

## 工单 `ACCOUNTS-000003`：匿名设备记录转用户记录与退出后复用上次用户

### 1. 背景

### Q：为什么要新增这个工单？

A：`ACCOUNTS-000002` 的设计是“匿名记录与用户记录隔离并存”。现在业务口径调整为：

1. 未登录空用户场景下，同一安装只允许有一条匿名记录。
2. 用户登录后，如果当前设备存在匿名记录，不再长期保留匿名行，而是把这条匿名行升级为当前用户设备行。
3. 用户退出登录后，不删除用户设备行，而是把该行标记为 `is_revoked=true`，并保留上次登录用户 ID。
4. 退出后再次未登录打开 App，不能重新创建 `user=NULL` 匿名行；应继续更新上次登录用户的 revoked 设备行。
5. 如果同一设备退出 A1 后登录 A2，则创建或更新 A2 自己的设备行，不覆盖 A1 的 revoked 设备行。
6. 如果同一设备 0001 上 A1 仍处于登录态时又登录 B1，则 B1 登录成功时必须立即让设备 0001 上 A1 的设备行和登录会话失效。

这会改变 `ACCOUNTS-000002` 中“匿名行与用户行并存”的口径。本工单作为后续修订，以本工单为准。

### 2. 目标场景

### Q：初次下载、未登录启动时怎么登记？

A：

```text
初次下载
用户未登录
POST /device/register/ 无 Authorization
  -> 只 upsert user=NULL 的匿名记录
  -> 同一 bundle_id + device_id 只能有一条 user=NULL 记录
```

验收重点：

1. 未登录重复打开 App 不创建多条匿名记录。
2. 匿名记录只用于“从未登录过任何账号”的安装实例。

### Q：初次下载后，用户登录时怎么登记？

A：

```text
初次下载
未登录已登记 user=NULL 匿名记录
用户登录成功
登录态 /device/register/ 或登录侧设备绑定流程
  -> 先查当前 bundle_id + device_id 是否存在 user=NULL 匿名记录
  -> 如果存在：把该匿名记录升级为 user=当前用户
  -> 用登录态请求体覆盖设备画像、push_token、notifications_enabled
  -> is_revoked=false
```

如果不存在匿名记录：

```text
用户登录成功
当前设备没有 user=NULL 匿名记录
  -> 创建或更新 user=当前用户 的设备记录
  -> is_revoked=false
```

注意：这里的“升级”是把当前设备匿名记录变成当前用户记录，不是再额外创建一条并保留匿名行。

### Q：退出登录时怎么处理？

A：

```text
用户 A1 在设备 0001 主动退出登录
  -> 找到 TrustedDevice(bundle_id, device_id, user=A1)
  -> 更新 is_revoked=true
  -> 清空或保留 push_token 取决于通知策略，但必须保留 user=A1
  -> AccountDeviceSession 标记 LOGGED_OUT / REVOKED
```

关键点：

1. 退出登录不应把 `TrustedDevice.user` 置空。
2. 退出登录不应删除 `TrustedDevice`。
3. 退出后仍要保留上次登录用户 ID，用于后续未登录启动设备登记归属判断。

### Q：A1 在设备 0001 退出后，再次未登录打开 App 怎么登记？

A：

```text
设备 0001 已有 TrustedDevice(user=A1, is_revoked=true)
App 未登录冷启动
POST /device/register/ 无 Authorization
  -> 服务端识别该 bundle_id + device_id 最近一次用户设备行
  -> 更新 TrustedDevice(user=A1, is_revoked=true) 的设备画像
  -> 不创建 user=NULL 匿名记录
```

如果用户再次登录 A1：

```text
A1 再次登录设备 0001
  -> upsert TrustedDevice(user=A1)
  -> is_revoked=false
  -> 更新设备画像、push_token、notifications_enabled
```

### Q：A1 退出后，同一设备 0001 登录 A2 怎么处理？

A：

```text
设备 0001 已有 TrustedDevice(user=A1, is_revoked=true)
A2 在设备 0001 登录
  -> 不覆盖 A1 的 revoked 设备行
  -> 创建或更新 TrustedDevice(user=A2, bundle_id, device_id)
  -> is_revoked=false
  -> AccountDeviceSession 指向 A2 的设备行
```

这样可以同时满足：

1. A1 的历史设备信息可保留。
2. A2 登录不会污染 A1 的设备记录。
3. 当前 active session 与当前用户设备行一致。

### Q：同一设备 0001 上，A1 未主动退出又登录 B1，A1 何时变为失效？

A：A1 应该在 **B1 登录成功并激活设备会话的同一服务端事务内** 失效，不能等 A1 下次 refresh、前台恢复或业务请求时才更新。

正确流程：

```text
设备 0001 当前存在：
  TrustedDevice(user=A1, bundle_id, device_id, is_revoked=false)
  AccountDeviceSession(user=A1, trusted_device=设备0001-A1, status=ACTIVE)

B1 在设备 0001 登录成功
  -> 先定位同一 bundle_id + device_id 下 user != B1 的用户设备行
  -> 将 TrustedDevice(user=A1, bundle_id, device_id).is_revoked=true
  -> 将 A1 在该 trusted_device 上的 ACTIVE AccountDeviceSession 标记为 LOGGED_OUT / REPLACED
  -> 创建或更新 TrustedDevice(user=B1, bundle_id, device_id)
  -> TrustedDevice(user=B1).is_revoked=false
  -> 创建 B1 的 ACTIVE AccountDeviceSession
```

这样表达两条约束：

1. **同一安装实例只有一个当前登录用户**：设备 0001 当前有效用户是 B1。
2. **同一用户只有一台有效设备**：B1 登录时仍要按 `ACCOUNTS-000001` 替换 B1 在其他设备上的 ACTIVE session。

注意：这里不能把 A1 的 `TrustedDevice.user` 改成 B1，也不能删除 A1 的设备行。A1 行保留为 `is_revoked=true` 的历史设备记录。

### 3. 服务端设计

### Q：`/device/register/` 无 Authorization 时如何决定写匿名行还是上次用户行？

A：推荐规则：

```text
无 Authorization
  -> 若 body 显式携带 user_id，且数据库已有 TrustedDevice(bundle_id, device_id, user_id)：
       更新该行画像，保持 user 不变，保持 is_revoked=true（不因匿名登记 reactivate）
  -> 否则仅 upsert user=NULL 匿名行（或更新已有匿名行）
  -> 不允许匿名请求凭 body.user_id 创建任意用户设备行
  -> 无 user_id 或未命中时，不回退更新「最近用户行」
```

客户端未登录时通过 body.`user_id` 上送本机 `lastLoggedInAccountID`（非鉴权凭证）；服务端仅作辅助定位。

### Q：登录态设备登记如何处理匿名记录升级？

A：

```text
有 Authorization 且设备会话有效 / 登录成功上下文
  -> 查 TrustedDevice(bundle_id, device_id, user=当前用户)
     如果存在：更新该用户行，is_revoked=false
  -> 如果不存在：
       查 TrustedDevice(bundle_id, device_id, user=NULL)
       如果存在：把该行 user 改为当前用户，is_revoked=false
       如果不存在：创建 TrustedDevice(user=当前用户)
```

注意：

1. 只有登录态认证成功或登录成功上下文中，才允许把 `user=NULL` 升级为某个用户。
2. 匿名请求不能把 `user=NULL` 升级成 body 里的任意用户。
3. 如果当前设备已有其他用户行，例如 A1 revoked，A2 登录时必须创建 A2 行，不能复用 A1 行。

### Q：同一设备切换登录用户时，服务端事务顺序怎么设计？

A：推荐把“撤销同安装其他用户”放进登录成功后的设备会话激活事务里：

```text
activate_session_on_login(user=B1, bundle_id, device_id)
  -> transaction.atomic
  -> revoke_same_installation_other_users(bundle_id, device_id, except_user=B1)
       - TrustedDevice.objects.filter(bundle_id, device_id).exclude(user=B1).exclude(user=NULL)
         update(is_revoked=true)
       - AccountDeviceSession.objects.filter(
             trusted_device__bundle_id=bundle_id,
             trusted_device__device_id=device_id,
             user != B1,
             status=ACTIVE
         ).update(status=REPLACED/LOGGED_OUT)
  -> 按 ACCOUNTS-000001 撤销 B1 自己在其他设备的 ACTIVE session
  -> get_or_create / upgrade TrustedDevice(user=B1, bundle_id, device_id)
  -> TrustedDevice(user=B1).is_revoked=false
  -> create ACTIVE AccountDeviceSession(user=B1)
```

为什么要在这里做：

1. 这是服务端确认 B1 登录成功的唯一可信时刻。
2. 可以保证 A1 设备行失效和 B1 设备行生效是原子切换。
3. 避免客户端在账号切换过程中崩溃后，服务端仍认为 A1 在同一设备有效。

### Q：退出登录由哪个服务处理？

A：退出登录流程需要在服务端增加设备行失效处理：

```text
logout / sign_out / refresh revoke / device session logout
  -> 根据 token 中的 device_session_id 找到 AccountDeviceSession
  -> 找到 session.trusted_device
  -> TrustedDevice.is_revoked = true
  -> AccountDeviceSession.status = LOGGED_OUT / REVOKED
```

如果项目里没有显式 logout API，也需要在客户端主动退出时调用服务端接口，或在 refresh/session revoke 逻辑里统一处理。

### 4. 数据模型影响

### Q：是否还需要 `user=NULL` 唯一约束？

A：仍然需要，但语义改变：

```text
user=NULL 只代表“该安装从未登录过任何用户”的匿名占位记录
```

一旦登录成功，该匿名行会升级为用户行。后续退出后不再退回匿名行。

约束建议：

```python
Unique(bundle_id, device_id) WHERE user IS NULL
Unique(bundle_id, device_id, user) WHERE user IS NOT NULL
```

### Q：是否需要新增字段保存“上次登录用户 ID”？

A：优先不新增字段，因为 `TrustedDevice.user_id` 本身就保留了上次登录用户。退出后通过 `is_revoked=true` 表达该设备行当前不可用。

如果后续需要更明确的审计，可再增加：

```text
revoked_at
last_login_at
last_logout_at
```

第一期不是必须。

### 6. 验收标准

1. 初次下载未登录启动，多次调用 `/device/register/`，数据库只有一条 `user=NULL` 匿名记录。
2. 初次下载未登录登记后，A1 登录同一设备，原 `user=NULL` 行升级为 `user=A1`，不再保留匿名行。
3. A1 登录时如果没有匿名行，则创建或更新 `user=A1` 设备行。
4. A1 主动退出后，`TrustedDevice(user=A1, bundle_id, device_id).is_revoked=true`，且 `user_id` 保留。
5. A1 退出后未登录再次打开 App，不创建 `user=NULL`，而是更新 `user=A1, is_revoked=true` 的设备画像。
6. A1 退出后再次登录 A1，同一设备行更新为 `is_revoked=false`。
7. A1 退出后，A2 在同一设备登录，创建或更新 `user=A2` 设备行，不覆盖 A1 revoked 行。
8. A2 登录后，`AccountDeviceSession.trusted_device.user_id == A2`。
9. 设备 0001 上 A1 未主动退出时登录 B1，B1 登录成功后 A1 在设备 0001 的 `TrustedDevice.is_revoked=true`，且 A1 在该 trusted_device 上的 ACTIVE `AccountDeviceSession` 被标记为失效。
10. 同一设备切换到 B1 后，B1 的设备行 `is_revoked=false`，且 B1 仍满足“同一用户只有一个 ACTIVE 设备会话”。
11. 匿名请求即使携带 `user_id` / `last_logged_in_account_id`，也不能创建任意用户设备行；只能更新服务端已存在且匹配的设备行。
12. APNs 仍只投递给当前 ACTIVE session 对应的设备行，不投递给 `is_revoked=true` 的历史用户设备行。
