# `hospital_care` 服务端实施详细设计

> 阶段：设计冻结，尚未创建 App、迁移或接口代码。  
> 目标：让 `hospital_care` 能以最小侵入方式接入现有 SparkService，并成为医院、科室、医生和医生智能体的唯一业务事实源。

## 1. 实施边界

这是一个模块化单体内新增 Django App，不是新微服务，也不是第二套聊天系统。

| 保持原样 | `hospital_care` 新增的业务扩展 |
| --- | --- |
| `accounts.User`、`medical` 成员、`ChatThread`、`ChatMessage`、AI Run、知识库、记忆、文件、平台 RBAC | 医院组织、科室、职工身份、医生档案、医生智能体发布层、知识绑定、医院会话扩展、消息发言归属 |

实现时不允许复制 `ChatThread` / `ChatMessage` / `KnowledgeBase` / `AIMemory` 的字段或另建同步协议。医生工作台、iOS 和后台管理只通过医院业务 API 使用这层能力。

现有项目的统一响应格式、异常处理和请求追踪也保持复用：成功响应为 `{ code: 0, msg: "success", data }`，失败由 `common.exceptions.APIError` 和全局异常处理器返回，响应附带 `X-Request-ID`。

## 2. 目标代码结构与责任

```text
hospital_care/
├── apps.py                         # AppConfig；无业务规则
├── admin.py                         # 仅用于受控运维查看，不能替代医院后台
├── models/
│   ├── organization.py              # Hospital、Department、Staff、Doctor
│   ├── agent_profiles.py            # ClinicalAgentProfile、KnowledgeBinding
│   └── conversations.py             # ConversationBinding、MessageAttribution、命令回执
├── selectors/
│   ├── patient_catalog.py           # 面向患者的已发布目录，只读
│   ├── doctor_workspace.py          # 当前医生可见工作队列，只读
│   └── backoffice_hospital_catalog.py # 平台医院目录、汇总，只读
├── services/
│   ├── hospital_admin_service.py    # 医院/科室/职工/医生状态转换
│   ├── agent_service.py             # 智能体草稿、校验、发布、停用
│   ├── conversation_service.py      # 建会话、接管、关注、结束
│   └── doctor_message_service.py    # 医生真实身份发言、归属、同步事件
├── api/
│   ├── patient/{urls,serializers,views}.py
│   ├── staff/{urls,serializers,views}.py
│   └── backoffice/{urls,serializers,views}.py
├── permissions.py                   # 只做资源范围判定
├── exceptions.py                    # 稳定业务码
├── migrations/
└── tests/
```

规则分层：View 负责认证、Serializer 校验和调用；Selector 只读且集中做范围过滤；Service 是唯一写入入口、使用事务并产生日志；Model 只存约束与轻量派生属性。禁止在三套 View 中各自实现“暂停医院”“结束会话”等状态机。

## 3. 模型、约束和索引

### 3.1 组织与人员

| 模型 | 关键字段 | 约束 / 索引 |
| --- | --- | --- |
| `Hospital` | `code`、`name`、`short_name`、`grade`、地区/地址、服务电话、`service_mode`、`status`、`version` | `code` 全局唯一；`status` 取值 `draft/active/suspended`；索引 `(status, name)`；`version` 用于乐观并发控制 |
| `HospitalDepartment` | `hospital`、`code`、`name`、`parent`、`sort_order`、`status` | 唯一 `(hospital, code)`；索引 `(hospital, status, sort_order)`；父科室必须同医院 |
| `HospitalStaffMembership` | `hospital`、`user`、`role`、`status`、`joined_at` | 唯一 `(hospital, user)`；角色仅 `hospital_admin/doctor/nurse/auditor`；索引 `(user, status)` |
| `DoctorProfile` | `staff_membership`、真实姓名、职称、擅长、展示头像文件、`status` | 与职工身份一对一；只有 `role=doctor` 才可创建；档案不可跨医院 |
| `DoctorDepartmentMembership` | `doctor`、`department`、`is_primary`、`sort_order` | 唯一 `(doctor, department)`；数据库或 service 保证每医生至多一个主科室 |

`Hospital` 不能物理删除。`draft -> active -> suspended -> active` 是唯一目标状态路径；暂停只阻断新增患者服务和新的医生操作，不清除会话、审计或既有数据。

### 3.2 医生智能体与知识引用

| 模型 | 关键字段 | 约束 / 说明 |
| --- | --- | --- |
| `ClinicalAgentProfile` | `hospital`、`doctor`、`department`、`scenario_binding`、展示名/简介/风险说明、`status`、`published_at`、`version` | `scenario_binding` 仅引用既有 `AIScenarioModelBinding`；状态 `draft/published/disabled`；医院、医生、科室必须一致；索引 `(hospital, department, status)` |
| `ClinicalAgentKnowledgeBinding` | `agent`、既有 `knowledge_base`、`sort_order`、`status` | 唯一 `(agent, knowledge_base)`；只保存引用和业务启停，不复制文档或分片 |

知识库仍按既有所有权与访问控制读取。实施前必须确认“医院专属知识库由哪个受控服务账号拥有、如何授权调用”；不得为了跨医院查询而绕过现有 owner 过滤。病历脱敏、授权、内容审核完成前，Demo 只能绑定合规的模拟/公开资料。

### 3.3 会话与发言归属

| 模型 | 关键字段 | 约束 / 说明 |
| --- | --- | --- |
| `ClinicalConversationBinding` | `thread`、`hospital`、`department`、`doctor`、`agent`、`service_status`、`doctor_attention_level`、`risk_signal_level`、`ended_at/by`、`version` | `thread` 一对一；索引 `(doctor, service_status, doctor_attention_level, updated_at)`、`(hospital, department, service_status)`；不可把现有线程改绑到另一医院 |
| `ChatMessageAttribution` | `message`、`actor_type`、`actor_user`、`doctor`、`agent` | `message` 一对一；`actor_type` 为 `patient/ai_agent/doctor/system`；医生消息必须有医生与用户，AI 消息必须有智能体，患者消息不得伪造医生 |
| `HospitalCareCommandReceipt` | `actor_user`、`command_key`、`request_hash`、`resource_type/id`、`response_code`、`created_at` | 唯一 `(actor_user, command_key)`；仅存响应定位和摘要，不存患者全文；用于可重试写操作幂等 |

`ChatMessage.role` 不改：它仍是 LLM 传输语义 `system/user/assistant`。展示“AI 回复”或“真实医生回复”只能以 `ChatMessageAttribution.actor_type` 为准。风险信号与医生关注分开存储：前者是安全策略输出，后者是医生工作优先级，互不覆盖。

所有外键的删除策略以保护历史为原则：医院/医生/智能体/知识库被引用时优先 `PROTECT` 或业务停用；消息、线程和审计绝不因配置下架而被级联删除。

## 4. 迁移与上线顺序

1. `0001_organization`：医院、科室、职工身份、医生档案、医生科室关系及必要索引。
2. `0002_agent_profiles`：医生智能体发布层、知识绑定；此时尚不对患者开放。
3. `0003_conversations`：医院会话绑定、消息归属、幂等命令回执；跨 App 外键须明确依赖 `chat_sync`、`ai_config`、知识模型所在迁移。
4. `0004_backfill_and_constraints`：只给新 Demo 会话建立绑定；旧 ChatThread 不强行回填医院归属。数据校验通过后再增加不可为空或条件唯一约束。
5. 功能开关先仅允许 `demo` 医院进入 `active`，验证同步、权限和审计后，才开放真实医院配置。

迁移必须可向前兼容：先加表/索引，再发布读路径，再发布写路径；不要在同一次发布中给大表加高风险非空列或全表锁。所有 Demo 种子数据使用幂等管理命令或受控 fixture，并明确为虚构资料。

## 5. API 与 Serializer 落地规则

根路由目标如下，实际接入时才加入 `INSTALLED_APPS` 与 `SparkService/urls.py`：

```text
/api/v1/hospital-care/        -> hospital_care.api.patient.urls
/api/hospital/v1/             -> hospital_care.api.staff.urls
/api/admin/v1/hospital-care/  -> hospital_care.api.backoffice.urls
```

### 5.1 患者端

| 接口 | 数据范围 / 写入规则 |
| --- | --- |
| `GET hospitals`、`GET hospitals/{id}/departments`、`GET departments/{id}/agents` | 只返回 `active` 医院、科室和 `published` 智能体；绝不返回医生内部资料或未发布配置 |
| `POST agents/{id}/conversations` | 校验当前登录人拥有传入 `member_id`；创建既有 ChatThread 后在同一业务动作中创建绑定；返回 thread 与 agent 摘要 |
| `GET conversations`、`GET conversations/{thread_id}` | 以 `ChatThread.user` 和 `member_id` 双重限定；现有消息读取协议不改 |
| `POST appointments/redirect` | 仅返回可信医院挂号入口或 Demo 提示；不伪造号源、支付、预约成功 |

患者 Serializer 只接受稳定 ID、当前成员 ID、必要的幂等键和有限显示偏好。医院、医生、风险级别、消息发言者均由服务端推导，客户端不得提交。

### 5.2 医生工作台

| 接口 | 写入规则 |
| --- | --- |
| `GET me/workspace`、`GET conversations`、`GET conversations/{id}` | 只查询当前 active 医生在本人/所属医院范围内可见的绑定会话；默认不暴露平台调试数据 |
| `POST conversations/{id}/join` | 原子确认医生身份与会话归属，写接管时间和审计；可幂等重试 |
| `POST conversations/{id}/messages` | 同事务创建既有 `ChatMessage`、医生 `ChatMessageAttribution`，更新 thread/binding 时间；不得让医生客户端直接写 role 或 attribution |
| `POST conversations/{id}/attention` | 只允许 `normal/follow_up/priority`；不改变 AI 风险信号 |
| `POST conversations/{id}/end` | 写服务结束原因、时间和操作者；历史仍可按授权阅读 |
| `GET/PUT me/agent` | 医生只能维护本人档案允许修改的展示字段和受控参数；发布、知识绑定等按医院审核规则办理 |

### 5.3 平台医院后台

后台沿用 `/api/admin/v1/` 的登录、`AdminCodePermission` 和 `write_audit_log`。新增权限码应在既有 `backoffice.rbac.bootstrap_admin_permissions()` 种子树中声明，例如：

```text
menu:hospital_care
menu:hospital_care:hospitals
api:hospital_care:hospitals:list
api:hospital_care:hospitals:create
api:hospital_care:hospitals:update
api:hospital_care:hospitals:activate
api:hospital_care:hospitals:suspend
api:hospital_care:departments:manage
api:hospital_care:staff:manage
api:hospital_care:agents:manage
api:hospital_care:audit:view
```

后台接口应为医院列表/创建/详情更新、激活/暂停、嵌套科室、职工、医生、智能体和审计查询；每个写接口只调用 `hospital_care.services`。医院后台不能把平台 `AdminUserRole` 分配给医院医生。

## 6. 权限判定

| 权限组件 | 判定 |
| --- | --- |
| `HospitalPatientPermission` | `request.user` 与 Thread 所属账号一致，且 `member_id` 为该账号可访问成员 |
| `HospitalStaffPermission` | 当前用户在目标医院有 `active` 的 `HospitalStaffMembership` |
| `DoctorConversationPermission` | 当前 active 医生档案与会话的医院一致，并且会话分配/接管规则允许访问 |
| `HospitalAdminPermission` | 当前医院职工角色为 `hospital_admin`；只可管理所在医院 |
| `BackofficeHospitalPermission` | 委托 `AdminCodePermission` 验证平台权限码 |

所有 Selector 在 SQL 起点就带医院范围、状态和用户范围过滤，不能“先按 ID 取对象、再判断”。医生工作台不得复用 `SuperAdminOnlyPermission`；平台管理员也不应因为后台身份自动获得医生工作台中的患者聊天权限。

## 7. 事务、并发、幂等与同步

### 7.1 必须原子化的命令

| 命令 | 一个 `transaction.atomic()` 中完成 |
| --- | --- |
| 激活/暂停医院 | 锁定 Hospital、校验当前状态与版本、更新状态、写审计 |
| 发布/停用智能体 | 锁定 Agent、校验医生/科室/知识绑定/风险说明、更新版本、写审计 |
| 创建医院会话 | 校验患者成员与 Agent 发布态、创建 Thread 和 ConversationBinding、写初始归属/审计 |
| 医生回复 | 锁定 ConversationBinding、校验服务未结束和医生权限、创建 Message + Attribution、更新时间、写审计 |
| 标记关注/结束服务 | 锁定 Binding、校验版本/状态、更新、写审计 |

涉及状态变化的查询使用 `select_for_update()`；请求携带 `Idempotency-Key`，服务先按 `(actor_user, command_key)` 查回执，再校验同 key 的请求摘要是否一致。相同 key 同请求返回原结果；不同请求返回冲突，不能执行第二次写入。

### 7.2 消息与 AI 事件

医生回复完成前不持有数据库锁调用外部 AI、HIS 或推送服务。事务提交后再触发现有聊天同步/事件发布机制；若现有事件链不具备可靠投递，应增加 outbox 记录并由后台任务发布。任何客户端同步失败均应可通过既有 Thread/Message 拉取恢复，不能以 WebSocket 是否在线决定消息是否存在。

AI 运行仍使用既有 ChatThread 和 Run 管线；绑定层只决定“此次会话使用哪个已发布医生智能体及其可用知识”，不复制 Prompt、Provider Key 或运行记录。

## 8. 业务错误码与客户端语义

| 业务码 | 推荐 HTTP | 客户端行为 |
| --- | --- | --- |
| `HOSPITAL_NOT_FOUND` / `HOSPITAL_INACTIVE` | 404 / 409 | 返回医院列表，提示服务暂不可用 |
| `MEMBER_ACCESS_DENIED` | 403 | 重新选择当前成员，不能继续进入会话 |
| `HOSPITAL_MEMBERSHIP_REQUIRED` / `DOCTOR_PROFILE_NOT_ACTIVE` | 403 | 医生工作台退出或提示联系医院管理员 |
| `AGENT_NOT_PUBLISHED` | 409 | 患者端隐藏入口并刷新目录 |
| `CONVERSATION_NOT_ASSIGNED` | 403 | 不透露其他医生/医院会话存在 |
| `CONVERSATION_ENDED` | 409 | 禁止继续医生服务消息，展示后续就医指引 |
| `CONVERSATION_VERSION_CONFLICT` | 409 | 刷新会话后由用户重新操作 |
| `PATIENT_CONSENT_REQUIRED` | 403 | 提示完成授权流程；不得用默认同意绕过 |
| `IDEMPOTENCY_CONFLICT` | 409 | 客户端生成新的幂等键后由用户确认重试 |
| `REGISTRATION_INTEGRATION_UNAVAILABLE` | 503 | 明确提示跳转或联系医院，不能伪造成功 |

业务错误仍走项目统一错误响应和 `request_id`；接口文档不得要求客户端解析英文异常文本。

## 9. 审计、隐私与运维

敏感动作统一调用既有 `backoffice.audit.write_audit_log`，建议动作名包括：

```text
hospital.create / hospital.update / hospital.activate / hospital.suspend
hospital.department.create / hospital.staff.grant / hospital.doctor.update
hospital.agent.publish / hospital.agent.disable
hospital.conversation.join / hospital.conversation.attention_update
hospital.conversation.end / hospital.doctor_message.send
```

审计中只保留操作人、医院/科室/会话/消息 ID、前后状态、请求 ID 和必要原因。不得记录消息全文、病历正文、附件 URL、身份证号、手机号或模型上下文；如既有审计辅助函数会序列化 request body，医院接口必须先做脱敏白名单。

日志、监控和异常上报同样只使用内部主键及风险级别摘要。医生查看患者对话属于敏感读取，应保留 `read` 审计或至少记录打开会话/导出（后者默认不提供）行为。

## 10. 测试与验收门槛

| 层级 | 最低覆盖 |
| --- | --- |
| Model | 组织唯一约束、同医院约束、医生主科室、消息归属组合、引用保护 |
| Service | 状态机、版本冲突、同 key 幂等、结束后不能回复、暂停医院不能新建会话 |
| Permission / Selector | 跨医院、跨医生、跨账号成员、已停用职工与平台管理员越权均被拒绝 |
| API | 统一响应 envelope、请求 ID、字段白名单、错误码、分页/排序、敏感字段不泄露 |
| Chat 回归 | 原同步 Thread/Message/Block 不变；医生消息在 iOS/Web 拉取和实时事件中顺序一致 |
| 安全 | 日志/审计无消息全文，非法 `member_id`、伪造 actor、重复幂等键和并发结束会话均覆盖 |

验收 Demo 至少有一所虚构医院、三个科室、三名医生、已发布和未发布各一名智能体、两名家庭成员患者、AI 回复与医生接管各一条消息，并覆盖正常、重点关注、已结束、医院暂停四种状态。

## 11. 实施前需确认的决策

1. 患者授权的具体文案、版本、留痕与撤回后会话可见性。
2. 医生接管范围：仅本人智能体、同科室值班，还是医院管理员可转派。
3. 医院管理员能否发布智能体，或必须医生本人/科主任二次审核。
4. 真实 HIS/挂号接口能力、可信跳转域名和失败回退流程。
5. 风险策略的不可降级规则、人工介入 SLA 与紧急情况提示责任边界。

医院知识库所有权、文本录入、手工向量、智能体手工关联、患者会话内同步等已确认，见《医院知识库产品需求与落地方案（确认版）》。脱敏病历不属于本期知识库录入范围。

以上决策未定时，只能以 `demo` 医院和合成资料演示，不能把目标接口直接标为生产医疗服务。
