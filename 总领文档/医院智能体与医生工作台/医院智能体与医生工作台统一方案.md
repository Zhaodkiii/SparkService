# 医院智能体与医生工作台统一方案

> 阶段：需求确认 / 方案设计（不实施代码）  
> 更新日期：2026-09-01  
> 服务端事实源：`SparkService`  
> 客户端配套文档：`LookHealthClient/SparkClient/总领文档/医院智能体与医生工作台/`
> 服务端实施细节：`服务端实施详细设计.md`

## 1. 结论

本 Demo 不另起一套聊天、知识库、记忆或 AI 配置系统。服务端目标新增一个独立 Django App `hospital_care`，由它承载医院业务域并关联现有 SparkService 能力：

```text
hospital_care
├── 医院 -> 科室 -> 医院职工身份 -> 医生档案 -> 医生智能体发布档案
└── 医院会话绑定 -> 医生关注 / 接管 / 结束 / 消息发言归属
                                           |
患者账号 -> 家庭成员 -> 现有 ChatThread ----+----> 医院会话归属
                         |                         |
                         +-> ChatMessage/Block    +-> 医生关注、接管、结束状态
                         +-> AI Run/Tool/Event
                         +-> 既有知识库、记忆、AI 配置
```

目标是做出一套可向医院演示的闭环，而不是在本阶段伪造完整互联网医院：

1. 患者在医院首页选择科室、医生智能体，先进行 AI 导诊或健康咨询。
2. AI 明确自己是“某医生团队维护的智能助手”，输出风险提示和就医建议，不冒充真实医生。
3. 医生登录医院工作台，维护自己智能体的公开资料与受控配置，查看授权会话。
4. 医生可接管并以真实医生身份回复、标记重点关注、结束本次服务会话。
5. 挂号在 Demo 中使用演示数据或医院现有挂号入口适配，不虚构真实号源和支付结果。

### 1.1 患者身份冻结结论

- iOS 不新增 Patient 实体，也不新增一套“切换患者”状态。
- 登录账号 `User` 只表示账号与数据所有者；该账号下当前选中的既有成员就是本次医疗服务的患者。
- “切换患者”就是复用现有“切换成员”操作、状态源和账号隔离逻辑，两种产品文案背后是同一个 memberID。
- 创建挂号、AI 导诊或医院会话时，把当前 memberID 传给服务端并继续写入现有 `ChatThread.member_id`。
- 已有会话始终保留创建时的 memberID；切换当前成员不会把历史会话改绑给另一位患者。

## 2. 需求范围

### 2.1 本阶段设计范围

| 端 | 页面 / 能力 |
| --- | --- |
| iOS 患者端 | 医院首页、预约挂号入口、科室列表、院内医生智能体列表、医生智能体详情、对话列表、对话页、风险与就医指导状态 |
| 医院工作台 | 医生登录后的会话工作台、重点患者标记、医生回复、结束会话、本人智能体维护、对话审计信息 |
| 服务端 | 医院、科室、职工身份、医生、智能体发布、会话归属、发言人归属、关注与会话状态的模型和 API 方案 |
| Demo 数据 | 虚构/授权的医院、科室、医生、患者和对话；所有演示数据显式标注 Demo |

### 2.2 明确不做

- 本轮不改 Swift、Python、Vue、TypeScript、数据库迁移和部署配置。
- 本轮只冻结 `hospital_care` App 方案，不执行 `startapp`，不创建 Python 文件，也不加入 INSTALLED_APPS。
- 本轮不创建 Git 分支；实施时客户端与服务端分别切独立 Demo 分支。
- 不复制现有 ChatThread、ChatMessage、ChatMessageBlock、AI Run、知识库、记忆和 AI 配置模型。
- 不把脱敏历史病历直接当作可上线知识库；数据授权、脱敏标准、质量审核、使用范围需医院书面确认。
- 不在无 HIS/互联网医院接口时宣称挂号成功、支付成功、线上复诊成立。
- 不把 AI 风险分层包装成诊断结论，也不允许医生在后台关闭法定安全底线。

### 3.1.1 目标新增服务端 App

| App | 状态 | 拥有的职责 | 明确不拥有 |
| --- | --- | --- | --- |
| `hospital_care` | 目标设计，尚未创建 | 医院、科室、医院职工、医生、医生智能体发布层、知识绑定、医院会话扩展、发言归属、患者端医院 API、医生工作台 API | 登录账号、家庭成员、聊天消息、AI Run、模型配置、知识文档、个人记忆、文件实体和全局后台 RBAC |

### 3.2 当前缺口

- 当前尚无 `hospital_care` Django App，也没有 Hospital、Department、DoctorProfile 等正式组织实体。
- 没有医院租户范围的职工身份和医生角色。
- ChatThread 不知道自己属于哪个医院、科室、医生智能体。
- ChatMessage 的 `role` 只表达 LLM 传输角色，不能证明发言者是 AI 还是真实医生。
- 当前后台会话页面是 SuperAdmin 只读查看，不支持医院范围授权、医生回复、关注或结束会话。
- 当前客户端没有真实挂号领域和 HIS 号源接口。

### 3.3 医院必须确认

1. 医院是否允许展示真实医生姓名、头像、职称、科室与擅长领域。
2. 医生智能体由本人、科主任还是信息科审核发布；变更是否需要二次审核。
3. 医生能查看哪些患者资料和多久以前的对话；患者是否需单独授权。
4. 历史病历进入知识库的合法依据、脱敏规范、可用科室和禁止用途。
5. 风险等级由谁定义、谁能调整，以及“必须转人工/必须建议急诊”的不可降低项。
6. 挂号接 HIS、互联网医院、小程序 Deep Link，还是仅作 Demo 占位。
7. 医生线上回复属于健康咨询、互联网诊疗还是院后随访，对应资质、留痕和时限要求。

```text
现有 backoffice-web
└── 医院管理

    ├── 新增医院
    └── 医院详情
```

## 5. 关键业务规则

### 5.1 AI、医生与患者身份必须分开

- `ChatMessage.role` 保留 `system/user/assistant`，继续服务 LLM 上下文和既有同步协议。
- 新增独立的消息发言归属，标识 `patient / ai_agent / doctor / system`。
- iOS 另派生展示角色 `currentUser / otherUser / assistant / system`：患者本人是 currentUser，后台真人医生是 otherUser，AI 智能体是 assistant。
- `otherUser` 不加入 `ChatMessageRole` 或 `AIRuntimeRole`；医生消息底层 role 保持 assistant，同时随消息下发 sender.doctor 医生快照。
- 医生发言在 LLM 上下文中可以按 assistant 历史参与，但界面必须显示医生姓名、职称与“真人医生”标识。
- AI 消息必须显示“AI 助手”，不得仅显示医生姓名造成冒充。
- 每条医生回复需记录操作者账号、医生档案、时间、来源端和审计记录。
- 医生从医院后台使用专用授权接口代写患者原 ChatThread，不能调用患者账号的普通消息 push 接口。

### 5.2 风险分层与重点关注分开

| 概念 | 用途 | 能否被医生调整 |
| --- | --- | --- |
| AI 医疗风险信号 | 给患者展示风险提示和就医建议 | 可在医院审批的规则范围内校准；法定/安全底线不可关闭 |
| 医生关注级别 | 工作台排序和随访提醒 | 医生可设普通、随访、重点 |
| 会话服务状态 | 待接管、AI 服务中、医生已接管、已结束 | 授权医生可变更 |

重点关注不等于患者已被诊断为高风险；UI 和字段命名禁止混用。

### 5.3 结束会话不删除历史

- “结束”只更新医院会话绑定状态和结束原因。
- ChatThread、消息、消息块和审计记录继续保留。
- 患者再次咨询时创建新会话，或按医院确认的规则恢复；默认不静默复用已结束会话。

### 5.4 知识库与记忆

- 医院、科室和医生智能体只绑定现有 KnowledgeBase，不复制文档。
- 医院知识库归 Hospital 所有，底层由医院专属 service User 承载；本期仅录入文字资料，不走审核流。资料可多选关联科室作分类，不作为授权边界；正文变更后立即生效。
- 患者个人记忆继续由患者账号隔离；医生只有在授权会话内按最小必要原则读取摘要。
- 脱敏病历应优先沉淀为经过审核的病例知识或指南，不直接把原始病历全文暴露给模型和医生端搜索。

### 5.5 挂号 Demo

按能力分三级展示：

1. `演示模式`：合成号源，确认页标明“仅用于产品演示，不产生真实挂号”。
2. `跳转模式`：跳转医院小程序、公众号或互联网医院，Spark 只记录跳转，不声称成功。
3. `真实接入`：医院提供 HIS/统一预约平台接口后，才展示真实医生排班、号源、订单和支付状态。

## 6. Demo 最小闭环

建议固定一所演示医院、3 个科室、每科 1–2 名医生智能体、6–10 个合成患者会话：

1. 用户登录后直接使用当前选中成员作为患者；需要更换患者时复用现有切换成员流程。
2. 从医院首页进入科室或医生智能体。
3. 查看医生及 AI 助手边界，发起咨询。
4. AI 询问必要信息，输出低/中/高风险提示和下一步行动。
5. 中高风险案例进入医生工作台“待接管”；重点患者在卡片上显示标记。
6. 医生查看授权摘要和完整对话，以真人身份回复。
7. 医生结束会话；患者端显示已结束及挂号/就医入口。

至少准备三类脚本：普通健康咨询、建议尽快门诊、高风险建议急诊；不得在演示中输出确诊或处方承诺。

## 7. 安全与合规门槛

- 演示数据默认全部合成；若使用真实数据，必须先取得授权并通过医院脱敏验收。
- 身份与权限按医院租户、科室和医生绑定过滤，禁止仅靠前端隐藏。
- 医生查看患者资料、打开会话、发送消息、标记关注、结束会话、修改智能体都写审计。
- 医生工作台不显示 Provider Key、系统密钥、其他医院数据和患者未授权的完整档案。
- AI 风险提示必须包含不确定性、建议行动和急症兜底；不替代诊断。
- 上线前需医院医务、信息、网安/法务共同确认数据、诊疗边界和留存策略。

## 10. 跨入口服务交付一致性

医院患者端、医生工作台和平台后台可以有不同路由和权限，但不是三套业务。服务端 `hospital_care` 的模型、Service、状态机、审计和业务码是唯一事实源；患者端与 Web 只做展示、输入收集和状态恢复。

| 领域动作 | 患者入口 | 医生入口 | 平台后台入口 | 同一服务端结果 |
| --- | --- | --- | --- | --- |
| 发现医院/智能体 | 读取已启用医院与已发布智能体 | 读取本人已分配智能体 | 维护医院/智能体发布状态 | Hospital / ClinicalAgentProfile 的同一状态 |
| 新建咨询 | 当前成员发起医院会话，首条展示医生简介系统卡 | 不可创建空白患者会话 | 不可替患者直接新建 | ChatThread + ClinicalConversationBinding + ChatMessageBlock 快照 |
| AI 回复 | 正常阅读与继续提问 | 阅读 AI 历史与风险摘要 | 不默认查看患者全文 | ChatMessage + AI Run + Attribution |
| 医生接管/回复 | 看见真实医生与服务状态 | 接管、发言、结束服务 | 仅审计/治理，不代替医生发言 | ConversationBinding + ChatMessageAttribution |
| 重点关注 | 仅按必要范围展示后续指引 | 标记 normal/follow_up/priority | 查看聚合或审计 | `doctor_attention_level`，不等于风险 |
| 风险提示 | 接收 AI 提示和就医建议 | 查看辅助摘要，不可随意篡改 | 配置审核与服务治理 | `risk_signal_level` 与风险策略记录 |

### 10.1 写入的统一规则

1. 每一个写动作都进入 `hospital_care.services`，在事务内校验身份、医院范围、当前状态、并发版本和幂等键，再写领域记录与审计。
2. 所有客户端均使用项目统一响应与错误语义；不得为 Web/iOS 单独造相同含义但不同名字的字段、状态或业务码。
3. 医生真实发言同时写既有 `ChatMessage` 与独立 `ChatMessageAttribution`；`role=assistant` 不承担真人身份判定。
4. 医院暂停、智能体停用、会话结束等状态必须由服务端阻断后续写入；前端收到实时事件后仍以详情接口复核。
5. 医生智能体首屏的简介卡必须是 `role=system` 的 `hospital_doctor_intro_card`，不是医生真实发言，也不是 AI 回复；它由服务端在创建医院会话时按审核发布版本写入，历史会话保留快照，完整简介页读取最新发布版本。
5. 平台后台只负责医院治理，不能绕过医生授权以“管理员”身份给患者线程发言；医生工作台也不能借用后台 SuperAdmin 权限。

### 10.2 实施交付物顺序

| 顺序 | 服务端交付 | 下游可开始的工作 |
| --- | --- | --- |
| 1 | `hospital_care` 模型、迁移、状态机、权限、基础错误码与 Service 测试 | 后台可用假数据联调 DTO |
| 2 | 医院/科室/职工/医生/智能体后台 API、审计与 RBAC | `backoffice-web` 医院管理页面 |
| 3 | 医生工作台查询、接管、关注、结束、医生消息 API 与同步事件 | `chat-web` 医生工作台改造 |
| 4 | 患者医院目录、发起医院会话、挂号模式 API | iOS 医院首页与医生智能体目录 |
| 5 | 真实 HIS/知识库/患者授权适配（医院确认后） | 医院联调与生产准入 |

详细的模型、迁移、并发、审计和验收要求见 `服务端实施详细设计.md`。本阶段三端均不得以尚未交付的目标接口伪造真实医院服务成功。
