# 医院后台管理模块 Plain Text UI 原型

> 目标前端：`SparkService/backoffice-web`  
> 目标服务端：新增 Django App `hospital_care`  
> 阶段：需求与 UI 原型，尚未实现代码  
> 更新日期：2026-09-01

## 1. 模块定位

在现有后台管理系统增加一级模块“医院管理”，供平台管理员新增医院并维护医院基础资料、科室、职工/医生、医生智能体、服务接入和审计。

```text
backoffice-web 负责管理页面与 RBAC 按钮显隐
        ↓ /api/admin/v1/hospital-care/
hospital_care.api.backoffice 负责输入输出与权限接入
        ↓
hospital_care.services 负责唯一业务规则和状态转换
        ↓
Hospital / Department / Staff / Doctor / Agent 等统一模型
        ↓
AdminAuditLog 记录全部敏感写操作
```

后台不直接操作数据库，不复制医院模型，也不使用医生工作台权限替代平台 RBAC。

## 2. 与现有后台框架的复用

| 现有能力 | 证据 | 医院模块用法 |
| --- | --- | --- |
| Vue Router 懒加载 | `backoffice-web/src/router/routes.ts` | 增加 `/hospital-care/*` 路由组 |
| 管理布局和分组菜单 | `layouts/AdminLayout.vue` | 增加一级菜单“医院管理” |
| 登录门禁 | `router/index.ts`、`stores/auth.ts` | 继续校验管理员登录态 |
| RBAC | `backoffice` AdminRole/Permission/UserRole、`usePermission` | 菜单、按钮、API 三层权限码 |
| HTTP 封装 | `backoffice-web/src/api/http.ts` | 新增 `api/modules/hospitalCare.ts` 消费统一后台 API |
| 表格/表单/Modal/Drawer | 现有 Users、AIProviders、VersionConfigs 等页面 | 复用列表、筛选、表单校验和确认交互 |
| 操作审计 | `AdminAuditLog`、Audit 页面 | 新增医院资源类型和动作筛选 |

## 3. 菜单与路由

```text
后台管理
├── 仪表盘
├── 用户管理
├── 医院管理                 menu:hospital_care
│   └── 医院列表             menu:hospital_care:hospitals
├── 医疗数据
├── AI 配置
└── 审计日志
```

| 路由 | 页面 | 权限 |
| --- | --- | --- |
| `/hospital-care/hospitals` | 医院列表 | `menu:hospital_care:hospitals` |
| `/hospital-care/hospitals/new` | 新增医院 | `button:hospital_care:hospital:create` |
| `/hospital-care/hospitals/:hospitalId` | 医院详情与维护 | `api:hospital_care:hospital:read` |

普通医生和医院职工不进入该后台模块；他们使用独立医生工作台。平台后台角色也不会自动获得患者会话回复权限。

### 4.1 列表行为

- 默认按最近更新时间倒序；筛选与分页由服务端完成。
- 医院名称进入详情，操作列只展示当前管理员有权执行的动作。
- 列表不提供删除按钮。草稿、启用、暂停使用明确状态标签。
- 科室/医生数量来自后台聚合摘要，不由前端额外请求逐行计算。
- 搜索失败保留上次成功结果并显示 request_id；不把失败渲染成空列表。

### 4.2 页面状态

| 状态 | 表现 |
| --- | --- |
| loading | 统计卡与表格骨架 |
| empty | “尚未新增医院”并在有权限时显示新增按钮 |
| filtered_empty | “当前筛选无结果”与清除筛选 |
| error | 保留筛选条件，显示错误和重试 |
| unauthorized | 返回仪表盘并提示无医院管理权限 |

## 5. 新增医院

新增采用独立页面，避免将较多字段塞进小型 Modal。首次保存只创建 `draft` 医院，不自动启用。

```text
┌──────────────────────────────────────────────────────────────────────┐
│ < 返回医院列表                  新增医院                              │
├──────────────────────────────────────────────────────────────────────┤
│ 基本信息                                                             │
│ 医院官方名称 *       [________________________________________]       │
│ 医院简称             [____________________]                           │
│ 医院唯一编码 *       [____________________]  创建后不可随意修改       │
│ 医院等级             [请选择⌄]                                       │
│ 医院 Logo            [上传图片]                                      │
│                                                                      │
│ 地址与联系方式                                                       │
│ 省 / 市 / 区 *        [____⌄] [____⌄] [____⌄]                        │
│ 详细地址 *           [________________________________________]       │
│ 服务电话             [____________________]                           │
│ 急诊电话             [____________________]                           │
│ 官方网站             [________________________________________]       │
│                                                                      │
│ 服务模式                                                             │
│ (●) Demo 演示   ( ) 跳转医院官方入口   ( ) 已对接 HIS                 │
│ 跳转地址             [________________________________________]       │
│                                                                      │
│ 医院简介             [________________________________________]       │
│                      [________________________________________]       │
├──────────────────────────────────────────────────────────────────────┤
│                                      [取消] [保存草稿]                │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.1 校验规则

- 官方名称、唯一编码、行政区划、详细地址和服务模式必填。
- 医院编码进行唯一性校验；冲突返回字段级错误，不能静默追加随机后缀。
- Logo 通过 file_manager 上传并保存 file_id，不在医院表保存 Base64。
- redirect 模式必须填写 HTTPS 官方入口并通过可信域名校验。
- integrated 模式在真实接口配置完成前只能保存草稿，不能启用。
- 放弃未保存内容时二次确认；保存请求使用幂等键避免双击产生两家医院。

### 6.1 概览

```text
[科室 12] [有效医生 36] [已发布智能体 18] [进行中会话 24]

基础资料完整度：92%
待处理事项

```

进行中会话只显示聚合数量；平台医院管理页不默认展开患者敏感对话。

### 6.2 基础资料

复用新增页面字段，进入编辑态后显示“取消 / 保存”。保存必须携带 `version`；冲突时提示“资料已被其他管理员更新”，展示服务端新值，不覆盖提交。

医院编码默认只读。确需修改时走单独高权限流程，并检查外部系统映射和审计，不把它当普通表单字段。

### 6.3 科室

```text
│ 科室管理                                      [+ 新增科室] │
│ [搜索科室] [状态⌄] [排序模式]                              │
│ 科室名称   编码       上级科室   医生数  智能体数  状态 操作│
│ 心内科     CARD       内科中心    12       6       启用 编辑│
│ 皮肤科     DERM       --           8       4       启用 编辑│
```

- 支持新增、编辑、排序、隐藏，不物理删除已有业务关联的科室。
- 隐藏科室前显示受影响的已发布智能体和新咨询入口。
- 科室编码在医院内唯一。

### 6.4 职工与医生

```text
│ [职工] [医生资料]                              [+ 邀请职工] │
│ 姓名    工号    角色      科室    资质状态    账号状态  操作│
│ 张医生  10086   医生      心内科  已核验      有效      详情│
│ 李主任  10010   医院管理员 --     --          已邀请    重发│
```

- 职工身份关联现有 User，不新建用户名密码表。
- 邀请医院管理员不等于授予平台 SuperAdmin。
- 医生资料维护包括职称、科室、擅长、简介、头像和资质状态。
- 证件材料属于敏感文件，只向获准角色展示，列表不显示完整证件号。

### 6.5 医生智能体

```text
│ 智能体管理                              [状态⌄] [科室⌄]     │
│ 智能体名称       医生    科室    知识库    发布状态    操作 │
│ 张医生 AI 助手   张医生  心内科  2 个      待审核      审核 │
│ 李医生 AI 助手   李医生  皮肤科  1 个      已发布      查看 │
```

- 平台管理员审核公开资料、服务边界和知识绑定。
- 审核页不展示 Provider Key；底层模型配置继续由 AI 配置模块管理。
- 驳回必须填写原因；暂停智能体不会删除历史会话。

### 6.6 服务接入

```text
挂号与就医模式
(●) Demo  ( ) 官方跳转  ( ) HIS 已接入

官方跳转地址  [https://hospital.example/registration]
可信域校验    [已通过]

HIS 接入状态  [未配置]
[配置说明] [连接测试] [查看最近同步]
```

密钥、签名 Secret 和生产凭证不返回前端明文；后台只显示配置状态、掩码标识和最近测试结果。Demo 模式不得显示真实接入成功。

### 6.7 审计记录

```text
│ [动作类型⌄] [操作人] [日期范围] [查询]                       │
│ 时间                操作人    动作            结果  Request ID│
│ 2026-09-01 09:20    管理员 A  更新医院资料    成功  req_***   │
│ 2026-08-31 16:40    管理员 B  启用科室        成功  req_***   │
```

复用 AdminAuditLog；请求与响应 payload 必须脱敏，不记录完整证件、患者资料、密钥和知识正文。

## 7. 医院状态操作

### 7.1 启用医院

启用前检查：基础字段完整、至少一个有效医院管理员、服务模式配置合法。是否必须有科室/医生/智能体由 Demo 阶段确认；校验失败按项目逐项展示。

```text
启用天长市中医院？

启用后患者端可发现该医院，并可按当前服务模式使用入口。
检查结果：
✓ 基础资料完整
✓ 已配置医院管理员
✓ Demo 服务模式可用
! 暂无已发布医生智能体（允许启用，但患者端不展示智能体）

[取消] [确认启用]
```

### 7.2 暂停医院

```text
暂停医院服务

暂停后禁止创建新的挂号和医院咨询；历史会话仍可查看，
进行中会话按医院确认的策略继续或转人工处理。

暂停原因 * [________________________________]
[取消] [确认暂停]
```

不提供物理删除。暂停原因、操作人、时间和影响范围进入审计。

## 8. RBAC 权限建议

| 类型 | 权限码示例 |
| --- | --- |
| 菜单 | `menu:hospital_care`、`menu:hospital_care:hospitals` |
| 按钮 | `button:hospital_care:hospital:create/update/activate/suspend` |
| API | `api:hospital_care:hospital:list/read/create/update/activate/suspend` |
| 科室 | `api:hospital_care:department:list/create/update` |
| 职工医生 | `api:hospital_care:staff:list/create`、`api:hospital_care:doctor:list/update` |
| 智能体 | `api:hospital_care:agent:list/review` |
| 审计 | `api:hospital_care:audit:list` |

建议预置角色：

- 平台医院管理员：维护医院、科室、职工和服务配置。
- 医院内容审核员：只审核医生资料和智能体，不改医院接入配置。
- 医院审计查看员：只读医院资料和审计日志。
- SuperAdmin：拥有全部权限，但操作仍写审计。

## 9. API 与页面映射

| 页面动作 | 服务端入口 | 成功后 UI | 失败回滚 |
| --- | --- | --- | --- |
| 查询医院 | GET `/api/admin/v1/hospital-care/hospitals/` | 更新统计和列表 | 保留旧列表 |
| 新增医院 | POST `.../hospitals/` | 进入草稿医院详情 | 保留表单和幂等键 |
| 保存资料 | PATCH `.../hospitals/{id}/` | 刷新 version 和更新时间 | 冲突时展示最新值 |
| 启用 | POST `.../{id}/activate/` | 状态改为已启用 | 展示逐项校验错误 |
| 暂停 | POST `.../{id}/suspend/` | 状态改为暂停 | 保留原因输入 |
| 新增科室 | POST `.../{id}/departments/` | 插入科室行 | 保留表单 |
| 邀请职工 | POST `.../{id}/staff/` | 显示 invited 状态 | 不在前端创建假账号 |
| 审核智能体 | POST `.../agents/{id}/review/` | 更新审核状态 | 保留审核意见 |

## 10. 验收标准

1. 有权限的管理员可以新增草稿医院，重复提交不会产生重复医院。
2. 医院编码唯一；字段错误能定位到具体输入项。
3. 医院可以维护基础资料、科室、职工/医生、智能体和服务模式。
4. 启用与暂停均经过服务端状态机校验并写审计，不允许前端直接改 status。
5. 医院、科室、医生和智能体没有物理删除入口，历史关系与会话不丢失。
6. 不同后台角色只能看到和操作获准的菜单、按钮和 API。
7. 医院后台修改后，患者端和医生工作台从同一 `hospital_care` 模型读取最新状态。
8. 敏感证件、患者资料、Provider Key、HIS Secret 不进入列表、普通日志或审计明文。
9. 网络失败、权限失效、版本冲突、重复点击和部分加载失败都有明确恢复路径。
10. 所有目标页面均延续现有 backoffice-web 的表格、表单、Modal、Drawer 和审计交互，不另建管理框架。

本文件只定义目标模块；当前 `backoffice-web` 和 `hospital_care` 尚未实现上述医院管理代码。
