> 状态：目标设计，尚未实现。所有名称均需在 D0 评审后再进入 migration。  
> 原则：现有聊天、AI、知识、记忆、用户、成员模型是单一事实源。

## 0. Django App 决策

服务端新增独立 Django App：`hospital_care`。本文件内全部新增模型、患者端医院 API、医院职工 API、权限和业务状态转换归该 App 所有。

总路由目标挂载：


## 1. 复用清单

| 现有模型 / 模块 | 保持不变的职责 | 本方案如何关联 |
| --- | --- | --- |
| `accounts.User` | 登录账号 | 医院职工和患者统一关联 User |
| `medical` 成员模型 | 登录账号下的当前咨询人 / 家庭成员 | iOS 当前选中成员就是患者，继续使用 ChatThread.member_id，不新增 Patient 表 |
| `ChatThread` | 会话容器和 AI 参数 | 由一对一医院会话绑定扩展 |
| `ChatMessage` | 唯一消息记录 | 由一对一发言归属扩展 |
| `ChatMessageBlock` | 流式内容、工具卡片、风险卡片 | 不新建医院专用消息块 |
| ChatRun / Event / Tool / Interaction | AI 执行与审计 | 医生智能体继续走原管线 |
| `AIModelCatalog` / `AIScenarioModelBinding` | 模型、agent 身份和运行配置 | 医生智能体发布档案只引用绑定行 |
| `KnowledgeBase` / `KnowledgeDocument` | 知识容器和文档 | 通过知识绑定复用 |
| `AIMemory` | 患者个体记忆 | 保持用户级隔离，不挂到医院共享域 |
| `AdminAuditLog` | 后台操作审计 | 记录医院工作台敏感读写操作 |

## 2. 新增实体关系

```text
Hospital 1 --- n HospitalDepartment
Hospital 1 --- n HospitalStaffMembership n --- 1 User
HospitalStaffMembership 1 --- 0..1 DoctorProfile
DoctorProfile n --- n HospitalDepartment (DoctorDepartmentMembership)
DoctorProfile 1 --- n ClinicalAgentProfile
ClinicalAgentProfile n --- 1 AIScenarioModelBinding
ClinicalAgentProfile n --- n KnowledgeBase (ClinicalAgentKnowledgeBinding)

ChatThread 1 --- 0..1 ClinicalConversationBinding
ChatMessage 1 --- 0..1 ChatMessageAttribution
ClinicalConversationBinding 1 --- n AdminAuditLog (resource reference)
```

以上新增实体全部定义在 `hospital_care`；图中的 User、ChatThread、ChatMessage、AIScenarioModelBinding 和 KnowledgeBase 都是跨 App 外键引用，不迁移、不复制。

患者身份不出现在新增实体中：`User` 负责认证和数据归属，既有 medical member 负责表示实际接受咨询的人。服务端创建医院会话时必须校验当前登录 User 对传入 member_id 的访问权；通过后继续把 member_id 写入 ChatThread。医院扩展表不得再保存一份可漂移的 patient_id/member_id。

## 3. 模型规格

### 3.1 Hospital

模型归属：`hospital_care`。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| id | UUID PK | 医院主键 |
| code | varchar unique | 医院内部稳定编码 |
| name | varchar | 官方名称 |
| short_name | varchar | 客户端简称 |
| grade | varchar nullable | 等级展示，不作为权限依据 |
| logo_file_id | FK nullable | 复用 file_manager |
| province_code / city_code / district_code | varchar nullable | 行政区划编码，不只保存自由文本 |
| address | varchar | 对外地址 |
| service_phone | varchar blank | 对外服务电话 |
| emergency_phone | varchar blank | 急诊电话；需医院审核 |
| website_url | varchar blank | 官方网站 |
| introduction | text blank | 医院简介 |
| registration_redirect_url | varchar blank | redirect 模式的官方挂号入口；需可信域校验 |
| service_mode | demo / redirect / integrated | 挂号与就医服务模式 |
| status | draft / active / suspended | 发布状态 |
| version | bigint | 乐观锁，防止后台多人覆盖 |
| created_at / updated_at | datetime | 审计时间 |

医院不提供物理删除。`draft -> active -> suspended -> active` 为目标状态转换；启用前至少校验官方名称、唯一编码、地址、服务模式和管理员配置。暂停医院不会删除科室、医生、智能体或历史会话，只禁止新服务并向客户端返回明确状态。

### 3.2 HospitalDepartment

模型归属：`hospital_care`。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| id | UUID PK | 科室主键 |
| hospital_id | FK + index | 所属医院 |
| parent_id | self FK nullable | 支持门诊中心 / 亚专科 |
| code | varchar | 医院内唯一，与 hospital 组成唯一约束 |
| name / short_name | varchar | 展示名称 |
| description | text | 科室说明 |
| sort_order | int | 排序 |
| status | active / hidden | 状态 |

### 3.3 HospitalStaffMembership

模型归属：`hospital_care`。

这是医院租户范围的身份，不复用全局 `AdminUserRole`，避免医生获得平台后台权限。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| id | UUID PK | 身份主键 |
| hospital_id | FK | 租户范围 |
| user_id | FK User | 登录账号 |
| role | hospital_admin / doctor / nurse / auditor | 医院内角色 |
| employee_no | varchar nullable | 工号；医院内唯一 |
| status | invited / active / suspended | 身份状态 |
| valid_from / valid_until | datetime nullable | 有效期 |

唯一约束：`hospital_id + user_id + role`。所有医院工作台查询必须先解析有效 membership。

### 3.4 DoctorProfile 与 DoctorDepartmentMembership

模型归属：`hospital_care`。

DoctorProfile 保存医生业务身份，不复制 User 登录信息。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| id | UUID PK | 医生主键 |
| staff_membership_id | OneToOne | 必须是 doctor 角色 |
| display_name | varchar | 医院审核姓名 |
| title | varchar | 职称 |
| professional_directions | JSON list（最多 3 项） | 对患者公开的专业方向；审核发布后展示 |
| specialties | JSON list | 演示期展示标签；正式期可结构化 |
| specialties_summary | text | 医院审核的专业擅长摘要，不得承诺诊疗效果 |
| introduction | text | 医生个人简介 |
| verified_experience_items | JSON list | 经医院审核的诊疗经验/服务项目事实；无依据则为空，不展示虚构病例数、成功率、排名或年限 |
| avatar_file_id | FK nullable | 头像 |
| license_status | unverified / verified / suspended | 资质状态；不保存公开证件全文 |
| profile_status | draft / active / hidden | 展示状态 |
| profile_version | bigint | 每次审核发布递增；用于会话首条简介卡快照 |

DoctorDepartmentMembership：`doctor_id + department_id + is_primary + status`，支持多科室执业或医生团队。

### 3.5 ClinicalAgentProfile

模型归属：`hospital_care`，运行配置事实源仍在 `ai_config`。

这是“医生智能体业务发布层”，不是第二套 AI 配置。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| id | UUID PK | 智能体发布主键 |
| doctor_id | FK | 归属医生 |
| department_id | FK | 面向科室 |
| scenario_binding_id | FK `AIScenarioModelBinding` | 复用模型、Prompt、工具和运行配置 |
| name | varchar | 如“张医生 AI 助手” |
| public_summary | text | 对患者展示 |
| greeting | text | 欢迎语 |
| quick_questions | JSON list | 经审核的推荐提问；不得暗示诊断或保证疗效 |
| service_boundary | text | 可回答 / 不可回答范围 |
| publication_status | draft / review / published / suspended | 发布状态 |
| doctor_editable_policy | JSON | 只保存获批可调项，不保存密钥 |
| published_at | datetime nullable | 发布时间 |

约束：发布前医生资质、科室和 AIScenarioModelBinding 必须有效。医生只能改可编辑字段；模型供应商、系统安全 Prompt、密钥和强制风险规则由医院管理员/平台控制。

### 3.6 ClinicalAgentKnowledgeBinding

模型归属：`hospital_care`，知识正文事实源仍在 `chat_sync` 知识模型。

| 字段 | 说明 |
| --- | --- |
| agent_profile_id | 医生智能体 |
| knowledge_base_id | 现有 KnowledgeBase |
| usage_scope | 既有 hospital / department / doctor；本期医院知识库绑定固定写入 hospital |
| priority | 检索优先级 |
| status | active / disabled |
| approved_by / approved_at | 既有审核留痕字段；演示版本不启用审核流 |

不复制 KnowledgeDocument。医院知识库已确认使用“Hospital 业务所有 + 医院专属 service User 技术承载”：所有底层 `KnowledgeBase.user` 指向医院 service User，操作人记录在医院扩展档案中；不能绕过 user 过滤硬查共享文档。知识库的科室多选仅是分类，不启用 `department/doctor` 绑定授权语义。

### 3.7 ClinicalConversationBinding

模型归属：`hospital_care`，会话与消息事实源仍在 `chat_sync`。

一对一扩展 ChatThread，不给 ChatThread 堆叠医院专用字段。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| thread_id | OneToOne PK/FK | 现有 ChatThread |
| hospital_id | FK + index | 医院快照归属 |
| department_id | FK + index | 科室归属 |
| doctor_id | FK + index | 当前负责医生 |
| agent_profile_id | FK + index | 发起时智能体 |
| service_status | ai_active / pending_doctor / doctor_joined / ended | 服务状态 |
| doctor_attention_level | normal / follow_up / priority | 工作台关注级别 |
| attention_note | text blank | 内部说明，不回传患者端 |
| risk_signal_level | none / low / medium / high | AI 最近一次风险信号摘要，不代替原风险消息块 |
| risk_signal_message_id | FK nullable | 可追溯到原 ChatMessage |
| assigned_at / doctor_joined_at | datetime nullable | 流程时间 |
| ended_at / ended_by_user_id / end_reason | nullable | 结束留痕 |
| version | bigint | 乐观锁，防止多人覆盖 |

规则：结束服务不更新 ChatThread.is_deleted；priority 与 risk_signal_level 互不推导。

患者关联规则：患者事实源是 `thread.member_id`。当前成员切换只影响后续新建会话和挂号请求，不更新本行对应历史 Thread 的 member_id。

### 3.8 ChatMessageAttribution

模型归属：`hospital_care`，通过 OneToOne 扩展现有 ChatMessage。

一对一扩展 ChatMessage，解决“LLM role”和“真实说话人”语义冲突。

| 字段 | 类型 / 约束 | 说明 |
| --- | --- | --- |
| message_id | OneToOne PK/FK | 现有 ChatMessage |
| actor_type | patient / ai_agent / doctor / system | 真实发言类型 |
| actor_user_id | FK nullable | 操作账号 |
| doctor_id | FK nullable | 真人医生身份 |
| agent_profile_id | FK nullable | AI 智能体身份 |
| display_name_snapshot | varchar | 发送时展示名，用于审计历史 |
| source | patient_app / doctor_console / ai_runtime / system | 来源 |

约束示例：actor_type=doctor 时 doctor_id 和 actor_user_id 必填；actor_type=ai_agent 时 agent_profile_id 必填。`ChatMessage.role` 不新增 doctor 枚举。

iOS 展示映射：服务端持久化的是事实角色 `patient/doctor/ai_agent/system`，不持久化依赖观察者视角的 `currentUser/otherUser`。患者端收到 actor_type=doctor 后派生 `displayRole=otherUser`；医生消息的 ChatMessage.role 仍为 assistant，以兼容既有同步和 AI 上下文。

同步消息必须增加可选 sender 嵌套快照，至少包含 actor_type、actor_id、display_name、avatar_url，以及医生的 doctor_id、display_name、title、hospital_name、department_name、avatar_url、verified。该快照由统一序列化服务生成，后台接口与患者同步接口不得各自拼装。

## 4. API 命名空间

患者、医院职工和平台后台三组 API 都由 `hospital_care` 交付，但使用不同 URL 模块和权限类；共享相同 services、models、状态机和异常语义。

### 4.1 患者端 `/api/v1/hospital-care/`

| 方法与路径 | 用途 |
| --- | --- |
| GET `hospitals/{hospital_id}/home/` | 首页聚合：医院、当前成员摘要、快捷服务、科室、推荐智能体 |
| GET `hospitals/{hospital_id}/departments/` | 科室目录 |
| GET `hospitals/{hospital_id}/agents/` | 智能体列表；支持 department、keyword、cursor |
| GET `agents/{agent_id}/` | 医生、智能体边界、可用状态和快捷问题 |
| GET `agents/{agent_id}/doctor-profile/` | 最新已审核发布的医生完整简介；包含身份、专业方向、专业擅长、审核经验项与智能体服务边界 |
| POST `conversations/` | 用 agent_id + 当前选中 member_id 创建医院会话和现有 ChatThread，并原子写入首条医生简介系统卡；member 必须属于当前登录账号 |
| GET `conversations/{thread_id}/context/` | 医院会话状态、医生/AI 身份、行动入口 |
| GET `hospitals/{hospital_id}/registration/entry/` | 返回 demo / redirect / integrated 能力声明 |

消息发送、同步、消息块和 Run 继续调用现有 chat_sync 契约，不另建医院消息 API。

### 4.2 医院工作台 `/api/hospital/v1/`

| 方法与路径 | 权限与用途 |
| --- | --- |
| GET `me/` | 当前 hospital membership 与 doctor profile |
| GET/PATCH `me/agent/` | 查看/维护本人获准字段 |
| GET `doctor/conversations/` | 仅本医院且分配给本人/本人团队；支持状态、关注、风险、关键字 |
| GET `doctor/conversations/{thread_id}/` | 对话、患者授权摘要和状态 |
| GET `doctor/conversations/{thread_id}/messages/` | 复用现有消息时间线序列化 |
| POST `doctor/conversations/{thread_id}/messages/` | 医生直接发送；事务写 role=assistant 的 ChatMessage + doctor Attribution + AuditLog，并通过现有同步投递患者端 |
| PATCH `doctor/conversations/{thread_id}/attention/` | 更新 normal / follow_up / priority |
| POST `doctor/conversations/{thread_id}/join/` | 医生接管 |
| POST `doctor/conversations/{thread_id}/end/` | 结束服务，要求原因与 version |

医院管理员可在同命名空间下增加 `admin/departments/`、`admin/doctors/`、`admin/agents/`；不得把医生直接接入 `/api/admin/v1/` 的 SuperAdmin API。

### 4.3 平台后台管理 `/api/admin/v1/hospital-care/`

供现有 `backoffice-web` 的“医院管理”模块使用。路由由 `hospital_care.api.backoffice` 提供，认证/RBAC/审计复用 `backoffice`。

| 方法与路径 | 用途 | 目标权限码 |
| --- | --- | --- |
| GET `hospitals/` | 医院分页列表、搜索、状态和服务模式筛选 | `api:hospital_care:hospital:list` |
| POST `hospitals/` | 新增草稿医院 | `api:hospital_care:hospital:create` |
| GET `hospitals/{hospital_id}/` | 医院详情与各分栏数量摘要 | `api:hospital_care:hospital:read` |
| PATCH `hospitals/{hospital_id}/` | 编辑医院基础资料；要求 version | `api:hospital_care:hospital:update` |
| POST `hospitals/{hospital_id}/activate/` | 校验并启用医院 | `api:hospital_care:hospital:activate` |
| POST `hospitals/{hospital_id}/suspend/` | 暂停新服务；要求原因 | `api:hospital_care:hospital:suspend` |
| GET/POST `hospitals/{hospital_id}/departments/` | 科室列表与新增 | `api:hospital_care:department:list/create` |
| PATCH `departments/{department_id}/` | 编辑、排序、隐藏科室 | `api:hospital_care:department:update` |
| GET/POST `hospitals/{hospital_id}/staff/` | 职工列表与邀请/绑定 | `api:hospital_care:staff:list/create` |

后台菜单/按钮权限继续由现有 AdminRole、AdminPermission、AdminRolePermission、AdminUserRole 控制；医院职工身份 HospitalStaffMembership 不等同于平台后台角色。

## 5. 核心事务与幂等

### 5.1 创建医院会话

```text
校验登录账号 token 与当前选中 member 权限
-> 校验 hospital / department / agent 已发布
-> 创建或接收 client thread_id
-> 写现有 ChatThread
-> 写 ClinicalConversationBinding
-> 读取已发布 DoctorProfile + ClinicalAgentProfile，生成仅含公开审核字段的简介快照
-> 写既有 ChatMessage(role=system) + ChatMessageBlock(kind=hospital_doctor_intro_card)
-> 写既有系统身份/免责声明消息和 Attribution（如风险策略要求）
-> commit 后启动 AI Run
```

`hospital_doctor_intro_card` 是系统消息而非医生或 AI 的一次发言；卡片内容含医生身份、专业方向/擅长、简介摘要、智能体名称和服务边界，并携带 `doctor_profile_version`、`agent_profile_version`。同一 ClinicalConversationBinding 只允许一张该卡，使用 `Idempotency-Key` 或 client thread_id 防止重复创建。

医院医生智能体会话不调用客户端本地的通用 `ChatGuideCard` 首条插入逻辑；普通健康会话仍保持既有逻辑。历史消息中的医生简介卡读取其落库快照，保证审计可追溯；“查看完整医生简介”再读取上述最新已发布资料。已存在的演示会话不得静默改写，只有无患者业务消息的样例线程可经审计的一次性迁移补卡。

### 5.2 医生发送

```text
解析有效 HospitalStaffMembership
-> SELECT FOR UPDATE 会话绑定
-> 校验 hospital、doctor、service_status、version
-> 写 ChatMessage（role=assistant）
-> 写 ChatMessageAttribution（actor_type=doctor）
-> 更新 thread/server_updated_at
-> 写 AdminAuditLog
-> commit 后走现有同步/WS 通知
```

医生后台不能复用患者普通 push API，因为 ChatThread.owner 仍是患者账号。专用接口根据登录医院职工身份完成授权后代写原 Thread；医生、医院、科室均从服务端 membership / assignment 推导，禁止由请求 body 自报。

兼容门槛：旧客户端没有 sender/otherUser 展示能力时会把 role=assistant 的医生消息误判为 AI。因此生产环境必须在 `message_sender_v1` 客户端能力或最低版本满足后才开放医生直接发送；不支持版本只能收到升级提示，不能收到会被误标为 AI 的医生原文。

### 5.3 结束会话

仅允许 `ai_active/pending_doctor/doctor_joined -> ended`；重复请求返回同一 ended 快照。结束后拒绝医生继续发送，患者端可读历史并创建新会话。

## 7. 错误语义

## 8. 索引、审计和测试门禁

- 列表索引至少覆盖 `(hospital, doctor, service_status, doctor_attention_level, updated_at)`。
- 所有详情查询先过滤医院和医生范围，再按主键取对象，避免对象存在性泄露。
- 审计记录 action、actor、hospital、doctor、thread、patient user、结果、IP/设备和 request_id；不在日志写完整病历正文。
- 必测：跨医院越权、同院未分配越权、已停用医生、重复发送、并发结束、结束后写入、患者撤回授权、AI/医生身份映射、知识库跨租户访问。
- 现有 chat sync、AI Run、Knowledge、Memory 测试必须全部回归，证明增量层没有破坏旧协议。
