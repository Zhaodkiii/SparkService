# 记忆：服务端与客户端数据模型设计

> 状态：修订建议方案，待评审（2026-08-27）
>
> 范围：仅定义“记忆”领域的持久化、客户端本地模型与同步 DTO；不包含 API、服务、界面或代码实现。
>
> 结论：服务端保存唯一权威记录；客户端保存可离线编辑、可重试同步的本地镜像与 Outbox。记忆不是完整聊天记录，也不是知识库文档。
>
> 配套需求文档：[`记忆系统与AI工具完整需求文档.md`](./记忆系统与AI工具完整需求文档.md)。工具协议、API、工作台、异步任务、客户端改造与验收以配套需求文档为准；本文只冻结数据模型。

## 1. 设计目标与边界

### 1.1 什么是记忆

记忆是可在未来对话中复用的、具备明确作用域的结构化事实或偏好。例如“使用中文回答”“成员张三对花生过敏”“本周暂停运动”。

不属于记忆的数据：完整聊天原文、未经筛选的模型推断、知识库原始文件、临时 UI 状态。聊天原文保留在既有聊天模型；知识库文件保留在知识库模型；记忆只保留经确认或可追溯的结论。

### 1.2 核心原则

| 原则 | 数据模型含义 |
| --- | --- |
| 服务端为准 | 服务端 `revision` 与服务端快照是冲突最终结果；客户端不以本地时间覆盖云端。 |
| 作用域隔离 | 每条记忆都必须绑定账号及 `scope_key`，避免成员 A 的信息被带入成员 B。 |
| 可审计 | 保存来源、确认状态、置信度与证据引用；不默认复制完整敏感原文。 |
| 幂等同步 | 每次变更都有稳定 `mutation_id`；重试不重复创建记录。 |
| 删除可传播 | 删除为墓碑，不立即物理删除；所有客户端和检索派生数据都能收到删除。 |
| 结构化优先 | `normalized_key` 用于业务去重，`structured_value` 用于准确使用，`content` 用于用户可读展示。 |

### 1.3 与现有项目的关系

当前项目已有知识库同步模型可作为模式参考：[`chat_sync/ai_models/knowledge.py`](/Users/hua/Documents/project/Reference/SparkService/chat_sync/ai_models/knowledge.py)。其中的 `revision`、删除标记、来源设备信息及 `KnowledgeMutationReceipt` 可复用其设计思想，但记忆必须拥有独立的实体、唯一约束和回执表，不能混入知识库文档。

当前 [`ai_config/models.py`](/Users/hua/Documents/project/Reference/SparkService/ai_config/models.py) 已有 `save_memory`、`retrieve_memory`、`update_memory` 工具动作枚举，但尚未发现记忆的权威持久化模型。后续应新增单独的记忆模型文件，例如 `chat_sync/ai_models/memory.py`；本文不执行该改动。

## 2. 统一术语与枚举

### 2.1 记忆类型 `memory_type`

| 枚举 | 含义 | 示例 |
| --- | --- | --- |
| `preference` | 回答、语言、称呼等一般偏好 | “默认中文、简洁回答” |
| `personal_fact` | 用户明确提供的个人事实 | “用户居住在杭州” |
| `member_fact` | 家庭成员的事实 | “张三是用户的父亲” |
| `health_preference` | 健康相关偏好或非诊断性习惯 | “饮食偏清淡” |
| `instruction` | 用户要求 AI 长期遵守的规则 | “解释报告时先给结论” |
| `conversation_summary` | 筛选后的长期会话摘要 | “用户正在准备三个月运动计划” |

`conversation_summary` 不等于聊天全文。它必须带来源证据与复核规则，且不应默认无限期保存。

### 2.2 作用域 `scope`

| 枚举 | 归属 | 查询时必须满足 |
| --- | --- | --- |
| `account` | 当前账号的全局记忆 | 同一 `user_id` |
| `member` | 某个家庭成员 | 同一 `user_id` + `member_id`，并通过成员权限服务校验可见性 |
| `agent` | 特定 Agent 的偏好或指令 | 同一 `user_id` + `agent_key`；当前工程没有稳定 Agent 实体，首期不启用 |
| `thread` | 单一会话临时记忆 | 同一 `user_id` + `thread_id` |

`thread` 作用域默认不进入长期跨端记忆同步；若产品确认需要恢复会话上下文，可同步，但保留期必须更短。`scope_key` 是服务端和客户端都必须持久化的规范化作用域键：

```text
account
member:<member_id>
agent:<agent_key>
thread:<thread_id>
```

真实主键类型必须按当前工程冻结：账号 `user_id`、成员 `member_id` 为整数；聊天 `thread_id` 为 UUID；当前未发现可作为外键的稳定 Agent 模型，因此 `agent` 作用域只能作为后续扩展，不能在首期伪造外键。`scope_key` 不再重复包含 `user_id`，因为数据库查询和唯一约束已经强制带 `user_id`。

### 2.3 DeepTutor 分层映射

SparkService 使用数据库记录表达 DeepTutor 的三层语义，不照搬 Markdown 文件：

| 字段 | 枚举 | 说明 |
| --- | --- | --- |
| `layer` | `L2` / `L3` | `L2` 为单业务表面稳定事实，`L3` 为跨表面长期记忆。L1 使用独立 Trace 表，不写入主记录。 |
| `document_key` | L2：`chat` / `knowledge` / `health` / `task`；L3：`recent` / `profile` / `scope` / `preferences` | 对应 DeepTutor 的 surface 或 slot。首期实际启用范围由功能开关控制。 |
| `section_key` | 受控字符串 | 工作台中的分组；由服务端白名单校验，不允许模型任意创建无限分组。 |

硬规则：`L3/preferences` 只能由用户手工编辑或 `write_memory` 写入；不得由工作台 `update`/`audit` 自动推断。其他 L2/L3 记录必须有证据引用。

### 2.4 来源、确认与生命周期

| 字段 | 枚举 | 说明 |
| --- | --- | --- |
| `source` | `user` / `ai` / `system` / `import` | 谁提出或写入这条记忆。 |
| `confirmation_status` | `not_required` / `pending` / `confirmed` / `rejected` | 是否可参与长期检索。 |
| `status` | `active` / `candidate` / `superseded` / `expired` | 生命周期状态；删除不放在此字段中。 |
| `sensitivity` | `normal` / `sensitive` / `health` / `identity` | 决定确认、展示和审计规则。 |

规则建议：

- 用户主动保存：`source=user`，通常为 `confirmed`。
- AI 自动提取：`source=ai`、`status=candidate`、`confirmation_status=pending`；健康和身份信息必须确认后才可检索。
- 系统业务事实：`source=system`，仅允许明确且可验证的事实；默认 `not_required` 或 `confirmed` 由产品确认。
- `is_deleted=true` 与 `deleted_at` 构成删除墓碑；墓碑优先于任何其他状态。

## 3. 服务端持久化模型

### 3.1 模型总览

```text
AIUser / Account
  ├─ AIMemorySettings                 账号级记忆开关与跨端设置
  ├─ AIMemoryTraceEvent               L1 追加式证据事件
  ├─ AIMemoryDocumentState            L2/L3 文档级版本、处理游标与运行锁
  └─ AIMemory                         权威记忆条目
       ├─ AIMemoryEvidence             条目到证据的引用（1:N，追加式）
       ├─ AIMemoryMutationReceipt      同步变更幂等回执（按用户、mutation）
       └─ AIMemoryChangeSet            工作台/手工修改与撤销快照

AIMemoryRun
  └─ AIMemoryRunEvent                 update/audit/dedup/merge 运行与事件流

ChatRun / ChatMessage / 业务事件
  └─ 可被 AIMemoryEvidence 引用

ChatTurnContextSnapshot.sources
  └─ 保存一次对话实际使用过的记忆引用快照（不复制 AIMemory）
```

首个可用版本至少需要 `AIMemorySettings`、`AIMemory`、`AIMemoryEvidence`、`AIMemoryTraceEvent`、`AIMemoryDocumentState`、`AIMemoryMutationReceipt`。`AIMemoryRun`、`AIMemoryRunEvent`、`AIMemoryChangeSet` 在交付 Memory Workbench 时同时启用。向量、全文索引、缓存均是从 `AIMemory` 派生的可重建数据，不应成为跨端同步的主数据。

### 3.2 `AIMemory`：权威记忆主表

一条记录代表一个可管理、可同步、可版本控制的记忆。它是所有客户端的最终事实源。

| 字段 | 建议类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 稳定的 `memory_id`；客户端离线创建时可预生成。 |
| `user_id` | 外键/整数 | 是 | 账号隔离的第一条件；取自认证身份，客户端不能上传覆盖。 |
| `scope` | 枚举 | 是 | `account`、`member`、`agent`、`thread`。 |
| `scope_key` | `varchar` | 是 | 规范化作用域键；用于过滤与去重，服务端生成并校验，客户端不可任意指定。 |
| `member_id` | 外键/整数 | 条件必填 | `scope=member` 时必填，其他作用域为空；必须通过成员权限服务校验。 |
| `agent_key` | `varchar(128)` | 条件必填 | `scope=agent` 时必填；首期不启用，待稳定 Agent 实体后再决定是否改为外键。 |
| `thread_id` | 外键/UUID | 条件必填 | `scope=thread` 时必填。 |
| `layer` | 枚举 | 是 | `L2` 或 `L3`。L1 不写入此表。 |
| `document_key` | `varchar(32)` | 是 | L2 surface 或 L3 slot，见 2.4；与 `layer` 联合校验。 |
| `section_key` | `varchar(64)` | 是 | 工作台分组键；服务端白名单校验。 |
| `memory_type` | 枚举 | 是 | 见 2.1。 |
| `normalized_key` | `varchar` | 是 | 业务语义键，如 `diet.preference`、`answer.language`；不是内容 Hash。 |
| `dedup_key` | `char(64)` | 条件必填 | `SHA-256(user_id + scope_key + layer + document_key + memory_type + normalized_key)`；仅有效槽位保留值。 |
| `title` | `varchar(128)` | 否 | 管理页短标题；为空时由 `content` 生成展示标题，不作为去重依据。 |
| `content` | `text` | 是 | 面向用户的简短自然语言表达。 |
| `structured_value` | JSON | 否 | 可供程序准确消费的值，如 `{ "language": "zh-CN" }`。 |
| `is_pinned` | boolean | 是 | 用户置顶标记；参与工作台排序，不绕过有效性和权限过滤。 |
| `sort_order` | integer | 是 | 同文档、同分组内稳定排序；`merge` 可调整。 |
| `content_hash` | `char(64)` | 是 | 规范化后的 `content + structured_value` Hash；用于诊断、变更识别，不能单独作为去重依据。 |
| `source` | 枚举 | 是 | `user`、`ai`、`system`、`import`。 |
| `confidence` | decimal(4,3) | 否 | AI 或系统推断的置信度，范围 `0~1`；用户主动写入可为空。 |
| `confirmation_status` | 枚举 | 是 | 见 2.3。 |
| `confirmed_at` | datetime | 否 | 最近一次确认时间。 |
| `sensitivity` | 枚举 | 是 | 用于隐私控制及确认策略。 |
| `status` | 枚举 | 是 | `active`、`candidate`、`superseded`、`expired`。 |
| `expires_at` | datetime | 否 | 临时记忆到期时间；到期后不可检索。 |
| `last_confirmed_at` | datetime | 否 | 用户或系统最近复核时间。 |
| `last_used_at` | datetime | 否 | 被上下文构建实际采用的时间，不能用请求时间代替。 |
| `superseded_by_id` | 自关联 UUID | 否 | 被同一业务键的新记录替代时指向新记录。 |
| `created_by_run_id` | 外键/UUID | 否 | AI 生成时关联既有 Chat Run；用户主动创建为空。 |
| `origin_device_id_hash` | `char(64)` | 否 | 首次客户端来源设备的不可逆标识。 |
| `last_device_id_hash` | `char(64)` | 否 | 最近修改来源设备的不可逆标识。 |
| `revision` | bigint | 是 | 服务端单调递增版本号；修改、确认、过期、删除均递增。 |
| `is_deleted` | boolean | 是 | 删除墓碑开关，默认 `false`。 |
| `deleted_at` | datetime | 否 | 逻辑删除时间；仅 `is_deleted=true` 时存在。 |
| `server_updated_at` | datetime | 是 | 服务端排序与 Pull 游标的依据，不能由客户端上传。 |
| `created_at` / `updated_at` | datetime | 是 | 常规审计时间。 |

#### 3.2.1 业务唯一性

有效记忆的业务身份为：

```text
user_id + scope_key + layer + document_key + memory_type + normalized_key
```

同一业务身份的新内容应更新同一逻辑记忆，或将旧记录标记为 `superseded` 后创建新 revision；不得仅因文本措辞不同而新增第二条。例如“偏清淡饮食”和“我喜欢清淡饮食”应归并到 `diet.preference`。

建议以 `dedup_key` 实现此约束，而不是直接依赖多字段唯一索引：在 MySQL 中，已删除或已替代记录可将 `dedup_key` 置为 `NULL`，从而允许保留历史与删除墓碑，同时保证有效槽位唯一。唯一约束建议为：

```text
UNIQUE (user_id, dedup_key)
```

服务端负责生成和验证 `scope_key`、`dedup_key`、`content_hash`。客户端可以携带它们用于诊断，但服务端不得信任客户端计算结果。

#### 3.2.2 推荐索引

| 索引 | 目的 |
| --- | --- |
| `UNIQUE(user_id, id)` | 避免跨账号错误引用同一个 UUID。 |
| `UNIQUE(user_id, dedup_key)` | 防止同一业务记忆重复。 |
| `(user_id, server_updated_at, id)` | Pull 增量同步与稳定分页。 |
| `(user_id, scope_key, is_deleted, status)` | 对话上下文按账号和作用域加载。 |
| `(user_id, memory_type, normalized_key)` | 管理页、去重诊断和定向查询。 |
| `(expires_at, is_deleted, status)` | 过期处理任务。 |
| `(superseded_by_id)` | 查询替代链和审计。 |

### 3.3 `AIMemorySettings`：账号级设置

客户端现有 `MemoryPreferences` 只存 UserDefaults，无法跨设备对齐；应升级为服务端权威设置并在客户端保留镜像。

| 字段 | 建议类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `user_id` | 一对一外键/整数 | 是 | 每账号一条。 |
| `is_enabled` | boolean | 是 | 总开关；关闭后不挂载记忆工具、不注入记忆上下文。 |
| `allow_tool_write` | boolean | 是 | 是否允许 `write_memory` 写显式偏好。 |
| `allow_cross_thread_recall` | boolean | 是 | 是否允许跨会话读取 L3。 |
| `max_recall_count` | smallint | 是 | `1..20`；仍受服务端 Token 预算二次限制。 |
| `auto_consolidation_enabled` | boolean | 是 | 是否允许后台自动触发工作台 `update`；首期默认 `false`。 |
| `revision` | bigint | 是 | 设置乐观锁版本。 |
| `server_updated_at` | datetime | 是 | 设置同步与诊断。 |

### 3.4 `AIMemoryTraceEvent`：L1 追加式事件

| 字段 | 建议类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 稳定事件 ID。 |
| `user_id` | 外键/整数 | 是 | 账号隔离。 |
| `surface` | 枚举 | 是 | `chat`、`knowledge`、`health`、`task` 等真实业务来源。 |
| `event_type` | `varchar(64)` | 是 | 如 `preference_stated`、`chat_completed`、`knowledge_used`。 |
| `entity_type` / `entity_id` / `entity_revision` | 字符串 | 条件必填 | 指向真实业务实体；避免复制全文。 |
| `payload` | JSON | 否 | 最小必要结构化信号；禁止默认保存完整聊天正文或工具敏感结果。 |
| `content_hash` | `char(64)` | 是 | 事件规范化 Hash，用于去重诊断。 |
| `occurred_at` / `created_at` | datetime | 是 | 业务发生时间与落库时间。 |

### 3.5 `AIMemoryDocumentState`：文档级状态

| 字段 | 建议类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `user_id` | 外键/整数 | 是 | 账号隔离。 |
| `layer` / `document_key` | 枚举/字符串 | 是 | 唯一定位一个 L2 surface 或 L3 slot。 |
| `revision` | bigint | 是 | 文档级乐观锁与工作台预览应用版本。 |
| `last_processed_trace_at` / `last_processed_trace_id` | datetime/UUID | 否 | L2 增量处理游标。 |
| `last_processed_l2_revision` | JSON | 否 | L3 对各 L2 文档最后处理版本。 |
| `active_run_id` | UUID | 否 | 同一文档只允许一个变更型运行。 |
| `updated_at` | datetime | 是 | 状态审计。 |

约束：`UNIQUE(user_id, layer, document_key)`。

### 3.6 `AIMemoryEvidence`：记忆证据表

主记录只存“当前可用结论”；证据表记录结论从何而来，允许审核与纠错。证据是追加式记录，不应在更新记忆时覆盖历史。

| 字段 | 建议类型 | 必填 | 设计说明 |
| --- | --- | --- |
| `id` | UUID | 是 | 证据 ID。 |
| `memory_id` | 外键 UUID | 是 | 所属记忆。 |
| `user_id` | 外键/整数 | 是 | 冗余账号字段，保证权限和查询隔离。 |
| `evidence_type` | 枚举 | 是 | `user_input`、`chat_message`、`chat_run`、`system_event`、`import`、`knowledge_document`。 |
| `reference_id` | UUID/字符串 | 否 | 被引用消息、Run、文档或业务事件 ID。 |
| `reference_revision` | bigint/字符串 | 否 | 外部记录存在版本时保留，用于证明来源版本。 |
| `excerpt_hash` | `char(64)` | 否 | 原始摘录的 Hash，用于证明且避免重复保存敏感全文。 |
| `evidence_payload` | JSON | 否 | 最小必要元数据，如字段路径、导入批次号；禁止默认写入聊天全文。 |
| `created_at` | datetime | 是 | 证据生成时间。 |

健康和身份类记忆的 `evidence_payload` 应采用最小化存储。若需要展示原文，优先通过受权限保护的原始消息/业务记录查询，不复制到记忆表。

### 3.7 `AIMemoryMutationReceipt`：幂等变更回执表

此表解决客户端离线重试、网络超时和重复提交。其职责与知识库的 `KnowledgeMutationReceipt` 相同，但模型必须独立，避免两个领域的回执和错误码混用。

| 字段 | 建议类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 回执记录 ID。 |
| `user_id` | 外键/整数 | 是 | 变更所属账号。 |
| `mutation_id` | UUID | 是 | 客户端或服务端 AI 为一次逻辑变更生成；重试必须复用。 |
| `memory_id` | UUID | 是 | 目标记忆。 |
| `operation` | 枚举 | 是 | `create`、`update`、`confirm`、`reject`、`delete`。 |
| `request_hash` | `char(64)` | 是 | 相同 `mutation_id` 的请求内容校验。 |
| `base_revision` | bigint | 否 | 客户端操作基于的版本；新建为空。 |
| `result_revision` | bigint | 否 | 服务端处理后的版本。 |
| `result_snapshot` | JSON | 是 | 最终权威快照，供重复请求直接返回。 |
| `created_at` / `expires_at` | datetime | 是 | 回执保留期由隐私和重试窗口决定。 |

约束：`UNIQUE(user_id, mutation_id)`。相同 `mutation_id` 且 `request_hash` 相同，直接返回原 `result_snapshot`；Hash 不同则返回幂等键复用错误，不执行写入。

### 3.8 `AIMemoryRun` / `AIMemoryRunEvent` / `AIMemoryChangeSet`

| 模型 | 核心字段 | 作用 |
| --- | --- | --- |
| `AIMemoryRun` | `id,user_id,layer,document_key,mode,status,params,base_document_revision,cancel_requested_at,error_code,started_at,finished_at` | 持久化 `update/audit/dedup/merge` 异步运行；客户端断线不终止。 |
| `AIMemoryRunEvent` | `run_id,sequence,event_type,payload,created_at` | 进度事件持久化与 `since` 重放；唯一 `(run_id, sequence)`。 |
| `AIMemoryChangeSet` | `user_id,run_id,document_revision_before,document_revision_after,operations,before_snapshot,expires_at` | 保存一次原子变更，支持工作台撤销；快照应限量、加密与定期清理。 |

### 3.9 不在首期作为主数据同步的模型

| 对象 | 是否首期持久化 | 说明 |
| --- | --- | --- |
| 记忆 Embedding / 向量 | 否 | 如需语义检索，仅服务端派生、可重建，不下发到客户端。 |
| 向量索引状态 | 否，按需增加 | 可后续增加 `AIMemoryIndexState`，记录 `memory_id`、模型版本、内容 Hash、索引状态和错误；不参与业务事实冲突。 |
| 完整聊天副本 | 否 | 通过 `AIMemoryEvidence.reference_id` 引用既有聊天数据。 |
| 独立候选表 | 否 | 首期使用 `AIMemory.status=candidate` + `confirmation_status=pending` 即可。 |
| 独立上下文快照表 | 否 | 既有 `ChatTurnContextSnapshot.sources` 可记录实际采用的记忆引用。 |

## 4. 服务端状态与数据规则

### 4.1 有效性判断

一条记忆仅在同时满足以下条件时可被 AI 检索：

```text
is_deleted = false
AND status = active
AND confirmation_status IN (not_required, confirmed)
AND (expires_at IS NULL OR expires_at > now)
```

查询还必须加上 `user_id` 和允许的 `scope_key`。任何缺少账号或作用域条件的查询都应视为缺陷。

### 4.2 状态迁移

```text
AI 候选： candidate + pending ──用户确认──> active + confirmed
                         │
                         └──用户拒绝──> candidate + rejected

有效记忆： active ──新值替代──> superseded ──保留替代关系──> 新 active
               │
               ├──到期──> expired
               └──删除──> is_deleted=true + deleted_at（墓碑）
```

- 删除优先：即使记录此前为 `candidate`、`expired` 或 `superseded`，删除后都必须同步墓碑。
- 更新有效记忆时，推荐优先在同一 `memory_id` 上增加 `revision`；只有需要保存清晰版本链时才新建记录并填充 `superseded_by_id`。该选择需全端统一，不能按客户端各自决定。
- `last_used_at` 仅在记忆确实进入该轮模型上下文后更新，不能因列表展示或预加载而更新。

### 4.3 删除、保留与派生数据

删除操作写入 `AIMemory` 墓碑并增加 `revision` 后，异步清理以下派生数据：服务端/客户端检索索引、Embedding、缓存、待执行的本地 Outbox 内容和 AI 可检索集合。清理失败不影响删除语义：新对话必须立刻按 `is_deleted=false` 条件排除该记录。

墓碑的最短保留期必须覆盖所有支持客户端的最长离线周期；在此之前不能物理删除，否则长期离线设备无法获知“已忘记”。具体天数待产品与隐私规则确认。

## 5. 客户端本地数据模型

客户端不拥有最终事实，只保存账号隔离的本地镜像、待发送变更及 Pull 游标。所有本地表均必须带 `account_id`，登出、切换账号和本地数据库升级不得跨账号复用记录。

### 5.1 `MemoryEntity`：服务端镜像与离线编辑实体

`MemoryEntity` 字段应镜像 `AIMemory` 的业务字段，以便列表展示、离线编辑和 Pull 落库。建议保持与服务端 JSON 字段同名或可一一映射，避免 iOS、Web、Android 分别创造不同语义。

除镜像字段外，客户端新增以下仅本地字段：

| 字段 | 建议类型 | 含义 |
| --- | --- | --- |
| `account_id` | Int64 | 本地分区键，必须与服务端整数 `user_id` 对应。 |
| `last_synced_revision` | bigint | 最后成功落盘的服务端版本。 |
| `sync_state` | 枚举 | 见下表；只表示本地同步进度，不上传为业务真相。 |
| `last_sync_attempt_at` | datetime | 最近一次 Push/Pull 关联尝试。 |
| `last_sync_succeeded_at` | datetime | 最近一次收到该记录权威快照的时间。 |
| `last_sync_error_code` | 字符串 | 可展示/诊断的稳定错误码，不存服务端错误文案。 |
| `last_sync_error_at` | datetime | 最近失败时间。 |
| `server_snapshot_hash` | `char(64)` | 最后服务端快照 Hash，用于诊断重复应用和版本升级。 |

`sync_state` 建议枚举：

| 值 | 说明 |
| --- | --- |
| `local_only` | 已在本地创建，尚未进入可发送队列。 |
| `pending` | 已产生 Outbox，等待发送。 |
| `syncing` | 当前正在发送；崩溃恢复后必须可回到 `pending`。 |
| `synced` | 已应用服务端确认快照。 |
| `failed_retryable` | 临时失败，按退避策略重试。 |
| `failed_permanent` | 需要用户操作或版本升级，例如权限被撤销、字段不合法。 |
| `resolved_by_server` | 本地冲突内容已被服务端快照覆盖；可用于一次性提示。 |

客户端本地修改时，不得覆盖 `revision`。应保留最后已知服务端 `revision` 作为此次 Outbox 的 `base_revision`。

### 5.2 `MemorySyncOutboxEntity`：离线变更队列

一项 Outbox 是一次不可变的逻辑 mutation，不是“当前对象的最终快照”。网络重试、应用重启和前后台切换必须复用同一个 `mutation_id`。

| 字段 | 建议类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 本地队列记录 ID。 |
| `account_id` | Int64 | 是 | 队列账号隔离。 |
| `mutation_id` | UUID | 是 | 与服务端回执一一对应。 |
| `memory_id` | UUID | 是 | 目标记忆。 |
| `operation` | 枚举 | 是 | 与服务端 `operation` 对齐。 |
| `base_revision` | bigint | 否 | 创建为空，其他变更为本地最后已知服务端版本。 |
| `payload_json` | JSON/Blob | 是 | 本次操作的不可变请求体。 |
| `payload_hash` | `char(64)` | 是 | 防止本地错误复用 mutation。 |
| `state` | 枚举 | 是 | `pending`、`sending`、`acknowledged`、`retryable_failed`、`permanent_failed`、`discarded`。 |
| `attempt_count` | int | 是 | 重试计数。 |
| `next_retry_at` | datetime | 否 | 指数退避后的下一次重试。 |
| `last_error_code` | 字符串 | 否 | 稳定错误码。 |
| `last_error_at` | datetime | 否 | 失败时间。 |
| `created_at` / `updated_at` | datetime | 是 | 队列审计与恢复。 |

约束建议：`UNIQUE(account_id, mutation_id)`。成功 ACK 后，Outbox 可标记 `acknowledged` 后延迟清理；不能在收到 ACK 前删除。

### 5.3 `MemorySyncCursorEntity`：增量拉取游标

| 字段 | 建议类型 | 说明 |
| --- | --- | --- |
| `account_id` | Int64，唯一 | 每个账号每个记忆同步域一条记录。 |
| `cursor` | 不透明字符串 | 服务端发放；客户端不可解析、排序或自行构造。 |
| `last_pull_started_at` | datetime | 诊断拉取任务。 |
| `last_pull_succeeded_at` | datetime | 最后完整成功拉取时间。 |
| `last_pull_error_code` | 字符串 | 最后拉取错误。 |
| `schema_version` | 整数/字符串 | 本地已接受的协议版本。 |

知识库和记忆必须分别维护游标：`KnowledgeSyncCursor` 与 `MemorySyncCursor` 不可共享。一个领域的失败不能阻断另一个领域启动同步。

### 5.4 客户端不应持久化的内容

- 服务端 Embedding、向量索引和索引任务状态。
- 服务端幂等回执完整快照；客户端只需把 ACK 应用回 `MemoryEntity`。
- 被拒绝/删除记忆的完整旧内容副本，除非离线审计策略明确要求且经过隐私评审。
- 原始完整聊天消息的二次副本；通过既有聊天本地数据库或证据引用访问。

### 5.5 `MemorySettingsEntity`：服务端设置镜像

客户端现有 `MemoryPreferences` 的 `isEnabled`、`allowToolWrite`、`allowCrossThreadRecall`、`maxRecallCount` 应保留为领域模型，但持久化来源从仅 UserDefaults 升级为服务端设置镜像。新增 `revision`、`serverUpdatedAt`、`syncState`；本地修改通过设置接口提交，冲突仍以服务端快照覆盖。UserDefaults 只能作为启动期缓存，不再作为跨设备权威来源。

## 7. 同步请求中的数据对象

以下是数据契约，不定义具体 URL 或接口行为。

### 7.1 `MemoryMutation`

```json
{
  "schema_version": 1,
  "mutation_id": "uuid",
  "operation": "create | update | confirm | reject | delete",
  "memory_id": "uuid",
  "base_revision": 12,
  "memory": {
    "scope": "member",
    "member_id": 123,
    "layer": "L3",
    "document_key": "profile",
    "section_key": "health_preferences",
    "memory_type": "health_preference",
    "normalized_key": "diet.preference",
    "content": "饮食偏清淡",
    "structured_value": {"preference": "light"},
    "source": "user",
    "sensitivity": "health",
    "expires_at": null
  }
}
```

- `base_revision`：创建为空；修改、确认、拒绝、删除必须携带最后已知服务端版本。
- `revision`、`scope_key`、`dedup_key`、`server_updated_at` 不由客户端写入。
- 删除 mutation 只需 `memory_id`、`base_revision`、`mutation_id`；不得用空内容伪装删除。

### 7.2 `MemorySnapshot`

服务端 Push ACK 与 Pull 变更项都返回同一种快照：完整的 `AIMemory` 可同步字段、当前 `revision`、`is_deleted`、`deleted_at`、`server_updated_at`。客户端只要统一按快照 upsert，即可避免 Push 与 Pull 的合并逻辑分叉。

### 7.3 冲突结果对象

当 `base_revision` 过期或业务唯一键冲突时，服务端返回权威 `MemorySnapshot` 与机器可读的 `resolution`：

```json
{
  "resolution": "server_wins",
  "reason_code": "revision_conflict | duplicate_memory_key | tombstoned",
  "memory": {"...": "authoritative snapshot"}
}
```

客户端处理规则：应用该快照、将相关 Outbox 标记 `discarded` 或 `acknowledged`、把 `sync_state` 设置为 `resolved_by_server`。不得创建“冲突副本”，也不得再次以新 UUID 自动上传本地旧内容。

## 8. 模型驱动的关键流程

### 8.1 客户端离线创建

```text
生成 memory_id + mutation_id
  → 写 MemoryEntity（local_only / pending）
  → 写不可变 MemorySyncOutboxEntity
  → 异步 Push
  → 收到服务端 MemorySnapshot
  → 覆盖本地业务字段、记录 revision、标记 synced
```

网络失败仅更新 Outbox 重试字段和 `sync_state=failed_retryable`，不影响创建记忆之外的客户端流程。

### 8.2 设备 B 拉取

```text
读取账号的 MemorySyncCursor
  → 拉取服务端变更快照（含墓碑）
  → 按 memory_id upsert MemoryEntity
  → 不创建 Outbox
  → 原子更新 Cursor
```

服务端快照的 `revision` 小于或等于本地已应用版本时可忽略；若本地有待发送变更而服务端返回更高版本，仍以服务端快照覆盖，并按第 7.3 节处理相关 Outbox。

### 8.3 启动同步

账号恢复完成后，知识库同步与记忆同步各自启动独立的 single-flight 任务。两个任务各自拥有 Outbox、Cursor、失败重试时间与日志；任何一个失败均不阻断首页、登录或另一个同步任务。

### 8.4 服务端 AI 创建候选记忆

```text
Chat Run / AI 提取
  → 创建 AIMemory(status=candidate, confirmation_status=pending)
  → 写 AIMemoryEvidence(created_by_run_id / message reference)
  → 仅向有权限的客户端同步候选记录
  → 用户确认后更新同一 memory_id 与 revision
```

服务端 AI 应直接调用统一的记忆领域服务写入权威表，不经由客户端转发。离线端本地模型产生的记忆才进入客户端 Outbox。

## 9. 记忆检索与向量设计

首期记忆以结构化过滤和轻量相关性排序为主：账号与作用域过滤 → 确认/有效状态过滤 → 类型、重要度、最近使用时间与当前问题相关性排序 → Token 预算裁剪。

向量检索可作为后续服务端派生能力，适合 `conversation_summary` 或自由文本偏好，但不改变主模型：

```text
AIMemory（权威事实）
  └─ 可选 AIMemoryIndexState / embedding（可删除、可重建的派生索引）
```

不建议把 Embedding 同步到客户端，原因是模型版本、隐私策略和向量尺寸均可能变化，且它不代表用户可见的事实。删除墓碑一经生效，检索层必须先排除 `is_deleted=true`，再异步完成向量物理清理。

对话实际使用的记忆应在既有 [`chat_sync/ai_models/context.py`](/Users/hua/Documents/project/Reference/SparkService/chat_sync/ai_models/context.py) 的 `ChatTurnContextSnapshot.sources` 中记录最小引用，例如 `memory_id`、`revision`、`memory_type`、`scope_key`、是否被裁剪。不要复制记忆正文，以避免历史上下文快照形成第二份难以删除的敏感数据。

## 10. DeepTutor 参考映射

DeepTutor 的记忆以可审计文件层为主：原始痕迹/快照（L1）、按业务表面保存的稳定事实（L2）、近期/用户档案/范围/偏好（L3）。其中“用户显式偏好可直接写入，其他信息经整理、去重、审计后升级”的原则值得保留。

SparkService 不应照搬其文件与 Markdown 存储：多客户端同步需要数据库级账号隔离、幂等 mutation、稳定 revision 和删除墓碑。建议映射如下：

| DeepTutor 概念 | SparkService 对应数据模型 |
| --- | --- |
| L1 原始痕迹 | `AIMemoryEvidence` 对既有聊天/业务记录的引用。 |
| L2 业务表面事实 | `AIMemory` 的 `member`、`agent`、`thread` 作用域记录。 |
| L3 profile / preferences | `AIMemory` 的 `account` 作用域与 `preference`、`instruction` 类型。 |
| 整理与去重 | `normalized_key`、`dedup_key`、候选状态、证据和服务端领域规则。 |

## 11. 跨端版本与直接升级要求

- 每个同步对象携带 `schema_version`；服务端需要声明最低可用版本和未知字段忽略策略。
- 枚举新增值时，旧客户端必须按“保留原始值但不执行未知业务动作”处理，不能把未知状态改写为默认值。
- 服务端维护跨端 JSON fixture：创建、确认、替代、删除墓碑、冲突覆盖、过期六类快照至少各一份。
- 本方案不设计旧版客户端记忆数据迁移。客户端直接升级到最新数据模型、协议和同步组件；旧版本地记忆不自动转换、不自动上传，也不作为服务端初始数据来源。
- 最新客户端首次启用记忆同步时，以服务端快照为准建立本地 `MemoryEntity`、`MemorySyncOutboxEntity` 和 `MemorySyncCursorEntity`。如果服务端没有对应记忆，则本地从空数据集开始。
- 若产品后续要求保留旧版本地记忆，应另立迁移需求并补充数据盘点、用户授权、去重和失败恢复设计；不在本模型范围内临时兼容。
- 每个客户端必须按账号分区保存 Cursor 和 Outbox；切换账号时不能使用前一账号游标。

### 11.1 升级前提

- 发布新版本时，服务端只保证最新客户端模型的完整行为；旧客户端不作为记忆同步协议的兼容对象。
- 可通过最低客户端版本、强制升级或灰度开关控制接入范围。具体采用哪种方式待发布策略确认，但不应让旧客户端提交未定义字段。
- 本地数据库升级只负责创建最新表结构和清理无效同步状态，不负责把旧业务记忆转换成新 `AIMemory` 记录。
- 升级后的首次同步必须能够从服务端完整快照重新建立本地状态；因此客户端不能依赖旧本地记忆才能完成启动。

## 12. 待确认项与建议

| 待确认问题 | 建议 | 为什么影响模型 |
| --- | --- | --- |
| `agent` 作用域的稳定业务实体与 key | 首期关闭 `agent` 作用域；当前账号/成员/会话分别使用整数、整数、UUID。 | 当前工程未发现稳定 Agent 模型，提前开放会产生不可校验的悬空引用。 |
| 更新是否永远复用同一 `memory_id` | 首期推荐复用同一 ID、递增 revision；仅需要可见历史链时使用 `superseded_by_id`。 | 决定唯一约束、审计和客户端合并复杂度。 |
| 系统生成的健康/身份事实是否也必须确认 | 建议健康、身份默认 `pending`，除非来自可审计且用户授权的业务来源。 | 直接影响候选记录是否进入 AI 上下文。 |
| `thread` 作用域是否跨端同步 | 首期建议不同步长期记忆；如需恢复会话再加入短保留同步。 | 决定 Cursor 数据量、隐私边界和清理策略。 |
| 删除墓碑、回执和证据的保留期限 | 墓碑至少覆盖最长离线周期；证据/回执按隐私与审计规则分别定期清理。 | 影响长期离线设备能否正确“忘记”。 |
| `normalized_key` 的注册表维护者 | 建议服务端维护类型到 key 的白名单/规范化规则，客户端共用 fixture。 | 防止多端把同一事实写成不同键并重复。 |
| 是否对 `conversation_summary` 建向量 | 首期不要求；先验证结构化筛选和 Token 预算。 | 决定是否增加派生索引模型与删除链路。 |

## 13. 验收口径（数据模型层）

1. 任意 `AIMemory` 可通过 `user_id + scope_key` 证明其可见边界，成员间不存在交叉读取。
2. 相同 `mutation_id` 重放不会创建第二条主记录，且返回第一次处理的权威快照。
3. 相同业务键的不同表述不会形成多个有效记忆。
4. 设备冲突后，本地最终收敛到服务端 `revision` 与快照，不产生冲突副本。
5. 删除墓碑可经 Pull 到达长期离线设备，并在到达后立刻排除检索。
6. AI 候选的健康/身份记忆在确认前不会进入对话上下文。
7. 知识库同步和记忆同步拥有独立 Cursor/Outbox；任一失败不影响另一方和应用启动。
